# RDX OTA 移植说明

## 1. 范围与依据

本文记录把根目录参考工程 `tide-bridge/` 的 RDX V23 OTA 业务移植到 AC710N/BR56 Type-C 工程的实现边界、协议合同和验收方法。

协议与时序以以下材料交叉确认：

- 参考工程 `rdx_ota.c/.h`；
- 参考工程 RDX 协议常量和 BLE GATT Profile；
- 参考工程链接产物中的 RDX Wire 行为；
- 根目录 `参考工程的OTA流程日志.log` 中 2026-09-01 的完整升级记录。

本次只移植 RDX BLE 全镜像双备份升级，不移植 RCSP OTA、TWS 同步 OTA、WebUSB OTA 或断点续传。当前产品为单机、独占 RDX 的 Type-C PC 模式。

2026-09-01，当前实现已由用户完成一次正式 APP 实机 OTA 主链路验证，确认本章记录的“原始被动双 Bank 接口 + Norflash 写保护管理”方案可以完成升级。临时冻结基线提交为 `dca2710`；后续若修改升级接口、打包模式、Flash 布局或最终应答时序，应重新执行第 8 节回归清单。

## 2. 外部协议合同

### 2.1 GATT

沿用参考工程已有 OTA Service 指纹和 Handle：

| 用途 | Handle | 属性 |
| --- | ---: | --- |
| OTA RX | `0x0012` | Write Without Response |
| OTA TX | `0x0014` | Notify |
| OTA TX CCC | `0x0015` | Notification CCC |

APP 先在 OTA TX CCC 写入 `0x0001`，再向 OTA RX 下发升级命令和数据。OTA 应答只从 OTA TX 返回，不复用普通 RDX TX。

### 2.2 Upgrade 命令

```text
*APP#upgrade#<版本>#<文件大小>#<单包数据大小>#<总包数>#
```

参考日志中的实际请求为：

```text
*APP#upgrade#9.9.9#1048664#448#2341#
```

约束如下：

- 版本格式为三个十进制段 `major.minor.patch`，每段为 `0..255`；
- 新版本必须严格大于当前固件版本；
- 文件大小、单包大小和总包数均为非零十进制数；
- `总包数 = ceil(文件大小 / 单包大小)`；
- 单包数据最大为 448 B；
- 字段末尾必须有 `#`，不接受多余尾部数据。

握手成功后设备返回：

```text
*DEV#otareq#0#1#
```

### 2.3 Data 命令

```text
*APP#ota#<包号>#<数据长度>#<CRC32十进制>#<binary>
```

约束如下：

- 包号从 1 开始并严格递增；
- 除最后一包外，数据长度必须等于 Upgrade 声明的单包大小；
- 最后一包结束位置必须严格等于声明的镜像大小；
- CRC32 使用标准反射算法，多项式 `0xEDB88320`，初值和结果异或均为 `0xFFFFFFFF`；
- CRC32 在 Wire 中使用无符号十进制 ASCII；
- 二进制区长度必须与数据长度字段完全相等。

每个非末包通过包序、长度、CRC 和 Flash 提交检查后，设备请求下一包：

```text
*DEV#otareq#0#<下一包号>#
```

### 2.4 最后一包与复位

最后一包不立即请求下一包。设备先提交剩余 Flash 数据，等待所有异步写入结束，再校验完整升级镜像并写入双备份 Boot Info。

参考日志确认成功时序为：

1. 镜像校验成功，返回一次 `*DEV#otareq#0#0#`；
2. Boot Info 写入成功，再返回一次 `*DEV#otareq#0#0#`；
3. 约 1000 ms 后执行软复位；
4. Bootloader 在下次启动切换到已提交的新 Bank。

两次 `0#0` 是参考工程可观察到的兼容行为，当前实现予以保留。

### 2.5 状态码

`otareq` 的状态值由命令阶段决定，同一个数值在 Upgrade 和 Data 阶段具有不同语义：

| 状态 | Upgrade 阶段 | Data/收尾阶段 |
| ---: | --- | --- |
| 0 | 接受升级 | 数据成功或升级完成 |
| 1 | 保留 | 包号错误 |
| 2 | 版本不高于当前版本 | 数据长度或镜像校验错误 |
| 3 | 双备份空间不足 | 单包 CRC32 错误 |
| 4 | 其他平台或状态错误 | 其他平台或状态错误 |

录音等资源繁忙时使用参考协议已有的忙应答：

```text
*DEV#upgrade#1#
```

## 3. 当前工程实现

实现继续遵守本工程的分层边界：

| 层 | 文件 | 职责 |
| --- | --- | --- |
| Protocol Adapter | `protocol/v23/rdx_protocol_v23_ota.c` | Wire 严格解析、版本和十进制字段校验、应答编码 |
| Application Service | `application/rdx_ota_service.c` | OTA 状态、包序、CRC32、总长度、超时和录音互斥 |
| Firmware Update Port | `include/rdx/ports/rdx_firmware_update_port.h` | 与芯片无关的升级语义和异步事件 |
| BR56 Adapter | `adapters/jl_br56/rdx_firmware_update_jl_br56.c` | 双备份初始化、写入、校验、Boot Info 和复位 |
| BLE Transport | `adapters/jl_br56/rdx_transport_jl_br56.c` | OTA Handle、CCC、RX 事件和 TX Notify |
| Composition Root | `integration/type_c_ac7106f6/rdx_runtime.c` | 启动结构能力探测和 Capability 汇总 |

RDX 静态库仍只提供既有加密 Provider，不从参考库抽取 OTA 业务对象，避免本地业务实现与参考静态库形成双栈。

## 4. 会话、安全与资源规则

只有同时满足以下条件时才处理 OTA 写入：

- BLE 链路属于当前 connection generation；
- 普通 RDX AppKey 已认证；
- OTA TX CCC 已开启；
- OTA Service 处于可接受该命令的状态。

以下事件会中止尚未提交的 OTA，退出双备份被动升级并清理状态：

- BLE 断链；
- OTA CCC 关闭；
- 10 秒未收到后续数据；
- 包号、长度或 CRC32 错误；
- Flash 写入、镜像校验或 Boot Info 提交失败；
- 协议或平台状态异常。

本实现不支持断点续传。中止后重新升级必须从 Upgrade 和第 1 包开始。

RDX OTA 与在线录音双向互斥：录音非空闲时拒绝 Upgrade；OTA 处于接收、校验或已提交待复位状态时拒绝新录音。该互斥不改变 USB Audio 的所有权，USB Speaker/Mic 共存仍需实机压力验证。

## 5. BR56 双备份映射

BR56 Adapter 使用 SDK 的原始被动双备份接口：

- `dual_bank_passive_update_init()`；
- `dual_bank_update_allow_check()`；
- `dual_bank_update_write()`；
- `dual_bank_update_verify_without_crc()`；
- `dual_bank_update_burn_boot_info()`；
- `dual_bank_passive_update_exit()`。

虽然文件名包含 `db_update`，但当前 `TCFG_UPDATE_COMPRESS = 0` 配置下，由 `CONFIG_DB_UPDATE_DATA_GENERATE_EN` 生成的 `db_update_data.bin` 是第三方协议使用的原始被动双 Bank 镜像，并不包含 `db_update_*` 所要求的明文 DB Package 文件头。将它交给 `db_update_*` 会在第一个聚合写块以 `ota head verify fail, -2` 失败；BR56 的 `bt_fmy` 和 `update_tws_new.c` 示例也使用上述 `dual_bank_*` 路径。

产物与接口必须按构建模式区分：

| 产物或模式 | 当前 RDX 是否使用 | 正确理解 |
| --- | --- | --- |
| `TCFG_UPDATE_COMPRESS = 0` 下的 `db_update_data.bin` | 是 | 原始被动双 Bank 镜像，交给 `dual_bank_*` |
| 压缩升级流程生成的 `db_update.bin` / DB Package | 否 | 属于另一种包格式；若将来启用，需单独适配并验证 `db_update_*` |
| `update.ufw` | 否 | 下载/升级容器，不是当前 RDX Wire 的等价 Payload |
| `jl_isd.bin`、`jl_isd.fw` | 否 | 烧录和封装产物，不应由 RDX APP 直接下发 |

不能根据 `db_update_data.bin` 的文件名推断它应使用 `db_update_*`。`db_update_check_ota_head()` 要求 DB Package 首字为 `0x5C6A7B8E`（文件字节序为 `8E 7B 6A 5C`）；当前非压缩产物不具备该文件头，这是两套接口最直接的判别依据。

两套接口的回调语义也不能混用：

- `dual_bank_update_write()` 的完成回调类型为 `int (*)(void *priv)`，SDK 通过 `priv` 携带写入错误；当前 Adapter 使用 `(int)(uintptr_t)priv` 取出结果；
- `db_update_write()` 的完成回调类型为 `int (*)(int err)`，不能把它直接替换到 `dual_bank_update_write()`；
- 当前 RDX 使用参考工程和 BR56 第三方 OTA 示例采用的同步 `dual_bank_update_verify_without_crc()`，函数返回 `0` 表示校验成功，非零表示失败；日志中的 `result=255` 是该 `u8` 返回值承载的失败值，不是第 255 包或 CRC 数值；
- `dual_bank_update_verify_without_crc_new()` 是回调驱动的新任务式接口，主要用于 TWS 流程，不是同步接口的同名升级版。未经错误回调、断链竞态和最终应答时序验证，不能直接替换，否则可能使 RDX 会话停留在 `FINALIZING`；
- `dual_bank_update_burn_boot_info()` 的完成回调可能在 API 返回前触发，因此串口中 `commit=done` 可能先于 `commit=accepted`。判断成功应看两者结果均为 `0`，不能强依赖打印先后。

Application Service 以 1024 B 缓冲聚合 448 B Wire 数据包。`dual_bank_update_write()` 会把传入数据复制到内部临时缓冲并异步编程；Adapter 记录未完成写入数，只有最后一包已提交且所有写回调结束后才开始完整镜像校验。

本产品默认启用了 Norflash 写保护。OTA 开始时必须先调用 `norflash_set_write_protect_remove()`，在初始化失败、传输失败、中止或 Boot Info 提交完成后恢复 `norflash_set_write_protect_en()`。若未解除保护，协议仍可能传输到 100%，但目标 Bank 没有得到有效镜像，最终表现为 `file head crc verify fail` / `UPDATE_ERR_NOT_FIND_TARGET_FILE`。

校验回调在会话仍有效时才允许进入 Boot Info 提交，避免已经中止的异步校验继续提交新 Bank。Boot Info 成功后延迟 1000 ms 复位。

## 6. 配置与构建边界

OTA 产品开关位于：

```c
#define RDX_COMPAT_OTA_ENABLE 1
```

V23 没有已发布的 OTA Device Ability 位，因此该开关不修改 Manufacturer Data 的 Device Ability。OTA 只作为内部 Compiled/Boot Structural Capability 参与启动检查。

启用 RDX OTA 时，编译期要求：

- `TCFG_UPDATE_ENABLE = 1`；
- `TCFG_DUAL_BANK_ENABLE = 1`；
- `CONFIG_DOUBLE_BANK_ENABLE = 1`；
- 当前 Flash 布局能够容纳目标镜像和双备份元数据。

`set_ota_status(1)` 不是普通日志状态：SDK 的低功耗目标通过它阻止 OTA 期间进入 powerdown。应只在平台初始化和空间检查成功后置位，并在成功、失败、中止的所有出口清零；否则可能出现 OTA 过程中休眠，或失败后设备长期无法进入低功耗。

OTA 源文件只由 `SDK/build/genFileList.c` 在 `RDX_CFG_OTA_ENABLE` 为真时选入。`SDK/build/fileList.mk` 是生成物，不应手工维护。

为接收参考 APP 的 448 B 分包和最长十进制 ASCII 头，RDX 专用 ATT Local Payload 从 128 B 调整为 517 B。相对原配置增加 389 B 常驻 ATT RAM；ATT Send CBUF 保持 4096 B。参考实机协商日志显示完整 MTU 路径可承载约 477 B 的 OTA Write。

## 7. 已完成验证与验证边界

Host 测试覆盖：

- 未认证或 OTA CCC 未开启时拒绝 OTA；
- 448 B Golden Packet 和十进制 CRC32；
- Upgrade 包数、包长上限和严格格式校验；
- 首包为 1、逐包应答及最后一包不提前应答；
- 镜像校验成功和 Boot Info 成功各返回一次 `0#0`；
- OTA CCC 撤销和 BLE 断链中止；
- 长度错误返回状态 2。

Host 测试使用 `rdx_firmware_update_fake.c` 替代 BR56 平台层，因此只能验证 Wire 合同、状态机和会话边界，无法发现以下问题：实际产物格式与 SDK API 不匹配、Norflash 写保护未解除、目标 Bank 地址/空间错误、Boot Info 写入失败以及复位后的 Bank 切换。本次两个关键问题都通过了 Host 测试却在实机暴露，平台适配修改后必须重新做目标构建和实机 OTA。

## 8. 实机验收清单

编译和 Host 测试不能证明 Flash、Bootloader 或无线链路的硬件行为。量产前至少完成：

当前状态：正式 APP 的正常 OTA 主链路已由用户实机确认通过；以下清单仍作为每次发布和量产前的完整回归要求，尤其不能由一次正常升级推导出异常恢复和断电保护已经通过。

5. 在写入阶段断电，确认旧 Bank 仍可启动且不会进入不可恢复状态；
6. 注入包号、长度、CRC32、低版本和超大镜像错误，核对状态码；
7. OTA 过程中尝试开始会议/通话录音，录音中尝试 Upgrade；
8. 同时保持 USB Speaker/Mic 工作，检查 USB reset、音频中断、堆栈和 Flash 时序；
9. 连续多轮升级和回退，检查双 Bank 交替、VM/认证码/RTC/录音数据不被破坏；
10. 检查复位前最后两条 Notify 在 Android 和 iOS 上均能被 APP 收到。

当前可以结论为“RDX OTA 已完成源码移植、Host 合同验证、目标固件构建和一次正常实机 OTA 主链路验证”。在完成第 4～10 项之前，仍不能声称断链/断电保护、双 Bank 连续交替或 USB Audio 并发压力已经通过硬件验证。

## 9. 实机问题复盘与避坑记录

### 9.1 最终正确路径

当前产品必须保持以下平台链路：

```text
db_update_data.bin
    -> RDX 448 B Wire 分包
    -> 1024 B Application Service 聚合缓冲
    -> dual_bank_passive_update_init()
    -> norflash_set_write_protect_remove()
    -> dual_bank_update_write()
    -> dual_bank_update_verify_without_crc()
    -> dual_bank_update_burn_boot_info()
    -> 两次 otareq 0#0
    -> 延迟复位并由 Bootloader 切换 Bank
```

其中写保护管理不是可选优化，而是 BR56 本产品的必要步骤：

1. OTA 初始化成功后、实际擦写前解除写保护；
2. 初始化/空间检查失败、Flash 写失败、校验失败、断链、CCC 关闭、超时和主动中止时恢复写保护；
3. Boot Info 提交完成后恢复写保护；
4. 所有失败路径都必须退出被动升级并清除 `ota_status`；
5. 镜像校验成功前绝不能写 Boot Info。

### 9.2 问题一：传输到 100%，APP 仍显示失败或 `request timeout`

失败日志 `COM3_2026-09-01_15-45-20.log` 的关键顺序为：

```text
data_complete bytes=556649 packets=1243
verify=start mode=sync
file head crc verify fail
UPDATE_ERR_NOT_FIND_TARGET_FILE
verify=done result=255
```

该日志说明 BLE 分包、包号、单包 CRC 和总长度均已完成，故“进度 100%”只表示文件传输完成，不表示目标 Bank 镜像校验和 Boot Info 提交完成。设备没有产生 `image_verified`、`commit=done result=0` 和最后两次 `otareq 0#0`，APP 最终只能表现为升级失败或等待应答超时。

最终根因是 BR56 Adapter 没有解除 Norflash 写保护。失败版本的日志中也没有 `norflash write protect area 0 to 0 KB`，而 BR56 SDK 的 `bt_fmy` 和 `update_tws_new.c` 在被动双 Bank 写入前均显式调用 `norflash_set_write_protect_remove()`。协议层能够持续接收并提交缓冲，不代表受保护的目标 Bank 已形成有效镜像；问题直到完整镜像校验才暴露。

修复原则：保留参考工程的 `dual_bank_*` 时序，在 `dual_bank_passive_update_init()` 之后、`dual_bank_update_allow_check()` 和实际数据写入之前解除写保护，并在所有结束路径恢复。

### 9.3 问题二：误切换到 `db_update_*` 后，第 3 包立即失败

排查 100% 后校验失败时，曾根据 BR56 中存在 `db_update_*` 接口以及产物名 `db_update_data.bin`，误把 Adapter 切换为：

```text
db_update_init()
db_update_allow_check()
db_update_write()
db_update_verify()
db_update_burn_boot_info()
```

结果两次都在第 3 个 448 B Wire 包之后失败：前三包累计 1344 B，Application Service 在填满首个 1024 B 聚合块后第一次调用 `db_update_write()`，SDK 随即打印：

```text
db_update_loop
ota head verify fail, -2
failed reason=flash_write state=4 next=4 received=1344
```

这是确定性的包格式/API 不匹配，不是 BLE 链路退化。BR56 库的 `db_update_check_ota_head()` 在首字不等于 `0x5C6A7B8E` 时返回 `-2`，而当前非压缩 `db_update_data.bin` 没有该 DB Package 文件头。失败后第 4 包出现的 `result=-5` 只是会话已经中止后的次生状态，不能把它当成首因。

经验：选择升级 API 必须同时核对构建模式、打包脚本、文件头和 SDK 示例，不能只看产物文件名。当前 `TCFG_UPDATE_COMPRESS = 0` 的 RDX 路径应使用 `dual_bank_*`；若以后启用 `TCFG_UPDATE_COMPRESS`，必须把它当作新的升级方案重新设计和实机验证。

### 9.4 问题三：增量构建缺少生成对象

切换升级接口并完成一次干净构建后，曾再次执行增量 `all`，链接阶段出现：

```text
reopening objs/apps/earphone/sdk_version.z.S.o: No such file or directory
```

该错误来自生成对象和增量依赖状态不一致，不是 RDX OTA C 源码语法错误。修改源文件选择、链接接口、配置宏或生成资源后，应从 `SDK/` 依次执行：

```powershell
.vscode\winmk.bat clean
.vscode\winmk.bat all
```

不要手工补写 `SDK/objs/`、`SDK/build/fileList.mk` 或其他生成文件。

### 9.5 构建、线刷和 OTA 包的版本一致性

`all` 会重新生成 OTA 产物；设备在线时，后处理流程还可能把本次构建固件直接下载到设备。验证时需要明确区分：

- 设备当前运行的基线固件；
- 包含待验证 Adapter 修复的固件；
- APP 实际选择的 `db_update_data.bin`；
- APP Upgrade 命令声明的文件大小和总包数。

每次回归至少记录 payload 的生成时间、大小和 SHA-256。源码重新构建后必须重新选择新文件，不能继续下发日志中曾使用的 556649 B、560701 B 等旧包。若要验证真正的 A -> B 升级，应分别归档 A 固件、B 固件和 B 对应的 OTA payload，避免线刷动作无意中改变测试基线。

Upgrade 命令中的版本号只参与 RDX 协议层的“必须高于当前版本”检查，不能证明 APP 选择的二进制就是该版本。`9.9.9` 是参考/调试日志中的测试值，不应作为长期发布策略。每个版本号必须和唯一 payload 哈希建立对应关系，并在复位后读取设备实际版本确认 B 固件已经运行。

### 9.6 日志判读矩阵

| 阶段 | 正常关键日志 | 典型失败 | 优先检查 |
| --- | --- | --- | --- |
| 握手 | `started ... packet_size=448`、`otareq state=0 next=1` | Upgrade 被拒绝 | 版本、认证、CCC、总包数、空间 |
| 平台初始化 | `dual_bank_passive_update_loop`、写保护解除 | `db_update_loop` 后很快 `ota head verify fail, -2` | 包格式与 API 是否匹配 |
| 数据传输 | 包号和 `next` 单调递增 | `packet_crc32`、`packet_number`、`data_timeout` | APP 分包、CRC32、BLE 链路 |
| 最后一包 | `data_complete bytes=... packets=...` | 最后一包长度错误或残余缓冲提交失败 | 文件大小、末包长度、异步写回调 |
| 镜像校验 | `verify=start mode=raw_bank`、`verify=done result=0`、`image_verified` | `file head crc verify fail`、`UPDATE_ERR_NOT_FIND_TARGET_FILE`、`result=255` | 写保护、目标 Bank 内容、payload 是否为本次构建 |
| Boot Info | `commit=accepted result=0`、`commit=done result=0`、`committed` | commit 非零 | Flash 写保护恢复时机、Boot Info 区域 |
| APP 收尾 | 两次 `otareq state=0 next=0` | APP `request timeout` | 先看设备是否完成 verify/commit，再查 Notify 是否送达 |
| 复位启动 | 延迟约 1 秒复位并重新连接 | 未复位、版本未变化、旧 Bank 启动 | reset timer、Boot Info、Bank 切换 |

APP 的 `request timeout` 是结果而不是根因。排查顺序应固定为：是否 `data_complete` -> verify 结果 -> commit 结果 -> 两次最终 Notify -> reset/Bank；不要先通过放宽 APP 超时掩盖设备端校验失败。

日志判读还需注意：

- 同一偏移、同一包数连续多次稳定失败，通常是包格式、写保护或平台状态等确定性问题，不应优先归因于随机 BLE 丢包；
- 多任务串口输出可能夹杂单独的 `#`、空行或墙上时钟交错，分析时应以 `[RDX][OTA]`、`[DOWNLOAD_MAIN]`/`[UPDATE_BANK]` 标签和设备运行时间的相对顺序为主；
- `TX ... ret=0` 只表示 Notify 已被协议栈接受/排队，不等于手机已经收到。最后两次 `0#0` 仍须由 APP 行为和 Android/iOS 实机确认；
- 同步镜像校验可能打印大量分块日志并持续一段时间，APP 超时必须覆盖正常 verify/commit 时长，但不能靠无限延长超时掩盖非零校验结果。

### 9.7 实现不变量

- 448 B 是 Wire 单包上限，1024 B 是内部 Flash 聚合块，两者不能混为 SDK 单包格式；
- `dual_bank_update_write()` 返回成功表示本次写任务被接受，最终校验必须等最后一次写回调完成；
- `dual_bank_update_write()` 与 `db_update_write()` 的回调签名和错误传递方式不同，重构时必须同步核对 typedef/函数原型；
- `outstanding_writes` 未归零时不得开始完整镜像校验；
- 最后一包不能提前返回下一包号，成功收尾必须保留参考工程的两次 `0#0`；
- verify 成功后先通知 `image_verified`，会话仍有效时才允许提交 Boot Info；
- 断链、CCC 关闭或超时后的迟到回调不得继续提交 Boot Info；
- 失败时不写 Boot Info，因此一次传输或校验失败不应破坏当前运行 Bank；
- 恢复写保护和清除 `ota_status` 必须覆盖成功、失败和主动中止三类出口；
- `ota_status` 必须覆盖整个接收、校验和提交阶段，既不能过早清零，也不能在失败后残留；
- `update.ufw`、`jl_isd.bin` 和 `jl_isd.fw` 不能替代当前 RDX payload；
- 编译成功、下载成功、进度 100% 和 OTA 成功是四个不同的验收层级。

### 9.8 后续回归建议

正常主链路已经打通后，后续修改应优先做以下高风险回归：

1. 连续执行至少两轮 OTA，确认两个 Bank 可以交替启动；
2. 分别在首包、中间包、最后一包、verify 和 commit 阶段断开 BLE；
3. 在写入阶段断电，确认旧 Bank 仍可启动；
4. 注入错误包号、长度、CRC32、低版本和超大文件；
5. Android 和 iOS 分别确认最后两次 Notify 均能到达；
6. OTA 同时保持 USB Speaker/Mic 工作，观察音频中断、USB reset、RAM 和 Flash 时序；
7. OTA 前后核对 VM、认证码、RTC 和录音数据；
8. 每轮在测试归档中保存完整串口日志以及实际 payload 的大小和 SHA-256；不要把临时日志、对象文件和生成固件作为日常源码提交内容。
