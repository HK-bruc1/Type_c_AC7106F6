## 1. 目的与当前结论

阶段 D 已完成 Local Storage Ability 正式广播，并打通录音落盘、在线镜像、容量查询、文件列表、删除和格式化等首轮业务。新增资源日志随后证明阶段 D 初始镜像尚不能作为性能达标或可长期运行的发布基线，因此启动本轮 O0～O2 与 O3-A 优化。当前优化已经完成阶段验收：STOP 超时正式关闭，既有录音断言按当前阶段关闭；完整架构收敛与量产长稳迁入 7-2。

`添加录音落盘后直接触发断言.log` 在正式本地存储镜像中记录到：

- 启动可分配 RAM 总量为 124 KiB，录音前最近一次周期采样仅剩 43 KiB；但当前资源监测把 RAM0 与 RAM1 相加，该数值不能直接代表 `vmalloc_` 所依赖内存池的真实余量；
- Local + Online 录音成功启动，SN 4 和文件名已分配，在线帧持续发送；
- 录音约 5.3 秒后，在周期 WRITING marker 的第一次写事务内触发 `ASSERT: vmalloc_ 147`；日志尚未出现随后重新打开回读的第二次路径打印，因此只能确认与 marker 事务时序邻近，不能证明“写后回读”是唯一触发点；
- 10 秒周期资源监测未覆盖断言前的瞬时低水位，因此日志中的 `min_free=43KB` 不是实际分配器低水位；
- 日志没有给出失败申请大小和调用栈，该样本不能把“目标内存池总量不足”“最大连续块不足”“allocator 页池或映射耗尽”“FAT/VFS 分配泄漏”“非法申请大小”“allocator 元数据破坏”及“并发生命周期错误”完全区分；触发时序和重复文件开关行为只支持优先审计 FAT/VFS 动态内存峰值，不能提前冻结唯一根因。

随后使用 O0-A 镜像采集的 `COM3_2026-09-03_17-34-11.log` 证明，完全关闭录音期间的周期 checkpoint 后，第一轮 Local + Online 能完整提交，但同次上电第二轮仍在 JL 私有 ATT 发送队列内触发断言。新断言不是原 `vmalloc_ 147`，而是 `att_send.c:602` 的 `send_list_len >= packet_size` 记账一致性检查失败。因此，O0 排除了“周期 checkpoint 是唯一根因”，但当时没有关闭 P0；该阶段问题应描述为高负载、低 RAM 余量下的 ATT 私有队列一致性失败，不能继续只描述成 checkpoint 路径分配失败。

O1 首轮镜像采集的 `COM3_2026-09-03_18-06-27.log` 没有断言、复位或 BLE 断链，但三轮 Local + Online 中有两轮因 Engine candidate queue full 被 RDX 强制停止。两次故障窗口同时出现 `btprofile: qfull`、`stack_resume_fail!!!:21`、逐帧 taskq wake 和 can-send 重臂压力；第二轮 `can_req=0` 时仍收到 `can_evt=824`，进一步证明当前 JL 多 Profile packet handler 收到的是共享就绪事件，不能再把所有“无 waiter”事件解释成 RDX 的无效事件。

O0-B 镜像采集的 `COM3_2026-09-03_19-39-14.log` 再次触发 `ASSERT: vmalloc_ 147` 和异常复位。Online 发送到 500 帧仍为 `send_fail=0 / pending=0 / peak=1 / drop=0`，但 Local + Online CPU 已升至 90%～92%，RAM0 最近一次采样只剩 20,224 B、低水位 18,688 B，并先出现 `source node have too much frame`。符号化回溯确认失败申请发生在 `jlstream_0` 的 `jlstream_get_frame()` 路径。O0-B 因此判定失败，P0 继续打开；由此转入 O2 首轮热路径减负，但这属于继续消除 P0 放大条件，不表示已经通过 O2 性能验收。

O2 首轮镜像采集的 `COM3_2026-09-03_20-24-17.log` 在同次上电连续完成三轮 Local + Online，最长一轮约 82.6 秒，未再出现断言、复位、`source node have too much frame`、Engine/Local 队列溢出或 Online 丢包。三轮 Native append 次数分别为 248、301、687，严格等于 `ceil(persisted_frame_count / 6)`，证明 6 帧批量落盘已在目标板生效。该样本同时暴露新的 APP 可见时延：STOP 首包到最终提交回执分别为 1.830、2.185、3.869 秒，APP 约每 0.5 秒重发 STOP，并在较长轮次显示指令超时；设备始终以 `duplicate_stop state=pending` 幂等吸收重发，最终回执 `ret=0`，文件和 Index 均成功提交。直接瓶颈是 STOP 内 256 B 分块的全文 CRC 回读，三轮 `close_verify` 分别耗时 1.170、1.490、3.180 秒，并随 118,800、144,400、329,680 B 文件长度近似线性增长，不是 BLE STOP 应答丢失。

O2 第二轮镜像采集的 `COM3_2026-09-03_20-38-28.log` 再次复现 `att_send.c:602` 断言。新固件第一轮 62,720 B 录音完整提交，但第二轮在录音流发送期间先累计 `send_fail=200 / q_peak=12`，随后于约 45 秒处触发 `user_att_send_streamer(601): send_list_len(0) >= packet_size(114)`；断言前没有 STOP，3,072 B CRC workspace 未处于使用期。本轮证明 O2 首轮三次成功只是明显改善，不能关闭 P0；当时直接可控的风险是 RDX 在一次可重试发送失败后仍随每个 20 ms 新帧再次探测 JL 私有 ATT 队列，必须先在 Online Destination 边界形成真正的背压等待门闩。

O2 第三轮镜像采集的 `COM3_2026-09-03_21-03-00.log` 连续完成三轮约一分钟 Local + Online 录音，未出现断言、复位、Online 发送失败或帧丢弃，但三次 APP STOP 均提示指令出错。设备每轮都收到了 STOP 首包和随后 3 次约 0.5 秒间隔的重试，说明请求没有被覆盖或漏收；最终 STOP 回执均在 Artifact 完整提交后以 `ret=0` 进入 ATT，分别晚于首包约 2.925、2.530 和 2.886 秒。三轮 `close_verify` 分别占约 2.20、1.80 和 2.02 秒，仍是主要耗时。现有设备侧日志不能证明每个 Notify 已被手机空口确认，但“请求全部到达、无发送错误、最终回执稳定晚于 APP 重试窗口”的一致证据已经把当前 APP 报错定位为同步 Commit 超窗，而不是 Online 16 帧队列覆盖或已有证据支持的 BLE 丢包。

依据参考工程“先上报 STOP 状态、后保存 UXFILE 索引”的直接实现证据和产品兼容决策，O3 第一轮已将现有长 `record#0` 从 Artifact Commit 回执纠正为 Session 状态回执：Engine 关闭音频源、建立 STOP cut 并将 cut 前候选帧交给 Destination 后即通知 Protocol；Protocol 立即携带 START 时已经预留的 SN/文件名上报，不再等待全文校验。强 Commit 仍继续执行，成功文件才进入列表；它不是现有 V23 APP 指令完成的前置条件。

O3 第一轮目标板日志 `不出现STOP指令出错了.log` 已验证上述时序。两轮 Local + Online 通话录音的 STOP 状态分别在首包后约 17 ms、18 ms 发出，均为 `ret=0 / committed=0`，APP 不再重发 STOP，用户端也确认不再出现指令出错或超时；随后 Artifact 分别在约 1.046 秒、1.110 秒完成全文校验、publish 和 Index commit。两轮 Local、Online 与 Engine 计数全部闭合，没有断言、异常复位、发送失败、丢包或队列溢出。由此，STOP 控制超时作为已知功能缺陷正式关闭；既有短时断言在背压门闩后的连续三轮约一分钟样本和本轮两轮功能样本中均未复现，按产品决策通过当前阶段验收，不再阻塞推进。20 次 × 5 分钟、30 分钟及更长录音转为后续压测观察项；若复现同类断言，再以新日志重开问题，不能把当前短测写成量产长稳结论。

本轮优化采用以下结论：

1. **P0 是消除正常录音路径上的全部断言，而不是只消除某一个断言文本，也不是先机械删除任务。**
2. **RDX 要求的是单一、可串行化的 FAT 执行上下文，不要求必须新建一个 OS 任务。** Storage Service 与执行载体必须解耦。
3. 当前独立 `rdx_storage` 任务有明确内存成本，但它不是 22 KiB RAM 差异的全部来源，也不是现有证据能够单独确认的断言根因。
4. 优先回收大块静态 RAM、减少运行期 FAT 文件事务和重复 CRC，再依据栈水位与 I/O 最坏时延决定 Storage Executor 的最终载体。
5. 阶段 D 功能提交可以保留；O3 第一轮目标板复测后，已知 STOP 超时正式关闭，既有录音断言按当前阶段验收关闭，不再阻塞正式 Ability 和后续业务推进。但短测通过仍不得扩大为“长稳通过”或“量产可靠性完成”。
6. 当前恢复只验证 A/B Index 已引用的 `INDEXED/PUBLISHED` Artifact，尚不能发现未入索引的 WRITING marker；在发现与恢复裁决闭合前，录音中的周期 WRITING marker 只是未来恢复合同的占位成本，不得描述为已经可用的断电 checkpoint。
7. 在按 RAM0/RAM1 分池取得失败申请证据前，不冻结固定的“最低空闲 RAM”数值；首轮门槛只要求零断言、各池低水位可解释且保留经实测确定的安全系数。
8. O0-A 的新证据足以启动 O1 静态 RAM 回收，但不足以证明 ATT 断言已经解决；O1 编译通过后仍必须刷机完成连续多轮实测。
9. `ATT_EVENT_CAN_SEND_NOW` 在当前 JL 多 Profile 路径中是共享事件；RDX 只能记录“本次是否由 RDX waiter 消费”，不能从事件数大于请求数反推 JL 私有栈产生了无效事件。
10. O0-B 已证明只约束 can-send 主动请求并合并 Record Engine wake 仍不足以关闭 P0；下一步先降低每帧 FAT 调用、allocator churn 和重复 CRC，再根据同配置目标板数据判断是否还需继续追查 ATT 私有累计、堆碎片或其他生命周期问题。
11. O2 第二轮曾反证“批量 append 已消除全部断言”；其后 O2 第三轮背压门闩镜像完成三轮约一分钟录音，本轮 O3 镜像又完成两轮录音，均未复现。产品据此接受当前阶段关闭，20 次 × 5 分钟和长录音不再作为本次推进的阻塞门禁，而作为后续压测项目保留。
12. STOP 指令超时已定位为“强 Commit 完成后才回最终成功”与 APP 等待窗口冲突。参考 V23 的 `record#0` 本义和实现时序是录音状态通知，不是 Artifact Commit 凭证；O3 已恢复 `SESSION_STOPPED` 快速 ACK，让强 Commit 在设备内部继续完成。只有产品要求 APP 明确显示“文件已提交/提交失败”时，才需要定义新的 `ARTIFACT_COMMITTED/FAILED` Wire 并修改 APP。
13. O2 第三轮已在 RDX OPTIONAL Online 边界加入背压门闩，不修改或屏蔽 JL 私有断言。新日志没有触发发送背压，因而不能单独证明极端拥塞分支，但当前正常功能路径已通过验收；未来压测若复现，继续从 RDX/JL 公开集成边界取证，不修改 JL 私有 ATT 实现来掩盖。
14. O2 第三轮三次 STOP 已反证“回执被 Online 队列覆盖”与“设备漏收 STOP”：APP 的 4 次发送全部进入 Protocol，最终 TX 均返回 0；当前必须进入 O3 两阶段 completion，而不是继续扩大队列或只调整 CRC 分块。对现有 APP 的首选兼容路径是不改 APP：快速 `record#0` 只表达 `SESSION_STOPPED`，正常文件仍须 Commit 后才进入列表；是否继续发送第二条携带 SN/文件名的状态通知属于兼容性实验，不得预设为新 APP 的强制要求。
15. 产品已选择更贴近参考工程的现有 APP 兼容语义：SN/文件名在 START 时已经稳定预留，快速长 STOP 可以携带该身份，但只表示录音停止和 Artifact 关联，不表示介质强校验完成。正常 Commit 成功后不重复上报 STOP；若 Commit 失败，Artifact 不进入列表，并以内部 completion 与日志保留失败事实。
16. `不出现STOP指令出错了.log` 已确认快速 STOP 的功能效果：两轮均在约 20 ms 内回复、无 APP 重试，之后正常 Commit；STOP 指令错误/超时问题正式关闭。当前样本没有断言，既有断言按阶段验收关闭并转入压测复发观察。

## 2. 证据基线

### 2.1 两份资源日志的可比结果

| 项目 | 在线录音基线 | 加入正式本地落盘 | 结论 |
| --- | ---: | ---: | --- |
| 启动 allocator 总量 | 146 KiB | 124 KiB | 可分配空间减少约 22 KiB |
| 录音期已采样最小空闲 | 44 KiB | 未采到断言前瞬时值 | 本地镜像 10 秒采样周期遗漏了关键峰值 |
| 在线录音 CPU | 约 81%～82% | 断言前无完整稳定窗口 | 原在线链路已经处于高负载，不能假定落盘 CPU 余量充足 |
| 正常录音结果 | 可连续录音并 STOP | 约 5.3 秒触发 `vmalloc_` 断言 | 当前本地镜像存在 P0 稳定性缺陷 |

两份日志的 Flash Code capacity 也不同，说明它们不是只改变一个函数后的严格 A/B 镜像。后续性能对比必须固定产品配置、资源文件、日志开关和编译选项，只切换明确的测试门控。

历史 RDX/USB Audio 内存复盘还记录过：另一场景在约 35,072 B physical memory 余量时触发 `vmalloc_ 147`，提升到约 64,768 B 后越过峰值。该数据与本轮合并 RAM 日志不是同一指标、同一场景，不能直接用作当前门槛；但它进一步说明不能把 20 KiB 合计空闲量设为通用安全线。

### 2.2 当前 ELF 的常驻 RAM 构成

当前 ELF 中与本地存储直接相关的主要常驻对象如下：

| 对象 | 大小 | 主要内容 |
| --- | ---: | --- |
| `rdx_local_wire` | 11,788 B | 8 KiB 列表 JSON、32 项文件信息、上传和发送缓冲 |
| `rdx_sd0` | 6,680 B | 打开文件状态、索引序列化缓冲、32 项枚举缓存 |
| `rdx_local_storage` | 5,692 B | 16 帧队列、Artifact、32 项 Service scratch、操作状态 |
| Recording Coordinator | 48 B | 编排引用和状态 |
| 合计 | 24,208 B | 约占当前 58,580 B BSS 的 41.3% |

当前三个大对象中存在明显的生命周期互斥与数据重复：

- `rdx_local_wire.files[32]` 保存完整文件列表；
- Local Storage Service scratch 再保存 32 项文件或索引；
- Native Backend 又保存 32 项 `enumerate_entries`；
- Wire 另行常驻 8 KiB 完整 JSON，但 BLE 实际按 96 B 分片发送。

因此，第一优先级不应是缩减 16 帧录音缓冲。该队列约提供 320 ms 的介质抖动容忍，当前尚未测得 FAT 最坏写时延，过早缩短会把内存问题转换成丢帧问题。

### 2.3 任务成本的准确解释

当前任务表配置为：

~~~c
{"rdx_record",  4, 0, 1024, 128},
{"rdx_storage", 5, 0, 1024, 128},
~~~

JL `os_task_create()` 的 `stksize` 单位是 `u32`。因此：

- `rdx_storage` 的任务栈预算是 4,096 B，而不是 1,024 B；
- 任务队列另占 128 B，并有 TCB、对齐和调度器管理开销；
- `rdx_record` 从 512 调到 1024，相比阶段 A 额外增加约 2,048 B 栈预算；
- 两项任务配置带来的新增动态 RAM 预算至少约 6 KiB，尚未计入 TCB 和分配器开销。

这部分在 124 KiB allocator 上是显著成本，必须测量并收敛，但它仍小于本地存储相关 24,208 B 常驻对象总量。

### 2.4 参考工程并非无任务实现

对参考工程 `tide-bridge/SDK/apps/common/third_party_profile/rdx_protocol/librdxApp.a` 的 `rdx_uxfile.c.o` 做符号与 LLVM IR 审计可见：

- 对象依赖 `os_task_create`、`os_task_del`、`os_taskq_pend` 和 `os_taskq_post_msg`；
- 对象包含私有 `rdx_uxfile_task` 与 `is_uxfile_task_created`；
- `rdx_uxfile_init()` 调用 `os_task_create(rdx_uxfile_task, NULL, 3, 4096, 512, ...)`；按 JL 单位换算，其任务栈预算为 16 KiB，队列为 512 B；
- 同一初始化路径还尝试申请 32 KiB `dat_fixed_buffer`；
- 参考工程 `rdx_app.c` 确实调用 `rdx_uxfile_init()`。

参考工程之所以在 `task_info_table` 看不到 UXFILE，是因为它直接调用 `os_task_create()`，不是因为没有任务。参考工程的任务和缓存预算不能直接复制到当前 124 KiB allocator 产品，也不能作为删除当前执行上下文的依据。

可以借鉴参考工程的业务行为和文件兼容合同，但性能方案必须以当前 BR56 产品的真实 map、栈水位、分配器低水位和介质时延为准。

### 2.5 当前 WRITING marker 的恢复能力边界

当前 Native Backend 的 `store_marker()` 会序列化 marker，执行写入和关闭，再重新打开同一路径回读校验。该过程可以验证本次 marker 文件事务，但当前启动恢复存在更前置的发现缺口：

- `recover()` 只加载 A/B Index，并遍历 Index 已引用的 Artifact；
- 恢复只接受 `INDEXED` 或 `PUBLISHED` marker，不扫描 `RDXTMP/`，也不发现未入索引的 WRITING marker；
- `load_latest_marker` 虽已存在于 Native Port，但 Service 恢复流程尚未调用它发现未提交 Artifact；
- 因此设备在录音中断电后，目前不能依靠每秒 WRITING marker 自动找到并恢复临时音频。

这意味着周期 WRITING marker 当前每秒承担 `fopen/fwrite/fclose`、LFN 和回读成本，却没有形成可被启动恢复消费的 checkpoint。P0 可以关闭或降级该周期事务；真正恢复路径完成后，必须重新定义 marker 发现、音频持久化边界、长度裁决、CRC 裁决和隔离规则，再决定 checkpoint 周期。

断言日志最后一次 marker 路径只打印了一次，随后即触发 `vmalloc_ 147`，没有进入回读阶段的第二次路径打印。因此取消写后回读会降低事务次数，但不保证消除当前断言；“完全关闭周期 checkpoint”必须作为独立隔离组。

### 2.6 JL FAT 每次写入的动态分配成本

当前产品设置 `FATFS_SUPPORT_OVERSECTOR_RW=1`。对当前 ELF 的 pre-opt LLVM IR 审计可见，JL `f_write()` 在该路径按写入长度执行近似如下的临时申请：

~~~text
zalloc((btr + 1023) & ~511)
~~~

当前 Service 对每个 20 ms、80 B Opus 帧单独调用一次 `fwrite()`，因此每次写入会触发约 1,024 B 临时申请，频率约为 50 次/秒。该缓冲会在 FAT 调用内释放，但高频申请/释放会增加 allocator churn、峰值重叠和碎片风险；这是 O2 批量写的首要依据之一。该事实不能单独证明本次断言由 `f_write()` 唯一触发，仍须由 O0 记录失败申请大小和调用点。

当前同时设置 `FATFS_SUPPORT_WRITE_SAVE_MEANTIME=0`，即逐次写入不主动同步目录项。marker 文件自身关闭不能证明仍保持打开的音频文件长度、目录项和前 N 帧已经持久化。JL 提供公开的 `f_flush_wbuf()`，但它对本产品 sd0/FAT 的数据与元数据保证、最坏时延和 RAM 峰值必须在目标板上审计，不能仅凭接口名称定义 durability。

### 2.7 调度与唤醒成本

当前 `rdx_record` 优先级为 4，`rdx_storage` 优先级为 5，而 `jlstream_0`～`jlstream_7` 同样是优先级 5。独立任务成本不仅是 4 KiB 栈和队列，还包括逐帧唤醒、上下文切换、同优先级 runnable latency 及可能对音频流任务产生的调度干扰。

当前 START 流程还会先以预备 Session 写一次 WRITING marker，再在 `attach()` 绑定实际 Session 后重写一次。后续事务统计必须覆盖 START 双 marker、逐帧 append、周期 marker、终态 marker 和 Index，而不能只统计录音中的周期 checkpoint。

### 2.8 O0-A 目标板复测与 ATT 断言取证

由此冻结以下工程结论：

1. O0-A 已排除周期 checkpoint 为唯一根因，不能把“关闭 checkpoint”写成 P0 已修复。
2. 第一轮成功、第二轮失败说明问题具有峰值、累积或时序相关性，不是每次 START 后固定在同一帧必现。
3. Online 队列目标板峰值仅为 1，64 帧常驻容量没有数据依据；Online 是 OPTIONAL，可先降到 16 帧，为 ATT/FAT 释放 RAM。
4. 不修改或屏蔽 JL `att_send.c` 断言，不直接改 JL 私有 BT 库，不以额外 RDX 锁掩盖问题；先在既有 RDX/JL 集成边界内回收静态 RAM 并降低热路径动态分配频率。
5. 尚无证据证明 RDX 存在确定的越界写；后续若 O1/O2 后仍复现，必须继续采集失败申请、堆完整性和异常地址证据，再定位实际破坏源。

### 2.9 O1 目标板复测与队列强制停止取证

`COM3_2026-09-03_18-06-27.log` 来自 O1 首轮正式构建，仍为 checkpoint A 隔离策略，但已包含流式文件列表和 Online TX 队列 64→16 的静态 RAM 优化。该日志没有出现 `ASSERT`、异常回溯、看门狗复位或二次启动；故障后资源监测和 BLE 连接参数更新仍继续输出。因此，本次现象不是芯片断言复位，也不是 BLE 链路断开，而是 RDX 对录音 Session 的强制停止。

同次上电共执行三轮 Local + Online：

- 第一轮运行约 3.7 秒后强制停止：`mode=2 cause=5 result=10`，即 `RDX_RECORD_TERMINATION_FORCED + RDX_RECORD_CAUSE_QUEUE_FULL + RDX_RECORD_RESULT_QUEUE_FULL`；Engine `overflow=1`、`stop_discarded=16`，证明 16 帧 Engine candidate 队列已经饱和；
- 第二轮由 APP 下发 STOP，完整成功：Engine `produced=914`，扣除 10 帧 warm-up 后 `destination_out=904`；Local `accepted/persisted=904`，最终文件 72,320 B、CRC `08694ADC`，publish、Index commit 和 INDEXED marker 完成；Online `sent=904`、`q_peak=1`、`send_fail=0`；
- 第三轮运行约 19.5 秒后以同一 `cause=5` 强制停止：Engine `produced=971`、`destination_out=944`、`overflow=1`、`stop_discarded=16`。Local 对已收到的 944 帧全部 `persisted=944`，但由于 REQUIRED Artifact 所属 Session 已异常终止，最终按失败 Artifact 收敛，不能发布为成功文件。

BLE 与调度侧证据为：

- 整份日志只有一次 LE connection complete，没有 `HCI_EVENT_DISCONNECTION_COMPLETE` 或 `[RDX] disconnected`；两次强停之后仍有 `conn_param_update status=0`，所以 APP 看到的“断开”只能解释为录音状态被设备端强制结束，不能写成 BLE 断链；
- 第一轮 Online TX 已达到 `q_peak=16`，发生 `tx_drop=5`、`send_fail=171`；第三轮为 `q_peak=15`、`send_fail=315`。先前 O0-A 两轮 `q_peak=1` 的样本不足以证明 16 帧在所有时序下安全，O1 的 64→16 参数不能按原理由直接进入发布配置；
- 两次强停前均密集出现 `stack_resume_fail!!!:21` 与 `btprofile: qfull: 4, 0`。这不是任务栈越界文本；它表明 JL Bluetooth profile/stack 唤醒或消息路径已发生队列拥塞。同一窗口内 Engine `overflow=1`，说明 `rdx_record` 未能在 320 ms candidate 预算内持续消费，但当前日志尚不能证明两种队列拥塞之间的单向因果关系；
- 第三轮正常发送阶段 CPU 约为 87%～90%，RAM0 最近一次空闲 21,248 B，本次上电低水位仍为 9,472 B；O1 回收的 14,432 B 静态空间没有转化为已证明的运行期安全余量。CPU 和低水位仍是拥塞放大条件，但不能单独写成唯一根因；
- `can-send` 诊断在第一轮记录 `can_req=153 / can_evt=253 / spurious_evt=101`，第三轮进一步达到 `can_req=271 / can_evt=1102 / spurious_evt=831`；更关键的是正常第二轮在 `can_req=0` 时仍有 `can_evt=824 / spurious_evt=824`。这证明旧字段 `spurious_evt` 命名和“无效事件”解释不成立：JL 多 Profile packet path 会把不归当前 RDX waiter 所有的共享就绪事件也分发给 RDX。事件数不能证明 JL 私有库缺陷，但 RDX 逐次调用全局 `att_server_request_can_send_now_event()` 会叠加到同一 `btprofile` 路径，因此仍须作为 P0 约束对象；后续字段改名为 `unowned_evt`，只表达“未被 RDX waiter 消费”。

由本轮复测冻结以下结论：

1. O1 避免了本次测试中的硬断言和复位，但以 Engine candidate queue full 强制停止两轮录音，**O1 目标板稳定性验收失败，P0 继续保持打开**。
2. 本次直接停止原因已经定位为 Engine candidate 队列饱和；未出现 `local_queue_full`，且 Local 对进入 Service 的帧均已落盘，因此不能把直接原因写成 Local 16 帧队列溢出。
3. Online 16 帧队列确实出现峰值和丢包，原容量假设失效；但 Engine candidate 饱和与 `btprofile` 拥塞并不等价于 Online 数组容量不足，单纯恢复 64 帧不能被宣称为根治，并可能重新扩大 ATT/heap 峰值。
4. 下一步优先级仍属于 O0/P0 的 BLE back-pressure 与调度止血：先约束 RDX 对共享 `can-send` 路径的主动重臂并合并 worker 唤醒，再决定 Online 队列容量；`unowned_evt` 是共享分发观测量，不设置为零门槛。在零 candidate overflow、零 `btprofile qfull` 前不进入 O2 性能验收。
5. 不修改 JL `att_send.c`、Bluetooth 私有队列或断言；修复应先落在 RDX Transport Adapter、Online OPTIONAL 背压策略和 Record Engine 有界唤醒边界内。

本轮取证还纠正了两个曾经合理、但已被新证据反证的假设：

1. 从 `audio_pipeline_ready` 的 56,320 B 到首个 250 帧采样点的 20,224 B，表面下降约 36 KiB；不能据此按 250 包折算出约 144 B/包并宣称 ATT 私有链表线性滞留。`在线录音时的资源监测.log` 中 Online-only 基线也在 Pipeline 启动后的首个采样窗口一次性下降约 48 KiB，随后长期稳定在约 44～49 KiB。该下降包含 JL 音频 Pipeline 的延迟建池和场景切换成本，不满足“按 Online 帧数线性增长”的证据条件。ATT 无界累计仍可保留为待验证方向，但不得冻结为本轮根因，也暂不实施会改变吞吐合同的“单在途信用”改造。

### 2.11 O2 首轮目标板复测与 STOP 指令超时

`COM3_2026-09-03_20-24-17.log` 来自 O2 首轮 6 帧/480 B 批量落盘镜像。同次上电连续执行三轮正常 STOP，结果如下：

| 轮次 | Local 持久化帧/字节 | Native append 次数 | `close_verify` | STOP 首包至最终 TX | pending 重发 | 最终结果 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 1,485 / 118,800 B | 248 = `ceil(1485/6)` | 1,170 ms | 1,830 ms | 3 次 | SN 11，CRC `AE588300`，提交成功 |
| 2 | 1,805 / 144,400 B | 301 = `ceil(1805/6)` | 1,490 ms | 2,185 ms | 3 次 | SN 12，CRC `64D0A774`，提交成功 |
| 3 | 4,121 / 329,680 B | 687 = `ceil(4121/6)` | 3,180 ms | 3,869 ms | 3 次 | SN 13，CRC `737C7384`，提交成功 |

本轮可以冻结以下结论：

1. 三轮均满足 Engine `overflow=0 / mismatch=0 / stale=0 / stop_discarded=0`，Local `accepted == persisted`，Online `sent == destination_in / pending=0 / q_peak=1 / send_fail=0 / tx_drop=0`；没有断言、异常复位、`btprofile qfull`、`stack_resume_fail` 或 `source node have too much frame`。因此 O2 批量写至少在本次约 30 秒、36 秒和 83 秒样本中消除了此前可复现的短时崩溃/强停，但三轮短测不能替代 20 次 5 分钟和 30 分钟长测，P0 暂不关闭。
2. 批量写确实在目标板生效。append 次数精确等于持久化帧数除以 6 向上取整，而不是仍按 80 B 单帧写；最大单次 append 时延为 90～100 ms，当前 16 帧/320 ms Local 队列在本样本中未溢出。
3. STOP 超时不是“偶发 BLE 丢包”的现有证据。APP 在首个 STOP 后约每 0.5 秒重发；Protocol 保持 `STOP_PENDING`，不重复提交、不提前回成功；最终三次 `*DEV#record#0...#sn#filename#` 发送均 `ret=0`。APP 提示是否出现受自身重试/总 deadline 竞争影响，固件端的根因却是确定的完成时延。
4. `close_verify` 覆盖 `fclose()`、重新打开临时文件并以 256 B 栈缓冲全文 `fread()`/CRC。它占三轮 STOP 总时延约 64%、68% 和 82%，吞吐约为 97～102 KiB/s；随后 SEALED marker、publish、PUBLISHED marker、Index load/commit 和 INDEXED marker还需约 0.61～0.64 秒。文件越长，最终 STOP 回执越晚，因此当前实现明确未通过 O2 的“STOP 时延不随文件长度线性增长”门槛。
5. Local + Online 录音窗口整机 CPU 约 80%～88%，低于 O0-B 已观测的 90%～92%，但仍属高负载；RAM0 本次低水位为 24,320 B，三轮结束并退出相关音频流后空闲恢复到 97,024 B，当前未见按轮次单调下降。`rdx_record` HWM 为 901/1024（约 88%），超过本文 75% 首轮门槛；`rdx_storage` 为 251/1024。后续禁止继续给 `rdx_record` 叠加大块栈缓冲，并应在 O3 把 SEAL/FAT 工作迁移到 Storage Executor。
6. 下一步先在不降低 `on_media_verified` 的前提下提高全文回读块大小，并复用 Backend 已有、与 close verify 生命周期互斥的 workspace，避免增加 `.bss` 和 `rdx_record` 栈；目标板重新测量 `close_verify`、STOP 总时延、RAM0 低水位和栈 HWM。该动作只能降低线性项系数，不能宣称从架构上消除 O(n)。若 1 分钟及更长文件仍超过 APP deadline，O3 必须把快速 `SESSION_STOPPED` ACK 与异步 `ARTIFACT_COMMITTED/FAILED` 最终通知拆开，同时保持失败不得携带成功身份。

### 2.15 O3 第一轮参考兼容 STOP 状态解耦

本轮根据产品决策直接保留当前长 STOP 的 SN/文件名，并把发送时点前移到参考语义允许的最早安全边界，不修改 APP 和 JL 私有库：

1. `RDX_RECORD_ENGINE_STOP_ACK_READY` 是新增的 Engine 内部事件。正常 STOP 先关闭 frame gate、进入 stopping、关闭音频源，再排空 Engine 中 STOP cut 前的候选帧；只有这些帧已经被 Destination 接纳后才发事件。它不是“收到命令立即乐观成功”，也不等待 Local `seal()` 的全文 CRC、publish 和 Index。
2. Protocol 收到该事件后保持内部 `STOP_PENDING`，但把 Wire state 置为 0，并立即发送既有长格式 `*DEV#record#0#...#SN#filename#`。SN 和文件名来自 START 前已持久化高水位分配的 Artifact 身份，本次上报只表达 Session 已停止及其关联身份，不能再作为文件已 Commit 的证明。
3. STOP cut 建立前的重复命令仍只做 pending 去重；快速 ACK 可用后，重复 STOP 只幂等重发相同长回执，不重复提交 Engine STOP 或 Local Commit。若第一次 ATT 发送返回非零，后续 APP 重试可以恢复回执；若没有重试，最终 completion 仍会在尚无成功 ACK 时执行兼容兜底发送。
4. 正常 Artifact 提交完成且快速 ACK 已发送时，不再发第二条 STOP，避免要求现有 APP 理解新的两阶段 Wire。全文校验、marker、publish 和 Index 顺序保持不变，只有 Commit 成功的 Artifact 才进入文件列表。若快速 ACK 后 Commit 失败，APP 已知的是“录音已停止及预留身份”，失败文件不会进入列表；当前 V23 没有独立保存失败通知，失败事实由内部 completion 和日志保留。
5. 该改动解决的是 APP 控制 deadline，尚未完成 O3 的线程所有权收敛：`seal()` 仍在 `rdx_record` 调用链继续执行，后续才迁移为 Storage Executor 完整异步 completion。因此不能把本轮描述为已经删除 Storage task 或完成 O3 架构验收。
6. 快速 ACK 后 APP 若立刻请求文件列表，Local Service 仍可能处于 Commit，占用期间应返回现有 BUSY/失败语义；目标板复测必须检查 APP 是否自动触发该竞态。若存在，只在 Local Wire 层增加可重试状态或完成后刷新，不允许把未提交文件提前放入列表。

Host Golden Trace 15/15 组通过；录音专项用例覆盖“cut 前重复 STOP 不回复”“cut 后首次 ATT 返回可重试错误”“下一次 STOP 重试成功重发同一长 ACK”“最终 Commit 不重复上报”。快速 ACK 的跨任务标志使用显式易变字段，completion 发送还检查 Protocol 上下文，避免 Commit 期间断链/退出后访问陈旧上下文。BR56 Windows `all` 已完成编译、链接和打包，`.bss=0xB134=45,364 B`，未增加静态 RAM；最终仓库固件时间戳为 2026-09-03 21:27:04。下载器明确报告 `Device online`、`Start downloading data to flash`、`Download completed` 和 OTP 参数保存成功，因此 O3 第一轮最终镜像已经实际烧录。

### 4.2 O1：常驻 RAM 收敛

本轮完成两个可独立验证的静态 RAM 优化：

- 删除常驻 8 KiB 完整列表 JSON，改为按 `requested_pack` 确定性重编码的流式输出，保留随机包、重复包、乱序和 JSON 转义兼容；
- Online OPTIONAL 队列由 64 帧降为 16 帧；Local REQUIRED 的 16 帧队列保持不变，不以牺牲本地落盘抗抖能力换取 RAM。

| 项目 | O0-A | O1 后 | 差值 |
| --- | ---: | ---: | ---: |
| `.bss` | 59,796 B | 45,364 B | -14,432 B |
| `rdx_local_wire` | 11,788 B | 3,600 B | -8,188 B |
| `rdx_online_record` | 8,456 B | 2,216 B | -6,240 B |

O1 达到了“不少于 12 KiB”的静态回收目标。16 帧队列曾在拥塞样本中达到峰值，因此后续采用背压门闩控制底层重入，而不是简单扩大队列。任务栈没有在缺少最坏水位证据时继续缩减。

### 4.3 O2：录音热路径与 Online 背压

- 正式 Opus 路径由每个 80 B 帧一次 `fwrite()` 改为 6 帧/480 B 批量落盘；STOP 时强制冲刷不足 6 帧的尾批次；
- 批次成功后仍按原始帧边界推进计数和 rolling CRC，short write 继续使 REQUIRED Local Artifact 失败；
- 480 B staging 复用已证明生命周期互斥的 Service scratch，没有增加 `.bss`，也没有压入高水位 Record/Storage 任务栈；
- Storage wake 按批次、SEAL 和异步操作进行边沿合并，避免逐帧 taskq post；
- 删除 Native Backend append 期间的第二份 rolling CRC，保留 STOP 后全文回读、文件长度比较、publish 和 Index commit；
- 全文 CRC 回读改为复用 3,096 B Backend workspace、按 3,072 B 连续读取，移除 `rdx_record` 调用栈上的 256 B 局部缓冲；
- Online Destination 增加 `tx_waiting` 背压门闩：首次可重试发送失败后停止逐帧重入 JL ATT，直到 owned can-send 到达；队列和 Wire 均不扩张。

目标板证明 6 帧批量已经生效：Native append 次数严格等于 `ceil(persisted_frame_count / 6)`。背压门闩后的三轮约一分钟录音未再复现断言；极端拥塞分支尚未被本轮正常样本触发，其压力验证保留到 7-2。

### 4.4 O3-A：STOP 状态与强提交解耦

本轮没有修改 APP，也没有扩展现有 V23 Wire：

1. START 时预留稳定的 SN 和文件名；
2. STOP 时关闭音频源、建立 STOP cut，并移交 cut 前候选帧；
3. 随即发送现有长格式 `record#0`，表达 `SESSION_STOPPED` 及其 Artifact 身份；
4. 全文 CRC、publish 和 Index commit 在回执后继续执行；
5. 只有 Commit 成功的 Artifact 才进入文件列表；失败文件不进入列表；
6. Commit 成功后不再发送第二条 STOP；重复 STOP 在 cut 前去重，快速 ACK 可用后可幂等重发，但不重复提交。

这一语义与参考工程“先上报停止状态、后完成文件索引”的行为一致，同时保留当前产品的强 Artifact Commit 合同。`record#0` 不再被错误地解释为介质强校验凭证。

### 6.1 提交镜像的诊断门控

本轮取证能力保留在源码中，但提交/发布配置默认关闭，避免周期串口输出、FAT 热路径采样和诊断统计占用正式运行资源。产品诊断镜像的统一入口为 `TCFG_PRODUCT_DIAGNOSTIC_BUILD_ENABLE`，RDX 内部普通诊断再由 `RDX_CFG_DIAGNOSTIC_ENABLE` 统一派生；两者默认值均为 `0`：

| 门控 | 默认值 | 关闭后效果 | 需要时的用途 |
| --- | ---: | --- | --- |
| `TCFG_PRODUCT_DIAGNOSTIC_BUILD_ENABLE` | 0 | 关闭常规诊断集合 | 构建临时排障镜像的统一入口 |
| `TCFG_RESOURCE_MONITOR_ENABLE` | 跟随统一入口 | 不编译 10 秒周期 RAM/Flash、瞬时低水位及关键任务快照 | 观察 RAM0/RAM1、任务栈水位和 CPU |
| `TCFG_RESOURCE_MONITOR_EXCEPTION_BACKTRACE_ENABLE` | 跟随统一入口 | 不为 JL 异常打印追加调用栈回溯 | 定位断言和异常调用链 |
| `RDX_CFG_DIAGNOSTIC_ENABLE` | 跟随产品诊断入口 | 关闭普通 RDX 诊断集合 | RDX 内部诊断的统一入口 |
| `RDX_CFG_LOCAL_STORAGE_O0_DIAG_ENABLE` | 跟随 RDX 诊断入口 | 不编译 FAT 时延直方图，不在 append 后查询 heap，不追加存储事件资源快照 | 定位 FAT/VFS 时延与低水位窗口 |
| `RDX_CFG_RECORD_PERF_DIAG_ENABLE` | 跟随 RDX 诊断入口 | 不保留、不更新、不打印 Record wake 统计 | 验证 worker 唤醒合并效果 |
| `RDX_CFG_BLE_TX_DIAG_ENABLE` | 跟随 RDX 诊断入口 | 不采集、不打印详细 ATT/TX 统计 | 定位 Online 背压、队列和 can-send 行为 |
| `RDX_CFG_KEY_DIAG_ENABLE` | 跟随 RDX 诊断入口 | 不打印按键所有权与路由明细 | 排查按键路由 |
| `RDX_CFG_SENSITIVE_DATA_DIAG_ENABLE` | 0，独立门控 | 不打印完整 AppKey、AuthKey、BLE MAC 和 Label SN | 仅用于受控身份联调，禁止随普通诊断自动开启 |
| `RESOURCE_MONITOR_HEAP_TRACE_RECORDS` | 0，独立门控 | 不启用 JL allocator trace | 仅在低水位根因仍不明确时显式设置 16～512 |

## 7. RDX 与 JL 原生边界结论

本轮符合 RDX 框架的核心约束：

- Protocol 只处理 Wire、幂等和结果映射，不直接访问 FAT；
- Record Engine 拥有 Session、Capture Generation、STOP cut 和音频生命周期；
- Local REQUIRED 与 Online OPTIONAL 的失败语义保持隔离；
- Artifact 只有在强 Commit 成功后才能进入文件列表；
- 音频回调和 BLE 回调不直接执行 FAT 阻塞操作；
- 不把 expected CRC、VFS close、Session 状态回执和 on-media verified 淵称为“提交成功”。

本轮符合 JL 原生修改边界：

- 没有修改 JL SD/MMC、FAT、allocator、JLStream 或私有 ATT 实现；
- 只在 RDX BR56 Adapter、应用/领域层、Protocol、测试、产品配置和诊断入口内收敛；
- 使用现有 JL 公开任务、ATT 事件和 FAT/VFS 接口；
- 保留 JL 私有断言作为真实故障保护，不关闭、不绕过。

独立 `rdx_storage` 任务目前仍然保留。它有约 4 KiB 栈、队列、TCB 和调度成本，但现有证据不支持为了删除任务而把 FAT 放回 Record Engine、`btstack` 或音频回调。其最终执行载体与锁外 I/O 收敛属于 7-2 的 O3-B。

## 8. 保留问题与后续入口
