# BR56 通用按键消息接管层与分发方案

## 1. 文档目的

本文在 `4-1.添加MIC按键.md` 已解决 MICKEY 硬件接法、PA4/ADC5 采样和六线耳机配置问题的基础上，继续说明如何在不修改杰理按键驱动和各模式按键表主体代码的前提下，通过消息注册机制接管按键消息，并统一完成后续分发。

本方案的设计目标是建立一个可复用的通用按键消息接管层，但当前实施范围严格限定为 MICKEY 产生的 MIC AD 按键：

- 注册监听杰理统一的 `MSG_FROM_KEY` 消息；
- 当前只在 PC 模式接管 `KEY_MIC_NUM0`、`KEY_MIC_NUM1` 和 `KEY_MIC_NUM2`；
- 非 MIC 按键一律返回原生流程，不改变现有行为；
- 接管后的 MIC 按键由独立分发器映射为业务消息；
- 后续增加 IO 按键时复用同一入口和分发框架，并按键值、应用模式和业务状态扩展所有权策略；
- 当前不修改 MICKEY ADC 扫描、Type-C 多击识别、PC 模式主循环和 USB HID 底层实现。

本文当前状态为“设计方案已明确、固件代码尚未实施”。文中的新增文件和代码均为下一步实现约定，不代表当前固件已经完成按键接管。

本方案的核心结论是：

```text
注册范围：监听全部 MSG_FROM_KEY
所有权范围：当前仅在 PC 模式拥有 KEY_MIC_NUM0～KEY_MIC_NUM2
消费规则：属于本层的 MIC 按键返回 1，阻止原生映射
透传规则：非 PC 模式或其他按键返回 0，继续走杰理原生按键表
```

这里的“通用”是指接管入口、消息解析、所有权判断和分发方式可以被不同按键类型复用，并不表示当前版本要吞掉所有按键消息。

## 2. 当前问题与实施边界

### 2.1 `4-1` 已经解决的是“能否识别”

MIC 按键的硬件和驱动链路为：

```text
PA0/MICLDO
    |
R3 1.5 kΩ
    |
MIC_BIAS/PA4
    |
按键电阻
    |
AVSS
```

PA4/ADC5 读取按键分压，MICKEY 驱动根据电压识别按键。六线模式使驱动以 AVSS 为 MIC 公共端，而不是错误地减去 DACLN 电压。

完成这些配置后，驱动能够产生 `KEY_MIC_NUM0`、`KEY_MIC_NUM1` 或 `KEY_MIC_NUM2`。这是物理检测层的问题，详见 `4-1.添加MIC按键.md`。

### 2.2 `4-2` 要解决的是“识别后由谁处理”

MICKEY 驱动识别出按键后，杰理默认流程会把按键值和动作送入当前模式的按键表，再映射为播放暂停、音量或 USB HID 消息。

如果 RDX 或产品业务以后需要根据录音状态、连接状态或其他场景重新定义按键含义，直接修改以下代码会造成较强耦合：

- MICKEY ADC 驱动；
- 公共 `key_event_handler()`；
- `pc_key_msg_table.c`；
- PC 模式消息主循环；
- USB HID 发送代码。

因此，本方案把接管点放在原始按键消息已经形成、但尚未进入模式按键表的位置。这样既复用杰理扫描和动作识别，又能在必要时停止原生处理。

### 2.3 当前只接管 MICKEY，不接管普通 ADKEY

虽然 MIC 线控按键也是通过 ADC 电压检测，但它使用的是专用 MICKEY 驱动：

```c
#define TCFG_ADKEY_ENABLE   0
#define TCFG_MICKEY_ENABLE  1
```

因此本文所说的“MIC AD 按键”在软件中的键值是：

```c
#define KEY_MIC_NUM0  80
#define KEY_MIC_NUM1  81
#define KEY_MIC_NUM2  82
```

不是 `KEY_AD_NUM0`、`KEY_AD_NUM1` 等普通 ADKEY 键值。

当前原理图只实现了直接短接到 AVSS 的 0 Ω 播放/暂停按键，实际硬件主要产生 `KEY_MIC_NUM0`。软件同时保留 `KEY_MIC_NUM1` 和 `KEY_MIC_NUM2` 的所有权位置，用于兼容将来增加 200 Ω、400 Ω 音量按键的三键线控版本。

## 3. 杰理现有按键消息链路

### 3.1 从 ADC 扫描到统一按键消息

当前 MIC 按键经过以下链路：

```text
PA4/ADC5 电压变化
        |
        v
MICKEY 驱动识别按键电阻
        |
        v
KEY_MIC_NUM0 / KEY_MIC_NUM1 / KEY_MIC_NUM2
        |
        v
key_event_handler()
        |
        +-- Type-C 多击转换
        +-- 组合键转换
        +-- 过滤 KEY_ACTION_NO_KEY
        |
        v
msg[0] = (key_value << 8) | key_action
        |
        v
app_send_message_from(MSG_FROM_KEY, ...)
        |
        v
app_core 消息队列
```

相关实现位于：

- `SDK/apps/common/device/key/mickey.c`：MICKEY ADC 检测；
- `SDK/apps/earphone/message/adapter/key.c`：多击转换和 `MSG_FROM_KEY` 投递；
- `SDK/apps/earphone/message/adapter/app_msg.c`：消息投递和模式按键表映射；
- `SDK/apps/earphone/app_main.c`：消息拦截器和模式按键表调用。

### 3.2 接管点位于多击转换之后

Type-C 产品的 `key_event_handler()` 会先执行 `multi_clicks_translate_typec()`，然后才投递 `MSG_FROM_KEY`。因此接管层收到的已经是杰理按键层整理后的动作，包括：

- `KEY_ACTION_DOWN`：物理按下；
- `KEY_ACTION_CLICK`：短按完成；
- `KEY_ACTION_LONG`：达到长按条件；
- `KEY_ACTION_HOLD`：持续按住；
- `KEY_ACTION_UP`：长按后抬起；
- `KEY_ACTION_DOUBLE_CLICK`：双击；
- `KEY_ACTION_TRIPLE_CLICK`：三击。

Windows 主机下，PP 键的连续短按会先由 Type-C 多击逻辑聚合，再生成单击、双击或三击动作。Android 和 iOS 分支不聚合 PP 多击。接管层不应再次实现一套多击计时，否则会与杰理现有状态机重复并产生时序冲突。

### 3.3 未接管时的原生处理

`app_get_message()` 取出 `MSG_FROM_KEY` 后，默认使用当前模式的 `key_remap_table` 进行映射。在本项目的 PC 模式中，对应文件是：

```text
SDK/apps/earphone/mode/pc/pc_key_msg_table.c
```

当前 MIC 按键的主要原生映射为：

| 原始按键 | 动作 | 原生应用消息 |
| --- | --- | --- |
| `KEY_MIC_NUM0` | `KEY_ACTION_DOWN` | `APP_MSG_PP_KEY_PRESS` |
| `KEY_MIC_NUM0` | `KEY_ACTION_CLICK` | `APP_MSG_PP_KEY_LIFT` |
| `KEY_MIC_NUM0` | `KEY_ACTION_UP` | `APP_MSG_PP_KEY_LIFT` |
| `KEY_MIC_NUM0` | `KEY_ACTION_DOUBLE_CLICK` | `APP_MSG_MUSIC_NEXT` |
| `KEY_MIC_NUM0` | `KEY_ACTION_TRIPLE_CLICK` | `APP_MSG_MUSIC_PREV` |
| `KEY_MIC_NUM1` | `KEY_ACTION_DOWN` | `APP_MSG_UP_KEY_PRESS` |
| `KEY_MIC_NUM1` | `KEY_ACTION_CLICK`、`KEY_ACTION_UP` | `APP_MSG_UP_KEY_LIFT` |
| `KEY_MIC_NUM2` | `KEY_ACTION_DOWN` | `APP_MSG_DOWN_KEY_PRESS` |
| `KEY_MIC_NUM2` | `KEY_ACTION_CLICK`、`KEY_ACTION_UP` | `APP_MSG_DOWN_KEY_LIFT` |

接管层一旦对某个 MIC 按键返回非零值，上述模式按键表就不会再处理该次消息。需要保留的原生行为必须由新的分发器显式发送，不能假设原生流程还会补发。

## 4. `APP_MSG_PROB_HANDLER` 接管机制

### 4.1 注册方式

杰理 SDK 提供 `APP_MSG_PROB_HANDLER` 注册机制。建议在 BR56 的 RDX 按键适配文件中注册：

```c
APP_MSG_PROB_HANDLER(rdx_key_msg_entry) = {
    .owner   = 0xff,
    .from    = MSG_FROM_KEY,
    .handler = rdx_key_msg_handler,
};
```

该注册项被放入 `.app_msg_prob_handler` 段。`app_get_message()` 在调用当前模式按键表之前遍历这些处理器：

```c
for_each_app_msg_prob_handler(handler) {
    if (handler->from == msg[0]) {
        int abandon = handler->handler(msg + 1);
        if (abandon) {
            return 0;
        }
    }
}
```

返回值语义为：

| 返回值 | 含义 | 后续行为 |
| ---: | --- | --- |
| `0` | 当前接管层不消费该消息 | 继续进入 RCSP 和当前模式按键表 |
| 非 `0` | 当前接管层已消费该消息 | `app_get_message()` 立即结束，原生按键映射不再执行 |

### 4.2 为什么选择这个位置

这个位置同时满足四个条件：

1. MICKEY 已经完成 ADC 电阻识别，不需要接触硬件采样算法。
2. Type-C 多击和基础动作已经转换完成，不需要重复实现按键时序。
3. 当前模式按键表尚未执行，可以阻止原生消息和自定义消息重复触发。
4. 所有标准按键最终都可进入 `MSG_FROM_KEY`，以后增加 IO 按键能够复用。

因此它是“复用杰理底层能力”和“接管产品业务语义”之间最合适的边界。

### 4.3 为什么不使用更早的按键检测回调

`key_event_handler()` 中也存在 `REGISTER_KEY_DET_CALLBACK` 回调，但其函数签名为：

```c
int (*cb_deal)(void *arg);
```

回调只收到注册时保存的静态 `arg`，没有直接收到当前 `struct key_event`。它适合执行与具体键值无关的前置检查，不适合按 `KEY_MIC_NUM0～2` 做精确的所有权判断和统一分发。

直接修改 `key_event_handler()` 给该回调增加事件参数，会改变公共 SDK 接口和所有现有注册者，不符合本次最小侵入目标。

## 5. 通用接管层的结构

### 5.1 建议模块划分

建议新增以下文件：

```text
SDK/apps/common/third_party_profile/rdx_protocol/
    rdx_key_adapter_br56.c
    rdx_key_adapter_br56.h
```

职责分为三层：

```text
消息适配层
    解析 MSG_FROM_KEY
    提取 key_value、key_action 和来源标志
              |
              v
所有权策略层
    根据键值、应用模式和业务状态判断是否归 RDX/产品层管理
    当前只在 PC 模式拥有 KEY_MIC_NUM0～KEY_MIC_NUM2
              |
              v
业务分发层
    将“物理键值 + 动作”映射为应用消息或 RDX 业务动作
```

第一阶段可以把三层放在同一个 `.c` 文件中，用静态函数保持边界。等业务数量明显增加后再拆分，不需要一开始引入复杂的动态注册系统。

### 5.2 所有权应按完整物理按键确定

不建议针对同一个物理按键按动作零散接管，例如只接管 `DOWN`，却把 `CLICK` 或 `UP` 放回原生流程。这样容易产生以下问题：

- 自定义层发送 Press，原生层发送 Lift，状态归属不清；
- 场景切换时出现重复动作；
- 某些动作落入原生模式表，另一些动作落入 RDX，难以测试；
- 后续修改按键表时无意改变已接管按键的行为。

建议规则为：

```text
如果当前模式和状态下的 key_value 属于接管层：
    所有 action 都由接管层消费
    有映射的 action 执行业务
    无映射的 action 明确丢弃或限频记录
    最终返回 1

如果当前模式和状态下的 key_value 不属于接管层：
    不做任何业务处理
    返回 0
```

这意味着当前 `KEY_MIC_NUM0～2` 的 `LONG`、`HOLD` 等动作即使暂时没有业务，也应由接管层消费并映射为 `APP_MSG_NULL`，而不是继续落回原生处理。

### 5.3 当前阶段的处理骨架

建议处理逻辑如下：

```c
static bool rdx_key_is_owned(u8 key_value)
{
    if (!app_in_mode(APP_MODE_PC)) {
        return false;
    }

    switch (key_value) {
    case KEY_MIC_NUM0:
    case KEY_MIC_NUM1:
    case KEY_MIC_NUM2:
        return true;

    default:
        return false;
    }
}

static int rdx_key_msg_handler(int *msg)
{
    u8 key_value = APP_MSG_KEY_VALUE(msg[0]);
    u8 key_action = APP_MSG_KEY_ACTION(msg[0]);

    if (!rdx_key_is_owned(key_value)) {
        return 0;
    }

    rdx_key_dispatch(key_value, key_action, msg[1]);
    return 1;
}
```

这里使用显式 `switch`，不使用 `key_value >= KEY_MIC_NUM0 && key_value <= KEY_MIC_NUM2` 的范围判断。即使当前三个键值连续，也应让每个被接管的物理按键在代码中显式可见。以后 SDK 增加 `KEY_MIC_NUM3` 或调整键值定义时，新按键不会因为落在某个数值范围内而被意外接管。

当前 RDX 产品是专用 Type-C PC 模式，接管目标也是 PC 模式中的 MICKEY，因此示例同时检查 `APP_MODE_PC`。在 PC 模式以外返回 0，让启动、Idle、升级或未来新增模式保留原生处理权。

其中：

- `msg[0]` 保存编码后的键值和动作；
- `APP_MSG_KEY_VALUE(msg[0])` 提取物理键值；
- `APP_MSG_KEY_ACTION(msg[0])` 提取动作；
- `msg[1]` 是按键消息来源标志，当前本机按键为 0，不能当作新的业务消息编号使用；
- `rdx_key_dispatch()` 只做轻量映射和投递，不应在 `app_core` 消息处理路径中执行耗时业务。

应优先使用上述 SDK 宏解析消息，不建议像部分旧参考代码那样把 `msg` 直接强制转换为 `struct key_event *`。当前消息载荷是由 `(key->value << 8) | key->event` 编码得到的整数，使用公共宏可以明确表达这一消息格式，减少对结构体字节布局的隐式依赖。

### 5.4 表驱动分发

第一阶段建议复用杰理 `KEY_ACTION_MAX` 维度，用静态表描述动作映射：

```c
struct rdx_key_route {
    u8 key_value;
    const int *action_map;
};
```

示意表如下：

```c
static const int rdx_mic_num0_map[KEY_ACTION_MAX] = {
    [KEY_ACTION_DOWN]         = APP_MSG_PP_KEY_PRESS,
    [KEY_ACTION_CLICK]        = APP_MSG_PP_KEY_LIFT,
    [KEY_ACTION_UP]           = APP_MSG_PP_KEY_LIFT,
    [KEY_ACTION_DOUBLE_CLICK] = APP_MSG_MUSIC_NEXT,
    [KEY_ACTION_TRIPLE_CLICK] = APP_MSG_MUSIC_PREV,
};

static const int rdx_mic_num1_map[KEY_ACTION_MAX] = {
    [KEY_ACTION_DOWN]  = APP_MSG_UP_KEY_PRESS,
    [KEY_ACTION_CLICK] = APP_MSG_UP_KEY_LIFT,
    [KEY_ACTION_UP]    = APP_MSG_UP_KEY_LIFT,
};

static const int rdx_mic_num2_map[KEY_ACTION_MAX] = {
    [KEY_ACTION_DOWN]  = APP_MSG_DOWN_KEY_PRESS,
    [KEY_ACTION_CLICK] = APP_MSG_DOWN_KEY_LIFT,
    [KEY_ACTION_UP]    = APP_MSG_DOWN_KEY_LIFT,
};
```

未指定的数组项默认为 `APP_MSG_NULL`。分发器必须先检查：

```c
key_action < KEY_ACTION_MAX
```

避免异常动作值导致越界访问。对于已经拥有的 MIC 按键，即使动作越界，也应记录错误并消费消息，防止异常消息重新进入原生流程。

如果映射结果不是 `APP_MSG_NULL`，可以通过以下方式重新投递为应用消息：

```c
app_send_message(app_msg, 0);
```

新消息来源为 `MSG_FROM_APP`，不会再次命中只监听 `MSG_FROM_KEY` 的接管器，因此不会递归。

需要注意：`app_send_message()` 会把新的 `MSG_FROM_APP` 投递到 `app_core` 队列尾部，原始 `MSG_FROM_KEY` 则在接管器返回 1 后立即结束。因此它实现的是业务结果上的重新分发，不是原消息在当前循环中的原地改写：

```text
原生路径：
    当前 MSG_FROM_KEY
        -> 当前循环内完成模式按键表映射
        -> 当前循环继续处理 MSG_FROM_APP 语义

接管路径：
    当前 MSG_FROM_KEY
        -> 接管层投递新的 MSG_FROM_APP
        -> 当前原始消息结束
        -> 后续 app_core 循环处理新消息
```

这种异步重投递会带来以下语义差异：

- 新应用消息至少延后一个队列处理轮次；
- 队列中已经存在的其他消息可能位于新应用消息之前；
- 如果模式在两个消息之间发生切换，新应用消息可能由切换后的模式读取；
- 队列压力异常时，重投递比原地映射多一次入队操作。

当前产品固定使用专用 Type-C PC 模式，按键频率很低，参考工程也采用相同的重新投递方式，因此该取舍可以接受。但文档和测试只能声明“功能语义等价”，不能声明“处理时序完全等价”。实现时应保持接管处理轻量，并在压力测试中确认 USB 音频、BLE 和按键消息同时活跃时没有明显延迟或丢失。

建议让 `rdx_key_dispatch()` 返回独立的分发结果，例如 `POSTED`、`IGNORED`、`INVALID_ACTION`，用于日志和诊断；无论分发结果如何，只要物理键值已经归本层所有，`rdx_key_msg_handler()` 都应返回 1。不能把“没有业务映射”错误转换为“返回原生流程”。

### 5.5 当前阶段先保持功能语义等价

为了将“接管机制是否正确”与“新业务策略是否正确”分开验证，第一阶段建议先按上表复现 PC 模式现有 MIC 按键语义：

```text
NUM0：播放/暂停 Press、Lift，双击下一曲，三击上一曲
NUM1：音量加 Press、Lift
NUM2：音量减 Press、Lift
```

确认接管前后 USB HID 的功能语义等价后，再把分发表中的目标消息逐项替换为 RDX 录音、标记或其他产品业务动作。接管后的应用消息经过异步重投递，处理轮次与原生原地映射不同，因此还要单独检查消息延迟、消息交错和模式切换边界。这样出现问题时能够明确区分：

- ADC/按键动作识别问题；
- 消息接管和消费问题；
- 自定义业务策略问题；
- USB HID Press/Lift 配对问题。

## 6. 最小侵入原则

### 6.1 不修改杰理公共按键驱动

本方案不修改：

```text
SDK/apps/common/device/key/mickey.c
SDK/apps/common/device/key/key_driver.c
SDK/apps/earphone/message/adapter/key.c
SDK/apps/earphone/message/adapter/app_msg.c
SDK/apps/earphone/app_main.c
```

这些文件继续负责硬件扫描、消抖、动作识别、消息队列和公共分发。

### 6.2 不删除原生模式按键表

`pc_key_msg_table.c` 应继续保留。原因是：

- RDX 关闭时仍需要原生行为；
- 不属于接管层的按键仍依赖原生表；
- 调试时可以关闭接管模块快速回退；
- 接管策略不能替代 SDK 的通用默认配置。

启用 RDX 接管时，由于拦截器先于模式按键表执行，已拥有的 MIC 按键不会重复触发原生表。

### 6.3 编译边界

建议把 `rdx_key_adapter_br56.c` 加入 `SDK/build/genFileList.c` 的现有 `#if TCFG_RDX_ENABLE` 源文件列表，并在模块内部按产品能力保护 MIC 路由：

```c
#if TCFG_RDX_ENABLE

#if TCFG_MICKEY_ENABLE
/* 当前 MICKEY ownership 和 route */
#endif

#endif
```

不要把整个通用适配文件永久限制为 `TCFG_MICKEY_ENABLE`，否则未来只启用 IOKEY 时无法复用同一入口。后续增加 IO 按键时，可以在同一模块中增加：

```c
#if TCFG_IOKEY_ENABLE
/* IOKEY ownership 和 route */
#endif
```

修改源文件选择宏后需要执行 `clean` 再全量构建。

### 6.4 当前原生 PC 按键表中的重复项

复审发现 `pc_mode_key_table` 当前包含以下四项：

```c
{ .key_value = KEY_MIC_NUM0, .remap_table = key_pc_mic_num0_msg_table },
{ .key_value = KEY_MIC_NUM1, .remap_table = key_pc_mic_num1_msg_table },
{ .key_value = KEY_MIC_NUM2, .remap_table = key_pc_mic_num2_msg_table },
{ .key_value = KEY_MIC_NUM2, .remap_table = key_pc_mic_num2_msg_table },
```

最后一项重复注册了 `KEY_MIC_NUM2`，从现有的 `key_pc_mic_num3_msg_table` 定义看，疑似原意是注册 `KEY_MIC_NUM3`。该问题的影响边界为：

- 当前 `KEY_MIC_NUM0～2` 的查表行为不受影响；
- 重复的第二个 NUM2 项永远不会提供新的映射能力；
- 如果以后启用 `KEY_MIC_NUM3`，原生回退路径目前找不到 NUM3 映射；
- 当前接管方案明确不拥有 NUM3，因此不能依靠接管层掩盖该原生表问题。

本阶段只接管 NUM0～2，不需要为了接管机制顺带修改杰理原生表。等产品明确启用第四个 MIC 按键时，应单独确认硬件电阻、MICKEY 键值和 NUM3 业务定义，再把重复项修正为 `KEY_MIC_NUM3` 并进行原生回退验证。

## 7. 与参考工程的关系

只读参考工程 `t2616cc-firmware` 已使用相同机制：

```c
APP_MSG_PROB_HANDLER(rdx_app_key_msg_entry) = {
    .owner   = 0xff,
    .from    = MSG_FROM_KEY,
    .handler = rdx_app_key_msg_handler,
};
```

参考实现先执行场景按键映射，再投递新的应用消息，最后无条件返回 `true`，从而全面中断杰理原生按键分发。这个总体思路可以复用，但实现不能直接复制，原因有三点：

1. 参考实现只接受 `key->value == 0`，而当前 BR56 的 MICKEY 键值为 80、81、82。
2. 参考处理器对所有按键最终都返回 `true`，即使没有产生有效业务消息也会阻止原生处理。
3. 当前 BR56 RDX 是重新拆分后的 MVP 模块，没有参考工程中的 `rdx_app.c` 和场景按键表，必须按当前模块边界重新实现。

如果直接复制参考处理器，当前 MIC 按键很可能因为 `key_value != 0` 而不生成业务消息，但处理器仍返回 `true`，最终表现为“ADC 已经识别，按键却完全没有功能”。

因此当前工程应采用：

```text
参考工程：全局监听 + 无条件消费
当前方案：全局监听 + 按键所有权判断 + MICKEY 选择性消费
```

## 8. Press/Lift 配对与状态安全

### 8.1 为什么必须成对分发

PC 模式的播放暂停、音量加和音量减使用 Press/Lift 两个应用消息控制 USB HID 状态：

```text
KEY_ACTION_DOWN  -> *_KEY_PRESS
CLICK 或 UP      -> *_KEY_LIFT
```

如果接管层只发送 Press 而漏掉 Lift，主机可能认为按键一直处于按下状态，造成连续音量变化、后续按键无效或 HID 状态异常。

### 8.2 单击与长按的释放动作不同

杰理动作模型中：

- 短按通常以 `KEY_ACTION_CLICK` 表示短按完成和释放；
- 长按释放使用 `KEY_ACTION_UP`；
- 两者都可能需要映射到同一个 `*_KEY_LIFT`。

因此不能只处理 `KEY_ACTION_UP`，也不能只处理 `KEY_ACTION_CLICK`。

### 8.3 场景切换时的保护

如果以后根据 RDX 状态动态切换按键用途，不应在同一次物理按键周期中改变所有权。例如按下时由 HID 消费，抬起时却切换为录音业务消费，会破坏 Press/Lift 配对。

推荐规则是：

```text
物理键按下时冻结本次按键周期的路由目标
直到 CLICK 或 UP 完成后再允许场景策略切换
```

当前第一阶段保持固定 MICKEY 所有权，不需要引入这类状态；该规则作为未来场景分发扩展约束保留。

## 9. 未来增加 IO 按键时如何复用

标准 IOKEY 也会经过 `key_event_handler()` 并投递 `MSG_FROM_KEY`，因此不需要再注册第二个全局接管器。但 `APP_MSG_PROB_HANDLER(MSG_FROM_KEY)` 是跨模式生效的全局入口，未来不能只把一个 IO 键值追加到 `switch` 后就无条件返回 1。

IO 电源键、模式键等按键在 Idle、开关机、升级或其他模式中可能具有杰理原生职责。通用策略必须把所有权判断扩展为：

```text
按键所有权 = key_value + 当前应用模式 + 当前业务状态
```

建议边界为：

```text
当前：
    PC 模式 + KEY_MIC_NUM0～2 -> RDX 接管
    非 PC 模式                    -> 原生透传
    其他键                        -> 原生透传

未来：
    PC 模式 + KEY_MIC_NUM0～2        -> RDX 接管
    PC 模式 + 指定 IO 键 + 指定场景 -> RDX 接管
    同一个 IO 键处于其他模式/场景    -> 原生透传
    未指定 IO 键                      -> 原生透传
    其他键                            -> 原生透传
```

示意代码为：

```c
static bool rdx_key_is_owned(u8 key_value)
{
    if (!app_in_mode(APP_MODE_PC)) {
        return false;
    }

    switch (key_value) {
    case KEY_MIC_NUM0:
    case KEY_MIC_NUM1:
    case KEY_MIC_NUM2:
        return true;

#if TCFG_IOKEY_ENABLE
    case KEY_POWER:
        return rdx_io_key_should_take_over(key_value,
                                           rdx_current_state());
#endif

    default:
        return false;
    }
}
```

上例中的 `rdx_io_key_should_take_over()` 只是未来策略接口示意。当前 MICKEY 阶段不需要实现它，也不应为了尚未存在的 IO 按键提前增加状态机。

IO 驱动最终上报的是板级配置指定的逻辑键值，可能是 `KEY_POWER`、`KEY_NEXT`、`KEY_PREV`，也可能是其他 SDK 键值，不能仅根据物理 IO 编号推断为 `KEY_IO_NUMx`。实现前必须以实际 `key_event_handler()` 日志和板级按键表为准。

如果 IO 按键的业务所有权会随场景动态变化，还必须与第 8.3 节配合：在 `KEY_ACTION_DOWN` 时冻结本次物理按键周期的路由目标，后续 CLICK、UP 等动作继续交给同一个目标，完成释放后才能重新评估模式和业务状态。

增加 IO 按键时需要完成：

1. 在杰理工具中配置 IOKEY 硬件、有效电平和消抖参数。
2. 确认该 IOKEY 最终产生的 `key_value`。
3. 明确该键在 PC、Idle、升级和其他可能模式中的原生职责。
4. 定义允许接管的模式和业务状态，而不是只匹配键值。
5. 把需要接管的键值加入显式所有权表。
6. 在分发表中配置 CLICK、LONG、HOLD、UP 等动作。
7. 如果所有权动态变化，实现一次物理按键周期内的路由冻结。
8. 验证未接管的 IOKEY 仍能进入当前模式原生按键表。
9. 特别验证电源键、模式键在 Idle、关机和升级边界没有被错误吞掉。

六线耳机配置只影响 MICKEY 的电气参考和 ADC 判断，不影响 `MSG_FROM_KEY` 接管机制，也不影响未来 IOKEY 的使用。

## 10. 多个消息拦截器的约束

`app_get_message()` 会按链接段顺序遍历所有匹配 `MSG_FROM_KEY` 的 `APP_MSG_PROB_HANDLER`。任意处理器返回非零后，后续处理器和模式按键表都不会再执行。

因此同一个产品中不应存在多个彼此不知道的全局按键所有者。否则行为会依赖链接顺序，容易出现：

- 某个协议先吞掉消息，RDX 收不到；
- RDX 先吞掉消息，其他协议收不到；
- 调整源文件列表后顺序变化，按键行为随构建变化。

当前 RDX 产品配置要求第三方协议独占选择，BR56 的当前 RDX 源文件中尚未注册另一个 `MSG_FROM_KEY` 拦截器。SDK 中其他未选中的第三方协议可能存在类似注册，后续调整第三方协议选择时仍应重新检查。

统一原则是：

```text
一个产品只保留一个 MSG_FROM_KEY 所有权入口
所有按键业务在该入口内部按策略分发
```

## 11. 线程上下文与耗时限制

`MSG_FROM_KEY` 最终在 `app_core` 的取消息路径中处理。拦截处理器应保持轻量，只执行：

- 解析键值和动作；
- 检查所有权；
- 查询简单状态；
- 查静态映射表；
- 投递应用消息或 RDX 内部事件；
- 输出必要的限频日志。

不应直接执行：

- Flash 擦写；
- 文件系统格式化；
- 长时间同步等待；
- 大量 BLE 数据发送；
- 录音 Pipeline 的阻塞式启停；
- 高频无节制串口打印。

较重的 RDX 业务应通过已有控制队列或应用消息异步执行，避免阻塞 PC 模式和 USB 音频相关消息。

## 12. 实施步骤

后续代码实现建议按以下顺序进行：

1. 新增 `rdx_key_adapter_br56.c/.h`。
2. 注册唯一的 `APP_MSG_PROB_HANDLER(MSG_FROM_KEY)`。
3. 实现 `APP_MSG_KEY_VALUE` 和 `APP_MSG_KEY_ACTION` 解析。
4. 使用显式枚举实现“PC 模式下只拥有 `KEY_MIC_NUM0～2`”的所有权判断，不使用连续数值范围判断。
5. 实现带 `KEY_ACTION_MAX` 越界保护的静态分发表。
6. 第一阶段按现有 PC MIC 按键表异步投递功能语义等价的应用消息。
7. 对属于 MICKEY 但没有业务映射的动作明确消费。
8. 对所有非 MIC 键值返回 0。
9. 让分发函数区分 `POSTED`、`IGNORED`、`INVALID_ACTION` 等诊断结果，但不改变已拥有按键最终返回 1 的规则。
10. 将新源文件加入 `SDK/build/genFileList.c` 的 RDX 条件源列表。
11. 执行 clean build，并在硬件上验证 Press/Lift、多击、异步重投递时序和非 MIC 按键透传。

本阶段不需要删除或修改 `pc_key_msg_table.c` 中的原生 MIC 表。接管器关闭或 RDX 未编译时，原生表仍是回退路径。

## 13. 编译与验证方案

### 13.1 编译检查

在 `SDK/` 目录执行：

```bat
.vscode\winmk.bat clean
.vscode\winmk.bat all
```

确认根目录 `output/` 产生新的固件文件。编译成功只能证明注册项、符号和源文件选择正确，不能证明按键和 USB HID 已通过硬件验证。

### 13.2 建议调试日志

接管层可以临时输出限频日志：

```text
[RDX][KEY] value=80 action=... owned=1 app_msg=...
[RDX][KEY] value=... action=... owned=0 passthrough=1
```

需要观察三个阶段：

1. 是否收到正确的 `key_value` 和 `key_action`。
2. 所有权判断是否只在 PC 模式命中 MICKEY。
3. 命中后是否只发送一次目标应用消息。

### 13.3 当前 MICKEY 测试矩阵

| 测试项 | 预期结果 |
| --- | --- |
| PP 按下 | 收到 `KEY_MIC_NUM0 + KEY_ACTION_DOWN`，接管层返回 1 |
| PP 短按释放 | 收到 `KEY_ACTION_CLICK`，产生一次 PP Lift |
| PP 长按释放 | 收到 `KEY_ACTION_UP`，产生一次 PP Lift |
| Windows 双击 | 产生 `KEY_ACTION_DOUBLE_CLICK`，只分发一次下一曲 |
| Windows 三击 | 产生 `KEY_ACTION_TRIPLE_CLICK`，只分发一次上一曲 |
| Android/iOS 单击 | 不依赖自定义多击计时，基本 Press/Lift 正常 |
| 200 Ω 音量加键（若硬件存在） | NUM1 Press/Lift 成对出现 |
| 400 Ω 音量减键（若硬件存在） | NUM2 Press/Lift 成对出现 |
| 非 MIC 按键 | `owned=0`，继续执行杰理原生行为 |
| 非 PC 模式收到 MICKEY | `owned=0`，不由 PC/RDX 接管层消费 |
| RDX 功能关闭的编译变体 | 不注册本接管层，MIC 按键完全回到原生模式表 |
| USB 音频与 BLE 同时繁忙 | 重投递后的应用消息延迟可接受，没有动作丢失或顺序异常 |
| 原始消息与重投递消息之间发生模式切换 | 不在错误模式执行 PC/RDX 按键业务 |

### 13.4 必须检查的异常情况

- MIC 按下只出现 DOWN、不出现 CLICK 或 UP；
- 同一次动作同时触发自定义消息和原生消息；
- 接管 MIC 后 USB HID 一直保持按下；
- 非 MIC 按键被错误吞掉；
- 未映射 MIC 动作返回 0 后意外触发原生业务；
- 多个 `MSG_FROM_KEY` 拦截器因链接顺序产生不同结果；
- 把异步重投递误认为原地映射，遗漏消息交错和模式切换测试；
- 未来 IO 按键只按键值接管，导致 Idle、关机或升级阶段的原生电源键被吞掉；
- 高频日志影响 USB 音频或按键时序。

## 14. 回退方案

本方案不删除杰理原生按键表，因此回退路径简单：

```text
不编译 rdx_key_adapter_br56.c
或不注册 rdx_key_msg_entry
        |
        v
MSG_FROM_KEY 重新直接进入 pc_mode_key_table
```

不能采用“接管器仍注册，但对 MIC 返回 1 且不分发”的方式作为关闭开关，因为这会把 MIC 按键静默吞掉。

## 16. 总结

本项目可以复用参考工程的 `APP_MSG_PROB_HANDLER(MSG_FROM_KEY)` 注册机制，在杰理完成 MICKEY ADC 检测、消抖和 Type-C 多击转换之后，在当前模式按键表执行之前接管原始按键消息。

为了实现最小侵入和后续复用，本方案采用“全局监听、选择性拥有”的原则：当前在 PC 模式下显式拥有 `KEY_MIC_NUM0～2`，非 PC 模式和所有其他按键返回 0 并继续走杰理原生流程；属于 MICKEY 的全部动作则由接管层统一消费和分发，避免同一个物理按键的 Press、Lift 和多击动作分裂到不同处理路径。

第一阶段先复现现有 PC 模式 MIC 按键语义，验证接管前后 USB HID 功能语义等价，并单独验证异步重投递造成的队列延迟、消息交错和模式切换边界。后续增加 IO 按键或 RDX 场景业务时，可以继续复用该注册入口，但所有权必须同时考虑键值、当前模式和业务状态；动态场景还要在一次物理按键周期内冻结路由目标。整个扩展过程仍不需要修改 MICKEY 驱动、公共按键处理器或 PC 模式主循环。
