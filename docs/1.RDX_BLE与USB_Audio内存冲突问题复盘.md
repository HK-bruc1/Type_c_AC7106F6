# AC710N RDX BLE 与 USB Audio 内存冲突问题复盘

> 文档版本：v1.1
> 编写日期：2026-08-07
> 适用工程：AC710N / BR56 Type-C 有线耳机
> 问题状态：内存冲突修复已通过实机功能冒烟验证；30 分钟稳定性、Mic 实录和 HID 回归待完成
> 关联文档：`docs/0.RDX_BLE_MVP0架构整改方案.md`

## 1. 摘要

RDX BLE MVP0 移植后，BLE 单独上电可以正常启动，USB Device 也可以完成初始枚举，但 USB Audio 创建 Mic、CVP 和播放数据流时发生：

```text
MMASSERT: vmalloc_ 147
```

设备随后复位并重新枚举。手机端因此失去稳定的 USB Audio 输出设备，播放声音回退到手机扬声器。上电提示音发生在崩溃之前，所以用户仍可能短暂听到提示音。

本问题不是 BLE 与 USB Audio 在架构上不能共存，也不是单独开启 BLE 就超过芯片总 RAM，而是二者共享内存资源时出现了运行时峰值冲突：

1. 原 USB Audio 配置同时启用 Speaker、Mic、HID 和 CVP，本身已有较高的动态内存需求；
2. RDX 启用 BLE 后，SDK 按偏通用的蓝牙配置预留了 Classic、双连接、多 GATT 实例、较大 ATT 缓冲等资源；
3. BLE 常驻后，CVP 和后续音频节点仍能继续初始化一段时间，但在 `convert_data_ioc_start` 申请下一块内存时，相关物理内存池或连续内存不足，最终触发断言。

解决方案是在不关闭 USB Speaker、Mic、HID、CVP、BLE 和 RDX 功能的前提下，按 MVP0 的真实需求收缩蓝牙控制器、BLE Host、GATT、ATT 和音频缓冲配置。

## 2. 项目背景

本项目是 Type-C 数字有线耳机，SDK 使用历史命名的 `PC` 应用模式承载 USB Device/UAC 功能，对端既可以是电脑，也可以是支持 USB 数字音频的手机。

当前产品需要同时保留：

- USB Audio Speaker 下行播放；
- USB Audio Mic 上行；
- CVP 通话处理；
- USB HID 播放、暂停和音量按键；
- RDX BLE 广播、连接、GATT 和 MVP0 AppKey 握手。

RDX MVP0 移植前，USB Audio 可以正常播放。移植后，BLE 广播和协议初始化可以运行，但插入 USB 或随 USB 上电后会反复复位，手机播放最终走手机扬声器。

## 3. 用户可见现象

### 3.1 正常部分

- 耳机能够上电；
- BLE 初始化和 RDX MVP0 可以启动；
- USB Audio、Speaker、Mic 和 HID 接口描述符能够建立；
- 上电提示音可以短暂听到；
- CVP 初始化日志能够运行到 `audio_cvp_v3_open succ`。

### 3.2 异常部分

- 音频链路创建后期出现 `MMASSERT: vmalloc_ 147`；
- 芯片进入复位、重新枚举、再次崩溃的循环；
- USB Audio 设备无法在手机侧稳定存在；
- 手机开始播放歌曲后，声音从手机扬声器输出，而不是耳机；
- 日志中看不到移植前正常播放时的完整成功序列。

### 3.3 为什么还能听到提示音

提示音播放发生在完整 USB Audio 数据流稳定运行之前。设备可以先完成基础启动、DAC 上电或提示音播放，然后才在 USB Mic、CVP、采样率转换和播放节点共同建立时达到内存峰值。

因此，“能听到提示音”只能证明前半段音频硬件和启动流程工作过，不能证明 USB Speaker 播放链路已经成功建立并持续运行。

这说明：

2. BLE Controller 在 USB Audio 数据流完全打开前已经常驻；
3. CVP 成功初始化后，物理内存只剩 35,072 B；
4. 后续音频数据转换节点继续申请内存时失败；
5. 断言后设备复位，手机侧无法保留稳定的 USB Audio 路由。

移植前日志中的对应流程能够继续完成：

移植前 CVP 打开后仍有 77,056 B 物理内存，后续 USB Speaker 数据流可以正常创建。

### 4.3 内存对比

| 检查点 | RDX 移植前 | RDX 移植后、优化前 | 差值 |
| --- | ---: | ---: | ---: |
| CVP 打开前 free heap | 218,504 B | 207,632 B | -10,872 B |
| CVP 打开前 physics memory | 149,504 B | 107,520 B | -41,984 B |
| CVP 打开后 free heap | 146,300 B | 135,428 B | -10,872 B |
| CVP 打开后 physics memory | 77,056 B | 35,072 B | -41,984 B |
| 最终结果 | USB 播放正常 | `vmalloc_ 147` | — |

两份日志中，CVP 自身造成的内存下降基本相同：

- free heap 下降约 72,204 B；
- physics memory 下降约 72,448 B。

这说明 CVP 并没有因为 RDX 移植而突然变大。真正的差异是 CVP 启动以前，BLE/RDX 已经使可用物理内存减少约 41,984 B，导致后续音频节点失去安全余量。

## 5. 为什么 free heap 还有 135 KB，vmalloc 仍然失败

日志里的 `Current free heap` 不能简单理解为所有模块都可以任意使用的剩余 RAM。SDK 内部存在普通堆、物理内存池、共享算法内存、音频帧或连续内存等不同分配路径。

发生断言前的两个关键数值是：

```text
Current free heap:    135428 bytes
physics memory size:   35072 bytes
```

后续音频节点可能要求从特定内存池取得一块满足大小、对齐或连续性要求的内存。即使普通 free heap 看起来还有余量，只要目标内存池或最大连续块不足，`vmalloc` 仍会失败。

因此排查此类问题时，不能只看链接 Map 或单个 free heap 数字，还必须观察运行时各内存池、最低水位、最大连续块和具体失败调用点。

## 6. 根因分析

### 6.1 直接原因

BLE/RDX 常驻占用与 USB Audio、Mic、CVP、DAC 和转换节点的动态占用叠加，超过运行时可用物理内存或连续内存峰值，`convert_data_ioc_start` 后续分配失败。

### 6.2 Classic Controller 被意外带入

产品配置已经关闭业务层 EDR，但原控制器配置在 BLE 启用时仍采用：

```c
BT_MODULE_CLASSIC | BT_MODULE_LE
```

问题日志中的以下输出验证了 Classic Controller 确实被初始化：

```text
bredr_bd_init
bredr_bd_init_success
```

这说明 `TCFG_USER_EDR_ENABLE=0` 并不自动保证底层 Controller 只编译或初始化 LE。应用层功能开关、Host 配置和 Controller 资源配置是不同层次，必须分别检查。

### 6.3 BLE Host 按通用场景过度预留

优化前配置包括：

- 2 个 HCI Connection；
- 2 个 GATT Server；
- 1 个 GATT Client；
- BLE Slave 多链路；
- 超出 MVP0 所需范围的 LE Role 和 Feature。

当前 RDX MVP0 实际只需要：

- 单 BLE 外设连接；
- 广播和 Slave/Peripheral 角色；
- 1 个 GATT Server；
- 0 个 GATT Client；
- SMP/Encryption；
- 不需要 Slave 多链路。

通用 SDK 默认值并不等于当前产品的最低资源合同。

### 6.4 ATT 缓冲按大 MTU 场景配置

RDX 接入复用了多协议 ATT RAM 配置：

```text
ATT_LOCAL_PAYLOAD_SIZE = 517 B
ATT_SEND_CBUF_SIZE     = 1024 B
```

当前 MVP0 的最大请求和响应均小于 64 B，不需要为 517 B payload 和高吞吐发送场景长期保留缓冲。

### 6.5 音频缓冲余量偏大

产品原配置的 DAC DMA 缓冲为 50 ms。较长缓冲有利于抗调度抖动，但会放大 USB Audio Speaker、Mic 和 DAC 链路同时建立时的内存峰值。

JL 配置工具给出的合法范围是 20～100 ms，因此本次选择 20 ms 作为当前产品的实机验证起点。该调整不能只修改生成的 `sdk_config.h`，必须同步修改 `src/音频配置.json`，否则后续使用 JL 工具重新生成配置时会被覆盖。

### 6.6 验收流程缺口

BLE 单独运行成功、USB Audio 单独运行成功，不能推出 BLE 与 USB Audio 可以共存。此前关注了 MVP0 的 BLE 广播、连接和 AppKey 握手，但没有先完成以下峰值组合：

```text
BLE/RDX 常驻
  + USB Speaker
  + USB Mic
  + CVP
  + HID
  + 提示音或音频数据流切换
```

这是本次问题在集成后期才暴露的流程原因。

## 7. 解决方案

### 7.1 设计原则

本次不通过关闭产品功能绕过问题，保留：

- USB Speaker；
- USB Mic；
- USB HID；
- CVP；
- BLE；
- RDX MVP0 和 AppKey 校验。

优化范围只针对当前已经明确的 MVP0 资源合同，不改变 GATT Profile、Handle、UUID、广播内容和握手报文。

### 7.2 Bluetooth Controller 收缩

文件：`SDK/apps/earphone/log_config/lib_btctrler_config.c`

RDX 开启且 EDR 关闭时：

1. Controller Module 从 `BT_MODULE_CLASSIC | BT_MODULE_LE` 改为 `BT_MODULE_LE`；
2. LE Role 限制为 `LE_SLAVE | LE_ADV`；
3. LE Feature 限制为 `LE_ENCRYPTION`；
4. 关闭 BLE Slave 多链路；
5. 纯 BLE RDX 配置开启 Single Carrier 模式。

预期新日志不再出现：

```text
bredr_bd_init
```

### 7.3 BLE Host 和 GATT 收缩

文件：`SDK/apps/earphone/log_config/lib_btstack_config.c`

RDX 配置调整为：

```text
HCI Connection: 1
GATT Server:    1
GATT Client:    0
SMP/Encryption: 保留
```

该配置满足当前手机作为 Central、耳机作为单 Peripheral/GATT Server 的 MVP0 使用方式。

### 7.4 ATT RAM 收缩

文件：`SDK/apps/common/third_party_profile/multi_protocol_main.c`

只在 RDX 为唯一第三方协议时使用：

```text
ATT_LOCAL_PAYLOAD_SIZE: 517 B -> 64 B
ATT_SEND_CBUF_SIZE:    1024 B -> 512 B
```

其他第三方协议和 LE Audio 仍使用原配置，避免本次优化影响未知协议。

### 7.5 音频缓冲收缩

同步修改：

- `SDK/apps/earphone/board/br56/sdk_config.h`
- `src/音频配置.json`

配置变化：

```text
TCFG_AUDIO_DAC_BUFFER_TIME_MS: 50 ms -> 20 ms
```

按当前 96 kHz、双声道、16 bit 路径核算，30 ms 的缩减对应单个同规格缓冲约 11,520 B。PC Mic cbuf 路径可明确减少约 11,520 B；DAC 相关运行时缓冲预计再释放相近空间，合计约 23 KB。实际释放量和分配时序必须以新固件实机日志为准。

## 8. 已取得的静态结果

对以下历史节点进行了隔离干净构建和 Map 对比：

| 节点 | 提交 |
| --- | --- |
| RDX 移植前 | `2cb113c` |
| MVP0 骨架 | `606c7dd` |
| 问题调查基线 | `cb17d71` |

对比结论：

- 全程只有一次 `setup_arch` 和一次 `App Start - PC`；
- 没有 `MMASSERT`、`vmalloc_ 147`、异常回调或看门狗复位；

### 10.4 BLE/RDX 共存结果

USB 播放期间完成了以下 BLE 流程：

1. RDX 广播成功启动；
2. 手机建立 BLE 连接；
3. TX CCC 成功开启；
4. 处理 Battery、Version、AppKey、RTC 和 OS Type 请求；
5. 日志出现 `[RDX] APP-ready`；
6. BLE 与 USB 播放重叠运行约 11 秒；
7. 对端以 `0x13` 主动断开后，RDX 成功恢复广播。

这证明单连接、单 GATT Server、0 GATT Client 和 512 B ATT Send cbuf 足以承载当前 MVP0 交互。

### 10.5 本次日志中的非阻塞提示

以下日志没有阻止本次 USB/RDX 功能成功，但需要保留边界认识：

1. `fail select SC!!!, need config_le_sm_sub_sc_enable = 1`
   - 当前 MVP0 AppKey 流程成功；
   - 该日志不能证明 LE Secure Connections 配对或 Bond 已通过；
   - 如果量产要求链路级加密绑定，需要单独开启并验证对应 SC 配置和内存增量。
2. `ATT MTU = 514`、`[RDX] mtu=517`
   - 当前实际收到的最大 MVP0 报文为 45 B，低于 64 B ATT 本地 payload 配置；
   - 当前功能验证安全，但未来增加 OTA、大包或文件传输时必须限制报文长度或重新扩大 ATT RAM；
   - 不能因为协商 MTU 较大，就假设 64 B 本地缓冲可以承载任意长写入。
3. `[LL-Adv]LL Adv already destroy`
   - 出现在 BLE 已成功建立连接、关闭广播时；
   - 后续 CCC、AppKey 和 APP-ready 均成功，不影响本次结论，可作为重复关闭广播的独立日志整洁性问题处理。
4. `[USB]setup_interface() ... fail`、`CVP_V3_CFG.bin open fail` 和 `eqCoeffs is NULL`
   - RDX 移植前正常固件中也存在同类输出；
   - 新固件随后成功打开 CVP 和 USB Speaker，因此它们不是本次 RAM 冲突的根因。

## 11. 实机验收标准

核心内存冲突已经通过首次实机日志验证。以下检查全部完成后，才能将状态进一步更新为“完整共存回归通过”。

### 11.1 启动和内存

- 不出现 `MMASSERT: vmalloc_ 147`；
- 不进入复位和 USB 重枚举循环；
- 不再出现 `bredr_bd_init`；
- 日志出现 `[RDX] MVP0 started`；
- CVP 打开后的 `physics memory size` 明显高于旧问题固件的 35,072 B；
- 记录运行期间的最低内存水位。

### 11.2 USB Audio

- 手机或电脑稳定识别 USB Audio、Mic 和 HID；
- 手机播放声音进入耳机，不回退到手机扬声器；
- 日志出现 `APP_MSG_PC_AUDIO_PLAY_OPEN`；
- 日志出现 `pc spk player callback : 8`；
- 左右声道播放正常；
- Mic 录音和通话上行正常；
- HID 播放、暂停、音量和静音正常；
- 最大音量提示、插拔和通话切换正常。

### 11.3 BLE/RDX

- 广播内容和间隔符合 MVP0 合同；
- 手机可以连接并发现预期 GATT；
- Identity、Notify、AppKey 和 PING/PONG 正常；
- APP 可以进入 APP-ready；
- 断开后恢复广播并能够重连；
- BLE 连接和数据交互期间，USB 不重枚举。

### 11.4 20 ms 音频缓冲专项

- 多款手机连续播放无断音；
- 无周期性 click、pop、底噪或爆音；
- CPU 高负载、BLE 连接或收发时无持续 underrun；
- 连续插拔、切歌、通话进入和退出时保持稳定；
- 建议执行 USB 播放、Mic 上行和 BLE 在线同时运行 30 分钟。

## 12. 日志快速判断方法

收到新日志后，可优先检索：

```powershell
rg -n "MMASSERT|vmalloc|physics memory|bredr_bd_init|RDX|APP_MSG_PC_AUDIO_PLAY_OPEN|pc spk player callback" <日志文件>
```

判断顺序：

1. 是否仍有断言或复位；
2. 是否仍初始化 Classic Controller；
3. CVP 前后各内存池还剩多少；
4. USB Speaker 是否真正收到播放打开事件；
5. BLE 广播、连接和 AppKey 是否仍正常；
6. 是否只有枚举成功，却没有实际音频数据流成功。

## 13. 容易误判的日志

问题固件和 RDX 移植前正常固件中都可能出现：

```text
[USB]setup_interface() ... fail
[CVP_USER]CVP_V3_CFG.bin open fail
[CVP-V3][JLSP] eqCoeffs is NULL
```

因为移植前固件在出现这些日志后仍能进入：

```text
APP_MSG_PC_AUDIO_PLAY_OPEN
pc spk player callback : 8
```

所以它们不是本次“RDX 移植后手机声音回退”的充分根因。排查时应使用正常基线做同位置对比，不能只看到一条 `<error>` 就认定为根因。

## 14. 风险和后续边界

### 14.1 ATT 64 B 边界

64 B 满足当前 MVP0 报文。未来增加大包命令、长特征值、OTA、文件或录音传输时，必须重新统计最大 ATT payload，不能直接沿用本配置。

### 14.2 单连接和单 Server 边界

当前配置只支持一个手机连接和一个 GATT Server。未来增加多连接、GATT Client 或其他 BLE 协议时，必须重新做 RAM 预算和共存压力测试。

### 14.3 20 ms 缓冲边界

20 ms 是工具允许的最小值，不代表所有手机和所有负载下天然稳定。如果实机出现 underrun、爆音或杂音，应根据最低内存水位在 20～50 ms 之间寻找平衡，而不是无依据继续降低。

### 14.4 如果优化后仍失败

按以下优先级继续定位：

1. 在 BLE 初始化、USB 枚举、Mic 打开、CVP 打开、Speaker 打开前后打印各内存池和最大连续块；
2. 确认失败的是普通 heap、physics memory、共享算法内存还是连续块；
3. 检查闭源库是否仍按未收缩的配置分配，确认最终链接配置符号生效；
4. 检查音频节点是否存在重复创建、失败重试后未释放或生命周期交叉；
5. 评估 Mic/CVP 是否可以按 USB Host 真正打开上行流时延迟初始化；
6. 最后才根据产品需求评估关闭或降级 DSP 功能，不应先用关闭 USB Mic、HID 或 BLE 掩盖根因。

## 15. 经验总结

### 15.1 功能开关不等于资源开关

关闭 `TCFG_USER_EDR_ENABLE` 不代表 Controller 一定没有 Classic。应用模式、Host、Controller、链接库和运行时配置必须逐层核对，日志中的初始化函数比宏名称更可信。

### 15.2 单功能通过不代表组合通过

BLE-only 和 USB-only 都通过，只能证明各自需求低于总资源；必须验证所有常驻模块与动态峰值同时出现的最坏组合。

### 15.3 RAM 预算必须看峰值和内存池

至少同时记录：

- 链接后的静态 `.data/.bss` 和 heap 起点；
- 普通 free heap 与最低水位；
- physics/shared/overlay 等专用池；
- 最大连续块；
- 各模块初始化前后的增量；
- 失败时具体申请大小和调用路径。

### 15.4 Map 只能解释一部分问题

Map 可以证明静态 RAM 和代码变化，但 Controller、Host、CVP 和音频库可能在运行时根据配置动态分配。最终结论必须由实机日志和压力测试确认。

### 15.5 配置源必须保持一致

JL 工具生成的 `sdk_config.h` 和 `src/*.json` 必须同步修改。只修改生成头文件会导致以后重新生成工程时优化丢失，引入难以复现的配置漂移。

### 15.6 建议后续集成准入项

任何新增常驻协议或 DSP 功能，在合入前至少记录：

1. 功能关闭和开启后的 Map 差异；
2. 空闲、连接、USB 播放、USB Mic/CVP 和组合峰值的内存水位；
3. 是否引入未使用的角色、连接数、Client、Codec 或 Controller Module；
4. 30 分钟组合压力测试结果；
5. 固件哈希、设备、手机型号、系统版本和复现步骤。

## 16. 最终结论

本次问题可以概括为：

> RDX MVP0 引入 BLE 后，通用蓝牙配置提前占用了约 42 KB 的关键运行时物理内存余量；USB Mic/CVP 再消耗约 72 KB，导致后续 USB Audio 转换或播放节点申请失败并复位。手机声音回退是 USB Audio 设备因复位而消失的结果，不是手机主动拒绝将音频路由到 BLE 与 USB 共存设备。

当前解决方案通过纯 LE、单连接、单 GATT Server、关闭多链路、收缩 ATT 和降低合法范围内的音频缓冲恢复内存余量，同时保留完整产品功能。干净编译和首次实机功能验证均已通过：CVP 后物理内存增加 29,696 B，不再出现 `vmalloc_ 147` 和复位循环，USB Speaker 播放期间 BLE/RDX 可以连接并进入 APP-ready。

因此，原“RDX 移植后 USB Audio 无法播放并回退手机扬声器”的核心问题已经解决。Mic 实录、HID、多机型、连续插拔和 30 分钟共存压力测试仍需完成，完成后再将项目状态更新为完整回归通过。
