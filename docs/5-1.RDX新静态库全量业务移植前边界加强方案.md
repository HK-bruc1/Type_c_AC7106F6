# AC710N RDX 新静态库全量业务移植前边界加强方案

> 文档状态：v1.0（静态核查已完成；P0 边界尚未闭环，暂不允许继续扩大 RDX 业务面）
> 编写日期：2026-08-21
> 目标工程：AC710N / BR56 Type-C 有线耳机
> 代码基线：`3611015`（增加 APP 密钥名单）、`6c5d9b7`（更换 `librdxApp.a`）
> 实机证据：`COM3_2026-08-21_13-24-12.log`
> 适用范围：新 RDX 静态库已经加入、但不整体接管 RDX 协议和业务的过渡阶段

## 1. 结论先行

### 1.1 对当前三个问题的直接回答

1. 当前固件中的 APP 接入鉴权业务仍然存在，没有被屏蔽。`*APP#appkey#` 仍会进入 `rdx_appkey_verify()`；成功 ACK 后才把 `app_ready` 置为 1，失败会回复失败并请求断开 BLE。
2. `librdxApp.a` 确实参与了链接，但没有整体进入固件。当前 Map 只抽取了 `rdx_encryption.c.o`，只使用 `rdx_appkey_decryption_handle()`；`rdx_protocol.c.o`、`rdx_queue.c.o`、`rdx_uxfile.c.o`、`xxpUart.c.o` 均未进入当前固件。
3. 当前不是“APP 发送明文 AppKey，设备只查本地白名单”。APP 发送的是 32 B 二进制 Payload：前 16 B 在当前调用中作为 AES-CBC IV/解密参数，后 16 B 是 ciphertext。静态库负责把后 16 B 解密成 16 B ASCII AppKey，本地代码再用运行时策略决定放行或拒绝。后 16 B 不是另一段需要独立校验的“后半部分密钥”。

因此，当前真实架构是：

```text
目标 APP
  │  *APP#appkey# + 32 B Payload + #
  ▼
本地 rdx_mvp0_protocol：帧长、尾标记、会话条件
  ▼
本地 rdx_appkey_verifier：Provider Adapter
  ▼
librdxApp.a(rdx_encryption.c.o)：仅做 16 B 解密
  ▼
本地运行时 AppKey 策略：决定是否授权
  ▼
成功 ACK 后 app_ready=1 / 失败 ACK、撤权并断链
```

这里的“鉴权”专指 APP 对设备业务的接入鉴权，不等于 Secure Boot、固件镜像签名或 OTA 升级包真实性校验。当前核查不能据此宣称具备固件镜像级安全鉴权。

### 1.2 换库对当前功能路径的判断

就当前唯一被引用的加密路径而言，换库导致功能变化的概率较低：新旧 `rdx_encryption.c.o` 去除编译绝对路径和调试元数据后，逆向得到的 LLVM IR 一致；当前固件也没有引用新库的其他业务符号。这与“换库后现有功能似乎不受影响”的实机现象一致。

但这不表示整个新库已经完成兼容验证。archive 内四个未抽取对象只是当前休眠；未来任何新增未解析符号都可能把一个完整对象拉入固件，从而带入第二套协议状态、任务、队列、文件、UART 或资源生命周期。`--gc-sections` 和 LTO 不能替代架构边界审查。

### 1.3 当前不能直接继续全量业务移植

当前至少存在以下 P0 阻断项：

- 运行时白名单无条件接受 26 个 AppKey，明显宽于新库完整方案原有的产品选择策略；
- `CUSTOM_TEST` 的 BLE MAC 限制在本地移植中丢失，当前会无条件放行；
- 串口日志只证明兼容 Key `7C0BAF778B727175` 可用，尚未证明正式 IKKO Key 实机通过；
- `rtc` 命令在鉴权前即可写硬件 RTC 和 VM，属于未认证状态修改；
- 当前日志打印完整 32 B 线上 Payload 和解密后的明文 AppKey；线上 Payload 在当前无挑战值的流程中还可能被重放；
- 尚未把“只能抽取 `rdx_encryption.c.o`”变成每次构建必须通过的 Map 准入检查；
- 新库条件下尚未重新完成 RDX OFF 的零源码、零 archive、零符号和零运行行为验证。

在这些项目闭环前，只允许做边界修复、验证和文档工作，不新增 RDX 业务命令。

## 3. 统一术语与边界模型

| 术语 | 本文定义 | 不得混淆为 |
| --- | --- | --- |
| APP 接入鉴权 | APP 提交加密 Payload，设备解密出 AppKey 并依据本地策略建立 `APP-ready` 会话 | 固件签名、Secure Boot、OTA 包签名 |
| AppKey 字典 | 逆向记录新库所认识的品牌名与 16 B ASCII Key 映射 | 当前产品的运行时授权名单 |
| 产品 Key | 当前 IKKO 产品正式允许使用的 AppKey | 所有品牌的公共 Key |
| 兼容 Key | 为旧 APP/过渡协议保留的通用 Key `7C0BAF778B727175` | 永久默认的正式产品 Key |
| 受限测试 Key | 仅在测试构建并满足 BLE MAC 条件时使用的 `CUSTOM_TEST` | 量产白名单项 |
| 加密 Provider | 当前仅由 `rdx_encryption.c.o` 提供的解密能力 | RDX 协议解析器或最终授权决策者 |
| Adapter | `rdx_appkey_verifier.c` 对 Provider 的唯一封装层 | 任意业务都可直接调用库符号 |
| `APP-ready` | 当前 BLE 会话完成 APP 接入鉴权后的临时权限状态 | 持久绑定、BLE Bonding 或全局设备可信状态 |
| 业务所有权 | 某项状态、资源和生命周期只有一套实现负责 | 本地实现与静态库实现同时运行 |
| RDX OFF | 最终 `TCFG_RDX_ENABLE=0` 后无 RDX 源码、archive、符号、VM、任务、定时器和运行行为 | 仅关闭广播或 UI |

### 4.3 数值正确不等于授权策略正确

新库未进入当前固件的完整协议对象中，逆向得到的原始判定模型是：

1. 接受当前 `app_select` 对应的一个产品 Key；
2. 接受兼容 Key `7C0BAF778B727175`；
3. `CUSTOM_TEST` 只有在 BLE MAC 位于测试名单时才接受。

当前本地实现则把 24 个具名 Key和两个额外兼容项全部加入 `RDX_COMPAT_APP_KEY_LIST`，共 26 项无条件接受。结果是：

- 任一其他品牌 APP 的有效 Payload 都可能进入当前 IKKO 设备的 `APP-ready`；
- 已从新库删除的旧 ZENCHORD Key 仍可进入；
- `CUSTOM_TEST` 绕过了原本的 BLE MAC 门控；
- 字典和授权策略虽然写在两个宏层次中，实际上仍被配置成同一个全集。

因此，AppKey 逆向数值核查结论是“正确”，运行时授权边界结论是“当前不合格”。

## 5. 必须冻结的架构决策

### 5.1 决策 D1：静态库仅作为加密 Provider

在明确批准架构切换前，继续保持：

> 本地 RDX 协议与业务实现 + 静态库仅作为加密 Provider。

当前允许的库边界只有：

```text
允许的 archive member：rdx_encryption.c.o
允许的业务侧调用者：rdx_appkey_verifier.c
允许的库符号：rdx_appkey_decryption_handle
```

任何新增库符号或第二个 archive member 被抽取，都视为架构边界变化，必须停止合入并重新审查。不得用“链接器最后会裁剪未使用代码”作为放行理由。

### 5.2 决策 D2：禁止本地业务与原库业务双栈运行

| archive member | 可能承担的原库职责 | 当前所有者 | 决策 |
| --- | --- | --- | --- |
| `rdx_encryption.c.o` | AppKey 解密 | `rdx_appkey_verifier.c` Adapter | 唯一允许抽取 |
| `rdx_protocol.c.o` | 协议解析、AppKey 策略、业务分发 | 本地 `rdx_mvp0_protocol.c` | 禁止抽取 |
| `rdx_queue.c.o` | 队列、任务或发送调度 | 本地 BLE transport / record engine | 禁止抽取 |
| `rdx_uxfile.c.o` | 文件或存储业务 | 当前未整体移植 | 禁止抽取 |
| `xxpUart.c.o` | UART 通道 | JL 平台及产品串口边界 | 禁止抽取 |

如果未来决定让原库接管完整业务，必须单独形成架构切换评审，一次性明确协议入口、BLE 回调、任务、定时器、VM、文件、UART、音频和错误恢复的唯一所有者；不能通过“先多调用几个库函数”渐进形成双栈。

### 5.3 决策 D3：字典与授权策略彻底分离

AppKey 字典可以保留用于审计和兼容关系记录，但运行时策略只允许显式列出当前产品所需项。建议目标策略为：

| Key 类型 | 量产策略 | 开发策略 |
| --- | --- | --- |
| IKKO `72231C5642E6E60B` | 必须允许 | 允许 |
| 兼容 `7C0BAF778B727175` | 只有书面兼容结论、适用 APP 版本和退出期限齐全时才临时允许 | 可临时允许并记录非敏感命中原因 |
| `CUSTOM_TEST` | 必须拒绝 | 仅测试构建且 BLE MAC 名单通过时允许 |
| SAI、旧 ZENCHORD、其他品牌 Key | 必须拒绝 | 专项兼容测试固件可临时启用，不得进入正式配置 |
| 随机、损坏或未知 Key | 拒绝并撤权断链 | 同量产 |

不得再通过“把所有字典项加入数组”代替产品授权决策。

## 6. 加密 Provider 与 ABI 边界加强

### 6.1 唯一 Adapter

- 只有 `rdx_appkey_verifier.c` 可以声明和调用 `rdx_appkey_decryption_handle()`；
- 协议、录音、RTC、设备管理等模块不得直接包含静态库私有声明；
- Adapter 固定输入为恰好 32 B，前后各 16 B；拒绝空指针、短包、长包和别名错误；
- Provider 没有可用的返回状态，最终成功条件必须是解密结果与授权策略严格匹配，不能以“函数已返回”视为成功；
- 调用应串行发生在协议任务上下文，禁止在 ISR 或多个任务中并发调用，除非供应方明确给出可重入保证；
- IV、ciphertext、明文临时缓冲在使用后清零；量产接口不应为日志额外导出明文；
- 比较 16 B Key 时使用固定长度、尽量恒定时间的比较，不使用未限定长度的 C 字符串操作。

### 6.2 换库必须执行的 ABI 检查

每次替换同名库都必须核对：

1. 文件大小、SHA-256 和交付来源；
2. archive member 集合是否变化；
3. `rdx_encryption.c.o` 的已定义/未定义符号是否变化；
4. `rdx_appkey_decryption_handle()` 的参数数量、数据宽度、调用约定和副作用是否变化；
5. 固定输入向量的解密输出是否一致；
6. 最终 Map 是否仍只抽取一个允许对象；
7. ELF 中是否出现新的 RDX 库符号、初始化入口或隐藏资源所有者。

新旧加密对象 IR 一致只能作为本次换库证据，不能替代以后每个新版本的 ABI 和目标机测试。

### 6.3 已知答案测试

在继续业务移植前，应冻结至少以下测试向量；测试报告可引用本文，但不得把真实密钥或可重放 Payload 留在量产串口日志中：

- IKKO 正式 APP 生成的有效 32 B Payload，期望解密为 `72231C5642E6E60B` 并成功；
- 当前兼容 APP 生成的有效 Payload，期望解密为 `7C0BAF778B727175`，是否成功由兼容开关决定；
- 其他品牌有效 Payload，能够正确解密但最终必须拒绝；
- 单 bit 损坏、全零、随机、31 B、33 B、缺尾 `#` 和多余尾字节，全部拒绝；
- 受限测试 Key 在非名单 MAC 上拒绝，在专用测试构建和名单 MAC 上才允许。

## 7. 会话鉴权与命令门控加强

### 7.1 建立集中式状态机

当前 `app_ready` 检查分散在各 handler 内，新业务很容易漏加。应把命令分类和鉴权检查放在统一 dispatch 入口，形成最少状态：

```text
DISCONNECTED
  └─ BLE connected ─> LINKED
       └─ CCC ready ─> HANDSHAKE_READY
            └─ AppKey 验证且成功 ACK ─> AUTHENTICATED(app_ready=1)
                 └─ CCC off / disconnect / 鉴权失败 / 会话重置
                    ─> 立即 app_ready=0，再做资源清理
```

`identity_read` 是否作为强制转换条件，应以目标 APP Golden Trace 冻结；未冻结前不得悄悄改变线上顺序。无论是否强制 Identity，至少必须满足有效连接和 CCC ready 才能进入 `AUTHENTICATED`。

### 7.2 认证前命令白名单

默认规则是“未列入认证前白名单的命令一律要求 `app_ready=1`”。建议分类如下：

| 命令 | 认证前策略 | 理由 |
| --- | --- | --- |
| `PING` / `PONG` | 允许 | 无状态链路探测 |
| `battery` | 可允许，只读、严格长度 | APP 发现/握手兼容 |
| `version` | 可允许，只读、严格长度 | APP 兼容性判断 |
| `appkey` | 允许一次或受尝试次数限制 | 建立鉴权状态 |
| `ostype` | 只有 Golden Trace 确认必须前置时才允许；必须无副作用 | 当前无集中门控 |
| `rtc` | 禁止 | 当前会写硬件 RTC 和 VM，属于状态修改 |
| 录音、标记、名称修改、增益、绑定、解绑、恢复默认 | 禁止 | 控制资源或修改状态 |
| `authsn`、`cofftime` 等管理查询 | 默认禁止 | 可能泄露产品身份或策略信息 |
| 未知命令 | 拒绝 | 默认拒绝原则 |

当前 `record`、`recmark`、名称、增益、绑定、解绑、恢复默认、`authsn`、`cofftime` 等 handler 内已有不同形式的检查；`rtc` 和 `ostype` 在 dispatch 路径没有集中式 `app_ready` 检查。尤其 `rtc` 会调用 `rdx_rtc_set_timestamp()` 写硬件 RTC 并回写 VM，必须作为 P0 修复。

### 7.3 失败路径必须先撤权再断链

- 新连接、断开、CCC off、鉴权失败和协议重置都必须同步清零 `app_ready`；
- 不能只依赖异步断链回调稍后清零，否则失败 ACK 与真正断链之间仍有短暂授权窗口；
- 撤权后应取消待执行的业务动作、停止属于该会话的录音/发送并丢弃队列数据；
- AppKey 成功但 ACK 发送失败时不得置位 `app_ready`，当前这一点已做到；
- 已认证会话再次提交 AppKey 时，应明确选择“幂等验证”或“拒绝重认证”，不能让失败重认证保留旧权限；
- 单连接内限制失败次数；跨连接冷却只能采用不会造成永久拒绝服务的策略。

### 7.4 重放风险边界

当前设备侧代码未见由设备发出的 nonce/challenge，也未见 Payload 重放缓存。应按“截获的有效 32 B Payload 可能再次使用”处理，不能把当前 AppKey 流程表述为强抗重放认证。

在 APP 协议不能立即升级时：

- 量产日志不得输出完整 Payload；
- 高副作用业务必须严格依赖会话门控、BLE 链路安全能力和产品风险评估；
- OTA、格式化、量产身份修改等高权限业务不得仅凭现有 AppKey 流程直接开放；
- 是否升级为设备 challenge + APP response，应作为全量高权限业务移植前的产品安全决策。

### 8.2 每新增一项业务前必须回答

1. 该业务的协议解析、状态、VM、任务、定时器、队列和硬件资源分别由谁唯一拥有？
2. 断链、CCC off、USB 模式切换、异常 ACK、超时和复位时由谁清理？
3. 是否需要新增静态库符号？若需要，默认停止；先做架构切换评审。
4. 是否会抽取新的 archive member？若会，默认停止。
5. 是否与 USB Speaker、USB Mic/CVP、BLE Notify、RTC 或现有录音 Engine 争用 RAM、任务、时钟、ADC、Flash 或带宽？
6. Ability、源码选择、运行时 handler 和目标 APP 页面是否同时真实可用？
7. RDX OFF 后是否能够彻底消失？

没有明确答案的业务不得进入实现阶段。

## 9. Ability、源码选择与运行行为一致性

- `RDX_COMPAT_DEVICE_ABILITY` 是产品能力的单一声明入口；内部 `RDX_CFG_*` 只能由它派生；
- Ability 位只能在对应 handler、资源生命周期、异常路径和实机测试都完成后打开；
- `SDK/build/genFileList.c` 中的源码和 `librdxApp.a` 必须继续受最终 `TCFG_RDX_ENABLE` 约束；
- 单项业务源码要与对应 `RDX_CFG_*` 一致，禁止 Ability 关闭但任务/VM 常驻；
- 静态库包含某项实现，不代表当前产品具有该能力；
- 不得为打开 APP 页面长期发布虚假 Ability；开发占位值必须在量产准入前收敛；
- 不得在 USB、UAC、音频、PC 模式等 JL 核心模块中加入反向的 RDX 业务判断。

## 10. 资源与生命周期边界

### 10.1 VM 与 Flash

- 每个 RDX VM ID 必须有唯一所有者、版本、长度、默认值、读写校验和恢复策略；
- 恢复默认只清理明确属于 RDX 的可变状态，不清 BLE MAC、AuthKey、Label SN、音频校准或 USB 配置；
- 测试 VM 写失败、读短、版本升级、掉电中断和重复命令；
- 未认证命令不得写 RTC、名称、增益、绑定状态或其他 VM；
- 原库 `rdx_uxfile.c.o` 不得因文件业务尝试而被隐式抽取。

### 10.2 任务、队列和定时器

- 禁止本地队列与 `rdx_queue.c.o` 同时拥有同一路发送或录音数据；
- 任务、定时器、cbuf 和固定队列必须有创建、重复启动、停止、断链清理和异常回收闭环；
- 所有延迟断链、重试和 pending action 都要在新连接或 CCC off 时取消；
- 不在 BLE 回调、ISR 或持锁路径中执行可能阻塞的解密、Flash 或音频操作；
- 对每项常驻内存记录增量，并在 USB 双向音频最紧张场景复核余量。

### 10.3 BLE、USB 与音频

- BLE Notify 只由本地 transport 发送，统一处理 MTU、CCC、busy、重试和断链；
- 录音只能由本地 Record Engine 管理，协议 handler 不直接拥有音频 Pipeline；
- USB Speaker、USB Mic/CVP 与 RDX 录音的并发策略必须显式，不以“短时没有复位”代替资源合同；
- 新业务不得修改 JL 核心音频生命周期来迁就 RDX；
- 压力测试必须记录最低堆、队列峰值、Notify 失败、音频 underrun/overflow 和复位原因。

## 11. 日志、密钥与量产安全

当前 `rdx_mvp0_protocol.c` 会打印：

- 完整 32 B `wire_payload`；
- 解密后的明文 AppKey；
- 明文 AppKey 的十六进制形式。

量产前必须改为只记录非敏感结果，例如命令、长度、状态、失败原因和不可逆版本标识。不得打印：

- AppKey 明文；
- 完整 AppKey Payload；
- AuthKey、Label SN、量产认证码原文；
- 可用于重放或恢复凭据的中间数据。

开发日志也应由显式调试门控保护，默认关闭；调试固件不得作为量产候选。因当前 Payload 缺少已证明的防重放机制，完整 Payload应按凭据处理，而不是普通报文。

### 14.1 鉴权矩阵

| 用例 | 期望 |
| --- | --- |
| IKKO Key + 合法帧 + CCC ready | 成功 ACK，随后 `app_ready=1` |

- 未知命令、相似前缀、嵌入 NUL、超长帧和分包边界不得误匹配。

### 14.3 资源与共存矩阵

- USB Speaker 播放期间反复连接、正确鉴权、错误鉴权和断链；
- USB Mic/CVP 期间执行相同流程；

- RTC 设置、冷启动恢复、VM 写失败和非法时间戳；

## 16. 停止条件与回退

出现以下任一情况，立即停止业务扩展并回退到最近已验证固件，不继续叠加修复：

- `librdxApp.a` 哈希与本文不一致但没有新版本审计；
- Map 出现第二个 archive member 或新增库符号；
- 原库开始注册协议入口、BLE 回调、任务、定时器、VM、文件或 UART；
- 非 IKKO/非批准兼容 Key 可以进入 `app_ready`；
- 认证前命令能够修改 RTC、名称、增益、绑定、录音或持久状态；
- 鉴权失败后业务仍可在断链窗口执行；
- 量产日志仍输出 AppKey、完整 Payload 或量产身份；
- RDX OFF 仍残留源码、archive、符号或运行行为；
- Ability 宣告了未实现或未验证的业务；
- USB Audio、BLE、录音或 RTC 出现不可解释的内存下降、资源残留或复位。

回退时优先回退本次业务增量；若确认是换库引入，则把 `librdxApp.a` 单独回退到 `6c5d9b7` 的父版本并 clean + all。不得同时回退用户的产品配置、工具生成资源或无关业务变更，以免扩大定位变量。
