## 1. 目的与结论

当前 RDX 录音链路是：

~~~text
PA3 ADC mono -> AGC -> Opus Encoder -> AI_TX
    -> Record Engine -> Online Destination -> V23 BLE Notify -> APP
~~~

下一阶段需要在同一录音 Session 中增加本地保存：

~~~text
RecordFrame
    -> Composite Destination
       -> Online Destination (OPTIONAL mirror)
       -> Local Destination (REQUIRED artifact)
                         -> Local Storage Service
                            -> SD0/FAT Storage Backend
~~~

推荐决议：

1. Record Engine 继续拥有 Session、Capture Generation、音频资源和帧时间轴，不拥有文件系统。
2. 新增 Application 层 Recording Coordinator，统一编排 START/STOP/ABORT、租约、metadata 快照、Destination 生命周期和 Artifact completion；Protocol 只负责 Wire 映射。
3. Local Storage Service 串行拥有新合同下的 FAT 文件句柄、Artifact 状态、索引和恢复；若选择 Legacy UXFILE，则由 `rdx_uxfile.c.o` 的既有 worker 拥有 UXFILE/DAT/FAT，RDX 只能通过 Adapter 访问，Protocol 仍不直接访问 FAT 或 UXFILE。
4. 使用 Composite Destination 复用当前 Engine 的单 Destination 接口。Composite 内部扇出 Online 和 Local，不把 Engine 改成一组 SDK 相关回调。
5. 本产品第一版底层介质固定为 sd0 + FAT；文件业务后端在 JL FAT Native 与 Legacy UXFILE Adapter 中二选一。JL 平台负责设备初始化和挂载；BR56 SDK Adapter 只复用已经建立的 mount 和 VFS/FAT 能力，向 RDX 提供窄 Storage Port，不建立第二套 SD 协议、设备管理或挂载抽象。
6. 本地 Artifact 是 REQUIRED，在线镜像是 OPTIONAL。v1 中 Local 接纳或写入不可恢复失败即终止该 Session 并将 Artifact 标为 FAILED/QUARANTINED，不降级为“仅在线”并谎报本地保存成功。
7. 正常 STOP 与强制 ABORT 必须分流。`SESSION_STOPPED` 只表示采集资源已释放；模式 A 只有 `ARTIFACT_COMMITTED`、模式 B 只有经 APP 合同定义的 `LEGACY_FILE_COMMITTED` 才表示文件进入正常列表。
8. 先完成平台 bring-up、Service、Destination、提交恢复和 APP 文件业务，再开启 RDX_ABILITY_LOCAL_STORAGE。sd0 能挂载不等于该 Ability 已实现。

实施原则是“原生能力优先、必要改动最少、RDX 业务增量接入”：平台层只修正当前 Type-C 产品启用 JL 原生链路所缺失的配置派生和源码选择；已经由 JL SDK 正确提供的 SD pdata、probe、mount、FAT 和 dev_manager 生命周期不复制、不改写。

本文继承 3-3、3-4、3-8 和 6 号文档已经冻结的录音、时间轴、BLE 发送、资源租约和跨 SDK 边界；它取代重构前 4-1 文档中直接以旧 rdx_record.c/rdx_uxfile 为中心的物理组织方式。

## 2. 范围与非目标

### 2.1 本次设计范围

- 既有在线会议录音帧同时落盘并镜像到 APP；
- BR56 SD NAND 通过 sd0 设备和 FAT 文件系统提供本地后端；
- Storage Readiness、容量、空间、写入、提交、恢复和错误分类；
- 文件列表、删除、格式化、上传等 Local Storage Wire 业务的接入边界；
- BLE 断连、USB 抢占、关机、OTA 和存储失败的故障域；
- 编译期 Ability、Capability、Build Gate 和目标板验收矩阵。

### 2.2 不在第一轮实现范围

- 通话录音、本地播放、离线按键录音和 TWS 主从同步；
- 通过 BLE 命令在录音中切换 SD、SPI NAND、eMMC 等后端；
- 将 SD0 暴露为 USB Mass Storage 并与固件同时访问 FAT；
- 由 Engine/Protocol 直接调用参考工程的 rdx_uxfile 接口，或在两个后端模式中同时启用 UXFILE.DAT 与新 RDX 索引；Legacy UXFILE 只能经窄 Adapter 接入；
- 以全盘 fscan() 作为每次启动的默认索引恢复路径；
- 用主机编译替代断电、FAT 持久化或 SD 写入性能的目标板验证。

## 3. 统一语言

### 3.1 录音概念

**录音会话（Session）**：一次从成功 START 到用户停止或系统终止的逻辑录音。Pause/Resume 不创建新 Session；同一运行时 Session 只拥有一个稳定的 session_id，但该 ID 不保证跨重启稳定。

**采集周期（Capture Generation）**：Session 内一次连续占用音频资源并运行 Pipeline 的区间。Pause/Resume 会结束并重新开始采集周期，递增 capture_generation，但不改变 Session。

**录音帧（RecordFrame）**：Engine 为输出目的地提供的、带 Session 标识和有效时间轴的不可变编码帧。帧 payload 是借用数据，目的地需要异步保存时必须复制。

**输出目的地（Destination）**：消费 RecordFrame 并完成一种交付目标的组件。在线目的地负责 BLE 镜像，本地目的地负责把帧交给存储写入服务；目的地不是 Session controller。

**目的地重要性（Destination Requirement）**：目的地对当前录音目标的故障影响等级。REQUIRED 失败会使业务目标不成立；OPTIONAL 失败只摘除该目的地，其他目的地继续。

**录音协调器（Recording Coordinator）**：Application 层负责把 Wire 命令转换为有序录音操作的组件。它编排租约、Engine、Destination、metadata 快照和 Artifact completion，但不拥有 FAT 句柄。

**STOP cut**：停止请求建立的不可回退帧边界。cut 之后不再生成新帧；cut 之前已生成的候选帧必须在 deadline 内完成交付或被明确记为失败。

### 3.2 存储概念

**录音产物（Artifact）**：一次本地录音需要持久化的音频、索引、marks、命名和提交状态的集合。模式 A 的 Artifact 由本文 marker/index 合同定义；模式 B 只能把 legacy SN/文件 ID 作为兼容身份，除非 Adapter 另行持久化映射，不得把它宣称为模式 A Artifact。Artifact 可以在 Session 已停止后独立经历提交或恢复。

**持久化产物身份（artifact_id）**：模式 A 写入 marker/index 的稳定身份，可由持久化 SN 或独立 UUID 派生；它不等同于重启后可能重新计数的运行时 session_id。模式 B 默认使用 legacy SN/文件 ID，只有完成独立映射持久化后才能提供同等稳定身份。

**接纳帧与持久化帧**：Local 队列取得帧所有权时计为 `local_accepted`；帧写入并进入可恢复 checkpoint 时才计为 `persisted`。两者在正常提交时必须相等。

**存储后端（Storage Backend）**：对底层介质和文件系统的窄语义适配。本产品底层介质固定为 BR56 的 sd0 + FAT，文件业务再在 Native 或 Legacy UXFILE 模式中二选一；Storage Backend 不等同于 Local Storage Wire 业务。

**存储就绪（Storage Readiness）**：本次启动中介质已经探测、文件系统已经挂载并通过最小检查的运行时状态。它是瞬时运行条件，不是对介质永不故障的保证。

**产物提交（Artifact Commit）**：音频文件、metadata、marks 和索引均达到可验证恢复点后，Artifact 才进入正常文件列表的过程。

**恢复标记（Recovery Marker）**：描述 Artifact 最新可验证阶段、长度、CRC 和元数据的持久化记录，用于断电后判定恢复或隔离。

**操作租约（Operation Lease）**：对录音、写盘、扫描、删除、格式化、上传、USB 接管和 OTA 等互斥操作的业务级占用资格。它与 ADC/USB 的音频资源租约分开。

以下词语不作为领域术语使用：在线 owner、本地 owner、把采集周期或输出文件称为新录音、把 fclose 或 STOP ACK 单独称为保存成功、用“设备节点已注册”代替 READY、用一个全局 busy 标志表达所有资源冲突。

本轮已落地的基础实现如下：

- `include/rdx/rdx_storage_types.h` 固定 Storage Result、Readiness、Artifact、marker、索引和文件信息的数据合同，不泄漏 `FILE *`、JL 设备结构或 mount handle；
- `include/rdx/ports/rdx_storage_media_port.h`、`rdx_native_artifact_port.h` 和 `rdx_legacy_uxfile_port.h` 分别冻结 Common、Native 和 Legacy 三个窄端口，后端只能在 Composition Root 选择一个；
- `domain/rdx_artifact.c` 实现 `CREATING -> WRITING -> SEAL_QUEUED -> COMMITTING -> COMMITTED` 以及 `FAILED -> QUARANTINED` 的纯内存状态转移，并强制校验固定帧长、接纳/持久化计数闭合和文件字节数；
- `application/rdx_record_composite_destination.c` 实现 Local REQUIRED + Online OPTIONAL 的单 vtable 扇出：本地接纳失败不会继续镜像，在线失败只摘除镜像；
- `application/rdx_local_storage_service.c` 实现单 active Artifact、固定深度帧复制队列、受控 `pump()`、Native/Legacy 结果映射、正常 `seal` 和强制 `abort`；Native 正常提交严格写入 `SEALED`、publish、`PUBLISHED`、A/B index、`INDEXED` marker；每帧持久化 checkpoint 现在携带 CRC32/IEEE，seal 会将后端 close 的文件回读长度/CRC 与 Artifact 交叉校验；`application/rdx_record_local_destination.c` 将该服务暴露为 REQUIRED Destination。Service 支持 Coordinator 在 Engine 分配运行时 token 前使用 `session_id=0` 预备 Artifact，并在 `attach()` 时一次性绑定实际 Session；START 未入队时可显式取消预备。BR56 构建启用单一 worker 和互斥锁，Service 不在 Engine 回调中直接执行 FAT 写入；目标板 deadline、断电恢复和长期稳定性仍待验证；
- `application/rdx_record_coordinator.c` 提供 Application 层的 Local REQUIRED + Online OPTIONAL 组合准备切口：先启动 Artifact、填充 Composite Destination，Engine START 提交失败时回滚（包括尚未 attach 的预分配 Artifact）；它不生成 APP 文件命名/SN 策略，也尚未承接 V23 Wire、租约和 metadata snapshot；
- `adapters/jl_br56/storage/rdx_storage_backend_sd0_jl_br56.c` 初步复用现有 sd0 mount 和 JL VFS/FAT 原语，提供 readiness、容量、读写、删除、格式化、临时文件 publish、显式 marker 编解码、A/B index 读写和基于索引的文件枚举切口；READY 路径会幂等准备 `RDXREC/RDXTMP/RDXBAD` 目录，append 保留运行时 CRC，close/stat 对文件做实际回读，marker/index 写入后执行 CRC/字段回读；启动恢复会快速初始化空索引并有界验证已索引产物，删除先提交索引移除、FAT 删除失败则尝试回滚索引；失败路径会尽力移除已写入的当前 Artifact 索引项并将已发布文件隔离到 `RDXBAD/`；marker 使用完整 64 位 `artifact_id` 命名，A/B index 第一版上限为 32 条且使用固定介质缓冲；未入索引 marker 的枚举裁决、介质断电注入、发布文件的目标板隔离和完整恢复决策尚未完成，不能作为发布证据；
- `rdx_integration_config.h` 增加 Local Storage Build/Wire Gate、sd0/dev_manager/FAT 依赖检查和 Native/Legacy 互斥检查；当前 Product Profile 未选择后端，生产构建仍不编译该领域模块、不广播 Local Storage，也不抽取 `rdx_uxfile.c.o`；
- 增加 Artifact、Composite 和 Local Storage 主机回归用例；当前共 12 个测试组通过，覆盖队列满、短写、长度不一致、正常提交顺序和强制 abort。该用例只验证状态和计数不变量，不替代目标板 FAT、断电恢复或静态库链接验证。

当前 `rdx_protocol_v23_record.c` 仍承担 Engine 初始化和 Session Metadata 生命周期；这属于现状，不是目标职责。实现时必须把这些调用迁移到 Recording Coordinator，Protocol 只保留鉴权、Wire 解码/编码、命令幂等键和 completion 转换，避免 Local Storage 接入后继续扩大 Protocol 的编排责任。

这证明 JL 原生 VFS/FAT 路径已经完成固定文件创建、写入、关闭、重新打开校验、跨重启读回和容量查询。阶段 A 的验收边界是 SD0/FAT 平台持久化 Bring-up；日志中既有的 USB 枚举和 RDX 工厂身份问题不属于本次 SD0 增量改动，也不作为阶段 A 的阻塞项，仍按各自功能计划处理。一次 mount 成功或本阶段闭环完成均不表示 Local Storage Ability 已实现。

2026-08-31 使用 `RDX_LOCAL_STORAGE_DEV_TEST_ENABLE=1`、`RDX_STORAGE_BACKEND_NATIVE=1` 的 clean 开发镜像完成在线烧录，并以 `COM3_2026-08-31_11-43-25.log` 验证两次启动。Storage worker 已按 JL 原生 `task_info_table` 模式注册，启动不再触发 `rdx_storage info unknow` 断言；两次启动均报告 `required_caps=0x7f compiled_caps=0x5ff boot_caps=0x5ff`，SD0 识别和 FAT mount 成功。首次启动创建/初始化 `/UXIDX0.DAT`、`/UXIDX1.DAT`，第二次启动重新读取 A/B index 并完成幂等恢复，未出现 `local_storage=unavailable` 或 `local_storage=recovery_required`。`ability=00000632` 保持不变，符合开发 Build Gate 开启但 Local Ability/Wire 继续关闭的阶段边界。

该证据只关闭 Native Backend 初始化、任务调度、空索引和已索引恢复的目标板启动风险；当前 V23 START/STOP 尚未迁移到 Coordinator，也没有真实 Opus 帧进入 Local Destination，因此不能把本轮结果表述为“录音落盘回归通过”。下一阶段应先接通录音帧到 Native Service 的单会话正常提交路径，再执行文件长度、帧数、CRC、重启读回和在线镜像并行回归。

持久化证据取得后已经退出临时脚手架：`rdx_runtime.c` 不再包含 `dev_manager.h`、FAT API 或 `RDXA.TST` 读写逻辑，`rdx_integration_config.h` 不再定义 `RDX_CFG_SD0_BRINGUP_DIAG_ENABLE`，`lib_system_config.c` 的 `FATFS_WRITE` 恢复为原有产品派生规则。介质上可能遗留的 `RDXA.TST` 只是一份 Bring-up 测试产物，不进入 Artifact、索引或 APP 文件列表语义；正式代码不依赖也不主动访问它。

### 4.3 重构前提交 aa3502dc 提供的挂载证据

提交 aa3502dc01d5736a6a5630e64717a1de423c32dd 已在本产品分支之外落地过一次 BR56 SD0 相关改动，包含 dev_manager.c、BR56 platform、board 配置、app_config.h、genFileList.c 和 SD/Local Storage 设计文档。该提交可以作为“已验证过挂载方向”的输入，但不是当前分支可直接 cherry-pick 的实现方案。

可继承的事实：

- SD NAND 走 JL 原生 sd0/SDMMC 驱动和 FAT，不需要在 RDX 层增加 SPI NAND FTL；
- dev_reg.c 的逻辑根路径为 storage/sd0/C/；
- 固定焊接介质适合开机主动 probe 和常在线策略，不应依赖可插拔卡事件；
- 挂载结果必须可观察；RDX 后续把 JL 原生挂载状态映射为稳定的 Readiness。格式化和重新挂载属于独立维护/恢复策略，不能塞入正常启动路径。

不能直接继承的部分：

- 旧提交的文件组织和宏位置属于重构前的物理边界；
- SD0 引脚、检测方式、电源和时钟必须依据当前 BR56 原理图及实测确认；
- 开机自动格式化是破坏性策略，不能从参考工程或旧提交自动推导为量产默认；
- 旧 RDX/UXFILE 代码的任务、全局状态、Wire 和 FAT 调用混合方式不直接进入新架构；需要兼容旧文件业务时，只能封装为独立 Legacy UXFILE Adapter，并保留其单一 worker 所有权。

### 4.4 tide-bridge 参考工程的行为证据

参考工程 AC701N/BR28 已验证“在线发送 + 本地文件”的产品需求，但暴露出不能照搬的边界：

1. dev_manager_add("sd0") 在设备已经在线时返回 already in list，上层被误报为 sd add fail。新后端的 ensure_ready 必须先查询并复用 JL 已建立的 mount：已经挂载且探测通过返回 READY，正常路径不得再次 dev_manager_init/add/mount。
2. 新机 FAT 可挂载但没有业务索引文件是合法状态。参考工程曾在无索引空盘上无界递归 fscan()，导致录音启动长期阻塞；新 Service 必须有“空索引快速路径”，不能把没有 DAT 等同于文件系统损坏。
3. 参考工程中一次 START 可能重复分配多个 SN/文件，说明重复 Pipeline 初始化或 callback 会造成重复 Artifact。新实现只在当前运行时 session 内维护幂等关联，并以持久化 artifact_id/SN 作为跨重启身份，单 Session 只创建一次 Artifact。
4. 参考工程日志先发送 STOP 状态再保存 UXFILE.DAT，其时间顺序不能证明 STOP 等于保存成功。新协议必须区分 `SESSION_STOPPED` 和模式 A 的 `ARTIFACT_COMMITTED`；模式 B 使用等价的 `LEGACY_FILE_COMMITTED`，也不能把 STOP 当作保存成功。
5. UXFILE.DAT、文件扫描和格式化由旧库任务拥有，且与录音和 USB 事件存在并发访问风险。模式 A 由一个新的 Storage Service worker 串行拥有 FAT；模式 B 不再创建第二个 worker，而是由 Adapter 串行投递给旧库 worker；协议只投递消息。

参考工程可复用的是需求、Golden Trace、异常场景、sd0 + FAT 的平台事实，以及在 APP 要求兼容时通过 Adapter 复用的 UXFILE 能力；不能直接复用旧模块的全局状态、Wire 入口或未审计的文件二进制格式。

### 4.5 RDX 静态库的能力与复用边界

当前 BR56 工程实际链接的归档为：

~~~text
SDK/apps/common/third_party_profile/rdx_protocol/providers/appkey/librdxApp.a
  rdx_encryption.c.o
  rdx_protocol.c.o
  rdx_queue.c.o
  rdx_uxfile.c.o
  xxpUart.c.o
~~~

当前产品源码树没有对应的 `rdx_uxfile.c/.h` 实现，文件业务只以归档对象形式存在；因此接入前必须先确认公开 ABI、头文件来源和许可范围，不能从参考工程复制一份同名实现形成第二套 owner。

`rdx_uxfile.c.o` 不是单纯的 FAT 驱动，而是 RDX 上层 UXFILE 文件业务实现，已经提供录音文件创建、raw 写入/读取、SN 和文件元数据、`UXFILE.DAT` 索引/cache、文件列表、删除、上传读取、容量/格式化以及扫描/同步状态等能力。它同时带有自己的 worker、mutex、timer 和全局状态。其未定义符号还依赖 JL FAT/VFS（`fopen/fwrite/fread/fscan/f_format/fget_free_space` 等）、`dev_manager_add` 以及旧 RDX 录音、RTC、电源、VM、看门狗、Wi-Fi/BLE 和协议回调。因此它可以复用文件业务，不能当作与本设计 Storage Port 等价的通用后端。

当前 BR56 `SDK/cpu/br56/tools/sdk.map` 只抽取了 `librdxApp.a(rdx_encryption.c.o)`；参考工程 `tide-bridge/SDK/Makefile` 与其 map 的链接结果则会抽取归档中的五个对象，包括 `rdx_uxfile.c.o`。这说明“把静态库加入链接”不等于“已经接入文件业务”，也说明局部引用 UXFILE 符号时必须检查是否连带抽取 `rdx_protocol.c.o`、`rdx_queue.c.o` 或 `xxpUart.c.o`。阶段 B 增加 Legacy 适配前，必须完成一次只引用目标 `rdx_uxfile_*` 符号的 BR56 试链接，并把 map、未定义符号和 RAM/任务增量归档为构建证据；若出现不可接受的连带抽取，停止局部接入，转为完整 legacy stack 评审或选择 JL FAT Native Backend。

参考工程同时链接 JL 的 `cpu/br28/liba/fs.a` 和 `librdxApp_patched.a`：前者提供 FAT/VFS、挂载、格式化等平台文件系统基础，后者的 `rdx_uxfile.c.o` 提供 UXFILE/DAT、录音文件和列表等 RDX 上层业务。因此“参考工程的文件系统构建”不能概括为全部由 RDX 静态库提供；正确的复用关系是 JL `fs.a`/dev_manager 负责介质与挂载，RDX `rdx_uxfile` 负责旧文件业务。BR56 仍应沿用这条分层关系，不把两者合并成新的 RDX 挂载实现。

静态库成员的默认准入策略如下：

| archive member | 目标用途 | 默认状态 |
| --- | --- | --- |
| `rdx_encryption.c.o` | Crypto Provider | 允许按现有加密合同复用 |
| `rdx_uxfile.c.o` | Legacy UXFILE Storage Adapter | 只有选择 Legacy 模式时允许 |
| `rdx_protocol.c.o` | 旧协议栈 | 默认禁止由新 Protocol 间接抽取 |
| `rdx_queue.c.o` | 旧队列/运行时 | 默认禁止，除非完整 legacy stack 评审通过 |
| `xxpUart.c.o` | 旧串口运行时 | 默认禁止，除非完整 legacy stack 评审通过 |

准入按 archive member 而不是“整库可用”管理；不得使用 whole-archive 或未审计的全局初始化把旧协议、队列和串口运行时带入新架构。无论选择哪种后端，Engine 和 Protocol 都只能依赖窄 Storage Port；只有 Adapter 可以知道 `rdx_uxfile_*` ABI 和旧回调。静态库能力属于可选实现来源，不改变 JL 一次性 `dev_manager_init()`、sd0 probe、FAT mount 和 Storage Service 的所有权规则。

### 4.6 当前可复用性评估与阶段 B 进入条件

当前结论是“分层方向可复用，现有实现尚不可直接接入”：

| 部分 | 当前状态 | 阶段 B 进入条件 |
| --- | --- | --- |
| JL `dev_manager`/sd0/FAT mount | 已在目标板完成挂载、写入、重启读回和容量证据 | 只允许查询/复用现有 mount；不得新增第二套初始化或挂载 worker |
| Record Engine/Session/Online | Session、帧格式和单 Destination 结构可保留；已加入 `seal/abort/detach_capture`、REQUIRED 标记、候选帧 drain 切口、REQUIRED 队列不覆盖保护和 START 回滚 abort；Coordinator 已有准备/回滚切口，尚未接入 V23 | 由 Coordinator/Composite 提供新目的地并完成 STOP/ABORT、计数和 completion 迁移 |
| Protocol/Metadata | Protocol 当前直接初始化 Engine，并拥有 Metadata begin/end | 迁移到 Recording Coordinator；Protocol 只保留 Wire、幂等键和只读 completion 映射 |
| `rdx_uxfile.c.o` | 具备旧文件业务，但 ABI、worker 和全局状态与当前工程未闭合 | 取得头文件/许可，完成只引用 UXFILE 的 BR56 试链接和依赖白名单；失败则回退 Native 或转完整 legacy stack 评审 |
| Storage Service/Artifact/Local Wire | Common/Native/Legacy Port、纯内存 Artifact 状态模型、Native Service/Backend、Local Destination、Composite 和 Coordinator 准备切口已实现；BR56 唯一 worker 已接入；Local Wire、目标板恢复和长期稳定性尚未完成 | 完成所选模式的目标板 Service/Backend/Local Wire；Ability 保持关闭 |
| FAT 写门控/Capability | SD0/FAT 可编译，但正式写权限和存储 Capability 尚未独立派生 | `FATFS_WRITE`、Build/Wire Gate、Capability 和 `genFileList.c` 选择必须由正式 Storage Gate 驱动 |

因此，本文可以作为阶段 B 的架构基线，但不能把“静态库已加入链接”或“sd0 已挂载”作为 Local Storage 已实现的证据。未满足表中进入条件时，禁止开启 `RDX_ABILITY_LOCAL_STORAGE`。

## 5. 领域模型与不变量

### 5.1 主要对象

~~~text
Session
  session_id                逻辑录音身份，Pause/Resume 不变
  capture_generation        当前采集周期，Resume 递增
  session_frame_seq         跨 Pause 连续的有效帧序号
  active_pts                排除暂停时间的单调时间轴

Artifact
  artifact_id               持久化产物身份；不得直接复用运行时 session_id
  serial_number             已持久化高水位分配的单调 SN
  temp_name/final_name      写入中/已发布文件名
  produced_frame_count      Engine 已确认生成的有效帧数
  destination_accepted_count Destination 接纳的有效帧数
  local_accepted_count      Local 已接纳并承诺写入的帧数
  persisted_frame_count     已完成写入并纳入最近 checkpoint 的帧数
  rejected_frame_count      被目的地拒绝的帧数
  dropped_frame_count       被丢弃的帧数（仅允许在明确失败路径）
  first_error_cause         首个不可恢复错误原因
  audio_bytes/audio_crc     可验证音频长度和 CRC
  marks_snapshot            STOP 切点取得的不可变标记快照
  state                     CREATING/WRITING/SEAL_QUEUED/COMMITTING/
                            COMMITTED/FAILED/QUARANTINED

Storage
  readiness                 UNINITIALIZED/PROBING/RECOVERING/READY/
                            UNAVAILABLE/RECOVERY_REQUIRED/QUIESCING/
                            HOST_OWNED
  index_generation          A/B 索引当前有效版本
  operation_lease           当前文件操作所有者
~~~

上图的 `artifact_id`、marker 和 A/B `index_generation` 是模式 A 字段；模式 B 由 Adapter 映射为 legacy SN/文件 ID、DAT generation 或 `UNSUPPORTED`，不能在未持久化时填入伪造值。

### 5.2 必须保持的不变量

以下不变量中涉及 marker、checkpoint、A/B index 和 `persisted_frame_count` 的部分是模式 A 的强合同；模式 B 仍必须满足 Session、Destination、租约、幂等 START/STOP 和错误不可冒充成功等通用不变量，无法由 `rdx_uxfile.c.o` 证明的项必须报告为 `UNSUPPORTED`，不能以兼容模式名义放宽。

- 一个运行时逻辑 Session 至多有一个 Artifact；重复 START、重复 attach、重复 callback 和 Resume 都不得新建 Artifact。模式 A 的重启恢复必须依赖 marker/index 中的持久化 `artifact_id` 或 serial_number；模式 B 必须依赖 legacy SN/文件 ID 及其可验证的 DAT 记录；两者都不能依赖会在重启后重新计数的 `session_id`。
- session_id、capture_generation 和 session_frame_seq 不得互相替代；旧采集周期的延迟帧必须被丢弃。
- Local Destination 接受的每一帧要么最终进入已提交 Artifact，要么因明确错误进入 FAILED/QUARANTINED；不得静默覆盖旧帧。Engine 产生但未被 Local 接纳的有效帧必须有 rejected/dropped 计数和首个错误原因。
- 正常提交时 local_accepted_count == persisted_frame_count，且 file_size == persisted_frame_count * payload_size；第一版会议录音的 payload_size 固定为 80 B。任何计数不一致都不得发布为 COMMITTED。
- Pause 不结束 Artifact，不清空 marks，不重置 session_frame_seq；Resume 只递增 capture_generation 并丢弃新周期预热帧。
- SESSION_STOPPED 之前不能开始最终索引提交；模式 A 在 `ARTIFACT_COMMITTED`、模式 B 在 `LEGACY_FILE_COMMITTED` 之前不能向 APP 报告保存成功。
- Storage Readiness != READY 时不能接受本地 START；设备节点在链表中但 mount 无效不算 READY。
- Native 模式的 FAT 句柄、索引 generation、marker 状态和 Artifact 状态只由 Storage Service worker 修改；Legacy 模式的 UXFILE/DAT/FAT 状态只由旧库 worker 修改，RDX Service 只修改其兼容映射状态。
- RDX_ABILITY_LOCAL_STORAGE 关闭时没有隐藏的本地录音、删除、格式化、列表或上传入口。

### 5.3 领域错误分类

应用层只使用稳定类别，不传播 JL errno 或 FAT 私有码：

| 类别 | 含义 | 处理 |
| --- | --- | --- |
| NOT_READY | 未挂载、恢复中或被 USB 主机接管 | 拒绝新本地操作，可重试 |
| BUSY | 提交、扫描、删除、格式化或上传占用操作租约 | 不改变当前 Artifact |
| NO_SPACE | 剩余空间低于门槛或写入耗尽 | Local REQUIRED 触发 ABORT，Artifact 进入 FAILED/QUARANTINED（除非另行冻结部分文件合同） |
| IO_ERROR | open/write/close/rename/read-back 失败或短写 | 锁存首个主因，禁止报告成功 |
| CORRUPT | marker、索引、CRC 或文件长度不一致 | 恢复或隔离，不加入正常列表 |
| UNSUPPORTED | APP 请求的格式、文件操作或后端未实现 | Wire 返回稳定不支持结果 |
| TIMEOUT | 后端或 Service 超过有界期限 | 进入 UNAVAILABLE/RECOVERY_REQUIRED |

## 6. 目标分层架构

### 6.1 依赖关系

~~~text
V23 Record/Local Storage Protocol Adapter
    -> Recording Coordinator (Application)
       -> Record Engine
       -> Composite Destination
          -> Online Destination -> Transport Port
          -> Local Destination  -> Local Storage Service
       -> Artifact completion / APP state mapping

Local Storage Service
    -> Artifact Domain / Operation Lease
    -> Media Port + Artifact Repository Port
       -> JL BR56 Storage Backend Adapter
          -> query existing JL mount + VFS/FAT file operations

JL Platform (initialized before RDX)
    -> dev_manager_init() once
       -> native sd0 probe + FAT mount

Product Integration
    -> Ability / Build Gate / Product policy
    -> Composition Root selects one concrete adapter at link time
~~~

禁止的依赖：

- Domain/Application/Protocol 包含 system/includes.h、JL FAT 头文件、sd0 路径、GPIO、VM ID 或 BR56 宏；
- V23 Protocol 直接 fopen/fwrite/fclose/f_format；
- Record Engine 直接调用 dev_manager_* 或读取 Storage 全局状态；
- Storage Backend 反向包含 Protocol、APP Wire 或 Record Engine；
- Product Ability 自动 define TCFG_SD0_ENABLE 或自动修改板级配置。
- RDX 再次调用 dev_manager_init()，或在正常启动路径重复 dev_manager_add()/mount()；
- 为 RDX 复制 JL 已有的 SD 协议、pdata、FAT mount 或设备热插拔框架。

### 6.2 Storage Port 的语义边界

建议新增不含 JL SDK 头文件的窄端口，例如 `include/rdx/ports/rdx_storage_media_port.h`、`rdx_native_artifact_port.h` 和 `rdx_legacy_uxfile_port.h`。这里的 Port 是 RDX 业务语义边界，不是新的平台挂载框架：Media Port 查询 JL 已有 mount 并处理文件原语，Native Artifact Port 负责 marker、索引、发布和恢复，Legacy Port 只封装 UXFILE worker；不能把 VFS 函数表或 APP Wire 命令直接暴露给上层。各 Port 可以由同一个轻量 BR56 Adapter 实现。

实际合同已经拆成三个端口，定义位于 `include/rdx/rdx_storage_types.h`、
`include/rdx/ports/rdx_storage_media_port.h`、
`include/rdx/ports/rdx_native_artifact_port.h` 和
`include/rdx/ports/rdx_legacy_uxfile_port.h`。Common Media Port 只包含就绪、
quiesce、容量、读写/列表、删除和格式化；Native Artifact Port 才包含
temp/append/close、marker、A/B index、publish 和 quarantine；Legacy Port
只包含 UXFILE worker 的 init、文件创建、raw 写入、提交和 abort。后续扩展
必须修改对应端口，不要重新引入把 Artifact 操作混入 Media Port 的旧示例。

上述类型属于 RDX Storage/Application 公共合同，必须使用固定宽度整数和显式序列化；不能把 FILE *、struct __dev 或 JL mount handle 放入 Port。`enumerate_markers/load_latest_marker/read/stat/enumerate/read_for_upload` 是恢复和 Local Storage Wire 所需的最小读路径，`truncate/quarantine/format` 是异常产物和维护操作所需的最小写路径。所有函数都必须定义幂等性、超时和并发租约，不允许由 Protocol 绕过 Service 直接调用。

模式 A 的 BR56 实现集中在 `adapters/jl_br56/storage/rdx_storage_backend_sd0_jl_br56.c`，唯一允许知道：

- sd0、storage/sd0 和 storage/sd0/C/；
- dev_manager 的只读查询接口和现有 mount 状态；
- FAT fopen/fwrite/fclose/frename/fdelete/f_format/fread/fseek 和 fget_free_space；
- JL 返回码到稳定 Storage Result 的映射。

模式 B 的 `rdx_storage_backend_legacy_uxfile.c` 只额外知道 `librdxApp.a` 中已审计的 `rdx_uxfile_*` ABI、旧回调和 legacy 返回值；它不能把 UXFILE 私有结构、`FILE *` 或旧全局状态泄漏到 Storage Port。

Backend 合同要求：

1. ensure_ready() 在第一版只查询并验证 JL 原生 mount；已在线返回 READY，未就绪返回 NOT_READY/IO_ERROR。它不调用 dev_manager_init()，也不在健康路径重复 dev_manager_add()/mount()。若后续需要运行时重新挂载，必须作为独立、有界且经过目标板验证的恢复策略增量加入，不能改变正常路径。
2. 每次 append() 校验实际写入字节数；短写即 IO_ERROR，不把非负返回值视为完整写入。
3. close() 不命名为 fsync，除非目标板实验证明了持久化边界；Native 的 publish() 必须限制在同一 FAT 卷内。模式 A 的 marker/index 提交顺序由 Service 控制，Backend 不自行改变 Artifact 状态；模式 B 只映射 legacy raw/DAT 保存结果，不得伪造该顺序。
4. 容量在 Backend 转换为字节，禁止把 JL 的 KB 单位泄漏给 Domain 或 Wire。
5. ensure_ready()、读写、quiesce、enumerate 和恢复都必须有界，不得阻塞 BLE/USB 主路径到无限等待。Adapter 不修改 JL 原生 dev_manager、SD 驱动或 FAT 实现，除非目标板证据证明 SDK 缺陷且无法在产品适配层规避。

### 6.2.1 Storage Port 合同分层

当前 `rdx_storage_media_ops` 和 `rdx_artifact_repository_ops` 的完整定义主要服务模式 A；模式 B 不能为了复用同一组函数而填入伪造的 marker、checkpoint 或 `artifact_id`。实现时按以下三层拆分：

| Port 层 | 允许的语义 | 适用模式 |
| --- | --- | --- |
| Common Storage Port | `ensure_ready`、`quiesce`、容量、只读状态、列表、读取/上传、删除、格式化和稳定错误映射 | Native / Legacy |
| Native Artifact Port | `open_temp`、`append`、`close`、`truncate`、marker A/B、`publish`、`quarantine`、checkpoint 和恢复 | 仅 Native |
| Legacy UXFILE Port | Legacy init、`begin_file`、`raw_write`、flush/保存 DAT、legacy SN/文件 ID、worker 状态和兼容 completion | 仅 Legacy |

Native Port 才能产生本文定义的 `ARTIFACT_COMMITTED` 和 `artifact_id/marker_generation`。Legacy Port 产生 `LEGACY_FILE_COMMITTED/LEGACY_FILE_FAILED`，至少携带 legacy SN/文件 ID、最终计数和错误原因；不具备的 A/B、checkpoint 或稳定身份能力必须返回 `UNSUPPORTED`。`Storage Service` 根据链接时选定的后端绑定其中一组具体 vtable，Common Port 只保留一份，禁止两个后端同时注册。

### 6.2.2 后端模式选择（互斥）

Storage Port 只允许选择一个具体后端。两种模式都复用 JL 已建立的 `sd0`/FAT mount，但文件业务的所有者不同；同一固件、同一启动周期不能同时启用两种模式。

**模式 A：JL FAT Native Backend（新合同路径）**

- Storage Service 单独拥有 FAT 句柄、Artifact、A/B marker/index、发布和恢复；
- `librdxApp.a` 只按既有 Crypto 合同抽取 `rdx_encryption.c.o`，不抽取 `rdx_uxfile.c.o`；
- `RDXREC/RDXTMP/RDXBAD` 和 `UXIDX0/1.DAT` 等布局、计数、`SEALED -> rename -> PUBLISHED -> INDEXED` 提交流程由本文定义；
- 适用于 APP 接受新文件布局和新 Artifact/恢复合同的情况。

**模式 B：Legacy UXFILE Adapter（兼容模式）**

- 仅当 APP Golden Trace 明确要求兼容参考工程的 UXFILE 文件、SN、字段或 `UXFILE.DAT` 时选择；
- JL 仍只负责一次 probe/mount；窄 Adapter 调用 `rdx_uxfile_init`、`rdx_uxfile_dat_init`、`rdx_uxfile_raw_write`、`rdx_uxfile_dat_1_save_gen` 等已审计 ABI；
- `rdx_uxfile.c.o` 内部的 worker、DAT cache、SN 分配、文件列表/删除/上传/格式化和 FAT 访问继续由 legacy 实现拥有，RDX Coordinator 只编排 Session、租约、STOP/ABORT 和状态映射；
- 不得再创建第二个 FAT worker、第二套 `RDXIDX0/1` 索引或第二个 SN 分配器；Protocol/Engine 仍不得直接包含 UXFILE 头文件或调用其符号；
- 旧 API 没有新合同所需的 per-Artifact handle、A/B marker、`artifact_id`、四类持久化计数和明确的 `SEALED -> ... -> INDEXED` 边界，因此 Legacy 模式不能宣称已经实现模式 A 的断电提交合同。若 APP 同时要求 UXFILE 二进制兼容和本文 A/B/Artifact 合同，必须先增加独立的兼容层持久化设计，不能把两套格式混写。

模式选择必须在 Composition Root 和链接配置中显式落定，并派生互斥的 `RDX_STORAGE_BACKEND_NATIVE` / `RDX_STORAGE_BACKEND_LEGACY_UXFILE`。构建期若两者均为 1，必须 `#error`；若均为 0，Local Storage Build Gate 不得通过。Ability、Capability、Wire 和测试矩阵都必须记录所选模式，不能用运行时猜测切换后端。

### 6.3 Local Storage Service

在模式 A 中，Local Storage Service 是唯一的 FAT/Artifact worker；在模式 B 中，Local Storage Service 是唯一对上层可见的 Storage Service facade，但 FAT、UXFILE.DAT、SN 和旧文件业务的实际 worker 由 `rdx_uxfile.c.o` 拥有。两种模式都禁止 Engine、Protocol 或其他业务线程绕过 Service 直接访问文件。

建议状态机如下（模式 B 的 `RECOVERING/COMMITTING` 状态由 Adapter 映射 legacy worker 的可观察状态）：

~~~text
UNINITIALIZED -> PROBING -> RECOVERING -> READY
                             \----------> UNAVAILABLE

Artifact:
NONE -> CREATING -> WRITING -> SEAL_QUEUED -> COMMITTING -> COMMITTED
  |        |          |             |              |
  +--------+----------+-------------+--------------> FAILED -> QUARANTINED
~~~

模式 B 中 `COMMITTED/FAILED` 只能解释为 `LEGACY_FILE_COMMITTED/LEGACY_FILE_FAILED` 兼容状态；若 legacy worker 没有可验证的保存完成信号，状态必须停在 `COMMITTING`/`UNAVAILABLE`，不能升级为已提交。

模式 A 的 Service 负责：

- 启动 probe、挂载、空索引初始化和未完成 marker 恢复；
- 单调 SN 高水位、Artifact 创建、临时/正式名称和目录；
- 接收固定大小的 FRAME、MARK_SNAPSHOT、SEAL、ABORT、DELETE、FORMAT、QUIESCE 消息；
- 写音频、checkpoint、marker、索引和最小 read-back；
- 向 Recording Coordinator 发送 ARTIFACT_COMMITTED、ARTIFACT_FAILED、容量和列表 completion；Protocol 只能通过 Coordinator 获取只读结果；
- 处理关机、OTA、USB 接管和介质故障的有界 quiesce。

模式 B 的 Service 负责以下兼容职责（不同时执行模式 A 的 FAT/index worker 职责）：

- 将 Coordinator 的 Artifact/帧/STOP/ABORT 请求串行转换为 Legacy UXFILE 调用，并把 legacy 返回值映射为稳定 Storage Result；
- 通过适配层获取 UXFILE 文件列表、SN、容量、删除、格式化和上传结果，不在 RDX Service 内复制 DAT cache 或全盘 `fscan()`；
- 将 `rdx_uxfile_*` 的 worker 生命周期、回调和旧全局状态限制在 Adapter 内，确保退出、USB/OTA quiesce 和重复初始化有明确边界；
- 对不具备新 Artifact marker/index 语义的 legacy 结果标记为兼容完成，禁止伪造模式 A 的 `ARTIFACT_COMMITTED`/断电恢复保证。

第一版只允许一个 active 或 committing Artifact。Engine 即使已经回到 IDLE，只要 Service 仍在 COMMITTING，新的本地 START、删除、格式化和会改变索引的操作都返回 BUSY；只读状态/容量查询可排队。不要通过放宽状态判断伪造多 Artifact 并发。

Local consume() 只复制帧并入队，不执行 FAT 写入。队列容量按目标板实测最坏 SD 写阻塞确定：

~~~text
payload_capacity >= input_bytes_per_second
                   * worst_case_write_stall_seconds
                   + one_write_batch
~~~

MEETING_V1 的输入基线是 80 B/20 ms，即约 4 KB/s；最终深度还必须计入描述符、控制消息保留槽和最低 RAM 水位。队列满时，Local REQUIRED 不能覆盖旧帧或静默丢帧，必须锁存 NO_SPACE/IO_ERROR/QUEUE_FULL 并触发 ABORT；Online OPTIONAL 可以保留当前有限 BLE 队列策略。

### 6.4 Recording Coordinator

Recording Coordinator 是 Application 层的每个录音会话协调器，建议落在 `application/rdx_recording_service.c`（名称可在实现时冻结）。它是 START/STOP/ABORT 的唯一编排者，至少负责：

- 持有 RECORD、LOCAL_WRITE 等 Operation Lease，并把删除、格式化、上传、USB、OTA 的冲突映射为稳定错误；
- 在 START 中按“Storage READY -> Artifact 创建 -> Composite attach -> Engine capture open”顺序执行事务，失败时反向释放已取得资源；
- 在 STOP 中执行 frame gate、capture close、候选帧 drain、metadata snapshot、Destination seal 和 Artifact completion 的有界时序；
- 把 `SESSION_STOPPED`、`ARTIFACT_COMMITTED` 和 `ARTIFACT_FAILED` 映射给 V23 Protocol/APP，不允许 Protocol 猜测文件是否已保存。模式 B 另定义 `LEGACY_FILE_COMMITTED/LEGACY_FILE_FAILED` 兼容结果，只有 APP 合同明确接受时才映射为保存完成；不得把 legacy 返回值伪装成模式 A 的 marker 提交结果；
- 模式 A completion 必须携带持久化 `artifact_id`、marker generation、最终计数和错误原因；模式 B 至少携带 legacy SN/文件 ID、最终计数和错误原因，并明确没有 A/B marker generation。重复或过期 completion 必须幂等忽略，不能二次通知 APP；
- 保留运行时 `session_id` 与持久化 `artifact_id/serial_number` 的关联，重启后由 Storage Service 从 marker/index 恢复，不依赖旧的运行时 ID。

Protocol 只调用 Coordinator 的命令接口并订阅只读 completion；Engine 只报告采集边界和帧计数；Storage Service 只报告 Artifact/介质结果。三者不得互相持有对方的私有句柄。

### 6.5 Composite Destination

当前 Engine 只有一个 Destination 指针，第一轮不把它改成多个异构 vtable。新增一个 Application 层 Composite Destination：

- attach() 创建/挂接 Local Artifact，并重置 Online mirror 状态；
- consume() 对同一 RecordFrame 先后调用 Local 和 Online；Local 只入队，Online 只入 BLE 有界队列；
- Local 返回不可恢复错误时，Composite 通知 Coordinator 终止 Session（v1 不降级为仅在线）；Online 返回拥塞/断连时只摘除 Online；
- seal() 将不可变 marks 快照和最终帧边界交给 Local Service，同时完成 Online 的正常收尾；
- abort() 只用于强制终止、介质故障或启动失败，Local 进入 FAILED/QUARANTINED，不得伪装成正常保存；
- detach_capture() 表示采集资源已经释放，但不等于 Artifact 已提交；
- poll() 只服务 Online 发送就绪，不允许驱动 FAT。

建议把现有 vtable 扩展为等价语义，具体参数在实现阶段冻结：

~~~c
struct rdx_record_destination_ops {
    int  (*attach)(void *priv, uint32_t session_id,
                   uint32_t capture_generation);
    int  (*consume)(void *priv, const struct rdx_record_frame *frame);
    void (*poll)(void *priv, uint32_t session_id,
                 uint32_t capture_generation);
    int  (*seal)(void *priv, uint32_t session_id,
                 uint32_t capture_generation);
    int  (*abort)(void *priv, uint32_t session_id,
                  uint32_t capture_generation, enum rdx_record_cause cause);
    void (*detach_capture)(void *priv, uint32_t session_id,
                           uint32_t capture_generation);
};
~~~

cancel() 可以在迁移期保留为 Online 队列丢弃的兼容实现，但正常 STOP 不得再对 Composite/Local 调用 cancel()。Local completion 通过受控 callback/event 返回 Coordinator，不把内部数组指针交给 Protocol。

## 7. Session、目的地和故障策略

### 7.1 START

正常 START 顺序固定为：

~~~text
V23 START
  -> Protocol 校验鉴权/命令幂等
  -> Recording Coordinator 申请 RECORD + LOCAL_WRITE 租约
  -> Storage Service 确认 READY、空间和目录门槛
  -> 持久化 SN 高水位（允许空洞，不允许回退复用）
  -> 创建唯一 Artifact marker=ALLOCATED
  -> 创建 temp audio，marker=WRITING
  -> Composite attach(Local + Online)
  -> Record Engine readiness / capture open
  -> START_COMPLETE
  -> V23 状态包和在线镜像开启
~~~

如果 Local attach 或 Artifact 创建失败，Engine 不得只启动 Online 再谎报“双目的地”成功；本版本推荐 Local REQUIRED 时整个 START 失败。重复 START 只返回既有 Session/Artifact 状态，不重复分配 SN。

模式 B 的 START 将“创建 marker/temp audio”替换为 Legacy UXFILE 的有界 init、SN/文件创建和 Adapter attach；不得同时创建模式 A marker。若 Legacy API 只能返回全局成功而无法关联当前 `session_id`/SN，Adapter 必须拒绝 attach，不能靠回调顺序猜测 Artifact 归属。

### 7.2 帧和背压

Engine 继续生成规范 RecordFrame：

- session_frame_seq 跨 Pause 连续；
- capture_frame_seq 每个采集周期从零开始；
- active_pts 排除暂停和预热；
- payload 在 Destination 调用返回后失效。

当前 Engine 在候选帧队列满时会覆盖最老候选帧，这是在线/USB 场景的既有保护。Composite 模式不能沿用该行为：当 Local REQUIRED 已挂接时，Engine/Composite 必须改为“拒绝新帧并锁存 Local backpressure”，随后执行有界 STOP/SEAL 或 ABORT；不能先丢帧再生成看似完整的 Artifact。Engine 队列溢出、Local 入队失败和 Local 写入失败都必须记录首个原因，并使 Artifact 进入 FAILED/QUARANTINED。

Online 仍维持 3-8 已验证的 BLE 队列、can-send、burst budget 和 Notify 合同。Online ACCEPTED 只表示本地 ATT 队列接纳，不表示 APP 已收到；它不影响 Local Artifact 的 CRC 和帧数。

### 7.3 帧完整性计数与 STOP cut

以下四类持久化计数、文件长度/CRC 和 STOP cut 收敛规则是模式 A 的强合同；模式 B 必须使用 Adapter 能可靠取得的 legacy 写入/保存结果，不能凭旧 callback 次数补齐缺失计数。

Coordinator/Engine/Local Service 必须分别维护 `produced_frame_count`、`destination_accepted_count`、`local_accepted_count` 和 `persisted_frame_count`，并记录 `rejected_frame_count`、`dropped_frame_count` 与 `first_error_cause`。`local_accepted_count` 只在 Local 队列成功接纳并取得帧所有权后递增；`persisted_frame_count` 只在 append 成功且进入 checkpoint 后递增。`file_size` 和 CRC 只能由已持久化帧计算，不能用 Engine 生成数推算。

STOP 建立一个不可回退的 cut：关闭 frame gate 后，Engine 必须在有界 deadline 内排空已经生成但尚未调用 Destination 的候选帧。若 gate 关闭后仍有候选帧无法投递、队列曾经溢出，或 `local_accepted_count != persisted_frame_count` 无法在 deadline 内收敛，则不得 SEAL，必须 ABORT 并将 Artifact 标为 FAILED/QUARANTINED。只有 drain 成功且计数闭合，才允许取得 marks 快照并发出 SEAL。

### 7.4 正常 STOP

正常 STOP 必须分为两个事件：

~~~text
STOP request
  -> Engine 关闭 frame gate，停止新帧
  -> capture close，释放 Audio Lease
  -> 在 deadline 内 drain 已生成候选帧
  -> Composite.detach_capture()
  -> Coordinator 取得不可变 MARK_SNAPSHOT
  -> Engine emit SESSION_STOPPED
  -> Local Service 处理 MARK_SNAPSHOT + SEAL
  -> Artifact COMMITTING
  -> marker/index/read-back 完成
  -> emit ARTIFACT_COMMITTED 或 ARTIFACT_FAILED
~~~

SESSION_STOPPED 可用于释放 Pipeline 和更新录音状态；它不能作为文件保存成功。V23 STOP Wire 的含义必须在阶段 C 以 APP Golden Trace 冻结：

- 推荐延后“保存成功”状态到 ARTIFACT_COMMITTED；
- 若 APP 要求快速 ACK，则快速 ACK 只能表示 SESSION_STOPPED，必须另有文件完成/失败或列表同步证据；
- 不能依据写盘快慢随机改变 ACK 含义。

上述 `marker/index/read-back` 和 `ARTIFACT_COMMITTED` 顺序是模式 A 的新合同。模式 B 的正常 STOP 必须等待 `rdx_uxfile_raw_write` 队列排空及 `rdx_uxfile_dat_1_save_gen` 等 legacy 完成信号，再由 Adapter 发出 `LEGACY_FILE_COMMITTED` 或 `LEGACY_FILE_FAILED`；不得因为旧库返回 STOP/close 就直接宣称模式 A 的 Artifact 已提交。

### 7.5 强制 ABORT

USB 抢占、关机 deadline、介质不可恢复错误、Engine fault 和安全动作使用 ABORT：

- 立即关闭 frame gate，停止采集并释放 Audio Lease；
- 不等待 BLE 队列、不覆盖 stop/system-event latch；
- Local 关闭临时文件，保留 marker 和可诊断数据；
- 根据 marker 和 checkpoint 转为 FAILED 或 QUARANTINED；
- 不发送保存成功，不把强制结束写成正常 COMMITTED。

模式 B 的 ABORT 改为调用 legacy worker 可用的停止/关闭接口并保留其可诊断状态；不存在 marker/checkpoint 时必须返回 `LEGACY_FILE_FAILED` 或 `UNSUPPORTED`，不能套用 Native 的 `FAILED/QUARANTINED` 恢复结论。

### 7.6 Pause/Resume 和 marks

Pause/Resume 不新建 Artifact。STOP 前由 Coordinator 在 Engine/Metadata 串行点取得不可变 `marks_snapshot` 副本；建议 Metadata Service 提供 `rdx_session_metadata_snapshot(session_id, dst, capacity, &count)` 这类复制式 API，并在返回后允许其内部数组继续清理。Storage Service 只消费快照副本，不能在 COMMITTING 期间引用 Metadata Service 内部数组。

Resume 递增 capture_generation，旧 Pipeline callback 必须被丢弃。新周期预热帧仍不进入 local_accepted_count、active_pts 或 marks。

### 7.7 BLE 断连、USB 和关机

目的地故障与 Session 控制故障分开：

- 在线镜像断连或 CCC off：摘除 Online OPTIONAL，记录原因；Local REQUIRED 继续写盘。若当前产品决定“断连即停止”，也必须走正常 SESSION_STOPPED -> SEAL，不能走静默 cancel；该策略在阶段 C 通过 APP/产品决策冻结。
- Local 后端故障：Local REQUIRED 锁存首个主因并有界终止 Session；Online 不能继续宣称本地已保存。
- USB 音频抢占：通过现有 Audio Lease 强制结束当前采集周期；v1 固定走 ABORT（满足 Type-C/USB deadline），Artifact 标为 FAILED/QUARANTINED。若后续产品要改为正常封口，必须另行冻结 deadline、drain 和 APP 语义，不能在同一实现中按运行时猜测。
- 关机/OTA：先关闭新命令，投递可信 SHUTDOWN，等待 Engine 停止，再由 Storage Service 在 deadline 内 SEAL 或 ABORT；超时不得释放仍被 callback 引用的对象。
- USB MSD 若未来开启：必须实现 FIRMWARE_OWNED -> QUIESCING -> UNMOUNTED -> HOST_OWNED 及反向恢复状态。未完成所有权仲裁前保持 TCFG_USB_SLAVE_MSD_ENABLE=0。

租约优先级在 v1 固定为：正在录音时 `RECORD + LOCAL_WRITE` 阻止删除、格式化和上传；关机/OTA/USB 抢占可以打断录音，但必须先经 Coordinator 的 ABORT/QUIESCE 协议；任何调用方都不得绕过租约直接访问 FAT。

## 8. Artifact 格式、提交与恢复

### 8.1 兼容边界

第一版音频数据继续使用已验证的连续 raw Opus：16 kHz / mono / 32 kbps / 20 ms / 80 B。该数据格式同时服务 Online 镜像和 Local 文件；不因为落盘而加入 V23 私有头，也不复制参考工程的 stereo 约束。

文件名、目录、SN、marks 编码和列表字段属于 APP Local Storage 合同，必须在阶段 C 用 Golden Trace 冻结。阶段 B 内部测试可使用 8.3 名称和独立测试目录，不得把测试名称当成发布合同。

模式 A 使用本文定义的新 Artifact/marker/index 合同。模式 B 只在 APP 明确要求兼容时使用 `librdxApp.a` 提供的 UXFILE 文件组织和 `UXFILE.DAT` 语义；其二进制布局、SN 规则和列表字段以旧库 ABI/APP Golden Trace 为准，不能与模式 A 的 `RDXIDX0/1.DAT` 或 marker 混写。

### 8.2 介质布局建议（模式 A）

以下布局只属于 JL FAT Native Backend。在 APP 合同冻结前，使用以下内部布局：

~~~text
storage/sd0/C/
    RDXREC/       正式音频文件
    RDXTMP/       临时音频、A/B recovery marker
    RDXBAD/       无法证明完整的隔离产物
    UXIDX0.DAT    索引副本 0
    UXIDX1.DAT    索引副本 1
~~~

marker 至少包含：magic/version/header_len、state、generation、持久化 artifact_id、运行时 session_id（仅用于诊断）、SN、temp/final name、format、sample rate、channels、frame_ms、produced/destination_accepted/local_accepted/persisted frame count、rejected_frame_count、dropped_frame_count、first_error_cause、audio bytes/CRC、marks count/CRC、start time、last update 和 header CRC。所有整数的字节序、CRC 覆盖范围和结构版本必须显式定义，不能直接写带 padding 的 C struct。

模式 B 不创建上述 `RDXTMP/RDXBAD/UXIDX0/UXIDX1` 结构；Adapter 必须明确哪些恢复、隔离和列表能力由 legacy worker 提供，哪些新合同无法保证，并把缺失能力报告为 `UNSUPPORTED`，不能用文件名或 `UXFILE.DAT` 猜测 A/B marker 状态。

### 8.3 创建与 checkpoint（模式 A）

创建顺序：

1. READY、空间、目录项和操作租约通过；
2. 分配并持久化 SN 高水位；
3. 创建 marker ALLOCATED，关闭并 read-back 校验；
4. 创建临时音频，marker 更新为 WRITING；
5. Composite attach 成功后 Engine 才能完成 START。

录音过程中追加音频和内存 marks；按固定字节数或时间做 checkpoint，交替更新 marker A/B。断电最多丢弃最后一个已确认 checkpoint 之后的尾帧，不能把尾帧计入长度、CRC 或索引。阶段 C 必须确认 APP 是否允许恢复文件缩短；不允许时，WRITING 产物一律隔离。

### 8.4 正常提交（模式 A）

Storage Service 收到有序 SEAL 后，必须把 Coordinator 传入的最终帧边界、四类计数和 `marks_snapshot` 作为一次不可变提交请求；只接受当前 Artifact 的正确 generation，重复 SEAL 按已记录结果幂等返回：

1. 拒绝新 FRAME，等待已经接受的帧写完；
2. 校验长度、帧整除、frame count、audio CRC 和 marks snapshot；
3. marker 更新为 SEALED，关闭并 read-back；
4. 将临时文件在同一 FAT 卷内 rename 为正式名称；
5. 校验正式文件存在、长度和头尾最小读回；
6. marker 更新为 PUBLISHED 并 read-back；
7. 基于旧有效索引写入另一个 A/B generation，关闭并校验 header/entry CRC；
8. marker 更新为 INDEXED 并 read-back；
9. 发布 ARTIFACT_COMMITTED，之后才允许正常列表显示。

提交顺序固定为 `SEALED -> rename -> PUBLISHED -> index A/B -> INDEXED`。每个箭头都是独立的断电边界，恢复必须幂等且不能依赖内存状态。任一步失败都保留 marker/可恢复文件，发布 ARTIFACT_FAILED，禁止发送保存成功。close()/rename() 的断电边界必须通过目标板故障注入验证，不能以 API 返回成功代替。

### 8.5 启动恢复（模式 A）

启动先选择 A/B 索引中 CRC 有效且 generation 最大的副本，再处理 marker：

| marker | 文件事实 | 动作 |
| --- | --- | --- |
| ALLOCATED | 无临时文件或空文件 | 删除空产物，保留 SN 空洞 |
| WRITING | 临时文件存在 | 按最后 checkpoint 校验/截断；不满足策略则移入 RDXBAD |
| SEALED | 临时文件完整 | 幂等 rename；校验后写 PUBLISHED |
| SEALED | 正式文件存在、临时文件不存在 | 视为 rename 已完成，校验后写 PUBLISHED |
| PUBLISHED | 正式文件存在、索引无记录 | 校验后补写新索引，再写 INDEXED |
| PUBLISHED | 正式文件和索引记录均存在 | 校验索引 generation，幂等写 INDEXED |
| INDEXED | 文件和索引一致 | 视为已提交，清理 marker |
| 任意 | 名称、长度、CRC、版本冲突 | 隔离或进入 RECOVERY_REQUIRED，不展示 |

“无索引 + 空盘”必须快速初始化为 0 条记录，不执行无界全盘扫描。只有在显式维护恢复命令、进度、取消和超时均已实现后，才允许扫描孤立 raw 文件。没有 marker 的孤立临时文件和没有索引记录的正式文件不能靠文件名猜测为成功产物。

模式 B 的启动恢复只调用 Legacy UXFILE Adapter 的有界初始化/同步接口（例如 `rdx_uxfile_dat_init`、`rdx_uxfile_sync_files_with_dat`），不在 RDX Service 中再次执行 `fscan()`、重建 DAT 或创建第二份索引。若 legacy 同步失败，Readiness/兼容结果进入 `UNAVAILABLE` 或 `RECOVERY_REQUIRED`，不伪造模式 A 的 marker 恢复完成。

## 9. Ability、Capability 与编译门控

### 9.1 单向配置

在 rdx_integration_config.h 派生：

~~~c
#define RDX_CFG_LOCAL_STORAGE_ENABLE \
    ((RDX_COMPAT_DEVICE_ABILITY & RDX_ABILITY_LOCAL_STORAGE) != 0)

#ifndef RDX_LOCAL_STORAGE_DEV_TEST_ENABLE
#define RDX_LOCAL_STORAGE_DEV_TEST_ENABLE 0
#endif

#define RDX_CFG_LOCAL_STORAGE_BUILD_ENABLE \
    (RDX_CFG_LOCAL_STORAGE_ENABLE || RDX_LOCAL_STORAGE_DEV_TEST_ENABLE)
#define RDX_CFG_LOCAL_STORAGE_WIRE_ENABLE RDX_CFG_LOCAL_STORAGE_ENABLE

/* 由 Product/Build profile 显式二选一；未设置时为“未选择”，不构成生产默认值。 */
#ifndef RDX_STORAGE_BACKEND_NATIVE
#define RDX_STORAGE_BACKEND_NATIVE 0
#endif
#ifndef RDX_STORAGE_BACKEND_LEGACY_UXFILE
#define RDX_STORAGE_BACKEND_LEGACY_UXFILE 0
#endif
#ifndef RDX_LIBRDX_UXFILE_LINKED
#define RDX_LIBRDX_UXFILE_LINKED 0
#endif

#if RDX_CFG_LOCAL_STORAGE_BUILD_ENABLE && \
    ((RDX_STORAGE_BACKEND_NATIVE + RDX_STORAGE_BACKEND_LEGACY_UXFILE) != 1)
#error "RDX local storage requires exactly one storage backend"
#endif
~~~

规则：

- Product Ability 只维护 RDX_COMPAT_DEVICE_ABILITY；
- Build Enable 允许阶段 B 在 Ability 关闭时编译内部 Service/Fake，但不改变广播和 Wire；
- Wire Enable 才能编译 Local Storage 命令、列表、删除、格式化和上传入口；
- Backend mode 只能由 Product/Build profile 显式选择；共享 `rdx_integration_config.h` 不得默默选择 Native，未选择或双选必须失败；
- 发布构建必须拒绝 RDX_LOCAL_STORAGE_DEV_TEST_ENABLE != 0；
- rdx_integration_config.h 只能 #error 检查板级条件，不能反向打开 TCFG_SD0_ENABLE、FATFS 或 dev_manager。

### 9.2 Capability 分层

6 号文档的技术能力表需要增加独立的存储能力：

~~~text
RDX_CAP_STORAGE_BACKEND_NATIVE       sd0/FAT Native Backend 已编译
RDX_CAP_STORAGE_BACKEND_LEGACY_UXFILE librdxApp.a 的 rdx_uxfile.c.o 与 Adapter 已审计并编译
RDX_CAP_STORAGE_SERVICE               Service、Artifact、索引和恢复/兼容映射已编译
RDX_CAP_LOCAL_STORAGE                 恰好一个后端 + Service 已编译且所选合同满足
~~~

三种概念必须分开：

- Compile Capability：源码和后端是否被编译（`RDX_CAP_STORAGE_BACKEND_NATIVE`、`RDX_CAP_STORAGE_BACKEND_LEGACY_UXFILE`、`RDX_CAP_STORAGE_SERVICE`）；Legacy 能力还必须包含静态库成员、ABI、旧回调和 worker 生命周期审计；
- Boot Structural Capability：Native 模式要求本次启动完成 mount、空索引初始化和 marker/index 结构探测；Legacy 模式要求完成 mount 及 UXFILE DAT 初始化/同步，并明确 legacy worker 的可观察状态；
- Operational Readiness：此刻是否允许录音或文件操作（`READY`/`UNAVAILABLE`/`BUSY`）。

正式 Ability 要求前两层合同均满足，但 Ability 不能被一次启动故障动态改写；READY 仍是运行时 Operational Readiness，启动失败时只能拒绝 Local 操作并报告 UNAVAILABLE，不能伪装成永久不支持或继续接受 Local REQUIRED START。

### 9.3 强依赖检查

当 RDX_CFG_LOCAL_STORAGE_BUILD_ENABLE == 1 时，BR56 后端至少检查：

~~~c
#if !TCFG_SD0_ENABLE
#error "RDX local storage backend requires TCFG_SD0_ENABLE"
#endif
#if !TCFG_DEV_MANAGER_ENABLE
#error "RDX local storage backend requires TCFG_DEV_MANAGER_ENABLE"
#endif
#if !CONFIG_FATFS_ENABLE
#error "RDX local storage backend requires CONFIG_FATFS_ENABLE"
#endif
#if RDX_STORAGE_BACKEND_LEGACY_UXFILE && !RDX_LIBRDX_UXFILE_LINKED
#error "Legacy UXFILE backend requires audited librdxApp rdx_uxfile member"
#endif
~~~

固定焊接 SD NAND 的常在线策略和 USB MSD 互斥条件也必须检查，但具体宏必须依据当前 BR56 板级配置确认，不能复制 BR28 名称。存储业务与会议录音格式的依赖通过 RDX_CAP_MEETING_CAPTURE 合同表达；不在后端中直接包含 Audio Adapter。

`RDX_LIBRDX_UXFILE_LINKED` 不是“归档文件存在”的路径判断，而是构建脚本依据 map/符号审计结果产生的事实标志：必须确认实际抽取的是 `rdx_uxfile.c.o`，且没有未经批准的 `rdx_protocol.c.o`、`rdx_queue.c.o`、`xxpUart.c.o` 连带依赖。若 legacy ABI 需要这些对象，必须显式切换到完整 legacy stack 配置并重新评审任务、内存、协议和全局初始化，不能用单个宏掩盖。

### 9.4 Ability 开启时机

只有以下条件全部成立，才把 RDX_ABILITY_LOCAL_STORAGE 加入 RDX_COMPAT_DEVICE_ABILITY 和 RDX_PRODUCT_SUPPORTED_ABILITY：

- SD0/FAT 经过冷启动、热启动、读写和恢复验证；
- Local/Composite Destination、正常 seal、强制 abort 和故障域完成；
- 文件列表、删除、格式化、上传、容量和 APP 错误码合同完成；
- 所选后端的恢复合同验证完成：Native 覆盖空索引、A/B marker、索引损坏、断电切点和 SN 高水位；Legacy 覆盖 DAT 初始化/同步/保存、legacy SN 高水位和其明确支持的故障切点；
- 开发门控归零，负向编译矩阵通过；
- 长录音、BLE 断连、USB 抢占、关机、OTA 和 RTC 回归通过。

## 10. 运行时初始化与退出

### 10.1 启动

Composition Root integration/type_c_ac7106f6/rdx_runtime.c 在协议入口前后按以下顺序编排：

~~~text
应用 core 先完成一次 dev_manager_init()
  -> JL 原生 sd0 probe + FAT mount
  -> Storage Service init
  -> Backend ensure_ready（查询/验证现有 mount）+ 有界业务恢复
  -> 记录 Boot Structural Capability
  -> 初始化 Audio/Record Engine
  -> 初始化 V23 Protocol/Transport
  -> 根据 Product Ability 开放 Wire
~~~

当前 `SDK/apps/earphone/app_main.c` 已负责 `dev_manager_init()`；该调用会重置设备管理状态、创建任务，并在常在线配置下由 JL 原生路径完成 sd0 probe/FAT mount。RDX runtime 不得再次调用，也不得自行创建第二个 dev_manager worker。第一版 BR56 Backend 的正常路径只查询现有 mount、验证访问并映射 Readiness，不重复 add/mount；平台宏和源码选择仍由 `app_config.h`、板级配置及 `genFileList.c` 负责。

若选择模式 B，`Storage Service init` 之后只初始化一次 Legacy UXFILE Adapter，并在现有 mount 上调用其有界 `rdx_uxfile_*` 初始化/同步接口；不得再启动 Native Storage Service 的 FAT worker、A/B index 恢复或全盘扫描。若选择模式 A，则按本文定义的 marker/index 恢复路径执行。两者的启动日志必须能区分所选模式和实际 owner，便于发现重复 worker 或重复 `dev_manager_add()`。

Storage mount 失败时，RDX 可以保持其他已声明业务，但 Local Storage Readiness 为 UNAVAILABLE；不能因为暂时介质故障把产品 Ability 改写为 0，也不能继续接受 Local REQUIRED START。

### 10.2 退出

~~~text
关闭 Local Storage 新命令
  -> 关闭在线新命令
  -> 投递可信 SHUTDOWN
  -> Engine 停止采集并释放 Audio Lease
  -> Storage Service 在 deadline 内 SEAL/ABORT
  -> 取消 Transport/Timer/worker
  -> 释放仍未被 callback 使用的 Adapter 资源
~~~

退出超时必须保留仍可能被 callback 引用的对象，并报告 SHUTDOWN_TIMEOUT；不得释放后再声称 RDX 已安全退出。

## 12. 分阶段实施路线

### 阶段 A：SD0/FAT 平台 Bring-up（已完成）

目标是证明平台存储，不接 Local Wire：

- [已完成] 确认并配置 CMD/CLK/DAT0、电源、检测模式和保守时钟，目标板已识别 120 MB 介质；具体 SD NAND 型号和上拉仍应归档到硬件基线；
- [已完成] 复用 JL 原生 dev_manager/sd0/FAT 主动 probe/mount，不增加 RDX 平台挂载代码；
- [已完成] 修正 TCFG_DEV_MANAGER_ENABLE 和 genFileList.c 的必要平台源码选择，仅纳入固定介质挂载所需的 dev_reg.c；
- [已完成] 使用 JL VFS/FAT 路径完成固定文件写入、关闭、重新打开校验、第二次上电读回、generation 递增和容量查询；
- [已完成] 自动格式化保持关闭；没有因 mount 或测试文件失败格式化介质；
- [已完成] 取得目标板证据后移除 `rdx_runtime.c` 中的临时 SD0 诊断、`RDX_CFG_SD0_BRINGUP_DIAG_ENABLE` 及临时 FAT 写门控，RDX Runtime 恢复为只负责启停和装配。

阶段 A 不实现 RDX Backend/Service，不加入 Local Storage Ability，也不编译 APP 文件命令。`ensure_ready()` 属于阶段 B 的 RDX Storage Port 合同；第一版实现只查询和验证阶段 A 已建立的 JL 原生 mount，不以它为理由回头修改 JL 挂载链路。USB UAC/HID、BLE 在线录音、RTC、关机和 OTA 的跨功能回归属于相应功能验收及阶段 D 发布矩阵；若日志已存在与本次 SD0 增量无依赖关系的问题，不反向阻塞阶段 A。

## 14. 需要产品确认的决策

编码前必须用 APP、原理图和目标板事实冻结：

1. 当前 BR56 SD NAND 型号、实际 SDIO 引脚、供电控制和工作时钟；
2. 量产首次初始化是否允许自动格式化，格式化是否可由 APP 发起；
3. 文件目录、命名、SN、最大时长、最小剩余空间和列表排序；
4. RAW Opus 文件是否直接暴露 80 B 帧，metadata/marks 的 APP 编码；
5. STOP ACK 的准确语义及 Artifact 失败的独立通知；
6. BLE 断连后 Local 是否继续，若继续，自动封口、最大时长和重连同步规则；
7. Local 上传、删除、格式化与录音、提交、USB、OTA 的操作租约优先级；
8. WRITING 断电是否允许恢复到最后 checkpoint，还是必须隔离整个未完成文件；
9. SD 最坏写阻塞、队列 RAM、关机 deadline 和 APP ACK deadline；
10. 后续是否需要 USB MSD，以及 Host Eject/Restore 的完整所有权协议；
11. v1 是否接受“Local REQUIRED 失败即终止 Session、Artifact 进入 FAILED/QUARANTINED”的固定策略（默认按本文执行，不降级为仅在线）；
12. 运行时 session_id 与持久化 artifact_id/SN 的对外可见性、重启后列表和上传使用的稳定身份；
13. metadata snapshot 的 APP 编码、最大 marks 数量，以及 STOP cut/drain 的明确 deadline；
14. APP Golden Trace 是否要求兼容 `UXFILE.DAT`、旧文件字段、SN/命名和 legacy 列表语义；据此在 Native 与 Legacy UXFILE Adapter 中二选一；
15. BR56 试链接是否能只抽取 `rdx_uxfile.c.o`，以及允许的 legacy 依赖、任务/堆开销和退出顺序；若不能裁剪，是否接受完整 legacy stack，或改用 Native Backend；
16. Legacy UXFILE Adapter 的公开头文件、ABI/许可、Common/Legacy Port 参数和 `LEGACY_FILE_COMMITTED/FAILED` 语义；在这些内容冻结前，不得把 legacy 结果接入 Native Artifact Port。

在这些问题有 Golden Trace 或硬件证据之前，不能开启 RDX_ABILITY_LOCAL_STORAGE。

## 15. 最终决策摘要

> 平台采用“原生能力优先、必要改动最少、RDX 业务增量接入”：JL core 只初始化一次 dev_manager，并由原生 sd0 + FAT 链路完成 probe/mount；RDX 不实现第二套 SD 协议、设备管理或挂载流程。BR56 Adapter 只查询和复用现有 mount，并将 VFS/FAT 能力映射到 RDX Storage Port。RDX 静态库按 archive member 管理：`rdx_encryption.c.o` 可按既有合同复用，`rdx_uxfile.c.o` 仅能通过 Legacy UXFILE Adapter 复用，旧 Protocol/Queue/UART 成员默认禁止连带抽取。
>
> RDX 本地存储不是把参考工程的 fwrite() 接到当前录音 callback 上，而是 Record Engine 之下的第二个交付目的地。Recording Coordinator 负责编排会话、租约、STOP cut 和 completion；Composite Destination 将已验证的 V23 在线镜像与 Local Destination 分开；Local Destination 通过 Storage Port 进入单一 Storage Service。Artifact 拥有独立的提交/恢复生命周期，正常 STOP 与强制 ABORT 不共用路径，BLE Online 故障也不破坏 REQUIRED Local。Storage 后端必须在 JL FAT Native 与 Legacy UXFILE Adapter 中二选一：前者实现本文 A/B marker/index 合同，后者复用 `rdx_uxfile.c.o` 的 UXFILE/DAT/SN/文件业务但不创建第二套 worker/索引，也不能伪造前者的断电保证。
>
> Native 模式提交顺序固定为 `SEALED -> rename -> PUBLISHED -> index A/B -> INDEXED`，并为每个断电边界定义幂等恢复；Legacy 模式使用 UXFILE worker 已审计的 raw/DAT 保存顺序，不得宣称具备 Native 的 marker 保证。后端选择必须由 Product/Build profile 显式给出，公共配置不提供默认模式；阶段 A-C 只增量实现和验证平台闭环、Service、Artifact/兼容映射、文件业务及恢复合同，产品广播和 APP Wire 保持 Local Storage 关闭。只有开发门控归零、Capability/Readiness 检查、Golden Trace、目标板长稳和所选模式的断电矩阵全部通过后，才在 Product Compatibility Profile 中开启 RDX_ABILITY_LOCAL_STORAGE。
