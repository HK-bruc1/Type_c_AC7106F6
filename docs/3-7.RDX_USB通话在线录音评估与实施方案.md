> 文档状态：v0.3，分阶段实施中；阶段 1 代码与音频图已完成 clean build，硬件 PCM 证据待补
> 编写日期：2026-08-22
> 目标工程：AC710N / BR56 Type-C 有线耳机
> 参考工程：`t2616cc-firmware/`（AC701N / BR28）
> 前置文档：`docs/3-2.RDX在线录音业务移植评估与实施路线.md`、`docs/3-3.RDX录音基础设施架构优化方案.md`
> 本文范围：USB Audio 通话期间同时采集近端 MIC 与远端 PC Speaker，编码后通过现有 RDX BLE 在线发送给 APP
> 变更约束：评估、决策、实施记录和验收证据统一收束在本文；音频图只通过 JL 工具修改，不手改生成资源

## 1. 结论

**[推荐设计]** USB 通话录音不应启动现有 `ADC -> AGC -> Encoder -> AI_TX` 智能语音 Pipeline。它必须附着到已经运行的 USB 通话链路，在近端 `CVP/EQ` 后和远端 `PCSPK PlaySync` 后分别取 PCM，经独立 SRC 统一为 `16 kHz / mono / 16 bit`，再使用 JL 原生 Mixer 混成 mono，最后复用现有 `Encoder -> AI_TX -> RDX BLE` 在线发送路径。

**[已确认事实]** 目标工程已经实测证明：两个独立 ADC Pipeline 共享 PA3 时会重复设置 ADC 格式并破坏 USB MIC/CVP。USB MIC 当前已经持有最高优先级的 `audio_capture_lease`，所以通话录音必须“借用 USB 已有 PCM”，不能再申请一次采集租约，也不能再打开一条 ADC source。

**[已确认事实]** USB 近端和远端目前不在同一条顶层 Pipeline：`pc_mic` 使用 USB Audio Pipeline `0xDC8D`，`pc_spk` 被明确路由到媒体 Pipeline `0xD96F` 以保留 24-bit 播放。因此，仅在 `USB Audio.x6flow` 中增加 Mixer 不能自动拿到远端 PCM。

**[推荐设计]** 首版对 APP 保持已经验证的会议录音数据合同：`16 kHz / mono / 32 kbps / 20 ms / raw Opus`，每帧固定 80 B，仍由 `AI_TX` 进入现有 RDX Session、Destination 和 BLE 队列。首版将近端和远端混为 mono，不同时引入 stereo Opus、协议元数据和 APP 解码变化。

**[Spike 假设]** JL SDK 已包含 `mix_record_api`、保留录音 Pipeline `0x49EC`、`Zero Active`、`Switch`、`MIXER`、`SRC`、`Encoder` 等原生机制，可复用其“播放流分支受录音状态控制并汇入录音 Pipeline”的架构模式；但当前代码和生成资源尚不能证明 BR56 的原生 Mixer 能直接聚合两个不同顶层 Pipeline 的分支。这一能力必须作为第一项实机 Spike 验证。

**[推荐设计]** 实施路线按以下优先级推进：

1. 验证并优先复用 JL 原生 `mix_recorder` 跨流汇聚模式；
2. 若不支持跨 Pipeline 汇聚或会反压 USB 主链路，转入有界 `SinkDev/SourceDev` PCM Bridge，显式处理时钟、漂移、溢出和生命周期；
3. 暂不优先把 `pc_spk` 从 `0xD96F` 移回 `0xDC8D`。只有原生跨流和 Bridge 都被证据证明不可行，并经过单独评审后，才允许尝试组合图，避免把录音风险扩散到现有 24-bit 播放路径。

**[APP/硬件待验证]** 在 APP 通话场景 Golden Trace、mono 混录解码、USB 双向稳定性、静音策略和 2 小时耐久测试全部通过前，不得在 Ability 中发布 `RDX_ABILITY_CALL_RECORDING`。

## 2. 证据标签与范围

### 2.1 证据标签

本文所有技术判断使用以下标签：

| 标签 | 含义 |
| --- | --- |
| **[已确认事实]** | 可由当前目标代码、生成配置、既有实机记录或参考工程有效代码路径直接证明 |
| **[推荐设计]** | 本文建议冻结为目标实现的设计决策，尚未代表代码已完成 |
| **[Spike 假设]** | SDK 形态显示可行，但需要最小代码/流程图实验才能确认 |
| **[APP/硬件待验证]** | 编译或静态阅读不能得出结论，必须通过目标 APP 或 BR56 实机验证 |

### 2.2 目标

- **[推荐设计]** USB Speaker 和 USB MIC 都稳定运行时，APP 可显式发起“通话录音”。
- **[推荐设计]** 录音同时包含远端 PC 下行声音和近端经 CVP 处理的 MIC 声音。
- **[推荐设计]** 不影响 PC 侧正常听音、MIC 上行、CVP、HID、USB 枚举和已有 RDX BLE 传输。
- **[推荐设计]** 最大化复用 JL 原生音频节点，以及现有 RDX Engine、Session、Destination、Pause/Resume、Mark、帧队列和 BLE 发送能力。
- **[推荐设计]** 第一版保持现有 mono Opus 线上合同，后续可在明确 APP 合同后升级为 `L=near / R=far` stereo。

### 2.3 非目标

- **[推荐设计]** 本阶段不实现本地文件、SD/eMMC/Flash 存储或文件上传。
- **[推荐设计]** 本阶段不复制 BR28 私有 `EffectDev1/2/3`、`st_opus_enc` 或 RDX 业务直连 Sink 节点。
- **[推荐设计]** 本阶段不把 USB Speaker 活跃直接等同于“正在通话”，也不自动开始录音。
- **[推荐设计]** 本阶段不修改 USB 描述符，不要求 Host 固定为 16 kHz，也不牺牲现有 24-bit 播放能力来换取未经验证的快速接入。
- **[推荐设计]** 本阶段不承诺单边 USB stream 消失后继续用静音填充并保持录音；首版采取完整会话终止策略。

## 3. 术语与所有权边界

| 术语 | 统一含义 | 标签 |
| --- | --- | --- |
| 近端（near-end） | 设备本地 PA3 MIC 经 USB 通话 CVP/EQ 后的语音，不是新开的原始 ADC | **[推荐设计]** |
| 远端（far-end） | Host 经 USB Speaker Endpoint 下发、即将播放到 DAC 的数字 PCM，不是扬声器经 MIC 回采的声音 | **[推荐设计]** |
| USB 通话 | USB Speaker 和 USB MIC 双向流都稳定运行的候选业务状态；仅凭 USB 流本身不能区分会议软件、媒体播放或测试工具 | **[已确认事实]** |
| USB 通话在线录音 | RDX Wire scene `1`；由 APP 显式请求，同时记录 USB 近端与远端并在线交付；USB 双向流活跃只是可用条件，不等于用户已授权录音 | **[推荐设计]** |
| 在线会议录音 | RDX Wire scene `0`；以设备本地麦克风为唯一内容来源并在线交付，继续使用独立智能语音 ADC Pipeline，并与 USB MIC 互斥 | **[已确认事实]** |
| Tap | 在不改变主播放/采集出口语义的前提下，将节点输出分支给录音链路 | **[推荐设计]** |
| PCM Bridge | 在相互独立的 Near/Far 音频流与当前采集周期之间传递、对齐 PCM 的有界汇聚边界；它不负责协议发送，也不允许无限缓存 | **[推荐设计]** |
| Record Gate | START/PAUSE/RESUME/STOP 控制的录音分支开关，关闭时不影响 USB 主链路 | **[推荐设计]** |
| Capture Lease | 当前用于仲裁 ADC 采集所有权的 `audio_capture_lease` | **[已确认事实]** |
| Session | 一次 APP START 到最终 STOP/强制终止的业务会话；暂停和恢复不会创建新 Session | **[已确认事实]** |
| Capture Cycle | Session 中一段连续取得有效音频的采集周期；同一 Session 可因暂停、恢复或资源变化包含多个周期 | **[推荐设计]** |
| `capture_generation` | 单调标识同一 Session 内不同 Capture Cycle 的采集代次，用于拒绝旧 PCM 和旧编码帧；它不是 Session ID 或重试次数 | **[已确认事实]** |
| Capture Backend | 为指定录音场景提供编码音频的采集后端；Meeting 与 Call 使用不同 Backend，但共享 Session、Destination 和交付语义 | **[推荐设计]** |
| Source Lost | 当前场景必需的音频源关闭、重启、改变格式或持续无法提供有效内容；它不同于静音、短时欠载或 BLE 断连 | **[推荐设计]** |
| Destination | 消费录音帧并完成交付的业务对象；当前产品的必需目的地是在线 APP，不等同于 Capture Backend | **[已确认事实]** |

**[推荐设计]** 所有权规则冻结如下：

| 资源/对象 | 会议录音 | USB 通话录音 |
| --- | --- | --- |
| PA3 ADC / Capture Lease | RDX Engine 获取租约并打开独立 ADC Pipeline | USB MIC 已持有租约；RDX 只附着，禁止再次 acquire/open ADC |
| USB 主链路 | 不运行；若 USB 抢占则会议录音停止 | USB 子系统拥有，RDX 不得改变其格式或生命周期 |
| 录音 Tap/Gate/SRC/Mixer/Encoder | RDX Engine 拥有 | RDX Engine 拥有，但输入源生命周期受 USB 约束 |
| RDX Session/Destination/BLE 队列 | 复用 | 复用 |
| USB stream 重启/关闭 | 会议录音的资源抢占事件 | 通话录音的源失效事件，触发强制终止 |

## 4. 当前实现事实

### 4.1 当前 RDX 会议录音

**[已确认事实]** 当前目标链路为：

```text
PA3 ADC -> AGC -> Encoder(mono Opus) -> AI_TX -> RDX Engine
         -> Destination -> BLE TX queue -> RDX APP
```

**[已确认事实]** `rdx_record_defs.h` 已冻结参数：

| 参数 | 当前值 |
| --- | ---: |
| Sample Rate | 16000 Hz |
| Channels | 1 |
| Bit Rate | 32000 bps |
| Frame Duration | 20 ms |
| Opus Payload | 80 B/帧 |
| Warm-up | 前 10 帧丢弃 |
| Candidate Queue | 16 帧 |

**[已确认事实]** `rdx_record_audio_br56.c` 解析智能语音 Pipeline `0x5475`，从 ADC source 启动，并通过 `NODE_IOC_SET_ENC_FMT`、Encoder 私有格式和 `AI_TX` 回调固定上述格式。

**[已确认事实]** 当前 `rdx_mvp0_protocol.c` 只接受会议场景的简写和 scene `0` 命令，状态 ACK 也把 scene 固定为 `0`。当前 `rdx_integration_config.h` 的已实现 Ability 集合未包含 `RDX_ABILITY_CALL_RECORDING`。

### 4.2 当前 USB 近端路径

**[已确认事实]** 当前选中的 `TypeCEarphone` USB MIC 路径为：

```text
ADC -> CVP_V3 -> EQ -> PlaySync -> Vol_PcMic
    -> Channel Expander -> BitWidth Convert -> PCMIC
```

**[已确认事实]** `pc_mic_recoder_open()` 从 `pc_mic` 对应的 Pipeline `0xDC8D` 以 `NODE_UUID_ADC` 启动，设置 `STREAM_SCENE_PC_MIC` 后交给 UAC MIC Endpoint 读取。

**[已确认事实]** USB Host 可以重新选择 MIC 的采样率、声道和位宽；格式变化时 `uac_stream.c` 会重启 `pc_mic_recoder`。因此，录音分支不能假定 USB MIC 永远是 `16 kHz / mono`。

**[已确认事实]** USB MIC 使用名为 `usb_audio`、优先级 `0xff` 的 Capture Lease Client，并允许抢占优先级较低的会议录音 Client。它是 PA3 ADC 在 USB 场景下的唯一合法所有者。

### 4.3 当前 USB 远端路径

**[已确认事实]** 当前远端路径为：

```text
PCSPK -> Decoder -> PlaySync -> Vol_PcspkMusic
      -> EQ -> BitWidth Convert -> DAC
```

**[已确认事实]** `jlstream_event_handler.c` 中 `pc_spk` 没有返回 PC Audio Pipeline `0xDC8D`，而是明确返回媒体 Pipeline `0xD96F`，代码注释说明目的是让 PC Speaker 使用 24-bit 音频。

**[已确认事实]** `pc_spk_player_open()` 从 `NODE_UUID_PC_SPK` 解析该 Pipeline，并设置 `STREAM_SCENE_PC_SPK`。远端数据不经过 `pc_mic` 的 `0xDC8D` 顶层流。

### 4.4 已知冲突

**[已确认事实]** 既有实机记录显示，USB MIC/CVP 与第二条 RDX ADC Pipeline 并行时，共享 ADC 的采样格式会被后打开的 Pipeline 改写，并出现 CVP frame size 异常。

**[推荐设计]** 通话录音实现必须满足以下静态约束：

- 不调用 `rdx_record_audio_br56_open()` 的 ADC 会议路径；
- 不为通话录音 acquire 新 Capture Lease；
- 不创建第二个 `NODE_UUID_ADC` stream；
- 不修改 USB 主链路协商格式；
- 不以 MIC 声学回采代替远端数字 Tap。

## 5. JL 原生流程复用评估

### 5.1 SDK 已提供的能力

**[已确认事实]** SDK 中存在 `SDK/apps/earphone/audio/mix_record_api.c`。其入口通过名称 `mix_recorder` 取得保留 Pipeline UUID `0x49EC`，再从 `NODE_UUID_ZERO_ACTIVE` 打开 `file_recorder`。

**[已确认事实]** 原生 `mix_recorder` 的典型控制链包含以下概念：

```text
正在运行的播放/采集 Pipeline
    -> 分支或 Switch（由 get_mix_recorder_status 控制）
    -> 录音 Pipeline 0x49EC
    -> MIXER / SRC / Encoder
    -> WriteFile
```

**[已确认事实]** `jlstream_event_handler.c` 在 `TCFG_MIX_RECORD_ENABLE` 打开时，会把名为 `SW_Rec...` 的节点状态函数绑定到 `get_mix_recorder_status()`。`mix_recorder_stop()` 也明确要求先清录音 status，让 Switch 先关闭，再关闭文件，说明 Gate/Switch 是 JL 原生混合录音生命周期的一部分。

**[已确认事实]** 当前产品尚未启用这套能力：`TCFG_MIX_RECORD_ENABLE=0`，`TCFG_MIXER_NODE_ENABLE=0`，`TCFG_SWITCH_NODE_ENABLE=0`，`TCFG_SOUND_SPLITTER_NODE_ENABLE=0`；`SRC` 已启用。当前工程资源中也没有可被解析的 `0x49EC` 录音流程。

### 5.2 可以复用与不能直接复用的部分

| JL 原生部分 | 判断 | 标签 | 原因 |
| --- | --- | --- | --- |
| `Switch`/录音状态 Gate 模式 | 复用 | **[推荐设计]** | 可让 RDX 开关录音分支而不停止 USB 主链路 |
| `MIXER` 标准节点 | 优先复用 | **[Spike 假设]** | 可避免手写样本加法，但跨顶层 Pipeline 汇聚能力待确认 |
| `SRC` 标准节点 | 复用 | **[推荐设计]** | USB 两侧格式动态变化，编码前必须统一为 16 kHz mono |
| `Encoder` 标准节点 | 复用 | **[已确认事实]** | 当前会议录音 mono Opus 已通过 APP 实测 |
| `AI_TX` 标准节点 | 复用 | **[已确认事实]** | 当前已接入 RDX encoded-frame 回调 |
| Pipeline `0x49EC` | 保留为候选录音汇聚 Pipeline | **[推荐设计]** | 符合 SDK 命名和生命周期约定，需由 JL 工具创建实际流程 |
| `file_recorder`/`WriteFile` | 不复用业务层 | **[推荐设计]** | RDX 需求是在线 BLE，不是本地文件；文件系统会引入无关 RAM、Flash/SD 和异常路径 |
| `mix_record_api.c` 原样启用 | 不采用 | **[推荐设计]** | 它硬绑定文件创建、无返回值的 start/stop 接口和存储设备事件，不符合 RDX Engine 合同 |

**[推荐设计]** 正确复用方式不是调用当前 `mix_recorder_start()`，而是复用其 JLStream 组织模式，建立一个 RDX Call Capture Adapter：解析 `0x49EC`、注册 `AI_TX`、配置 Opus、控制 Gate，并把 open/close 结果返回给 RDX Engine。

### 5.3 必须先做的 JL 原生 Spike

**[Spike 假设]** 在不接 RDX 协议的最小固件中，建立两个受控 PCM 输入，分别模拟近端和远端，验证它们能否从 `0xDC8D` 与 `0xD96F` 的分支同时汇入 `0x49EC` Mixer。

**[APP/硬件待验证]** Spike 必须回答：

1. `Sound Splitter/Switch` 的支路能否连接到另一顶层 Pipeline 的 Mixer，还是只允许同 Pipeline 内连接；
2. 两个输入的驱动线程、帧长和时间戳不同，Mixer 是否会阻塞快支路或重复旧帧；
3. 某一路暂时断流时，Mixer 是补零、停流还是释放节点；
4. `SRC` 能否在 Host 16/44.1/48 kHz 和 16/24 bit 变化时正确重新协商；
5. Gate 关闭后 USB 主链路是否完全无音频抖动，重新打开是否出现旧 PCM；
6. `Encoder -> AI_TX` 是否仍稳定产生 20 ms、80 B mono Opus 帧。

**[推荐设计]** 第 1～5 项由阶段 2A 的 PCM Spike 验证，第 6 项由阶段 3 的编码闭环验证。若第 1 项失败，应立即停止在原生跨流图上继续堆叠节点，记录并回退失败实验后转入第 13 节的路线 C；不得由阶段 2A 自动进入路线 B。

## 6. BR28 参考工程结论

**[已确认事实]** BR28 参考 RDX 实现对通话场景使用 `MIC_DAC_TO_STERO_OPUS`。其产品语义是同时记录 MIC 与 DAC，下行和上行保持独立声道，并在 stereo 结果中约定 `L=MIC/near`、`R=DAC/far`。

**[已确认事实]** 参考工程通过私有 `EffectDev1/EffectDev2/SinkDev1` 和 `SourceDev1` 汇接 PCM，`EffectDev2` 直接调用私有 `st_opus_enc`，`SinkDev1` 又直接调用 RDX 数据处理。它不是 BR56 标准 Mixer + Encoder 的现成可移植实现。

**[推荐设计]** BR28 可复用的是以下业务语义：

- scene `0` 表示会议录音，scene `1` 表示通话录音；
- 通话录音必须同时包含近端与远端；
- 内部保留 `near/far` 身份，便于将来 stereo 使用 `L=near / R=far`；
- START、PAUSE、RESUME、STOP 的业务状态与音频流生命周期关联。

**[推荐设计]** 不复制以下实现：

- `translation_ear_recoder.c`；
- `EffectDev1/2/3` 与 `SourceDev1/SinkDev1` 的定制实现；
- 私有 `st_opus_enc`；
- RDX 业务直接写入音频节点；
- BR28 对场景和声道的隐式回退；
- 与 TWS、本地存储、LED、马达和提示音绑定的副作用。

## 7. 推荐音频架构

### 7.1 目标拓扑

**[推荐设计]** 首选目标拓扑如下：

```text
远端（Host -> device）

PCSPK -> Decoder -> PlaySync -> Tap Far -------------------------------+
                            |                                           |
                            +-> Vol_PcspkMusic -> EQ -> BWC -> DAC      |
                                                                        v
                                                  SRC -> mono 16k -> Gate Far --+
                                                                                 |
                                                                                 v
                                                                             JL MIXER
                                                                                 |
近端（device -> Host）                                                           v
                                                                               Gain
ADC -> CVP_V3 -> EQ -> Tap Near ----------------------------------+          / Limiter
                    |                                             |              |
                    +-> PlaySync -> Vol_PcMic -> Expander -> PCMIC|              v
                                                                  +-> SRC -> mono 16k
                                                                        -> Gate Near
                                                                                 |
                                                                                 v
                                                              Encoder(mono Opus 32 kbps)
                                                                                 |
                                                                               AI_TX
                                                                                 |
                                                    RDX Engine -> Destination -> BLE -> APP
```

**[推荐设计]** 图中的 `Gain/Limiter` 表示混音增益和饱和保护语义，不强制必须增加一个独立 Limiter 节点。若 JL Mixer 已支持输入增益与饱和，应优先使用原生能力。

### 7.2 Tap 位置

| 分支 | 推荐 Tap | 标签 | 选择理由 |
| --- | --- | --- | --- |
| 远端 | `PCSPK Decoder -> PlaySync` 之后、`Vol_PcspkMusic` 之前 | **[推荐设计]** | Tap 接近设备播放时钟域；避免用户调耳机音量后录音忽大忽小；不记录 DAC 后模拟失真 |
| 近端 | `CVP_V3 -> EQ` 之后、USB MIC `PlaySync/Vol_PcMic` 之前 | **[推荐设计]** | 复用已完成回声消除/降噪的通话语音；避免二次 ADC；在 USB 输出同步和声道扩展前保留清晰 mono |

**[APP/硬件待验证]** 远端 Tap 位于 PlaySync 后是否能与近端 CVP 输出保持可接受的相对时延，需要双音轨脉冲/回环测试确认。若同步偏差超过产品门限，应优先调整 Tap 或分支延时，不在 BLE 接收端猜测补偿。

**[推荐设计]** 禁止在 DAC 后通过 MIC 声学回采远端。该做法会重复记录远端声音，引入房间响应、啸叫、音量依赖和 CVP 残余回声。

### 7.3 首版声道与混音

**[推荐设计]** 第一版两个分支都转换为 `16 kHz / mono / 16 bit` 后再 Mixer：

```text
record_mono = saturate((near * gain_near) + (far * gain_far))
```

**[推荐设计]** 初始建议 `gain_near = -6 dB`、`gain_far = -6 dB`，为两路同相满幅叠加预留约 6 dB headroom；最终增益由双人对话听音、RMS/peak 和削顶统计调整，不能只凭公式量产。

**[推荐设计]** 内部接口和日志仍使用 `near`、`far` 两个身份，不把它们提前合并成无来源的 `pcm0/pcm1`。后续 stereo profile 才能稳定定义 `L=near / R=far`。

**[APP/硬件待验证]** 近端 CVP 输出与远端数字 PCM 的响度、残余回声和双讲清晰度必须在 Teams/Zoom/腾讯会议等真实软件下验收。

## 8. 时钟、SRC、缓冲与溢出

### 8.1 时钟基准

**[已确认事实]** USB MIC 和 Speaker 的 Host 格式及启停可以独立变化，且当前近端和远端位于不同顶层 Pipeline。两路 PCM 的调度周期和缓存水位不能假定完全一致。

**[推荐设计]** 录音输出时间轴以 16 kHz Encoder 的 20 ms 帧为唯一时间基准；每个输出周期需要 320 个 mono sample。Near/Far 各自先进入短有界缓冲，再由各自 SRC 供给 Mixer。

**[推荐设计]** 两路都应在接近各自 USB 同步节点之后 Tap。若仍存在长期采样漂移，使用 JL SRC 的动态比率/同步能力消化，不允许通过不断丢整帧维持水位。

### 8.2 缓冲边界

**[推荐设计]** 每路 PCM Bridge 或汇聚端必须使用固定容量环形缓冲，不允许在音频回调中动态分配。初始 Spike 可按每路 40～80 ms 设计，量产值依据实测调度抖动收敛。

**[推荐设计]** 必须分别统计：

- `near_pcm_in_samples`、`far_pcm_in_samples`；
- `near_src_out_samples`、`far_src_out_samples`；
- `near_underflow`、`far_underflow`；
- `near_overflow_drop_samples`、`far_overflow_drop_samples`；
- `mixer_out_frames`、`encoder_out_frames`；
- 当前/峰值缓冲水位；
- 两路估算 ppm 和累计相位差。

### 8.3 欠载与溢出策略

**[推荐设计]** 短时欠载允许对缺失的一路补零一个编码周期，同时增加计数；连续欠载达到明确门限时，认定 source lost 并终止通话录音。首版建议门限为 100 ms，最终值由实机 Spike 冻结。

**[推荐设计]** 溢出时丢弃最旧 PCM，使实时录音尽快回到当前时刻，并记录丢弃样本数；不允许覆盖未消费内存或让 USB 主链路反压卡顿。

**[推荐设计]** USB 主链路优先级高于录音。录音 Mixer、Encoder 或 BLE 拥塞只能丢弃/终止录音，不能阻塞 `PCSPK -> DAC` 或 `ADC/CVP -> PCMIC`。

**[APP/硬件待验证]** 上述 100 ms、40～80 ms 都是首轮 Spike 参数，不是量产结论。

## 9. RDX Engine 与资源模型调整

### 9.1 场景化 Audio Backend

**[推荐设计]** 将 Engine 的音频入口从“固定打开会议 ADC”演进为场景化 Backend：

```text
RDX_RECORD_SCENE_MEETING
    -> meeting backend
    -> acquire Capture Lease
    -> open ADC/AGC/Encoder/AI_TX

RDX_RECORD_SCENE_USB_CALL
    -> usb-call backend
    -> validate PCSPK + PCMIC stable
    -> attach Near/Far taps
    -> open Gate/SRC/Mixer/Encoder/AI_TX
    -> never acquire/open ADC
```

**[推荐设计]** Backend 对 Engine 至少提供 `probe/open/pause/resume/close/get_format`，并使用现有 frame callback 上交编码帧。Engine 继续拥有 Session、Controller、Destination、状态迁移和异常终止。

### 9.2 START 条件

**[推荐设计]** 通话录音 START 必须同时满足：

- APP 显式请求 scene `1`；
- RDX 已完成 AppKey/Bound/加密/CCC/Payload 门控；
- USB Speaker 和 USB MIC 都处于稳定 open 状态；
- 两路实际格式已知，且 SRC/Mixer/Encoder 可完成协商；
- 没有另一个录音 Session 或迁移态；
- RDX Destination 已 attach，固定队列已就绪。

**[推荐设计]** “USB 双向活跃”只用于 START 前置校验，不用于推断录音 scene，也不自动触发录音。

**[APP/硬件待验证]** 稳定 open 的定义建议为两路均收到有效 PCM 且格式在至少 2～3 个调度周期内未变化；具体周期必须由 USB 日志和实机抖动冻结。

### 9.3 运行期事件

| 事件 | 首版处理 | 标签 |
| --- | --- | --- |
| APP STOP | 关 Gate，阻止新帧，排空/丢弃尾帧，关闭录音 Backend，USB 继续运行 | **[推荐设计]** |
| APP PAUSE | 只关闭录音 Gate/Encoder 输入，保留 USB 主链路与 Session | **[推荐设计]** |
| APP RESUME | 清空旧 PCM，递增 `capture_generation`，重新同步两路并开 Gate | **[推荐设计]** |
| Speaker 或 MIC close | 强制终止通话录音，不继续单边录音 | **[推荐设计]** |
| USB 格式重协商/recorder restart | 强制终止当前通话录音；新格式稳定后等待 APP 新 START | **[推荐设计]** |
| USB 拔出/模式退出 | 强制终止，清理 Tap/Gate/队列，不发送旧帧 | **[推荐设计]** |
| BLE 断连/CCC off | 沿用当前在线录音强制停止语义 | **[已确认事实]** |
| PCM 连续欠载/Mixer fault/Encoder fault | 强制终止并上报失败原因 | **[推荐设计]** |

**[推荐设计]** Pause 不释放 USB 的 Capture Lease，也不关闭 `pc_mic_recoder` 或 `pc_spk_player`。Resume 必须创建新的 `capture_generation`，防止暂停前的 PCM 或 Opus 候选帧进入恢复后的时间轴。

### 9.4 生命周期顺序

**[推荐设计]** START 顺序：

```text
validate scene/link/USB formats
    -> attach Destination
    -> create/configure call Backend with Gate closed
    -> clear PCM and encoded queues
    -> wait near/far ready
    -> start Encoder/AI_TX
    -> open Gates
    -> receive first valid encoded frame
    -> send START success ACK
    -> allow stream packets
```

**[推荐设计]** STOP/强制终止顺序：

```text
close frame gate
    -> close near/far record Gates
    -> stop Encoder/AI_TX/Mixer/SRC
    -> cancel queued old-generation frames
    -> detach Destination
    -> emit final state/cause
    -> leave USB main streams untouched
```

## 10. Wire 合同与 Ability 演进

### 10.1 场景命令

**[已确认事实]** 参考工程的协议定义为 scene `0=会议`、scene `1=通话`；目标工程当前 parser 只接受会议 scene `0`，且状态 ACK 中 scene 固定为 `0`。

**[推荐设计]** 通话录音必须只由明确的 scene `1` 命令进入。按当前命令形态，候选 START 为 `*APP#record#1#1#1#`，但该字符串在目标 APP Golden Trace 确认前不得冻结为量产合同。

**[APP/硬件待验证]** 必须从目标 APP 抓取并确认以下内容：

- 通话 START/STOP/PAUSE/RESUME 的完整字节串；
- scene、sample-rate-format、record-mode 字段含义；
- 通话 Ability 打开后 APP 页面和命令行为；
- APP 是否接受 scene `1` + mono Opus；
- APP 是否根据 scene 强制按 stereo 拆声道；
- START 失败和运行期 USB source lost 的期望状态 ACK。

### 10.2 第一版线上格式

**[推荐设计]** 第一版仍使用：

```text
16 kHz / mono / 32 kbps / 20 ms / raw Opus
payload = 80 B
packet  = *DEV#stream#80#80# + 80 B payload
```

**[已确认事实]** 该 mono 合同已在会议录音中由同一 APP 实测清晰，BLE 队列、98 B Notify、DLE 和 2M PHY 也已有验证基础。

**[APP/硬件待验证]** 会议场景接受 mono 不等于通话 scene `1` 一定接受 mono。若 APP 对通话强制 stereo，则必须建立独立的 `CALL_V2_STEREO` profile，而不是悄悄复用 `MEETING_V1` 的 format id。

### 10.3 stereo 后续演进

**[推荐设计]** stereo 只作为第二阶段候选：`L=near / R=far`，16 kHz、20 ms。开始实现前必须先确认 APP TOC/声道语义、目标码率和最大帧长。

**[已确认事实]** Opus stereo 即使仍配置为 32 kbps、平均帧可能仍接近 80 B，TOC stereo 位、解码声道数和内容语义已经改变，因此不能以“包长没变”判断兼容。

**[推荐设计]** stereo profile 需要新的 format id、独立最大帧边界、APP Golden Trace、离线双声道解码和左右声道串扰验收。

### 10.4 Ability 发布门槛

**[已确认事实]** `RDX_ABILITY_CALL_RECORDING` 常量已经存在，但目标 `RDX_CFG_IMPLEMENTED_ABILITY` 尚未包含它。

**[推荐设计]** Ability 发布顺序：

1. 先在内部构建完成无 Ability 的音频 Spike；
2. 完成目标 APP scene `1` Golden Trace；
3. 完成 mono call profile 和异常路径验收；
4. 增加编译期 `RDX_CFG_CALL_RECORDING_ENABLE` 及依赖检查；
5. 最后将 `RDX_ABILITY_CALL_RECORDING` 加入已实现 Ability。

**[推荐设计]** 不允许先广播 Ability 再让 APP 试错，也不允许通话能力失败时静默降级为会议录音。

**[推荐设计]** 内部 PCM Spike 和受控联调使用不改变外部广播合同的调试门控。若开发工作区提前把 `RDX_ABILITY_CALL_RECORDING` 置入产品 Ability，而 `RDX_CFG_IMPLEMENTED_ABILITY` 和真实业务仍未实现，该状态只是不一致的开发中间态，必须在进入 Spike 构建前撤销或改为内部门控。

## 11. 隐私、静音与音量策略

### 11.1 MIC 静音

**[已确认事实]** 推荐近端 Tap 位于 `Vol_PcMic` 之前。该位置能得到稳定的 CVP mono，但可能绕过 UAC MIC mute/volume 的最终效果。

**[APP/硬件待验证]** 产品必须明确选择以下语义之一，不能由实现偶然决定：

| 策略 | 录音行为 | 影响 |
| --- | --- | --- |
| A：服从 UAC MIC mute | Host 将 MIC mute 后，近端录音也静音 | 隐私直观，但录音内容受 Host 控制 |
| B：录音独立于 UAC MIC mute | Host 听不到近端时，RDX 仍可录近端 | 录音连续，但必须有清晰授权/提示，隐私风险高 |

**[推荐设计]** 默认推荐策略 A。若产品明确选择 B，必须补充用户可见的录音状态、法规/隐私评审和硬件按键静音语义测试。

### 11.2 Speaker 静音与音量

**[推荐设计]** 远端 Tap 位于播放音量之前，所以用户把耳机听音音量调低时，录音仍保持远端原始数字响度；这符合“记录通话内容”而不是“记录耳朵实际声压”的目标。

**[APP/硬件待验证]** UAC Speaker mute 时是否仍记录远端需要产品确认。默认建议 Speaker mute 只影响 DAC，不影响远端录音；若法律或产品定义要求静音即不录，则 Gate 必须显式订阅 mute 状态。

### 11.3 授权与可见状态

**[推荐设计]** 通话录音仍必须经过现有 RDX 绑定、加密和 CCC 门控。USB 枚举或通话开始本身不构成录音授权。

**[推荐设计]** 录音的开始、暂停、恢复和停止应保持现有 APP 状态可见性。任何 USB source lost 导致的强制停止都必须让 APP 最终回到 stopped，而不是只在设备本地静默关闭。

## 12. 可观测性与诊断

**[推荐设计]** 每次 START 打印一条不含音频内容的结构化摘要：

```text
[RDX][CALL] start request=<id> session=<id> capture=<id>
            near=<sr/ch/bit> far=<sr/ch/bit>
            out=16000/1/16 opus=32000/20ms scene=1
```

**[推荐设计]** 运行期每 5～10 s 限频打印：

- near/far 输入样本数和当前格式；
- 两路 cbuf 当前/峰值水位；
- SRC 输出和估算漂移；
- Mixer 输出帧、peak、clipping count；
- Opus produced/enqueued/sent/drop；
- BLE 队列水位和 send fail；
- 当前 USB Speaker/MIC open、mute、format generation；
- heap、物理内存、最大连续块和 CPU 峰值。

**[推荐设计]** 每次 STOP 必须打印可对账摘要和唯一 cause，例如：`user_stop`、`usb_spk_lost`、`usb_mic_lost`、`usb_format_restart`、`pcm_underflow`、`pcm_overflow`、`encoder_fault`、`link_lost`、`ccc_off`。

**[推荐设计]** 调试版提供短时 PCM 抓取点：Near Tap 后、Far Tap 后、Mixer 后。抓取只能由编译开关启用，使用固定时长，并在量产构建中关闭。

## 13. 备选路线与决策矩阵

| 路线 | 说明 | 对现有 USB 影响 | 复用 JL 程度 | 主要风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A：JL 原生跨流 `mix_recorder` | 在 `0xDC8D`、`0xD96F` 增加 Tap/Gate，汇入 `0x49EC` Mixer/Encoder/AI_TX | 低到中 | 最高 | 跨顶层 Pipeline 汇聚能力未确认 | **[推荐设计] 首选，先 Spike** |
| B：把 PCSPK 移回 `0xDC8D` 组合图 | 近端、远端和录音分支置于同一 USB Audio Pipeline | 高 | 高 | 可能回退 24-bit 播放；流程协商和共存策略变化大 | **[推荐设计] 保留；A/C 均失败后单独评审** |
| C：有界 `SinkDev/SourceDev` PCM Bridge | 两条现有流把 PCM 写入录音汇聚层，由 `0x49EC` 读取 | 中 | 中 | 需要处理锁、生命周期、时钟漂移和溢出 | **[推荐设计] A 失败后的首选 fallback** |
| D：再次启动智能语音 ADC | 保持会议流程并用 MIC 回采远端 | 高 | 低 | 已知破坏 CVP；远端质量差且重复回声 | **[已确认事实] 禁止** |
| E：直接移植 BR28 私有节点 | 复制 `EffectDev/SourceDev/SinkDev/st_opus_enc` | 高 | 低 | 芯片/SDK差异、业务耦合、维护成本高 | **[推荐设计] 不采用** |
| F：只录 PCMIC Endpoint 输出 | 只记录近端上行 | 低 | 高 | 完全缺少远端，不满足需求 | **[推荐设计] 不采用** |

**[推荐设计]** 路线 A 的完整退出门槛是阶段 2A 通过第 5.3 节第 1～5 项，并在阶段 3 通过第 6 项。若只证明 Mixer 能混音但会阻塞 USB 主链路，也应判为失败。

**[推荐设计]** 路线 A 失败后必须保留流程截图、串口日志、Near/Far/Mix 计数和唯一失败原因，回退跨流 Spike，再进入路线 C；不允许同时保留两套半成品数据面。

**[推荐设计]** 路线 C 必须证明 Near/Far push 不阻塞 USB、缓冲水位可对账、20 ms 输出不被某一路回调绑死、长期漂移有界、旧 generation 不会泄漏。若路线 C 也失败，停止功能扩展并形成专项分析，不自动进入路线 B。

**[APP/硬件待验证]** 路线 B 启用前必须单独评审，并回归 24-bit PC Speaker、16/24 bit 切换、44.1/48 kHz、DAC 音质和 CPU/RAM，不能把“能出声”视为等价替代。

## 14. 分阶段实施计划与证据台账

所有阶段都必须遵守第 4～12 节的架构和数据合同。每个阶段只解决一个不确定性，达到退出条件后才进入下一阶段；编译通过不能替代 PCM、USB、APP 或硬件证据。

### 阶段 0：冻结 APP 合同与 USB 基线

**[推荐设计]** 工作项：

1. 使用目标 APP 和支持通话录音的参考固件抓取 scene `1` START/STOP/PAUSE/RESUME Golden Trace；
2. 记录 Ability、状态 ACK、record mode、format、stream header 和异常后的最终状态；
3. 确认 APP 是否接受 scene `1` + mono raw Opus；
4. 冻结 source lost、重复命令、BLE 断连和 CCC off 的 APP 期望；
5. 记录当前 USB Speaker/MIC 格式矩阵、RAM、CPU 和 10 分钟双向音频基线；
6. 冻结 Near/Far PCM 抓取方法和测试素材；
7. 清理“外部 Call Recording Ability 已置位、实际实现仍关闭”的中间态，阶段 1～5 只使用内部 Spike 门控。

**[APP/硬件待验证]** 退出条件：Wire 合同无猜测字段，mono/stereo 结论明确，当前 USB 基线无未解释掉音或 CVP 异常。若 APP 强制 stereo，先更新第 10.3 节 Profile 决策再进入实现。

### 阶段 1：USB 状态提供者与被动 Tap

**[推荐设计]** 工作项：

1. 提供只读 Speaker/MIC open、格式和 format generation；
2. 使用 JL 工具在第 7.2 节位置加入 Splitter/Tap，录音 Gate 默认关闭；
3. 调试构建分别抓取固定时长 Near-only、Far-only PCM；
4. 记录两路采样率、声道、位宽、帧长、回调任务和调度周期；
5. 验证 mute/volume 对 Tap 数据的实际影响，但不在本阶段替产品冻结隐私策略。

**[已确认事实，2026-08-22 实施记录]** 本阶段已经完成以下代码和静态资源闭环：

1. `uac_stream` 已提供 Speaker/MIC 的 `interface_open`、`stream_active`、采样率、声道、位宽和 `format_generation` 只读快照；Speaker 以真实 PCM 到达作为 active，MIC 以采集租约和 PC MIC recorder 成功打开作为 active；
2. USB Audio `0xDC8D` 的 `TypeCEarphone` 近端图已在 `EQ47` 后、`播放同步/config397398` 前加入 `Sound Splitter -> Switch(RDX_NearTap) -> Sink_Dev0` 旁路；
3. 媒体 `0xD96F` 的 `TypeCEarphone` 远端图已在 `播放同步/9B3B3` 后、`Vol_PcspkMusic` 前加入 `Sound Splitter -> Switch(RDX_FarTap) -> Sink_Dev1` 旁路；
4. `usb_call_audio_tap` 提供默认关闭的 Near/Far Gate、流格式代次、帧/字节/丢弃统计和单消费者接口；消费者运行在音频上下文，只允许向有界缓冲快速复制，Tap 层不依赖 RDX Protocol、不编码、不发送 BLE；
5. `Sink_Dev0/1` 分别只接 Near/Far PCM；节点启动/停止同步更新 Tap 格式和代次，数据回调不申请 ADC、不改变 USB 生命周期；
6. JL 工具生成配置已经启用 `Switch`、`Sound Splitter`、`Sink_Dev0` 和 `Sink_Dev1`，位宽分别覆盖近端 16-bit 与远端 32-bit；
7. 变更节点开关后已执行 `winmk.bat clean` 和 `winmk.bat all`。新增 Tap、两只 Sink 节点及 JL 标准 Splitter/Switch 均实际进入编译/链接，固件完成打包并下载到在线目标板；该结果只证明构建闭环，不等价于 PCM、USB 或音质硬件验证。

**[APP/硬件待验证]** 当前 Gate 默认关闭且尚未注册 Bridge 消费者。仍需通过受控测试入口分别打开 Near/Far Gate，采集格式和帧统计，并完成本阶段第 3～5 项及退出条件；在取得这些证据前，阶段 1 保持“进行中”。

**[APP/硬件待验证]** 退出条件：Near/Far 来源正确且清晰，Gate 关闭时无分支数据，Gate 开关和抓取不影响 USB 主链路，关键 Host 格式可被准确报告。

**[推荐设计]** 回退点：关闭或删除调试 Tap 即恢复阶段 0 基线，不把未验证分支带入量产资源。

### 阶段 2A：JL 原生跨 Pipeline PCM Spike

**[推荐设计]** 进入条件：阶段 1 的 Near/Far 独立 Tap 均通过。

**[推荐设计]** 工作项：

1. 使用 JL 工具创建临时 `0x49EC` PCM 汇聚流程，不接 Encoder、AI_TX 和 RDX Protocol；
2. 两路经 Channel/BWC/SRC 统一为 `16 kHz / mono / 16 bit` 后进入 Mixer；
3. 在 Near、Far、Mix 三处增加受控观察点；
4. 验证单边、双讲、短时断流、Gate open/close 和第 15.2 节 Host 格式矩阵；
5. 连续运行至少 10 分钟，记录样本计数、水位、Mixer 输出和 USB 主路统计。

**[APP/硬件待验证]** 退出条件：第 5.3 节第 1～5 项全部通过，USB 双向音频不受影响，无持续欠载、漂移失控或未解释丢样本。本阶段不要求验证 Encoder/AI_TX。

**[推荐设计]** 分支结果：通过则冻结路线 A 的 PCM 汇聚路径并跳过阶段 2C；失败则记录证据、回退跨流连接并进入阶段 2C。

### 阶段 2C：有界 PCM Bridge Spike

**[推荐设计]** 进入条件：路线 A 有明确失败证据，或 JL 工具静态证明无法跨顶层 Pipeline 汇聚。

**[推荐设计]** 工作项：

1. 定义只处理 PCM 的通用 Bridge 和非阻塞 Near/Far push；
2. 每路使用固定容量环形缓冲，初始按 40～80 ms 验证；
3. 输入优先由 JL 标准节点归一化为 `16 kHz / mono / 16 bit`；
4. Bridge 校验 `capture_generation` 和 USB format generation，拒绝旧代次输入；
5. 按 20 ms、320 sample 对齐混音，执行第 8 节欠载、溢出和漂移策略；
6. STOP、PAUSE、Resume 和 USB restart 时验证 Gate、缓冲和旧 PCM 清理；
7. Bridge 故障只上报 Backend，不直接改变 Engine 或发送 BLE。

**[APP/硬件待验证]** 退出条件：Near/Far push 不阻塞 USB，水位和丢弃可对账，长期漂移有界，10 分钟 Near-only/Far-only/双讲混音稳定，旧 generation 为零。

**[推荐设计]** 失败处理：停止功能扩展并形成专项分析；不得用无界扩容掩盖漂移，也不得自动进入路线 B。

### 阶段 3：标准 Encoder 与 AI_TX 闭环

**[推荐设计]** 进入条件：路线 A 或 C 只能有一条 PCM 汇聚路径通过并被冻结。

**[推荐设计]** 工作项：

1. 建立 USB Call Capture Adapter，封装 `probe/open/pause/resume/close/get_format`；
2. 将 mono PCM 接入 BR56 标准 Encoder 和 AI_TX，不移植私有 `st_opus_enc`；
3. 固定候选格式 `16 kHz / mono / 32 kbps / 20 ms`，验证每帧 80 B 和预热规则；
4. 主机离线重组 raw Opus，对比 Near-only、Far-only 和双讲；
5. Gate open/close 100 次，检查内存、资源、旧帧和 USB 主路。

**[APP/硬件待验证]** 退出条件：第 5.3 节第 6 项通过，Opus 可正确离线解码，`produced/enqueued/drop` 完整对账，100 次循环无泄漏、爆音或旧帧，会议录音完整回归。若阶段 2A 选择了路线 A，至此第 5.3 节六项才算全部通过。

### 阶段 4：Record Engine 场景化 Backend

**[推荐设计]** 工作项：

1. 增加 call scene/format/backend，不改变 `MEETING_V1` 含义；
2. 将固定会议 Adapter 演进为 Backend 分发，Engine 不依赖具体 Pipeline UUID；
3. Call Backend START 前校验 Speaker/MIC 稳定且格式已知，且不申请 Capture Lease；
4. Pause 只关闭录音 Gate/编码输入，Resume 清队列并递增 `capture_generation`；
5. source lost、format restart、Bridge/Mixer/Encoder fault 通过可信 system event 强制终止；
6. 复用 Session、Destination、candidate queue、TX Scheduler、Mark 和 BLE 门控。

**[APP/硬件待验证]** 退出条件：内部测试入口可明确选择 Meeting/Call 且二者不能并发；Call start/stop 不改变 USB 主路；强制终止有唯一 cause；会议录音回归通过。

### 阶段 5：scene `1` 协议与目标 APP 联调

**[推荐设计]** 进入条件：阶段 0 Golden Trace 和阶段 4 内部闭环均通过；Call Recording Ability 仍保持关闭，仅使用受控联调构建。

**[推荐设计]** 工作项：

1. Parser 接受已冻结的 scene `1` START/STOP/PAUSE/RESUME；
2. 状态 ACK 使用真实 scene、format 和 record mode；
3. START success 等待 Near/Far、Encoder、AI_TX 和首个有效候选帧就绪；
4. 验证 source lost、BLE 断连、CCC off、重复命令、USB restart 和格式切换；
5. 若 APP 拒绝 mono，停止本阶段并建立独立 stereo Profile，不修改 `MEETING_V1` 冒充兼容。

**[APP/硬件待验证]** 退出条件：APP 行为与 Golden Trace 一致，START/STOP 100 次、Pause/Resume 50 次通过，USB restart 后无旧 Session 自动恢复，会议 scene `0` 回归通过。

### 阶段 6：Ability、配置与量产收敛

**[推荐设计]** 工作项：

1. 增加 `RDX_CFG_CALL_RECORDING_ENABLE` 和完整编译期依赖，保证 source-selection 一致；
2. 完成第 15 节全矩阵、两小时长稳及 RDX/Call ON/OFF clean build；
3. 对比 Map、heap、物理内存、最大连续块、CPU 和功耗；
4. 最后将 `RDX_ABILITY_CALL_RECORDING` 加入已实现 Ability；
5. 使用 JL 工具保存、导出并记录 `.x6flow`、`stream.bin` 和固件版本。

**[APP/硬件待验证]** 退出条件：量产 Ability、APP UI、Wire 命令、真实音频能力和构建配置完全一致。

| 风险/问题 | 等级 | 当前结论 | 标签 |
| --- | --- | --- | --- |

## 17. 最终决策摘要

| 决策 | 冻结结果 | 标签 |
| --- | --- | --- |
| 首版目标 | USB 双向稳定时，近端 + 远端混为 mono 在线发送 | **[推荐设计]** |
| ADC 策略 | 附着 USB 已有近端 PCM，绝不再开 ADC/申请第二份租约 | **[推荐设计]** |
| Near Tap | CVP/EQ 后，PCMIC PlaySync/Vol/Expander 前 | **[推荐设计]** |
| Far Tap | PCSPK PlaySync 后，播放 Vol/EQ 前 | **[推荐设计]** |
| 编码合同 | 16 kHz / mono / 32 kbps / 20 ms / raw Opus / 80 B | **[推荐设计]** |
| JL 复用 | 复用 Gate/Switch、SRC、Mixer、Encoder、AI_TX 和 `0x49EC` 组织模式 | **[推荐设计]** |
| JL 文件录音 | 不复用 `file_recorder`/WriteFile 业务层 | **[推荐设计]** |
| 实施路线 | A 原生跨流 -> C 有界 PCM Bridge；B 合并 Pipeline 仅保留评审 | **[推荐设计]** |
| 场景触发 | APP 显式 scene `1`；USB 活跃只做前置校验 | **[推荐设计]** |
| 源失效 | 任一路关闭、重启、改格式或 USB 拔出即终止当前录音 | **[推荐设计]** |
| Pause/Resume | USB 不停；Gate 暂停；Resume 新建 `capture_generation` | **[推荐设计]** |
| Ability | APP Golden Trace 和全部实机验收通过后再发布 Call Recording | **[推荐设计]** |
| stereo | 后续独立 profile，语义固定 `L=near / R=far` | **[推荐设计]** |

**[推荐设计]** 下一步不是直接改完整业务，而是依次完成“阶段 0 APP 合同与基线 -> 阶段 1 被动 Tap -> 阶段 2A JL 原生跨 Pipeline Spike”。只有这些证据才能决定 mono 是否被 APP 接受、Tap 是否无侵入，以及 BR56 能否复用原生混合录音路径；在此之前不得发布 Ability 或提交完整通话录音业务。
