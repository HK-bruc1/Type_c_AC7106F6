## 1. 评估结论

RDX 在线会议录音闭环已通过。最终有效链路为 `PA3 ADC mono -> AGC -> Encoder mono -> AI_TX -> RDX BLE`，编码参数为 `16 kHz / mono / 32 kbps / 20 ms / raw Opus`。编码帧仍稳定为 80 B，完整 Notify 仍为 98 B，目标 APP 能进入录音状态、连续接收并清晰播放。此前按参考工程静态路径建立的 stereo 兼容假设已被目标工程实测修正：在 BR56 标准节点中加入 `Channel Expander` 做 mono 到 stereo 扩展会导致 Opus 解码波形失真；移除该节点并让 Encoder 原生接收 mono 后，声音恢复清晰。

USB MIC/Speaker/CVP 与第二条 ADC Pipeline 并发时会改变共享 ADC 格式并触发 CVP frame size 异常，且最低 RAM 只有约 20～22 KB；首版产品需求不包含该并发场景，因此不重构共同采集架构，会议录音采用独占采集链路。

推荐路线是：

1. 第一阶段只实现“在线会议录音”，不带本地文件、离线录音、通话录音、闪记和录音打标；
2. 目标 APP 不修改；以参考工程成功在线会议录音 Golden Trace 的实际线上行为作为兼容基线，不复制未启用分支、注释猜测和已知缺陷；
3. 首版目标工程冻结为 `16 kHz / mono / 32 kbps / 20 ms / raw Opus`；APP 已证明不要求参考工程的 stereo Opus TOC，不能再为“静态参数看齐”引入未经听音验证的声道扩展；
4. 一帧 Opus 为 80 B，真实头为 18 B `*DEV#stream#80#80#`，完整 Notify 为 98 B；首版一帧一 Notify，不新增私有分片；
5. 复用已验证的 `ai_voice` 最小 Pipeline；仅在 USB MIC/Speaker 均未运行时允许 START，USB 只保持枚举，不支持与会议录音并行；
6. 实测低吞吐连接参数无法承载 50 帧/秒；目标 Type-C 产品不要求 BLE 低功耗，固定请求 `{6,6,0,600}`，并保留 4096 B cbuf 与 16 帧固定补偿队列吸收短暂抖动；
7. 在线录音稳定后再补暂停/恢复，最后才决定是否正式打开 `Record Pause/Resume` Ability。

截至 2026-08-11，第一阶段 APP 链路验证已经完成：

- 参考成功日志已确认广播协议版本为 `0x17`（V23），START/STOP 状态 ACK 均为 24 B V23 格式；
- 参考工程的命令、V23 状态 ACK、stream 封装和前 10 帧预热行为已冻结；
- JL 工具 4.11.0 的最小 `ai_voice` 分组已改为 `ADC -> AGC -> Encoder -> AI_TX`，Encoder 为 mono；
- APP 已能解析 98 B Notify、重建 raw Opus、完成 START/STOP，并确认最终声音清晰；
- BLE 侧 `send_fail=0 / invalid=0 / drop=0`，DLE、2M PHY 和高性能连接参数已经通过；
- ADC、AGC 和 Opus 分段抓取已把历史失真定位到 `Channel Expander -> stereo Encoder` 边界，详见 11.6 节。

因此，本阶段结论是“独立在线会议录音最小闭环已实测通过”；后续工作是多轮稳定性、长时间录音和诊断信息收敛，USB 音频并发明确不属于首版验收范围。

## 2. 本次范围

### 2.1 第一阶段目标

第一阶段建立最小在线录音闭环：

```text
APP 完成 AppKey
    -> 下发开始录音
    -> 设备打开 BR56 RDX 录音流
    -> ADC PCM 经 Opus 编码
    -> RDX 音频包经 BLE Notify 连续上报
    -> APP 下发停止录音
    -> 设备关闭音频流并上报最终状态
```

首批业务范围：

- 会议录音场景；
- APP 主动开始和停止；
- 开始失败、重复命令、断连和发送拥塞处理；
- 录音状态查询/上报；
- Opus 在线音频上报；
- RDX OFF 构建和运行行为回归；
- USB Speaker、USB MIC/CVP、HID 与 RDX BLE 共存回归。

### 2.2 第二阶段候选

- 暂停和恢复；
- 暂停期间的资源释放和时间语义；
- 录音最长时长保护；
- APP 重连后的状态一致性；
- 可选的单 MIC DNS、EQ 或增益处理；
- 在协议确认后正式打开 `RDX_ABILITY_RECORD_PAUSE_RESUME`。

### 2.3 明确不在首批移植

- 离线录音和本地存储；
- `.dat`、Opus 文件、文件列表和文件上传；
- eMMC/SD、SPI 和 Wi-Fi；
- 通话录音、DAC 下行混录和双声道 MIC+DAC；
- TWS 主从同步、角色切换和双耳录音；
- 设备按键触发录音；
- LED、马达和提示音业务；
- 录音打标、闪记和对应 VM；
- 参考工程的录音异常重启恢复标志；
- MIC 增益设置/查询协议；
- OTA、文件传输和录音并发。

### 3.3 参考工程不是普通的单链路编码

BR28 参考工程定义了两个可选 Pipeline UUID：

```text
PIPELINE_UUID_TRANSLATION       = 0x218B
PIPELINE_UUID_TRANSLATION_MONO  = 0x9463
```

运行时根据声道数在二者中选择一个 UUID；随后可能以 ADC 和 `Source_Dev1` 为 source 打开两个同 UUID stream 实例，不是同时运行两个不同 UUID 的 Pipeline。当前会议入口使用 `MIC_TO_MONO_OPUS`，但在 `RDX_SUPPORT_ALGORITHM=1` 下输出和状态仍被配置为 stereo。立体声处理流程可简化为：

```text
ADC
  -> 声道拆分
  -> DNS / AGC / EQ / EffectDev1、EffectDev3
  -> 自定义通道汇接
  -> Source_Dev1
  -> EffectDev2（私有 stereo Opus 编码）
  -> Sink_Dev1
  -> rdx_record_run_data_handle()
```

其中 `EffectDev1/EffectDev3` 会将两路处理后 PCM 写入 `Source_Dev1`，`EffectDev2` 直接调用 `st_opus_enc` 接口编码，`Sink_Dev1` 又直接依赖 RDX 业务。该实现把算法、编码、节点和业务绑定在一起，是 BR28 项目定制代码，不适合复制到 BR56。

参考代码当前把会议和通话场景都强制设置为 `RECORD_FORMATE_OPUS_16K_STERO`。`EffectDev2` 使用 16 kHz、20 ms，码率为 `16 kbps * 声道数`，因此参考工程的 stereo 输出约为 32 kbps、80 B/帧。这是参考工程实现事实，不再等同于目标 APP 的强制线上合同。目标 APP 已实测接受 `16 kHz / mono / 32 kbps / 20 ms` raw Opus，并能清晰播放；BR56 不能为了复制参考工程的内部 stereo 结构而保留会破坏波形的节点组合。

参考实现还会丢弃每次 START/RESUME 后前 10 个编码帧，约 200 ms。首版保留该预热行为并显式统计，不复制其重复状态 ACK、忽略 open 失败和静默超时等缺陷。

### 3.4 目标工程已有可利用的 BR56 原生链路

目标工程的 `src/音频流程/智能语音.x6flow` 最终最小分组为：

```text
ADC -> AGC -> 编码器（mono） -> AI_TX
```

对应 Pipeline：

```text
name = pipeline-AI-voice
uuid = 0x5475
```

目标工程也已有运行时接口：

```text
SDK/audio/interface/recoder/ai_voice_recoder.c
SDK/audio/framework/nodes/ai_tx_node.c
```

`ai_voice_recoder_open()` 会解析 `ai_voice` Pipeline、从 ADC/PDM/IIS 输入中选择可用源并启动流；`AI_TX` 节点支持注册 `int (*)(u8 *, u32)` 回调。Spike 新增的 `ai_voice_recoder_open_with_tx()` 在启动前注册回调，并通过 `NODE_IOC_SET_ENC_FMT` 与 Encoder 私有参数显式固定 `16 kHz / mono / 32 kbps / 20 ms / raw Opus`。该合同已经通过帧统计、本地离线解码和 APP 实听验证。

当前页面已启用并选中最小“智能语音”分组，生成配置为：

```text
智能语音.x6flow enable       = true
会议分组 Channel Expander    = removed
TCFG_ENCODER_NODE_ENABLE     = 1
TCFG_AI_TX_NODE_ENABLE       = 1
TCFG_ENC_OPUS_ENABLE         = 1
TCFG_ENCODER_CHANNEL_NUM     = 1
```

工具重新导出后，`stream.bin` 从旧流程的 3170 B 变为 3102 B，最终 SHA-256 为 `A2DD1B66E22E28D85E40C770646C9F27D728909637FEB6AC4C3E989171C85ED7`。运行时代码同步将 `enc_fmt.ch_num`、`stream_enc_fmt.channel` 设为 1，并将 `fmt.channel_mode` 设为 `AUDIO_CH_MIX`。完整编译、在线下载和 APP 听音均已通过。

### 3.5 目标工程 USB MIC 当前链路

`USB Audio.x6flow` 当前选中的 `TypeCEarphone` 上行链路为：

```text
ADC
  -> CVP_V3
  -> EQ
  -> 播放同步
  -> 音量控制器
  -> Channel Expander
  -> BitWidth Convert
  -> PCMIC
```

当前物理输入为 PA3 单 MIC、两脚驻极体，已实测 ADC 采集有效；但现有 USB Audio 流图的 ADC 配置是 48 kHz，UAC MIC 描述符支持 Host 选择 16/44.1/48 kHz、16 bit、2 声道，物理单声道会在后级扩为 USB 双声道。因此，“USB 通话链路固定 16 kHz mono”不是当前工程事实。

`adc_file.c` 使用全局 `adc_hdl` 并支持注册多个 ADC output handler，但每个 ADC 节点仍会执行 sample rate、open 和 buffer 设置。第二条 Pipeline 对同一 PA3 重复 open、两条流使用不同采样率、第二次 buffer 设置和关闭引用计数能否安全共存，仍必须由 BR56 实机验证。USB Host 选择 44.1/48 kHz 时的共存是首版必达场景，不能只测双方均为 16 kHz。

三号文档中的 PA2 原始采样全零属于此前接线和采集脚位下的历史测试结果，不再代表当前硬件状态。当前实现已经统一选择 PA3；AGC 前后 PCM、Opus 离线解码和 APP 清晰播放均已证明可视化工具生成配置使用了有效 MIC 输入，不能继续沿用旧的 PA2 流程参数。

### 3.6 当前 BLE 资源边界

当前 RDX BLE Transport 使用既有 RDX TX Characteristic 发送控制和业务数据，没有单独的音频 Characteristic。参考工程同样通过 RDX 通用 TX Characteristic 上报在线音频。

当前已观察到的 BLE 资源基线为：

```text
一次实测协商 ATT MTU      = 517 B
当前本地有效 Payload 上限 = 128 B
ATT Send cbuf            = 4096 B
GATT Server / Client     = 1 / 0
```

协商 MTU 517 不表示每次连接都能发送 514 B，也不表示当前本地配置允许。参考工程配置的是 ATT MTU 517，最大 ATT Value Payload 为 514 B，不是“517 B Payload”。目标工程已把本地上限从 64 B 提高到 128 B，可容纳实测 98 B 的参考兼容 stream packet；4096 B ATT cbuf 和 16 帧固定补偿队列已经启用，DLE/2M 修复后实测 `send_fail=0 / invalid=0 / drop=0`。

## 5. 可视化音频流程方案

### 5.1 优先生产方案：RDX 专用 Pipeline

优先通过 JL 可视化工具 4.11.0 新增独立的 `RDX在线录音` 流程，使用工具生成并冻结唯一 Pipeline UUID。节点保持物理输入和编码声道一致：

```text
ADC（PA3，两脚驻极体 MIC，physical mono，16 kHz，16 bit）
    -> AGC（首版可保留，已证明不会引入失真）
    -> Encoder（Opus，mono，32 kbps，20 ms，raw/no container）
    -> AI_TX（回调输出编码帧）
```

优先使用独立 Pipeline 的原因：

- RDX 生命周期不占用 `g_ai_voice_recoder` 单例；
- 不与 RCSP/AI 翻译的 `ai_voice` 业务共享状态；
- 可以从流程图直接看到 RDX 的源、AGC、编码和出口；
- 后续加音效时不会改变 AI 翻译路径；
- RDX Adapter 可以独立解析、启动和释放该 Pipeline。

若后续从当前 `ai_voice` Spike 拆成 RDX 专用 Pipeline，必须保持与 USB 音频互斥、RDX 输出 16 kHz 且内存安全，才可成为生产方案。首版不要加入 `AI_RX`、Decoder、Bluetooth Sync、DAC、EQ、DNS 或 AEC，也不要复制参考工程的 `Source_Dev`、`Sink_Dev` 和 `EffectDev1/2/3`。

### 5.2 快速技术验证方案：复用 `ai_voice` 最小分组

现有 `智能语音.x6flow` 最终包含 `ADC -> AGC -> Encoder -> AI_TX` 最小分组，可用于验证：

- BR56 mono Opus 是否固定为 80 B/帧并每 20 ms 输出一次；
- PA3 单 MIC 是否能不经声道扩展直接清晰编码；
- Opus 动态内存、物理内存和 CPU 峰值；
- 98 B stream packet 的单 Notify 发送条件。

该页现已启用并选中最小“智能语音”分组，未把 DNS/Gain/EQ/AI_RX/DAC 纳入当前链路。该方案只用于一次性验证，不冻结为生产结构。

### 5.3 后续若产品要求并发：共同采集 + PCM Tap + 重采样

实机已经证明两个 ADC Pipeline 不能安全并行。首版没有 USB 音频与会议录音并发需求，因此不实施本节；只有后续产品明确要求并发时，才考虑由共同采集层唯一拥有 PA3，再分别向 USB 和 RDX 分流：

```text
PA3 ADC（共同采集所有者，当前基线 48 kHz）
    +-> USB CVP/EQ/后级 -> PCMIC
    +-> RDX Gate -> Resample 16 kHz
                 -> mono Opus Encoder -> AI_TX -> RDX
```

该备选必须同时满足：

- USB Host 未打开 UAC MIC Endpoint 时，RDX START 仍能启动共同采集并获得 PCM；
- USB Host 在 16/44.1/48 kHz 间切换时，RDX 输出合同保持 16 kHz；
- RDX START/STOP 不关闭、重配或重启 USB 音频；
- 非录音期间 RDX 编码支路不持续消耗 CPU；
- 首版 RDX 分支不强制继承 USB 的 EQ/DNS/AEC；
- RDX 只控制通用 Gate/Adapter，不在 UAC、CVP 或 PCMIC 核心节点中加入协议命令判断。

### 5.4 三种方案比较

| 方案 | 优点 | 风险 | 定位 |
| --- | --- | --- | --- |
| RDX 专用 Pipeline | 职责清晰、独立生命周期、便于调试 | 不同采样率 ADC 并发和额外内存未证实 | 优先生产候选 |
| 复用 `ai_voice` | 改动少、可快速验证 | 分组易选错，且与翻译单例/UUID 耦合 | 一次性 Spike |
| 共同采集 + PCM Tap | 单一 ADC 所有者，可显式重采样 | 需要重构采集生命周期和通用 Gate | 独立并发失败后的生产备选 |

### 5.5 可视化工具操作清单

实施时必须从 `project.jlproj` 用工程记录的 JL 工具 4.11.0 修改，不直接编辑 `.x6flow` JSON，也不只手改生成的 `sdk_config.h`：

1. 新增或复制一个最小录音流程并命名为 `RDX在线录音`；
2. 由工具生成唯一 Pipeline UUID，并冻结对应 stream scene、时钟所有权，在代码侧定义同值 `PIPELINE_UUID_RDX_RECORD`；
3. Spike 复用 `智能语音.x6flow` 时，先切换到最小“智能语音”分组，再启用页面；
4. 选择 PA3 ADC 和两脚驻极体配置，确认物理输入为 mono；
5. 独立 Pipeline 固定采集为 16 kHz、16 bit、mono；共享采集方案显式加入到 16 kHz 的重采样；
6. Encoder 选择 Opus、mono、32 kbps、20 ms；
7. Opus 输出选择 raw/no container，不能使用 OGG 文件封装；
8. 连接到标准 `AI_TX` 节点，确认没有 AI_RX、Decoder 或 DAC；
9. 保存后检查 `stream.bin`、`jlstream_node_cfg.h` 和 `sdk_config.h` 的生成差异；
10. 确认 `TCFG_ENCODER_NODE_ENABLE`、`TCFG_AI_TX_NODE_ENABLE`、`TCFG_ENC_OPUS_ENABLE` 和 `TCFG_ENCODER_CHANNEL_NUM=1` 已生效；
11. 建立 RDX ON/OFF 生成配置或等价联动方案，RDX OFF 的最终 Map 不得包含 RDX 专用 Pipeline、AI_TX、Encoder 和 Opus；
12. 将流程截图、Pipeline UUID、编码器参数、工具版本和生成文件哈希归档到验证记录。

工具参数名称与枚举值必须以 AC710N 当前工具版本实际界面为准，不能把 BR28 `.x6flow` 中的数字字段直接复制到 BR56 文件。

## 6. 冻结的首版目标音频合同

| 参数 | 首版值 | 依据 |
| --- | ---: | --- |
| 物理输入 | PA3 ADC，mono | 当前两脚驻极体单 MIC 硬件，已实测采集有效 |
| 编码前 PCM | 16000 Hz / 16 bit / mono | 与 PA3 物理输入一致；APP 清晰播放实测 |
| 共同采集备选 | 48 kHz 或实际公共采样率，再重采样到 16 kHz | USB 当前 ADC 48 kHz，Host 可选 16/44.1/48 kHz |
| 编码 | raw Opus | RDX 在线录音线上格式，不使用 OGG |
| Opus 码率 | 32000 bit/s | 保持 80 B/20 ms 帧长和既有 BLE 封包，不因 mono 降码率 |
| Opus 帧长 | 20 ms | 参考编码固定参数 |
| 预热丢弃 | 前 10 帧，约 200 ms | 参考当前有效代码路径；显式计数 |
| BLE 发送单元 | 1 Opus frame/Notify | 保持参考单帧语义，不新增分片 |

理论帧长：

```text
32000 bit/s / 8 * 20 ms / 1000 = 80 B
```

参考协议定义 `CMD_UP_RECORD_STREAM = "*DEV#stream#"`，固定前缀为 12 B；参考闭源实现还会追加两段十进制长度。80 B 帧的完整头和单次通知为：

```text
"*DEV#stream#80#80#" = 18 B header
18 B header + 80 B raw Opus = 98 B
```

原 64 B 本地有效 Payload 上限不满足该合同，现已提高到 128 B。首版无需直接复制参考工程的最大 Value Payload 514 或 4096 B ATT cbuf。

早期 V24 分支曾按 stereo `RDX_OPUS_FMT_PACK(16, 2, 40, 32)` 推导出 `1093142528`，但目标 APP 实际使用 V23 24 B 状态报文，不依赖这个 V24 长格式值。最终 mono Opus 仍固定输出 80 B，APP 能从 raw Opus 正常解码。后续若改变码率、VBR/CBR、封装或帧长，必须重新验证实际帧长并按最大合法帧规划 slot，Transport 不得截断。

## 7. 协议映射与参考兼容合同

### 7.1 已确认命令前缀

参考协议头给出的录音命令为：

```text
APP -> Device
*APP#record#0#       stop
*APP#record#1#       start
*APP#record#2#       pause
*APP#record#3#       resume
*APP#record#1#0#     start，scene=会议
*APP#record#1#0#1#   目标 APP 实际 start：会议，16 kHz
*APP#record#1#1#     start，scene=通话（首版拒绝）

Device -> APP
*DEV#record#         record state/ack 前缀
*DEV#stream#         online Opus stream 前缀
```

### 7.2 必须显式转换的状态编号

参考工程存在两套编号，不能直接共用：

| 语义 | Wire command | 参考 `RecordStatus.run` |
| --- | ---: | ---: |
| START | 1 | 0 |
| PAUSE | 2 | 1 |
| RESUME | 3 | 2 |
| STOP | 0 | 3 |

目标实现应定义独立的 Wire 枚举和内部状态枚举，在解析边界显式转换。不得使用 `cmd - '0'` 后直接当内部状态，也不得把参考 `RECORD_STATE_START=0` 当成 APP 下发 start=0。

### 7.3 参考工程已冻结的语义

本阶段先以参考工程运行日志冻结协议语义，再以目标 APP 的实际状态和清晰播放结果修正音频实现：

- 外部 Wire 命令为 STOP=0、START=1、PAUSE=2、RESUME=3；
- 闭源解析层传给参考 handler 的是另一套内部 ASCII 编号，目标边界必须显式映射；
- start 第二参数在实际 handler 中按 scene 使用，`0=会议`、非 0=通话；参考 `formate` 入参被忽略；
- 首版只接受会议 scene，并固定上报 `16 kHz / mono / 32 kbps / 20 ms` raw Opus；
- `*DEV#stream#` 固定前缀长 12 B，随后追加 `帧长#帧长#`；80 B 帧的完整头为 `*DEV#stream#80#80#`，首版一帧 raw Opus 对应一次 Notify，不新增序号、校验或分片；
- 每次 START/RESUME 丢弃前 10 个预热帧；
- START 只有在 Pipeline 和编码输出确认成功后才回一次成功状态，不复制参考工程“open 前 ACK + Sink 初始化再 ACK”的重复行为；
- STOP 禁止新帧、关闭 Pipeline、丢弃未发送尾帧，再发送停止状态；
- 断连或 CCC 关闭都立即终止会话，重连后状态为停止。

`*DEV#record#` 的字段顺序和结束符已按参考 V23 运行日志固定为 24 B 状态字符串。V24 长报文中的十进制 `opus_format` 不属于当前 APP 路径，不能用它反推目标 Encoder 必须为 stereo。暂停/恢复字段与时间轴留到第二阶段，不在首版猜测。

兼容证据优先级为：

1. 目标 APP 对目标固件的实际状态、数据接收和听音结果；
2. 参考工程当前选中 APP/Device/Ability 宏下的运行日志、实际代码路径与闭源库输出；
3. 正式 RDX 协议说明；
4. 参考头文件注释、变量名和未启用的历史分支。

### 7.4 会话门控

在线录音命令至少要求：

- RDX BLE 已连接；
- TX CCC 已打开；
- AppKey 成功，`app_ready=1`；
- RDX 业务状态为 `bound=1`；
- 当前 BLE 链路已加密；
- 当前没有解绑/恢复出厂 pending action；
- 当前未执行 OTA 或其他独占传输；
- 音频资源可用；
- 统一 TX 调度器和音频队列已初始化；
- 本次连接的有效 ATT Value Payload 不小于 `RDX_STREAM_PACKET_MAX`。

任一门控不满足时不得打开 ADC、Encoder 或定时器，必须记录明确拒绝原因。录音中关闭 CCC 与断连使用同一强制停止路径；如果目标 APP 实际不建立加密链路，则量产录音被视为兼容阻塞，不静默降级为明文发送。

## 8. 目标模块设计

### 8.1 建议模块关系

```text
rdx_mvp0_protocol ---- command event -----+
rdx_ble_transport ---- link/CCC event ----+--> rdx_record_service worker
AI_TX callback -------- frame/overflow ---+      | single state owner
                                                  +--> rdx_record_audio_br56
                                                  +--> rdx_record_stream
                                                  +--> record ACK encode

record/control packet -- high priority --+
audio stream packet ---- low priority ----+--> rdx_tx_scheduler
                                                  |
                                                  v
                                      rdx_ble_transport_br56
```

`rdx_record_service` 的工作任务是录音状态和 Pipeline 生命周期的唯一写入者。ATT write、HCI disconnect、CCC、AI_TX 和 timer 回调只投递事件，不得直接并发执行 START/STOP 或修改录音状态。`rdx_tx_scheduler` 是 RDX TX Characteristic 的唯一发送所有者，现有控制 ACK 也必须改走该入口。

### 8.2 文件职责建议

| 文件 | 类型 | 职责 |
| --- | --- | --- |
| `rdx_protocol_defs.h` | 修改 | 增加录音 Wire 命令、状态和音频头常量 |
| `rdx_mvp0_protocol.[ch]` | 修改 | 解析录音 Wire、执行会话门控、编码状态 ACK，并把命令投递给 Service |
| `rdx_record_service.[ch]` | 新增 | 单一工作任务、在线录音状态机、幂等命令、链路事件和错误转换 |
| `rdx_record_audio_br56.[ch]` | 新增 | BR56 Pipeline open/close、AI_TX 回调注册和音频参数校验 |
| `rdx_record_stream.[ch]` | 新增 | 固定帧队列、预热丢弃、RDX 音频封包和音频统计 |
| `rdx_tx_scheduler.[ch]` | 新增 | 统一串行化控制包和音频包，处理优先级、CAN_SEND_NOW 和发送统计 |
| `rdx_ble_transport_br56.[ch]` | 修改 | 暴露发送就绪/可发送事件，不承担录音状态机 |
| `apps/common/debug/resource_monitor.c`、`apps/common/include/resource_monitor.h`、`apps/earphone/include/resource_monitor_config.h` | 复用 | 提供独立门控的系统启动和周期资源采样；录音会话快照接口已预留，当前未接入录音流程 |
| `rdx_protocol_entry.c` | 修改 | 初始化/反初始化 Service、Stream、Scheduler 和 Audio Adapter，并保证安全停流顺序 |
| `genFileList.c` | 修改 | 在最终 `TCFG_RDX_ENABLE` 下加入 RDX 录音源码 |
| `src/音频流程/...x6flow` | 工具生成 | RDX 专用 BR56 音频 Pipeline |
| `project.jlproj` | 工具生成 | 登记新增流程文件和 RDX ON/OFF 配置来源 |

资源监控是公共诊断能力，不属于 RDX 生命周期。`rdx_protocol_entry.c` 不得启动或停止监控，RDX ON/OFF 对照必须使用相同的 `TCFG_RESOURCE_MONITOR_ENABLE` 和采样周期。未来如需记录录音会话检查点，应由对应业务点显式调用 `resource_monitor_snapshot()`，但不得改变公共监控的系统级生命周期。

不要新增公共 `rdx_app.c`，也不要把参考 `rdx_record.c` 复制后逐段 `#if 0`。

### 8.3 音频 Adapter 约束

`rdx_record_audio_br56` 只负责：

- 检查 Pipeline 是否空闲；
- 配置/确认物理和编码输入均为 mono、16 kHz、32 kbps、20 ms raw Opus；
- 注册 AI_TX 回调；
- 启动和关闭 Pipeline；
- 将编码帧交给 `rdx_record_stream_push_frame()`；
- 返回明确的 `busy/no-memory/format/start-failed` 错误。

它不得解析 `*APP#record#`，不得直接调用 BLE send，也不得修改 USB/UAC/CVP 状态。

### 8.4 统一发送与固定队列约束

目标工程现有 `rdx_ble_transport_send()` 是同步尝试接口，适合短控制包，不足以直接承接 50 frame/s 的实时音频。建议增加固定大小队列：

```text
AI_TX callback
    -> 校验帧长
    -> copy 到预分配 ring slot
    -> post 发送任务
    -> 返回，不等待 BLE

RDX TX scheduler
    -> 控制 ACK 优先
    -> 取控制包或已封装音频包
    -> 尝试 Notify
    -> 成功后释放 slot
    -> 空间不足时等待 CAN_SEND_NOW/短时重试
```

硬约束：

- 音频回调中不 `malloc/free`；
- 音频回调中不等待 mutex、semaphore 或 BLE；
- 每个队列 slot 长度固定并有编译期上限；
- `AI_TX` 会忽略回调返回值并立即释放 frame，因此 push 失败不能形成反压；回调只能锁存 overflow、计数并投递异步 STOP 事件；
- 控制 ACK 的优先级高于尚未进入 ATT cbuf 的音频帧；每次可发送事件只发送有限批次，避免音频一次灌满 512 B cbuf；
- 记录 warmup_dropped/produced/enqueued/sent/retried/overflow_dropped/stop_discarded/max_depth；
- 短暂 ATT cbuf 满只保留帧并等待，不立即丢帧；
- 队列持续满时进入明确错误并停止录音，不能无限积压或静默丢音；
- STOP 时先阻止新帧，再关闭 Pipeline，丢弃未发送尾帧，最后排队停止状态；
- 断连或 CCC 关闭时立即清队列并由 Service 关闭 Pipeline。
- 解绑/恢复出厂等 ACK 后延迟断开流程，必须以控制 ACK 实际发送成功为起点，不能以“已入调度队列”冒充“已发送”。

如果 APP 链路实测证明需要独立队列，初始深度可从 8 帧开始评估：80 B 原始帧约 640 B，按 98 B 完整包约 784 B，提供约 160 ms 抖动余量。最终 slot 上限和深度必须由 BR56 实测最大帧、BLE 调度和最低内存水位决定，不能照搬参考工程 15 个动态包或 4096 B cbuf。

## 9. 在线录音状态机

建议内部状态不要复用参考 `RecordStatus.run` 数字：

```text
IDLE
  | start
  v
STARTING ---- failure ----> ERROR -> IDLE
  | pipeline started
  v
RECORDING
  | pause                   | stop/disconnect/error
  v                         v
PAUSING -> PAUSED       STOPPING -> IDLE
             | resume
             v
          STARTING
```

### 9.1 START

1. 校验会话、场景和参数；
2. 检查当前状态和音频资源；
3. 清空旧发送队列和统计；
4. 切换到 `STARTING`；
5. 打开 RDX Pipeline；
6. 丢弃并统计前 10 个预热帧；
7. 收到第一个格式正确且成功入队的有效帧；
8. 切换到 `RECORDING`；
9. 通过统一 TX 调度器发送唯一一次成功状态，控制包优先于首个音频包。

如果 Pipeline 打开、格式校验、Payload 门控或首个有效帧入队失败，不得把内部状态留在 RECORDING，也不得发送成功 ACK。失败原因进入内部统计并回到 IDLE；在参考线上错误字段未确认前，至少上报当前停止状态，不能复制参考工程忽略 open 返回值或超时静默放弃的行为。

### 9.2 STOP

STOP 必须幂等：IDLE 收到 STOP 仍返回当前停止状态。正常停止顺序：

1. 切换 `STOPPING`，禁止新帧入队；
2. 关闭 Pipeline；
3. 丢弃并统计尚未发送的队列尾帧；
4. 清理定时器和资源；
5. 切换 `IDLE`；
6. 发送停止状态。

### 9.3 PAUSE/RESUME

暂停首版建议真正关闭 Pipeline 和 Encoder，以释放 ADC/Opus 动态资源；恢复重新打开同一参数的 Pipeline。协议层需确认 APP 是否允许编码流在恢复后重新起帧。

在暂停语义未完成前，不正式宣告 `Record Pause/Resume` Ability，也不对 PAUSE/RESUME 返回虚假成功。

### 9.4 重复和并发命令

- RECORDING 收到相同 START：不重开音频，重发当前状态；
- STARTING 再收到 START：记录 duplicate，不并发 open；
- STOPPING 收到 STOP：保持幂等，完成后回当前状态；
- 状态迁移中收到相反命令：不缓存 pending action，明确拒绝或返回当前状态；
- 解绑、恢复出厂、断连和 CCC 关闭优先级高于录音命令，并强制结束会话；
- 在线录音期间拒绝新 OTA/文件传输；OTA/文件传输已开始时拒绝 START；
- 所有命令和链路事件只由 Service 工作任务执行状态迁移，回调上下文不得直接 open/close。

### 9.5 BLE 断开或 CCC 关闭

目标产品没有离线存储，BLE 断开后没有继续录音的有效去向。因此首版合同应为：

```text
BLE disconnect / TX CCC off
    -> 禁止新帧
    -> 关闭 RDX Pipeline
    -> 清空发送队列
    -> 状态回 IDLE
    -> 清除 app_ready（断连）
```

CCC 重新打开或 BLE 重连后都必须由 APP 重新 START。不得复制参考代码库中未启用的“在线切离线”“本地继续写文件”或 30 分钟暂停超时分支；参考工程当前无 Local Storage Ability 的有效构建同样会在断连时立即停止。

## 10. USB Audio 与 RDX 音频互斥边界

### 10.1 已验证结论

USB MIC/Speaker/CVP 与 RDX 同时运行时只剩约 20～22 KB RAM、CPU 约 68%。更直接的复位原因是第二条 ADC Pipeline 改变共享 ADC frame size，日志出现 `CVP frame size unsupport 512 samples, only support 256 samples`，随后发生 `hmem exception`。这不是首版需要支持的会议录音场景，因此当前策略是互斥而非共存：USB 保持枚举；UAC MIC 或 Speaker 正在运行时，RDX START 返回停止状态且不打开 Pipeline。

### 10.2 首版场景矩阵

| USB Speaker | USB MIC/CVP | Host UAC MIC rate | RDX Record | 目标 |
| --- | --- | ---: | --- | --- |
| OFF | OFF | N/A | ON | 首版唯一正常录音场景，连续上报 APP |
| ON | OFF | N/A | START | 安全拒绝，不打开 RDX Pipeline |
| OFF | ON | 任意 | START | 安全拒绝，不打开 RDX Pipeline |
| OFF | OFF | N/A | 100 次 start/stop | 生命周期、泄漏和 APP 解码连续性 |
| OFF | OFF | N/A | 断连/CCC off | 立即关闭，无存储、无后台继续录音 |

每个场景至少记录：

- 普通 heap、physics memory 和最低水位；
- 最大连续块或失败分配点；
- CPU 使用率和时钟档位；
- Opus warmup_dropped/produced/enqueued/sent/retried/overflow_dropped/stop_discarded 计数；
- ATT cbuf 剩余空间和队列最大深度；
- USB underrun/overrun、CVP 异常和 USB 重枚举；
- 主机抓取或 APP 接收后重组测试音频的实际解码时长和连续性。

### 10.3 内存边界

一号复盘已经证明 BLE 常驻与 USB MIC/CVP 曾经造成运行时峰值冲突。启用以下功能都会重新增加代码或动态内存：

- Encoder 节点；
- AI_TX 节点；
- Opus encoder library；
- RDX 音频固定队列；
- 第二条 ADC 流的 frame/buffer；
- 共同采集方案的 Resampler/Gate；会议录音链路禁止重新引入未经解码验证的 Channel Expander；
- 后续可选 DNS/EQ；
- 更快 BLE 发送所需的额外排队。

独立 Spike 已确认录音运行时最低可用 RAM 约 110 KB，STOP 后恢复到约 139 KB。APP 闭环仍需验证多次 START/STOP 后水位不持续下降；USB Speaker+MIC 全开不再属于首版录音资源验收组合。

## 11. BLE 吞吐和连接参数

### 11.1 理论带宽

按实测一帧 98 B、每秒 50 帧计算：

```text
98 B * 50 = 4900 B/s
```

该速率本身不高，但实时性取决于连接间隔、slave latency、手机调度、ATT cbuf 和同 Characteristic 控制包竞争。只看平均带宽不足以判断稳定。

### 11.2 首版策略

- 把本地有效 Payload 上限提高到不小于 `RDX_STREAM_PACKET_MAX`，并在 START 时检查本次连接；
- 保持一帧一 Notify，不新增私有分片；
- 使用与参考工程一致的 4096 B ATT Send cbuf，并增加 16 帧固定补偿队列；队列满时只丢最新帧并计数，不允许无界增长；
- 在开始录音时记录 connection interval/latency/MTU/有效 Payload/加密状态；
- BLE 连接后立即请求 `{6,6,0,600}`（7.5 ms、零 slave latency）；任何成功的慢速参数更新后再次请求；
- START 时再次请求最高性能参数，STOP 后不恢复低功耗参数；
- 不移植参考工程的 latency hold、120 s 空闲窗口和低功耗连接管理器；
- 每 250 个有效帧记录 `sent/send_fail/queued/pending/peak/drop`，STOP 时再次输出最终统计。

### 11.3 Transport 需要补齐的事件

当前 Transport 已处理连接、MTU、断开和 CCC，但在线流至少还需要：

- `ATT_EVENT_CAN_SEND_NOW` 或等价可发送通知；
- 当前发送有效空间查询；
- CCC 关闭和链路加密状态变化；
- 连接参数更新结果；
- 可选的发送完成/失败统计；
- disconnect/CCC off 时向录音 Service 投递强制停止事件。

Transport 只报告链路事件和发送结果，不拥有录音状态。

### 11.4 2026-08-11 APP 实测结论

`COM3_2026-08-11_15-09-24.log` 首先暴露了 START 命令和状态字段可能未对齐的问题，因此排查从命令解析、状态 ACK 和 stream 输出三部分分别取证，而不是把“APP 无状态”直接归因于音频或 RAM。

`COM3_2026-08-11_15-19-05.log` 已证明音频采集、Opus 编码和协议封包均已运行：前 10 帧正常丢弃，随后持续产生 80 B Opus，并调用 BLE API 发送 98 B `*DEV#stream#80#80# + payload`。状态 ACK 为：

```text
*DEV#record#1#0#1093142528#1#0#16200##
```

此前依据参考 ELF 的 V24 分支反汇编，误判该长格式 ACK 与目标 APP 使用的参考协议一致。`参考工程的在线录音日志.log` 已用成功运行时行为推翻该结论：同一 APP 实际连接的参考固件广播协议版本为 `0x17`，并明确打印 `[REC>IND] V23 send`；目标固件当时广播 `0x18` 并发送上述 V24 长格式 ACK。这是 APP 状态不变化前出现的第一个确定协议差异。

当时的第二个异常发生在录音流开始后：ATT 可用空间从 2092 B 持续下降到 166 B，统计由 `frames=260 sent=77 send_fail=173` 恶化到 `frames=1010 sent=192 send_fail=808`。因此先验证快速连接参数能否把持续吞吐恢复到 50 帧/秒；只有在 `drop=0` 且 `pending` 能回到 0 后，才能根据 APP 状态和解码结果判断是否仍有协议解析问题。

`COM3_2026-08-11_15-40-17.log` 进一步确认参数请求本身成功，结果为 `interval=10 latency=4 timeout=600`，但实际仅发送约 14 帧/秒：`frames=260 sent=139 drop=95`，随后 `frames=510 sent=210 drop=274`。该速率与 `12.5 ms * (latency + 1)` 接近。参考工程使用该参数是为了兼顾低功耗，并在活跃期另有 latency hold 管理；目标 Type-C 产品无需 BLE 低功耗，因此不移植这套状态机，直接固定最高性能 `{6,6,0,600}`。

`COM3_2026-08-11_15-48-24.log` 证明仅修改连接间隔仍不足以承载在线流。手机先接受 `interval=6 latency=0`，随后实际稳定在 `interval=9/10 latency=0`；25 秒内约 1250 个有效帧只成功入 ATT 发送队列 419 帧，丢弃 815 帧，持续吞吐约 17 帧/秒。RAM 同期仍有约 95 KB，命令、START ACK、采集、编码和 98 B 封包均正常，因此该问题不是 RAM 或协议参数错误。

根因是目标 RDX 专用控制器配置只保留了 `LE_ENCRYPTION`，误裁掉了参考工程已有的 `LE_DATA_PACKET_LENGTH_EXTENSION` 和 `LE_2M_PHY`。98 B Value 加 ATT/L2CAP 头后约 105 B；默认 27 B Link Layer PDU 需要至少 4 段，吞吐与实测相符。现已恢复 DLE/2M 能力，连接和 START 时主动请求 `251 octets / 2120 us` 与 2M PHY，并记录实际 Data Length/PHY 更新结果。DLE 是 50 帧/秒的必要项；若手机不接受 2M，DLE + 1M 仍作为兼容回退路径。

`COM3_2026-08-11_16-04-41.log` 已确认上述吞吐修复有效：DLE 最终双向协商为 `251 octets / 2120 us`，PHY 为双向 2M，实际连接参数为 `interval=9 latency=0`。录音统计依次为 `frames=260 sent=250`、`frames=510 sent=500`、`frames=760 sent=750`；最终除前 10 帧预热外，782 个有效帧全部成功进入 ATT 发送链路，`send_fail=0 invalid=0 queued=0 pending=0 peak=0 drop=0`。ATT cbuf 可用空间始终保持 3916 B，停止后 RAM 从约 103 KB 恢复到 134 KB。由此冻结结论：采集、编码、98 B 封包、BLE 持续吞吐和断连释放均已通过本阶段验证，不再把 RAM、连接参数或发送队列列为当前阻塞点。

### 11.5 V23 状态兼容问题与结论

`参考工程的在线录音日志.log` 包含两轮成功 START/STOP。APP 下发 `*APP#record#1#0#1#` 后，参考固件上报：

```text
*DEV#record#1#0#1#1#1#0#
```

约 206 ms 后参考固件重复一次相同 START 状态；APP 正常 STOP 时，参考固件上报：

```text
*DEV#record#0#0#1#1#1#0#
```

目标固件最初按该证据完成最小修改：广播协议版本从 `0x18` 改为 `0x17`，START/STOP ACK 照抄上述 24 B V23 字符串。首轮只保留 Pipeline 成功打开后的一次 START ACK；参考工程的第二次 ACK 属于其初始化流程副作用，当前 APP 已能正常进入和退出录音状态，因此不复制该重复 ACK。

`COM3_2026-08-11_17-06-19.log` 对应的 V23 版本使 APP 首次出现正确录音状态变化，证明控制协议问题已经关闭。后续日志中的 APP 状态、在线流和 STOP 均正常，BLE DLE、2M PHY、连接参数、Opus 生成和 98 B Notify 吞吐也均已通过。此后唯一剩余问题从“协议不识别”转为“音频可收到但严重失真”。

2026-08-12 继续排查 APP 声道显示时，从参考工程 `librdxApp.a` 的 LLVM IR 确认 V23 六个字段依次为：`状态#场景#采样率#record_mode#类型#耗时#`。第 4 个数字不是固定兼容值，而是 `rdx_protocol_record_state_indicate()` 调用 `rdx_app_get_record_mode()` 得到的运行时值。参考源码虽然为会议录音选择 `MIC_TO_MONO_OPUS`，随后却调用 `rdx_app_set_record_mode(RDX_RECORD_CHANNAL_DUAL)`，因此参考 Golden Trace 中该字段为 `1`，APP 显示双声道符合其上报。

`COM3_2026-08-12_10-03-16.log` 同时证明目标线上码流已经是 mono：首个有效 Opus 帧 TOC 为 `0x4B`，stereo 位为 0，运行时打印 `ch=1 expected_ch=1 ok`。目标固件据此将 V23 `record_mode` 改为 `RDX_RECORD_CHANNAL_SINGLE (0)`，新状态为：

```text
*DEV#record#1#0#1#0#1#0#
*DEV#record#0#0#1#0#1#0#
```

该改动只修正 APP 元数据，不改变已经验证的 16 kHz、mono、32 kbps、20 ms raw Opus 数据面。完整构建和在线下载已成功；同一 APP 实测已显示单声道，在线录音正常。

### 11.6 音频失真排查、根因与最终修复

音质问题按“传输、解码、采集、处理、声道”顺序逐层排查，过程如下：

| 顺序 | 现象或实验 | 证据 | 得出的结论 |
| ---: | --- | --- | --- |
| 1 | APP 状态已变化，但手机听到杂音或持续失真 | `COM3_2026-08-11_17-06-19.log`、`17-22-55.log`；APP 能显示音频波动 | 控制协议已通，问题进入音频数据面 |
| 2 | 将 MIC 模拟增益提高到 27 dB | APP 波动幅度明显增加，但语音仍无法听清 | 增益太小只影响幅度，不是失真根因 |
| 3 | 连续复测 AGC、声道和测试音版本 | `18-12-01.log`、`18-21-59.log`、`19-16-29.log`、`19-29-31.log` 均可稳定复现；1 kHz 测试音表现为持续音 | 周期测试音能证明链路有输出，但不能证明语音样本顺序和声道布局正确 |
| 4 | 中途出现一次无法连接，随后恢复连接继续复测 | `19-36-38.log`、`19-41-20.log` | 这是并行出现的连接问题，不能解释脱离 APP 后仍可复现的本地解码失真 |
| 5 | 将 BLE Notify 中的 80 B payload 在主机侧直接重组并用 FFmpeg/PyAV 解码 | 主机解码也能听到与 APP 相同的失真 | 排除 APP 播放、APP 双声道合并、BLE 空口和 `*DEV#stream#80#80#` 封包 |
| 6 | 用清晰 USB 通话链路做同硬件对照 | `通话时MIC可以正常收音通话清晰.log` 显示 ADC 为 `16000 Hz / mono / 16 bit / channel_mode 0x14`；通话声音清晰 | PA3 MIC、ADC 基本配置和 27 dB 模拟增益本身正常；差异位于 ADC 后处理路径 |
| 7 | 在 AGC 节点内同时抓取对齐的 AGC 前后各 1 秒 PCM | `COM3_2026-08-11_20-04-59.log` 成功导出 pre/post，抓取期间最低 RAM 38 KB，结束后恢复 133 KB，无 ASSERT 或复位 | 获得可以逐样本比较的固件内部证据，且抓取机制未改变故障性质 |
| 8 | 对比 AGC 前后 PCM | pre：RMS `-40.31 dBFS`、peak `1623`、clipping `0`；post：RMS `-35.50 dBFS`、peak `2885`、clipping `0`；相关系数 `0.995196761`，增益 `+4.77 dB`，残差 RMS `53.85` | AGC 工作正常，没有削顶，也没有重排或破坏波形 |
| 9 | 对同一会话的 534 个 Opus 包离线解码 | 时长 10.68 s；左右声道相关系数 `1.000000000`，最大样本差 `0`；单独播放左声道仍失真；AGC-post 与解码 PCM 相关性约 `0.035` | APP 合并 L/R 不是原因；波形在 AGC 之后、Opus 输出之前或编码过程中被破坏 |
| 10 | 移除 `Channel Expander`，Encoder 和运行时代码同时改为 mono | 工具链路变为 `ADC -> AGC -> Encoder(mono) -> AI_TX`；重新导出 `stream.bin`，完整编译并在线烧录 | 对故障边界做最小有效 A/B 验证 |
| 11 | 使用同一 APP 再次 START、说话并播放 | APP 状态正常、在线流正常，用户现场确认声音已经清晰 | 失真问题关闭，mono Opus 与现有 APP 兼容 |

最终根因冻结为：BR56 目标工程中 `Channel Expander` 承担 mono 到 stereo 扩展后，与标准 stereo Opus Encoder 之间的 PCM 布局或格式协商不兼容，导致输入 Encoder 的语音波形被错误解释。该结论不表示 `Channel Expander` 在所有采样率和所有链路中都不可用；USB 通话链路在另一套 48 kHz 后级中可以正常工作。由于最终 A/B 同时移除了扩展节点并把 Encoder 改为 mono，当前证据能准确锁定“会议录音的声道扩展与 stereo 编码边界”，不进一步猜测闭源节点内部是哪一行实现错误。

最终修复包括：

1. 在 JL 可视化工具 4.11.0 中删除会议录音分组的 `Channel Expander`，将 AGC 直接连接到 Encoder；
2. Encoder 声道数从 2 改为 1，保持 Opus、16 kHz、32 kbps、20 ms 和 raw 格式不变；
3. 重新生成 `jlstream_node_cfg.h`、`init.bin` 和 `stream.bin`，不能只保存 `.x6flow`；
4. 在 `ai_voice_recoder.c` 中同步设置 `enc_fmt.ch_num=1`、`stream_enc_fmt.channel=1`、`fmt.channel_mode=AUDIO_CH_MIX`；
5. 关闭定位完成后使用的 AGC 双 PCM 抓取，回收约 64 KB 临时诊断内存；
6. 完整构建后检测到设备在线并成功下载，`stream.bin` 为 3102 B，SHA-256 为 `A2DD1B66E22E28D85E40C770646C9F27D728909637FEB6AC4C3E989171C85ED7`。

注意：当前 `rdx_mvp0_protocol.c` 和 `rdx_record_spike.c` 中仍有历史诊断字符串硬编码打印 `ch=2` 和 stereo `opus_format`。它们不参与 Encoder 配置，也不是最终格式证据；后续应改成读取实际 `stream_enc_fmt`，防止日志误导。最终格式应以生成配置、运行时 Encoder 参数、Opus 离线解码和 APP 实听共同判定。

- RTC 保持当前既有实现与配置，本阶段不改；
- `RDX_ABILITY_RECORD_PAUSE_RESUME` 仅在阶段 4 完成后打开；
- 不打开 `LOCAL_STORAGE`、`FLASHNOTE`、`RECORD_MARK` 和 `CALL_RECORDING`；
- 广播 Ability、APP 页面、实际命令和验收用例保持一致。

## 13. 验收标准

### 13.1 协议

- AppKey、Bound、链路加密、CCC 或 Payload 门控任一不满足时，不会打开任何音频资源；
- START/STOP 和状态 ACK 与参考闭源库接口及当前有效调用参数一致；
- Wire 状态和内部状态显式转换；
- malformed、未知 scene 和不支持 format 不越界、不误启动；
- START 成功状态只发送一次，且在 Pipeline 和有效编码帧确认后；
- 控制 ACK 与音频通知共享 TX 时由单一调度器保证优先级；
- 解绑/恢复出厂的延迟断开只在对应 ACK 实际发送成功后计时；
- 断连或 CCC 关闭后不再发送音频，恢复连接/CCC 后状态为已停止。

### 13.2 音频

- 物理输入和编码前 PCM 均为 PA3 mono、16 kHz、16 bit，不经过 Channel Expander；
- raw Opus 已可被离线解码，APP 也已确认清晰播放；
- 帧长约 80 B、周期 20 ms、码率 32 kbps，与状态上报一致；
- 前 10 帧预热丢弃、STOP 尾帧丢弃与接收时长差异可按统计精确对账；
- 无持续全零、削顶、声道错位、周期爆音、持续失真和异常静音；
- 首版只要求声音可懂；USB Speaker 的声学回声记录样本，但不作为首版阻断项；
- PA3 单 MIC、AGC 前后 PCM、mono Opus 离线解码和 APP 播放均已完成链路验收。

### 13.3 BLE

- warmup_dropped、produced、enqueued、sent、overflow_dropped、stop_discarded 和接收端帧数可对账；
- 2 小时连续录音队列不持续升高；
- 无未解释丢帧；
- ATT cbuf 满可恢复；
- 有效 ATT Value Payload 不足时拒绝 START，不截断、不私自分片；
- 控制命令在录音流期间仍可响应；
- 不新增 GATT Service/Characteristic/Handle/UUID；允许新增独立 Pipeline UUID；
- 若调整连接参数，有手机接受/拒绝两条路径测试。

### 13.4 USB/系统

- USB Speaker 不掉音；
- USB MIC/CVP 不失效；
- USB Host 选择 16/44.1/48 kHz 时，RDX START 均按互斥策略安全拒绝，不改变 USB 音频配置；
- HID 不失效；
- 不发生 USB 重枚举；
- 不出现 `vmalloc_`、P33 soft reset 或音频 ASSERT；
- START/STOP 100 次后各内存池回到稳定水位；
- RDX OFF 不注册录音任务、回调、定时器或运行时资源，最终 Map 也不包含 RDX 专用 AI_TX/Encoder/Opus/Pipeline 增量。

### 13.5 构建和静态检查

- RDX ON 干净构建；
- RDX OFF 干净构建；
- Map 中 Encoder、AI_TX、Opus 和 RDX 新模块增量已记录；
- 官方 `librdxApp.a` 使用边界明确；
- 不因录音移植整体链接闭源 `rdx_protocol.c.o`；
- `git diff --check` 通过；
- `.x6flow`、`stream.bin` 生成来源和工具版本可追溯。

## 14. 风险清单

| 风险 | 等级 | 处理 |
| --- | --- | --- |
| 目标 APP 目前只有单轮清晰录音确认 | 中 | 已有最小 Golden Trace；继续归档最终 mono 日志、100 次 START/STOP 和 2 小时连续录音 |

| Opus/Encoder 重新触发内存峰值 | 高 | 分阶段采样各内存池，队列固定，不盲目扩 ATT RAM |

| Spike 误启用“AI翻译”分组 | 中 | 工具中先选择最小“智能语音”分组再 enable，检查生成差异 |

## 17. 下一步

最小在线会议录音链路已经通过，V23 `record_mode` 已修正为 single，APP 单声道显示和在线录音均已实测通过；不再修改 80 B Opus 帧、98 B Notify、DLE/2M PHY 和 mono Pipeline。下一步进入稳定性收敛：

1. 归档一份最终 mono 版本完整串口日志，记录 START、`record_mode=0`、Opus TOC、前 10 帧预热、连续发送、STOP 和资源恢复；
2. 使用同一 APP 完成 100 次 START/STOP，确认无状态残留、无内存水位下降且每轮声音清晰；
3. 连续录音至少 2 小时，核对 produced/sent/drop、APP 时长和队列水位；
4. 覆盖断连、CCC off、重复 START/STOP、USB 音频 busy 拒绝和再次连接后的恢复；
5. 上述稳定性通过后，再决定是否进入 PAUSE/RESUME，不提前加入 EQ、DNS、AEC 或本地存储。
