# AC710N RDX BLE 名称查询与修改移植方案

> 文档状态：方案、代码、静态检查和完整构建已完成，硬件回归待执行
>
> 目标工程：AC710N/BR56 Type-C 专用 PC 模式
>
> 参考工程：`t2616cc-firmware/`，仅作为只读行为证据，不直接复制实现
>
> 日期：2026-08-14

## 1. 结论

本次只移植 RDX BLE 名称查询和修改，不移植经典蓝牙名称命令。推荐方案为：

1. 在协议层增加 `cblename` 查询和 `blename` 修改命令，只负责有界解析与 ACK 编码；
2. 新增独立 `rdx_ble_name.[ch]`，作为 BLE 名称唯一业务入口；
3. 将用户 BLE 名称覆盖值纳入现有 `CFG_RDX_DEVICE_STATE` 版本化状态记录，不复制参考工程的独立 VM ID；
4. BLE Transport 只从名称服务读取有效名称，并提供广播名称刷新接口；
5. GAP Device Name、Advertising Complete Local Name、查询 ACK 和修改 ACK 统一使用同一个有效名称；
6. 默认名称只在产品配置中维护，不新增第二组功能开关或 Ability 位；
7. 修改名称不调用 `bt_modify_name()`、`CFG_BT_NAME` 或 `lmp_hci_write_local_name()`，不触碰经典蓝牙、USB Audio 和 JL 公共业务模块。

选择扩展现有状态记录，而不是新增 `CFG_RDX_BLE_NAME`，主要原因是：Bound 和用户名称覆盖值都属于 RDX 自有可变设置；恢复出厂可以通过一次 VM 写入同时回到“未绑定 + 无用户覆盖”，有效名称自然重新取自 `RDX_COMPAT_LOCAL_NAME`，不会产生两个 VM 一成功一失败的半恢复状态。

## 2. 范围和非目标

### 2.1 本次范围

- 查询当前 RDX BLE 名称；
- 修改并持久化 RDX BLE 名称；
- 冷启动恢复上次成功修改的名称；
- GAP Device Name 特征值读取新名称；
- 未连接广播立即切换到新名称；
- 已连接修改后，当前查询立即生效，下一次广播使用新名称；
- 恢复出厂时清除用户覆盖，使有效名称恢复为 `RDX_COMPAT_LOCAL_NAME`；
- V1 `rdx_device_state` 到 V2 的兼容读取；
- RDX ON/OFF 构建门控、日志和目标硬件验收。

### 2.2 明确不包含

- `*APP#cbtname#` / `*APP#btname#` 经典蓝牙名称业务；
- 修改 `bt_cfg.edr_name`、`CFG_BT_NAME` 或 EDR Controller Local Name；
- BLE MAC、AuthKey、Label SN、Product Code、Factory Code 等量产身份修改；
- 为名称业务新增 Device Ability 位；
- 为查询和修改分别增加产品开关；
- 修改通用 JL BLE 框架或 USB/UAC/HID 模块；
- 为名称 ACK 增加自定义 ATT 分片协议；
- 修改只读参考工程 `t2616cc-firmware/`。

## 3. 术语和一致性合同

### 3.1 四个必须分开的概念

| 术语 | 含义 | 当前所有者 |
| --- | --- | --- |
| 默认 BLE 名称 | 出厂和恢复出厂采用的产品默认值 | `RDX_COMPAT_LOCAL_NAME` |
| 候选 BLE 名称 | APP 本次请求写入、尚未提交的值 | 协议调用栈 |
| 有效 BLE 名称 | 已通过校验并被状态模块接受的当前值 | `rdx_ble_name` |
| 经典蓝牙名称 | EDR/BR 名称，来自 `bt_cfg.edr_name` | JL 原生 BT 配置 |

候选名称只有在 VM 写入成功后才能成为有效名称。持久化失败时，查询、GAP 和广播必须继续返回旧的有效名称，不能回显或暂存未提交的候选值。

有效名称的选择规则只有一条：

```text
存在合法用户覆盖值  -> 用户覆盖值
不存在用户覆盖值    -> RDX_COMPAT_LOCAL_NAME
```

因此 `RDX_COMPAT_LOCAL_NAME` 是唯一的产品默认名称配置源；VM 不保存第二份“默认名称”，只保存用户修改产生的覆盖值。

### 3.2 单一值、多处投影

```text
                         ┌─ cblename 查询 ACK
RDX_COMPAT_LOCAL_NAME / 用户覆盖值 ──► 有效 BLE 名称 ─┼─ blename 修改 ACK
                         ├─ GAP Device Name (0x0003)
                         └─ Advertising Complete Local Name
```

四个对外入口不得各自保存一份名称。`rdx_identity` 不再拥有 Local Name，Transport 也不保存名称副本。

## 4. 当前工程事实

### 4.1 实施前 BR56 基线

本批实施前，名称仍是编译期常量：

- `rdx_mvp0_compat_config.h` 定义 `RDX_COMPAT_LOCAL_NAME`；
- `rdx_identity_get_local_name()` 直接返回该常量；
- `rdx_ble_transport_br56.c` 在广播组包和 GAP Device Name 读取时调用 Identity；
- `rdx_mvp0_protocol.c` 尚未识别 `cblename` 和 `blename`；
- `rdx_device_state` 目前是 4 B V1 记录，只包含 `version`、`bound` 和保留字节；
- RDX 初始化顺序为 State → Identity → Protocol → BLE Transport。

当前产品 `TCFG_APP_BT_EN=0`，RDX Ability 未声明 Classic Bluetooth。虽然 `user_cfg.c` 中存在 `bt_modify_name()`，它操作的是 `CFG_BT_NAME` 和 `bt_cfg.edr_name`，不应被 BLE 名称业务复用。

### 4.2 参考工程行为

参考工程提供：

```text
*APP#cblename#             查询 BLE 名称
*DEV#cblename#<result>#<name>#

*APP#blename#<name>#       修改 BLE 名称
*DEV#blename#<result>#<name>#
```

参考调用链为：协议事件 → `rdx_app.c` → `rdx_ble_server_ble_name_set_handle()` → `rdx_ble_server_get/set_local_name()`。名称保存在 `VM_RDX_BLE_NAME`，参考上限为 24 B，广播从 `g_rdx_ble_server_info.ble_local_name` 组包。

该参考实现证明了命令字、ACK 字段顺序、24 B 上限、持久化需求和恢复默认行为，但不适合原样复制。

### 4.3 参考实现不能照搬的原因

| 问题 | 参考工程表现 | 本工程处理 |
| --- | --- | --- |
| 模块耦合 | 名称、VM、广播和协议回包集中在 `rdx_ble_server.c` | 拆为协议、名称服务、状态存储、Transport |
| VM ID 冲突 | 使用 `VM_RDX_BLE_NAME=150` | 当前 BR56 的 150 已是 `VM_ALARM_NAME_3`，禁止复制 |
| 缓冲边界 | `char[24]` 同时作为 24 B 内容和 C 字符串 | 使用 24 B 内容 + 1 B NUL |
| 无界字符串 | 存在 `sprintf()`、`strlen()` 依赖输入终止符 | 全程使用 ATT Payload 的显式长度 |
| 截断语义 | 超长名称被静默截断 | 非法长度明确失败，绝不静默改名 |
| 写入长度 | 默认路径和修改路径写入长度不一致 | 固定版本化记录，一次写完整结构 |
| 失败回显 | VM 失败时可能回显未提交候选值 | 失败 ACK 返回旧的有效名称 |
| 广播刷新 | 修改名称后未形成清晰的立即刷新合同 | Transport 明确处理连接态和广播态 |
| 身份混用 | BLE 名称保存在 BLE Server 内部 | 可变名称从不可变 Identity 中移出 |

## 5. Wire 合同

### 5.1 查询

请求必须逐字节完全等于：

```text
*APP#cblename#
```

成功响应：

```text
*DEV#cblename#0#<effective_name>#
```

名称服务未初始化等内部异常响应：

```text
*DEV#cblename#1##
```

查询只允许在 `app_ready=1` 后执行，与当前 `authsn`、`cofftime` 等管理命令使用同一认证门控。多余字段、缺字节或错误结尾均按畸形查询记录并丢弃。

### 5.2 修改

请求格式：

```text
*APP#blename#<candidate_name>#
```

成功响应：

```text
*DEV#blename#0#<effective_name>#
```

名称校验或 VM 写入失败时：

```text
*DEV#blename#1#<old_effective_name>#
```

失败 ACK 返回旧有效名称，不回显未提交候选值。相同名称属于幂等成功：跳过 VM 写入和广播重启，仍返回 `result=0`。

### 5.3 名称字段规则

兼容基线保持参考工程的 24 B 上限：

```c
#define RDX_BLE_NAME_MAX_LEN 24
```

规则按字节而不是 Unicode 字符数计算：

- 长度为 1～24 B；
- 接受可打印 ASCII `0x20`～`0x7E`；
- `#` 是协议分隔符，不允许出现在名称中；
- 至少包含一个非空格字符；
- 不接受 NUL、控制字符、空名称和静默截断；
- 本阶段不开放 UTF-8 多字节名称，避免 APP 展示、字节上限和截断边界不一致。

默认名称也必须通过相同规则，并在编译期检查长度不超过 24 B。

### 5.4 ATT 长度约束

24 B 名称对应的最长查询 ACK 为 41 B，最长修改 ACK 为 40 B，因此 ATT MTU 至少需要 44，才能把完整响应放入单个 ATT Payload。当前 Transport 不做隐式协议分片；目标 APP 必须像参考产品一样完成足够大的 MTU 交换。

若 `rdx_ble_transport_send()` 因有效 Payload 不足而失败：

- 查询没有状态副作用，只记录 TX 失败；
- 修改已经成功落盘时不回滚名称，遵循现有“状态已提交但 ACK 失败，通过重连和幂等查询收敛”的规则；
- 实机验收必须覆盖 24 B 边界名称并确认协商 MTU，不得只测短名称。

## 6. 方案比较

| 方案 | 模块化 | 配置/持久化 | 入侵范围 | 一致性 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 原样复制参考 `rdx_ble_server` | 差 | 独立 VM 150 冲突 | 大 | 多份状态 | 拒绝 |
| 复用 `CFG_BT_NAME` / `bt_modify_name()` | 差 | 复用 JL EDR 配置 | 表面小、跨域副作用大 | 混淆 BLE/EDR | 拒绝 |
| 独立 `rdx_ble_name` + 新 VM ID | 好 | 需新增 ID | 中 | 恢复出厂跨两次 VM 写 | 备选 |
| 独立 `rdx_ble_name` + 扩展现有 State | 好 | 复用 `CFG_RDX_DEVICE_STATE` | 中且局部 | 单记录事务、可迁移 | 采用 |

采用方案不会修改 JL 公共 BLE API，也不要求 `user_cfg.c` 增加 RDX 判断。新增代码全部位于 RDX 目录，现有模块只增加最小接缝。

## 7. 目标模块边界

### 7.1 依赖方向

```text
rdx_mvp0_protocol
        │  query / set
        ▼
rdx_ble_name ───────────────► rdx_device_state
        ▲                            │
        │ get effective name         │ CFG_RDX_DEVICE_STATE
        │                            ▼
rdx_ble_transport_br56          JL syscfg
        │
        ├─ GAP Device Name
        └─ Advertising Local Name

rdx_identity ──► MAC / Auth / SN / Manufacturer identity
             （不再提供 Local Name）
```

协议层不得直接访问 VM，状态模块不得调用 BLE API，Transport 不得解析 RDX 文本命令。

### 7.2 `rdx_ble_name.[ch]`

新增模块是 BLE 名称的唯一业务入口，建议概念接口为：

```c
const char *rdx_ble_name_get(void);
int rdx_ble_name_set(const u8 *name, u16 len, u8 *changed);
```

职责：

- 校验名称长度和字符合同；
- 向 `rdx_device_state` 提交名称变更；
- 只在状态模块成功后暴露新有效名称；
- 相同值返回幂等成功并报告 `changed=0`；
- 不解析命令、不编码 ACK、不操作 BLE Handle。

### 7.3 `rdx_device_state.[ch]`

继续作为 RDX 自有可变设置的版本化持久化聚合，职责扩展为：

- 保存 Bound 和可选的用户 BLE 名称覆盖值；
- 兼容读取 V1 记录；
- 校验 V2 结构长度、版本、Bound、名称长度和 NUL 终止；
- 所有变更先构造 next state，VM 完整写入成功后再替换 RAM；
- 恢复出厂一次写入默认聚合状态；
- 对上层隐藏 `syscfg_read()` / `syscfg_write()`。

它不负责 Wire 规则或广播刷新。

### 7.4 `rdx_mvp0_protocol.c`

协议层增加两个有界 Handler：

- `rdx_mvp0_handle_ble_name_query()`；
- `rdx_mvp0_handle_ble_name_set()`。

职责：

- 检查 `app_ready` 和 `state_transition_pending`；
- 基于 `(data, len)` 解析，禁止直接对 ATT 输入调用 `strlen()`；
- 调用名称服务；
- 修改成功且 `changed=1` 时通知 Transport 刷新名称投影；
- 用固定上限缓冲和 `snprintf()` 编码 ACK；
- 记录 RX、校验结果、VM 结果、刷新结果和 TX 返回值。

### 7.5 `rdx_ble_transport_br56.c`

Transport 的两处名称读取改为 `rdx_ble_name_get()`：

- `rdx_ble_fill_adv_data()`；
- `RDX_HANDLE_GAP_NAME` ATT read callback。

新增内部刷新入口，例如：

```c
int rdx_ble_transport_refresh_local_name(void);
```

刷新只更新 RDX 自己的 BLE Handle，不操作其他第三方协议、通用 BT 名称或 USB 状态。

### 7.6 `rdx_identity.[ch]`

删除 `rdx_identity_get_local_name()`。Identity 继续只管理：

- BLE MAC；
- AuthKey、Wi-Fi MAC、Label SN；
- GATT Identity 读值；
- Manufacturer Data 中的产品身份、Bound 和 Ability 投影。

可变用户名称不是不可变产品身份，继续放在 Identity 会制造错误所有权。

## 8. 状态记录与兼容迁移

### 8.1 V2 记录

继续使用：

```c
#define CFG_RDX_DEVICE_STATE 15
```

不新增 VM ID。建议把状态版本从 1 升为 2，并保持固定 32 B：

```c
#define RDX_DEVICE_STATE_VERSION 2

typedef struct {
    u8 version;
    u8 bound;
    u8 ble_name_len; /* 0 = no user override, 1..24 = override length */
    u8 reserved0;
    char ble_name[RDX_BLE_NAME_MAX_LEN + 1];
    u8 reserved1[3];
} rdx_device_state_t;
```

必须保留编译期 `sizeof(rdx_device_state_t) == 32` 检查。`ble_name_len=0` 表示没有用户覆盖值，此时 `ble_name` 全部写零；`ble_name_len=1～24` 表示存在用户覆盖，且 `ble_name[ble_name_len]` 必须是 NUL，其余未用字节写零。

`rdx_ble_name_get()` 不把默认名称复制进状态记录，而是按以下规则返回：

```c
return state.ble_name_len ? state.ble_name : RDX_COMPAT_LOCAL_NAME;
```

用户把名称设置回 `RDX_COMPAT_LOCAL_NAME` 时，名称服务应将其规范化为“清除覆盖值”，避免 VM 长期保存一份与产品默认配置相同的副本。

### 8.2 为什么不使用参考 VM ID

参考工程把 `VM_RDX_BLE_NAME` 定义为 150；当前 BR56 `syscfg_id.h` 的 150 已用于 `VM_ALARM_NAME_3`。复制该 ID 会造成名称和闹钟数据互相覆盖，属于确定性数据破坏风险。

即使改用当前空闲的用户 ID 17，也会让恢复出厂跨 `CFG_RDX_DEVICE_STATE` 和名称 VM 两个记录，无法保证单次提交。本方案因此不分配 ID 17。

### 8.3 V1 兼容读取

现有已烧录设备可能持有 4 B V1：

```text
version=1, bound, reserved[2]
```

读取策略：

1. `syscfg_read()` 返回 4 且 `version=1`、`bound<=1` 时，保留原 Bound；
2. 在 RAM 中形成 `ble_name_len=0` 的 V2 快照，有效名称由 `RDX_COMPAT_LOCAL_NAME` 提供；
3. 启动阶段不为了迁移主动擦写 VM，避免每次异常启动反复写 Flash；
4. 下一次真实状态变化（改名、绑定变化或恢复出厂）直接写完整 V2；
5. V1 未发生状态变化时可以长期兼容读取，不影响广播和查询。

V2 用户覆盖字段损坏时保留合法 Bound、在 RAM 中清除覆盖并回退 `RDX_COMPAT_LOCAL_NAME`，同时记录原因；同样不在启动阶段反复修复写入。未知版本、非法 Bound 或完全读取失败时，整体回退“未绑定 + 无用户覆盖”。

### 8.4 写入事务

```text
候选名称
   │
   ├─ 校验失败 ──► 状态不变，失败 ACK 返回旧名称
   │
   └─ 校验成功
          │
          ├─ 与有效名称相同 ──► 不写 VM，不刷新广播，成功 ACK
          │
          └─ 构造 next_state
                 │
                 ├─ syscfg_write != sizeof(V2) ──► RAM 不变，失败 ACK
                 └─ 完整写入成功 ──► 提交 RAM，刷新 BLE 投影，成功 ACK
```

不先改 RAM 再尝试持久化，也不在写失败时用候选值填充 ACK。

## 9. 运行时行为

### 9.1 启动

推荐顺序保持为：

```text
rdx_device_state_init
        ↓
rdx_ble_name_init
        ↓
rdx_identity_init
        ↓
rdx_mvp0_protocol_init
        ↓
rdx_ble_transport_init
        └─ 从 rdx_ble_name_get() 生成 GAP/广播名称
```

名称服务不创建任务、定时器或动态内存，不改变现有 RDX 启动资源模型。

### 9.2 查询时序

```text
APP                     Protocol              Name Service        Transport
 │ *APP#cblename#          │                       │                  │
 ├────────────────────────►│ app_ready 检查        │                  │
 │                         ├──────────────────────►│ get effective    │
 │                         │◄──────────────────────┤                  │
 │ *DEV#cblename#0#name#   │                       │                  │
 │◄────────────────────────┤                       │                  │
```

查询是纯 RAM 读取，不在每次命令时访问 VM。

### 9.3 修改时序

```text
APP                     Protocol              Name Service/State    Transport
 │ *APP#blename#name#      │                         │                   │
 ├────────────────────────►│ 有界解析/校验           │                   │
 │                         ├────────────────────────►│ 写 V2、提交 RAM   │
 │                         │◄────────────────────────┤ result/changed    │
 │                         │                         │                   │
 │                         ├────────────────────────────────────────────►│
 │                         │      changed=1 时刷新名称投影               │
 │                         │◄────────────────────────────────────────────┤
 │ *DEV#blename#0#name#    │                         │                   │
 │◄────────────────────────┤                         │                   │
```

持久化成功是名称修改成功的提交点。新名称在 RAM 提交后立即成为有效名称，因此当前连接内再次执行 `cblename` 或读取 GAP Device Name 时会立刻得到新值，然后设备发送成功 ACK。

这里的“立即生效”不等于“立即断开并重新广播”。广播刷新是有效名称到 BLE Transport 的投影：刷新失败不得把 ACK 改成失败后再尝试回滚 VM，否则会形成“APP 收到失败但重启后名称已改变”的更严重歧义。刷新失败必须记录为 degraded，并在下一次合法广播启动时自动使用有效名称。

### 9.4 广播态和连接态

| Transport 状态 | 修改后的行为 |
| --- | --- |
| 已连接（APP 改名命令的实际路径） | 不主动断连；ACK 前提交新有效名称，GAP 读取和协议查询立即返回新值；等用户、APP 或链路正常断开后，下一轮广播使用新值 |
| 未连接且正在广播（仅内部调用或未来入口可能出现） | 记录原广播状态，关闭本 Handle 广播，重新组包并恢复广播 |
| 广播本来关闭 | 不擅自开启；下一次正常 `adv_enable(1)` 时使用新值 |
| Transport 正在退出 | 不访问已释放 Handle；名称已持久化，下一次启动恢复 |

RDX Wire 改名命令只能在 BLE 已连接且 `app_ready=1` 时到达，所以正常用户路径不会出现“改名时仍在广播”。本方案明确不为了改名主动断开：参考工程的名称 setter 只写名称并回 ACK，没有触发断连；强制断开还会打断在线录音和当前 RDX 会话。刷新接口仍必须先判断 `hdl`、`initialized`、连接和广播状态。

### 9.5 GAP 和手机缓存

GAP Device Name 回调每次从名称服务读取，因此固件侧连接内查询立即一致。但手机系统可能缓存扫描名称或已连接设备名称；这是客户端缓存行为，不能通过强制断连、修改 BLE MAC 或重启整机规避。

验收时应同时观察：

- RDX `cblename` 查询；
- 原始广播包中的 Complete Local Name；
- GAP Device Name 0x2A00 读取；
- APP/系统 UI 缓存刷新时机。

### 9.6 绑定、解绑和恢复出厂

- APP 绑定只改变 Bound，保留用户 BLE 名称；
- APP 解绑只清除 Bound，保留用户 BLE 名称；
- `*APP#default#` 同时恢复未绑定并清除用户名称覆盖值；
- 恢复出厂写入完整默认 V2 后按现有流程成功 ACK、延迟断开 RDX BLE；断连后广播名称重新取自 `RDX_COMPAT_LOCAL_NAME`；
- BLE MAC、AuthKey、Label SN 和 USB/JL 参数不因改名或恢复名称而变化。

## 12. 错误语义和日志

### 12.1 错误矩阵

| 场景 | 状态变化 | Wire 行为 |
| --- | --- | --- |
| 未 `app_ready` | 无 | 丢弃并记录 |
| 查询报文不完全匹配 | 无 | 丢弃并记录 malformed |
| 修改缺结尾 `#` 或字段数错误 | 无 | 丢弃并记录 malformed |
| 名称为空、全空格、超长或含非法字符 | 无 | `blename result=1`，携带旧有效名称 |
| 名称与当前值相同 | 无 VM 写、无刷新 | `result=0` |
| VM 写失败/短写 | RAM 和广播不变 | `result=1`，携带旧有效名称 |
| VM 成功、广告刷新失败 | 新名称已提交 | `result=0`，记录 degraded，后续广播周期恢复 |
| VM 成功、ACK 发送失败 | 新名称已提交 | 不回滚；重连后查询收敛 |
| 状态转换 pending | 无 | 修改返回失败；查询可返回当前有效值 |
| RDX Transport 正在退出 | 名称可持久化 | 不访问失效 Handle，下一次启动应用 |

### 12.2 日志字段

开发日志沿用现有分类，至少记录：

```text
[RDX][RX]      cmd=cblename/blename len=...
[RDX][DROP]    reason=app_not_ready/malformed/invalid_name/transition_pending
[RDX][STATE]   source=v1/v2/default old_len=... new_len=... vm_ret=... changed=...
[RDX][BLE]     name_refresh state=connected/advertising/off ret=...
[RDX][TX]      cmd=cblename/blename result=... len=... ret=...
```

量产日志不要输出 AuthKey 等身份密钥。BLE 名称通常不是秘密，但仍应使用长度受控的 `%.*s`，不能假定外部数据天然 NUL 终止。

建议分两个可审查提交：

### 提交 A：状态与名称服务

这样可以分别审查“持久状态是否正确”和“BLE/Wire 行为是否正确”。任一提交都不得夹带经典蓝牙改名、正式产品身份切换或 USB Audio 改造。

## 15. 硬件回归仍需冻结的外部证据

硬件签收前应使用目标 APP 对参考固件或已知兼容设备采集一次 Golden Trace，确认：

1. 查询 ACK 确实为 `*DEV#cblename#<result>#<name>#`；
2. 修改 ACK 确实为 `*DEV#blename#<result>#<name>#`；
3. 失败 ACK 的 APP 兼容策略；
4. APP 是否只接受 ASCII，以及 UI 允许的最大输入长度；
5. APP 在发名称命令前协商出的 ATT MTU；
6. APP 是否期望改名后设备主动断连。

本方案默认“不主动断连”，因为名称修改不应中止当前 RDX 会话，参考源码也没有在名称 setter 内直接断连。若 Golden Trace 明确要求 ACK 后断连，应复用现有 post-ACK action 生命周期，不能在协议 Handler 中同步阻塞或直接释放 Handle。

## 16. 最终决策摘要

1. 只移植 BLE `cblename` / `blename`，不移植 `cbtname` / `btname`；
2. 新增 `rdx_ble_name`，协议、Identity、Transport 和 VM 职责分离；
3. `RDX_COMPAT_LOCAL_NAME` 是唯一产品默认源；有效名称按“合法用户覆盖优先，否则默认源”解析，GAP、广播和两个 ACK 都从有效名称投影；
4. 可变名称进入 `CFG_RDX_DEVICE_STATE` V2，不新增 VM ID，不复制冲突的 150；
5. V1 兼容读取必须保留 Bound，启动不为迁移主动写 Flash；
6. 名称最大 24 B，可打印 ASCII，不允许 `#`、NUL、控制字符或静默截断；
7. VM 成功才提交 RAM；失败 ACK 返回旧有效名称；幂等设置跳过写入和刷新；
8. APP 改名在当前连接内立即逻辑生效，但设备不主动断连；等 APP、用户或链路正常断开后，下一轮广播自动使用新名称；
9. 恢复出厂一次恢复 Bound=0 并清除用户覆盖，普通绑定/解绑保留用户名称；
10. 保留 `RDX_COMPAT_LOCAL_NAME` 唯一配置，不新增同义默认宏、Ability 位或平行业务开关；
11. 所有新增源码统一受 `TCFG_RDX_ENABLE` 最终门控；
12. 编译通过后仍必须完成目标 APP、MTU、广播/GAP、掉电持久化和 USB Audio 共存实机验收。

本文同时记录目标架构和验收合同。当前代码已按上述边界实施；构建、Map 和目标板硬件结果以第 17 节实施记录为准。
