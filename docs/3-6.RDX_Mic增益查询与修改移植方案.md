# AC710N RDX Mic 增益查询与修改移植方案

> 文档状态：方案已实现，核心 Override 路径已通过目标 APP 与硬件回归
> 日期：2026-08-14
> 适用工程：AC710N / BR56 Type-C 专用 PC 模式
> 参考工程：`t2616cc-firmware/`（AC701N / BR28）
> 继承文档：`3-2.RDX在线录音业务移植评估与实施路线.md`、`3-3.RDX录音基础设施架构优化方案.md`、`3-4.RDX在线录音暂停恢复与录音标记移植说明.md`

## 1. 结论

本产品应移植 `cmicgain` 和 `micgain`，但不移植 AC701 的双 MIC、通话录音和独立 VM 实现。推荐方案如下：

```text
MVP0 Protocol
    -> Mic Gain Service
        -> RDX Device State V3
        -> BR56 Record Audio Adapter
            -> rdx_record ADC node
```

职责与生效语义固定如下：

1. MVP0 Protocol 只严格解析 Wire 命令、调用 Service 并发送 ACK；它不读写 VM，也不接触 ADC。
2. Mic Gain Service 持有模式、范围、镜像双字段和事务语义；查询返回已配置的 SDK Mic Gain Level，不读取瞬时 ADC 寄存器。
3. RDX Device State V3 在现有 `CFG_RDX_DEVICE_STATE` 中原子保存 Gain Override，与绑定状态和 BLE 名称覆盖共用一次 VM 写入、共用恢复出厂路径。
4. Record Engine 在每次逻辑录音 START 时取一次 Session Gain Snapshot；PAUSE/RESUME 仍复用该快照。
5. BR56 Adapter 将 Session Gain Snapshot 原值写入 `rdx_record` 专用 ADC 节点，由 `audio_adc_mic_set_gain()` 负责 SDK Level 到硬件的转换。不得使用面向 ESCO 的 `audio_adc_file_set_gain()`，不得影响 USB MIC/CVP、蓝牙通话、ANC 或其他 ADC 流程。

当前产品只支持 APP 已实际访问的 `mode=0`。它是 Conference Recording 的单物理 MIC 拓扑：PA3 / ADC0；当前 `rdx_record` 音频资源的 ADC0 `mic_gain` 为 19、前级增益为 1。Wire 协议仍有两个增益字段，因此本产品采用**镜像增益对**：两个字段必须相等，校验通过后只取一个 0 至 19 的 SDK Mic Gain Level，并原值传给 ADC0。`mode=1` 明确返回失败，不伪装为 Call Recording。

设置在 VM 成功落盘后立即应答；若当前存在录音会话，新值只在**下一次逻辑录音会话**生效。当前会话以及其中的 Resume 保持 START 时的快照，避免运行中模拟增益突变、爆音或会话内音量不一致。

## 3. 术语与产品边界

本章在当前功能范围内定义以下术语，避免把参考工程的双 MIC、通话录音或 dB 预设带入目标产品实现。

| 名称 | 当前产品含义 | 明确不等同于 |
| --- | --- | --- |
| Configured Gain | 用户配置或工厂默认解析出的未来会话 SDK Mic Gain Level | ADC 硬件寄存器实时读回值、dB 值 |
| Session Gain Snapshot | START 时冻结、整个逻辑 Session 不变的 SDK Mic Gain Level | 每次 Resume 重新读取的最新配置 |
| Factory Gain | 无 Gain Override 时从 RDX ADC0 音频资源读取的 `mic_gain` | 把旧 VM 内容或协议宏固化成“默认值” |
| Gain Override | 用户成功设置并落盘的 SDK Mic Gain Level | 运行中的临时音量调整 |
| SDK Mic Gain Level | Wire 和 `audio_adc_mic_set_gain()` 共用的 0 至 19 Level | ADC 寄存器值、`mic_pre_gain`、AGC |
| Tool Gain Preset | 可视化工具显示的 `-6/-2/0/3/9/15/21/27 dB` ADC 节点预设 | Wire 范围、运行时 API 范围 |
| Mirrored Gain Pair | 协议中的两个相等字段，共同代表 PA3/ADC0 | 两个真实物理 MIC |

现有 `rdx_record` 为 `16 kHz / mono / 32 kbps / 20 ms / raw Opus`，只含一个 PA3 物理输入。`src/音频流程/智能语音.x6flow` 的已选中 `rdx_record` 分组使用 `ADC1` 配置，启用 ADC0；实际启用的 ADC0 工具默认模拟增益为 19、前级增益为 1，未使用的 ADC1 保持原值 7。ADC0 是本功能的唯一物理目标。

不调整前级增益 1（6 dB）和 AGC 参数。RDX Mic Gain 只对应 `struct adc_file_param::mic_gain`；APP 值经校验后原值保存、原值查询、原值应用。

## 4. Wire 合同

### 4.1 下行

```text
APP -> Device
*APP#cmicgain#<mode>#
*APP#micgain#<mode>#<gain1>#<gain2>#
```

目前接受：

```text
*APP#cmicgain#0#
*APP#micgain#0#1#1#
```

严格要求：完整末尾 `#`、十进制非负整数字段、无额外字段、`mode=0`、`gain1/gain2` 均在 0 至 19，并且 `gain1 == gain2`。两个字段完整校验后合并为一个 SDK Mic Gain Level；不能接受其中一个值并静默丢弃另一个，也不做产品自定义映射。格式错误沿用现有 MVP0 风格记录 DROP 且不发送伪造 ACK；语法正确但不支持的模式或非法值发送失败 ACK。

### 4.2 上行

参考工程的 `RdxProtocolIndicateOps` 回调签名为 `(result, mode, gain1, gain2)`，命令前缀分别为 `*DEV#cmicgain#` 和 `*DEV#micgain#`。目标实现应编码为：

```text
Device -> APP
*DEV#cmicgain#<result>#<mode>#<gain1>#<gain2>#
*DEV#micgain#<result>#<mode>#<gain1>#<gain2>#
```

成功 ACK 回传当前 Configured Gain。当前音频资源 ADC0 `mic_gain=19`，因此无用户覆盖时的查询结果为：

```text
*DEV#cmicgain#0#0#19#19#
```

`result=0` 表示成功，`result=1` 表示失败。为保持参考兼容性，不新增 Wire 结果码；详细原因只写串口日志。目标 APP 回归日志已确认成功查询和设置 ACK 的字段顺序为 `result#mode#gain1#gain2#`，并确认 APP 在设置后会继续查询当前配置。失败 ACK 的非法模式和非法值填充仍按本节合同执行。

成功查询和成功设置都返回当前 Configured Gain。合法设置因 VM 写入失败时，失败 ACK 返回写入前的 Configured Gain；非法模式或非法字段返回 `0#0`，避免把非法请求值误报为已生效值。

## 5. 参考工程审计

参考实现能提供协议意图，不能直接作为 BR56 实现：

| 项目 | 参考工程行为 | 目标处理 |
| --- | --- | --- |
| 模式 | chat=0、call=1 | 仅开放 0；1 返回失败 |
| 物理拓扑 | chat 使用 MIC0/MIC3，call 使用 MIC2/MIC3 | 仅 PA3/ADC0；只接受镜像增益对 |
| 默认值 | chat=17/17，call=17/13 | 不复制；从目标 RDX ADC0 音频资源读取，当前为 19 |
| 存储 | `VM_RDX_MIC_GAIN=155` 独立保存四个值和标志 | 不占用 155；扩展现有 VM 15 的状态 V3 |
| 查询 | 每次读取独立 VM | 查询已初始化的 RDX State 并解析 Factory Gain/Override |
| 设置 | 越界通道可能被静默跳过，仍可能落盘/成功 | 两字段先完整校验，全部通过才提交 |
| SDK 应用 | APP 0 至 19 原值传入 `audio_adc_mic_set_gain()` | 保持同一接口合同；Adapter 在每个 Capture Period 启动前提交 Session Gain Snapshot |

参考 `rdx_audio_adc_file_get_gain()` 在没有活动 Handle 时可能返回 0，setter 也只在 Handle 存在时运行。因此不能把“读当前 SDK ADC 值”和“写 VM”作为协议真相；二者都会在未录音时失真。目标方案以 Configured Gain 为可查询状态、以 Session Gain Snapshot 为可验证的实际应用输入。

参考工程没有 RDX 自定义映射：`rdx_record_mic_gain_set()` 校验 0 至 19 后原值写 VM，`rdx_record_mic_gain_check()` 再把原值传给 `rdx_audio_adc_file_set_gain()`，后者直接调用 `audio_adc_mic_set_gain()`。BR28 和当前 BR56 的公开头文件都声明同一合同：0 为 -8 dB、19 为 30 dB、步进 2 dB、Level 4 为 0 dB。因此目标工程也直接透传，硬件换算属于 SDK 驱动职责。

## 6. 推荐架构

### 6.1 模块职责

```text
MVP0 Protocol
  strict Wire parse / ACK encode / app_ready gate
        |
        v
Mic Gain Service
  mode and topology policy / range validation / query and set transaction
        |                                      |
        v                                      v
RDX Device State V3                    Record Engine START snapshot
  persistent Gain Override                     |
                                                    v
                                          BR56 Record Audio Adapter
                                          optional ADC initial override
```

建议新增 `rdx_mic_gain_service.[ch]`，不把业务逻辑继续堆入 `rdx_mvp0_protocol.c`。Wire 的两个字段只存在于 Protocol 边界；完成范围和相等性校验后折叠为单值。Service 最小接口为：

```c
int rdx_mic_gain_get_configured(u8 mode, u8 *gain);
int rdx_mic_gain_get_override(u8 mode, u8 *valid, u8 *gain);
int rdx_mic_gain_set_configured(u8 mode, u8 requested, u8 *effective);
```

Protocol 负责解析 `gain1/gain2`、校验两者都在 0 至 19 且 `gain1 == gain2`，成功后只把一个值传给 Service；查询和设置 ACK 再编码为 `{gain, gain}`。Service 负责 `mode=0` 策略、Factory Gain 解析、单值 Override 读写和幂等写跳过。Protocol 不泄漏物理 ADC 编号；Service/VM/Engine/Adapter 都不保存伪双 MIC 数组；Adapter 不认识 Wire mode 或 VM。

### 6.2 默认值与配置唯一源

BLE 名称的工厂值继续仅由 `RDX_COMPAT_LOCAL_NAME` 定义。Mic Gain 不应放进该身份配置头，也不应在 `rdx_mvp0_compat_config.h` 再复制一个默认增益宏。

Mic Gain 的 Factory Gain 唯一来源是已选中 `rdx_record` 音频资源中的 ADC 配置。增加 Adapter 只读接口，例如：

```c
int rdx_record_audio_br56_get_factory_gain(u8 *gain);
```

该接口通过 JL 已有配置读取 API 读取冻结的 RDX ADC 节点配置（当前为 `pipeline-AI-voice / 0x5475` 的 `ADC1`，ADC0 启用），提取一个 ADC0 `mic_gain`。读取时必须校验：仅 ADC0 被启用、`mic_gain` 在 0 至 19；失败时 Mic Gain Service 拒绝 Factory Gain 查询，而不是猜测默认值。无用户 Override 的录音 START 不调用该查询接口，也不把 Factory Gain 再写回 ADC，完全沿用音频资源原始路径。Protocol 查询 ACK 才把该单值镜像为两个相同字段。

可视化工具在 ADC 节点中显示的 `-6/-2/0/3/9/15/21/27 dB` 是资源编辑预设；运行时以 `audio_adc_mic_set_gain()` 的公开 0 至 19 接口为准。目标代码不增加换算公式或查表，也不根据工具显示值反查协议值。若未来 SDK 改变该接口合同，只在 BR56 Adapter 中适配，Wire、Service、VM 和 Engine 不变。

这样，用户未修改时查询到的是音频资源原始 `mic_gain`，当前为 19；用户设置 0 至 19 后查询仍返回同一 Level。用户覆盖不会被固件升级覆盖，恢复出厂清除覆盖后又回到新固件音频资源中的 Factory Gain。

### 6.3 持久化与恢复出厂

优先扩展现有 `CFG_RDX_DEVICE_STATE=15` 为 V3，保持 32 B，不新增 VM ID：

| V2 偏移 | V3 含义 | 长度 |
| ---: | --- | ---: |
| 0 | `version=3` | 1 |
| 1 | `bound` | 1 |
| 2 | `ble_name_len` | 1 |
| 3 | 保留 | 1 |
| 4 至 28 | `ble_name[25]` | 25 |
| 29 | `mic_gain_override_valid` | 1 |
| 30 | `mic_gain` | 1 |
| 31 | 保留 | 1 |

V2 的后三个保留字节只复用前两个，最后一个继续保留，因此 ABI 大小仍为 32 B。初始化兼容 V1（4 B）和 V2（32 B），将其读作“无 Gain Override”；V3 则校验 `valid` 为 0 或 1、有效 `mic_gain` 在 0 至 19。迁移保持延迟写入，首次真实状态变更再写 V3，避免仅升级固件就增加 flash 擦写。

写入事务规则：先构造完整 `next_state`，`syscfg_write()` 返回完整 32 B 后才更新 RAM 状态和返回成功。重复设置为相同的 Override 时跳过 VM 写。VM 失败时 RAM 和 Session Gain Snapshot 均不变。

现有 `*APP#default#` 已通过 `rdx_device_management_restore_defaults()` 统一进入 `rdx_device_state_restore_defaults()`。V3 的恢复出厂必须一次 VM 写同时完成：解绑、清 BLE 名称覆盖、清 Gain Override。成功 ACK 后沿用现有 100 ms 延迟断连；重连后 `cmicgain` 应解析当前 Factory Gain，而不是旧用户增益。

### 6.4 实际应用时机

`cmicgain` 是纯只读命令：只从 Device State 读取 Override，或者从音频资源读取 Factory Gain；不创建 Pipeline、不调用 ADC ioctl，也不改变当前或后续录音状态。`micgain` 完成双值相等性校验后只更新 Device State，正在进行的 Session 不发生电平突变。

`rdx_record_engine` 在 START 请求处理的串行点只获取可选的用户 Override，并把 `{valid, gain}` 保存在 Engine 的 Session Runtime。没有 Override 时不解析 Factory Gain。它将该 Snapshot 放进 `rdx_record_audio_open_params`：

```text
START
  -> read optional Gain Override
  -> freeze {override_valid, gain}
  -> no override: open Capture Period 1 with resource defaults
  -> override: open Capture Period 1 with initial ADC override

PAUSE / RESUME
  -> open next Capture Period with the same snapshot

STOP
  -> discard snapshot

next START
  -> read optional Gain Override again
```

Adapter 使用 `jlstream_pipeline_parse(0x5475, NODE_UUID_ADC)` 创建专用 RDX 流程。无 Override 时不读取 ADC 配置、不调用 `NODE_IOC_SET_PARAM`，直接执行原有格式配置和 `jlstream_start()`。

有 Override 时，Adapter 先以冻结的资源配置构造本地 `struct adc_file_cfg`，仅把 ADC0 的 `mic_gain` 改为 Session Gain，然后在 `jlstream_start()` 之前通过逻辑 Source 节点 `NODE_UUID_SOURCE + NODE_IOC_SET_PARAM` 提交一次。ADC Source 对启动前参数做实例内缓存；后续 `adc_ioc_get_fmt()` 读完资源和在线参数后再合入缓存，`adc_file_ioc_start()` 打开 MIC 时自然把该值原样交给 `audio_adc_mic_set_gain()`。该能力属于 ADC 节点现有参数接口的通用启动前语义，不包含 RDX 状态、VM 或协议分支。

`COM3_2026-08-14_18-00-11.log` 显示，启动后立即用物理插件 UUID `NODE_UUID_ADC` 更新会在 ADC 打开前返回 `-2`。`COM3_2026-08-14_18-25-43.log` 进一步证明，同步等待 Stream Event 会形成任务自等待：框架已记录 `event 8`，但回调目标正是阻塞中的 `rdx_record`，最终 `os_sem_pend` 超时。`COM3_2026-08-14_18-31-05.log` 中没有 `cmicgain` 或 `micgain` 命令，但持久化的 `gain_override=1 gain=19` 使每次 START 都执行 20 次 `NODE_UUID_ADC` 重试并失败，证明查询不是故障来源，真正问题是把增益回写做成了所有录音的必经启动步骤。最终实现删除等待和重试，改为“无 Override 完全跳过；有 Override 经 Source 节点启动前提交”。

值链固定为：

```text
Wire gain1 == gain2
    -> one persistent Gain Override
        -> next START freezes {valid=1, gain}
            -> ADC0 cfg.param[0].mic_gain (unchanged)
                -> SOURCE / NODE_IOC_SET_PARAM before start
                    -> adc_file_ioc_start()
                        -> audio_adc_mic_set_gain()
```

日志记录 `wire_gain1`、`wire_gain2`、折叠后的 `configured_gain`、`override_valid` 和 `session_gain`。成功覆盖路径中这些值应相同；无 Override 时 `session_gain=0` 只是“无覆盖”的占位值，不代表硬件被设置为 0。不推导或打印未经 SDK/硬件实测确认的 dB。

覆盖提交必须发生在 `jlstream_start()` 之前、注册为可接收线上帧之前。若有 Override 且 Source 节点拒绝初始参数，START 按既有事务路径回滚 Pipeline、租约和 Destination；无 Override 则不存在该失败点。

绝不调用 `audio_adc_file_set_gain()` / `audio_adc_file_get_gain()`：它们绑定 ESCO 的全局 `esco_adc_f`，不是 RDX `rdx_record` 节点，还存在越界下标判断问题。公共 `adc_file.c` 只补充现有参数接口的实例级启动前缓存，不读取 RDX 状态；不修改 USB Audio.x6flow 或通话 ADC 资源配置。

### 6.5 设置期间的会话策略

| 请求时刻 | 设置 ACK | 实际 ADC 生效 | 查询值 |
| --- | --- | --- | --- |
| RDX IDLE | VM 成功后立即成功 | 下一次 START | 新 Configured Gain |
| RDX STARTING | VM 成功后立即成功 | 本次 Session 不变；下一次 START | 新 Configured Gain |
| RDX STREAMING | VM 成功后立即成功 | 当前 Session 不变；下一次 START | 新 Configured Gain |
| RDX PAUSED / RESUMING | VM 成功后立即成功 | 本次 Session 的 Resume 仍用旧快照；下一次 START | 新 Configured Gain |
| `default` / `unbound` 延迟断连中 | 失败 | 不适用 | 当前已恢复的值或断连 |

这不是“设置失败延迟生效”：成功 ACK 表示持久化的 Configured Gain 已更新。Wire 没有“当前 Session 实际增益”字段，强行在 STREAMING 或 Resume 中直接改 ADC 会造成会话内电平跳变且无法在 ACK 中表达。因此当前产品选择会话快照一致性。

## 7. 错误矩阵与日志

| 场景 | Wire 行为 | 状态变更 | 必要日志 |
| --- | --- | --- | --- |
| AppKey 未完成 | DROP，无 ACK | 无 | `reason=app_not_ready` |
| 查询 `mode=0` | `cmicgain result=0` | 无 | `source=factory|override gain=...` |
| 查询 `mode=1` | `cmicgain result=1 mode=1 gains=0,0` | 无 | `reason=unsupported_mode` |
| 设置合法镜像对、值改变 | `micgain result=0` | 成功写 V3 | `old/new/vm_ret/apply=next_session` |
| 设置相同镜像对 | `micgain result=0` | 跳过 VM | `vm=skip changed=0` |
| 取值越界、两值不等或 mode 非法 | `micgain result=1` | 无 | 精确 `reason=range|mirror|unsupported_mode` |
| VM 写失败 | `micgain result=1`，返回旧值 | 无 | `vm_id=15 vm_ret=...` |
| Factory Gain 资源不合法 | Factory 查询失败；无 Override 的 START 不受影响 | 无 | `source=factory ret=...` |
| 有 Override，Adapter 初始参数提交失败 | START 回滚 | 无新 Session | `adc_gain_prepare result=failed` |
| 无 Override，正常 START | 使用音频资源原始参数 | 无 | `adc_gain_prepare result=skip source=factory` |
| 恢复出厂 | 既有 `default` ACK | 清除 Override | `override=clear source=factory` |

日志必须包含 `mode`、请求的 `gain1/gain2`、折叠后的单值 gain、覆盖来源、VM 结果、`session_id`、`capture_generation`、是否为 `next_session`，但不打印 AppKey 或其他认证数据。Level 不标成 dB。

## 9. 验证矩阵

2026-08-14 已从 `SDK/` 执行 `clean -> all`，新增条件源文件参与编译，链接和固件打包通过且无新增编译告警。目标 APP 和硬件已验证 Gain 0/19、查询/设置 ACK、持久化、幂等写、START/STOP、Pause/Resume 和录音数据链路；以下矩阵继续作为完整产品回归基线，其中无 Override START、异常输入和故障注入仍需按发布流程覆盖。

1. 认证后发送 `*APP#cmicgain#0#`，确认仅收到一次正确字段顺序的 ACK，默认返回音频资源的 `19#19`。
2. 发送 `*APP#micgain#0#1#1#`，确认设置 ACK 后紧随的查询返回 `1#1`；断电重启后仍为 `1#1`。
3. 对 0 至 19 每一档发送相同镜像对并 START，确认 Wire、VM、Session 和 Adapter 日志中的 Level 全部原值一致；至少实测 Level 0、4、19 的硬件响应符合 SDK 接口合同。
4. STREAMING 中设置任意合法镜像对，确认 ACK/查询立即反映新的 Configured Gain，但当前 Session 和其 PAUSE/RESUME 仍记录 START 时快照；STOP 后下一次 START 才应用新值。查询前后不得出现 `adc_gain_prepare` 或录音状态变化。
5. 设置 `0/20`、`1/2`、`mode=1`、超长数值、缺末尾 `#` 和额外字段，确认无 VM/RAM 状态篡改，Wire 行为符合错误矩阵；尤其 `1/2` 必须失败，不能只采用其中一个值。
6. 注入 Protocol 单值折叠、Service、VM、Engine 和 Adapter 日志，确认成功设置后内部始终只有一个 gain，不出现双 MIC 数组或两个值分叉。
7. 注入或模拟 VM 写失败，确认 ACK 返回旧 Configured Gain，重启后也未出现半更新。
8. 故意使音频资源 ADC0 `mic_gain` 超出 0 至 19，确认无 Override 时查询失败但录音仍按资源原路径启动；有 Override 时因 Adapter 需要校验拓扑而拒绝 START。
9. 设置用户 Gain Override 后执行 `*APP#default#`，等 ACK 和延迟断连完成；重连后 `cmicgain#0` 回到当前 Factory Gain，并回归 BLE 名称恢复、解绑和录音强制停止。
10. 覆盖 V1/V2 旧状态、无覆盖 V3、有覆盖 V3 和损坏 V3，确认绑定/BLE 名称迁移不回退，损坏 Gain Override 不被采纳。
11. 回归 USB MIC/CVP、USB Speaker、BLE 名称、RTC、START/STOP、Pause/Resume、Mark；确认 RDX Mic Gain 不改变 ESCO 或 USB ADC 增益。
12. 获取并归档目标 APP 的完整 Mic Gain Golden Trace，尤其确认上行 ACK 字段顺序、失败值和 APP 重试停止条件。
13. 恢复出厂或清除 Override 后连续 START/STOP，确认每次只有 `adc_gain_prepare result=skip`，录音成功且不再出现 `ret=-2`、重试或等待 Stream Event。

## 10. 不在本期范围

- `mode=1` 通话录音、DAC 混录或第二物理 MIC；
- 在线录音中立即切换 ADC 增益；
- Mic pre-gain、AGC、CVP、ANC、USB 麦克风或系统数字音量调节；
- 新 Ability 位、新 GATT Service/Characteristic、新独立 VM ID；
- 修改 APP、修改参考工程或手工修改 Jieli 生成资源。

未来产品拥有两个真实 RDX 录音 MIC 时，应先扩展 Service、持久化结构、Session Snapshot 和 Audio Adapter 的物理拓扑，再解除镜像增益对约束；不能只放宽 `gain1 != gain2` 的协议检查。
