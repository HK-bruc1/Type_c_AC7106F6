# AC710N RDX 录音基础设施架构优化方案

> 文档状态：v1.2，阶段性实施中，已形成中途里程碑
> 编写日期：2026-08-12
> 目标工程：AC710N / BR56 Type-C 有线耳机
> 首版功能基线：8c82a29、a8ab654
> 当前实施里程碑：7713d91、4a5f966、3a1702a、4145d15、e337f80
> 前置文档：docs/3-2.RDX在线录音业务移植评估与实施路线.md
> 适用范围：RDX 录音基础设施、在线会议录音及已知后期录音业务的演进约束

## 1. 文档目的

前两个提交已经完成在线会议录音首版移植，并通过目标 APP 验证：

- START/STOP 主链路可用；
- APP 正确显示单声道；
- PA3 单 MIC 可清晰录音；
- 音频合同为 16 kHz、mono、32 kbps、20 ms、raw Opus；
- 当前 MEETING_V1 单帧 Opus 固定 80 B，完整在线包固定 98 B；
- DLE、2M PHY 和当前 ATT 资源能够承载 50 帧/秒。

首版证明了功能可行，但在本轮迁移开始前仍带有技术 Spike 的结构：

- Wire 解析、状态、Pipeline 生命周期、帧队列和 BLE 发送集中在 rdx_mvp0_protocol.c；
- ai_voice_recoder 公共接口包含 RDX 固定格式；
- adc_file.c 和 agc_node.c 中保留大量默认关闭的抓取、测试音和诊断代码；
- 在线控制包与音频包没有统一的发送所有者；
- 当前 Ability 包含尚未实现的本地存储、暂停、打标和闪记能力。

本文设计从“首版可用”到“可演进的 RDX 录音基础设施”的生产架构。当前里程碑仍只交付在线 START/STOP，并保持已验证的在线协议和音频数据面不变；同时把本地录音、暂停和打标等已知后期业务的领域约束纳入设计，避免固化必然返工的单 Sink 或仅 START/STOP 前提。公共 C ABI 不在设计阶段提前冻结，可随分阶段实现继续演进。

本期实施边界必须按以下口径理解：

- **当前里程碑已实现**：清理和能力配置收敛、通用音频采集租约、常驻 Record Engine 的 START/STOP 子集与固定容量控制面、在线录音生命周期迁移，以及 USB 麦克风抢占的任务上下文交接；
- **本期后续实现**：RDX 专用 Pipeline/BR56 Adapter、解除 `ai_voice_recoder` 依赖、完整 Online Service/Online Destination 边界、统一 TX Scheduler、首包保留与传输接纳，以及完整稳定性和硬件回归；
- **现在只保留架构边界**：多 Destination、Pause/Resume、Mark、Artifact、Catalog、Recovery、Transfer 和其他参考工程后期业务所需的职责归属、标识与演进约束；
- **现在不实现**：上述后期业务的 Wire 命令、运行时状态处理、文件格式、存储任务、恢复流程、上传流程或占位 Service；
- **现在不开放**：Local Storage、Pause/Resume、Record Mark 和 Flashnote Ability。

“纳入领域合同”不等于“本期提前移植业务”。未来业务必须在各自实施阶段补充协议兼容性、资源预算、故障注入和目标硬件验收后才能启用；不得仅凭当前框架已预留扩展点就广播对应 Ability。

## 2. 对 3-2 文档的继承与修正

docs/3-2 保留以下事实基线：

- PA3 physical mono 是当前有效输入；
- Channel Expander 与 stereo Encoder 的组合在本会议链路中造成失真；
- 目标 APP 已接受 mono Opus；
- 当前 USB 音频与 RDX 录音不允许并发；
- 前 10 个编码帧作为预热帧丢弃；
- 80 B Opus 帧、98 B 在线包、一帧一 Notify；
- 当前连接参数、DLE、2M PHY 和 4096 B ATT cbuf 的实测结论；
- 在线业务当前只实现 START/STOP，不实现暂停、本地文件和打标。

本文替代 3-2 中以下生产架构选择：

1. 不再把 ai_voice Pipeline 作为生产录音入口，改用 RDX 专用 Pipeline；
2. 不再让 rdx_mvp0_protocol 直接拥有录音状态和音频生命周期；
3. 不再保留 ai_voice_recoder_open_with_tx 及其中的 RDX 固定格式；
4. 不再把当前 16 帧补偿队列作为协议层永久实现；
5. Ability 必须表示真实业务能力，不再长期保留 0x00000EA2 开发占位；
6. 录音基础设施是 RDX 内部公共设施，不由会议录音 Ability 裁剪；
7. RDX OFF 只要求整个 RDX 及其录音基础设施退出，不要求 RDX ON 产品在清除某个业务 Ability 后裁掉公共录音设施。

若两份文档发生冲突，在线录音的已验证外部合同以 3-2 为依据，生产结构和配置语义以本文为依据。

## 3. 架构审计结论

### 3.1 模块化

以下审计结论主要描述 8c82a29、a8ab654 首版功能基线。当前里程碑已经把录音生命周期和固定容量控制面迁移到 Record Engine，但仍依赖 `ai_voice_recoder`，控制发送和音频发送也尚未统一，因此尚未达到本文定义的生产级模块化。

迁移前的 rdx_mvp0_protocol.c 同时承担：

- RDX Wire 命令解析；
- 在线录音协议状态；
- USB busy 判断；
- ai_voice Pipeline open/close；
- AI_TX 音频回调；
- 预热、帧校验和在线封包；
- 16 帧补偿队列；
- BLE 发送重试；
- 断连和 CCC off 时直接关闭录音。

这些职责具有不同的并发上下文、平台依赖和演进方向。继续在同一文件增加本地录音、暂停或异常恢复会放大竞态和耦合。

### 3.2 可配置化

rdx_integration_config.h 当前已经正确承担最终 RDX 门控和 BLE、PC 模式、RTC 等依赖检查，但录音依赖尚未收敛。

配置必须遵循单向关系：

    JL 产品配置和工具生成资源
        -> 声明 ADC、AGC、Encoder、AI_TX、Opus 和 Pipeline
        -> rdx_integration_config.h 验证最终组合
        -> RDX 业务消费已经成立的能力

rdx_integration_config.h 可以用编译期错误拒绝非法组合，但不得反向 undef 或 define JL 工具生成宏。仅改变 C 宏不能同步生成 x6flow 和 stream.bin，反向强开会制造“源文件已编译、资源图不存在”的半配置。

### 3.3 最小入侵

完全零修改 JL 公共代码不是本项目的硬目标。正确目标是：

- JL 公共模块不知道 RDX 业务；
- RDX 通过公开 JL API 和平台 Adapter 使用 SDK；
- 无法外置的 ATT RAM、Controller Feature 等只保留极小的产品配置接缝；
- 通用修复不包含 rdx 头文件、命名或业务判断；
- 技术诊断不永久嵌入 ADC、AGC 等公共节点。

当前可以清理的主要侵入：

| 位置 | 当前用途 | 生产处理 |
| --- | --- | --- |
| audio/framework/nodes/agc_node.c | AGC 前后 PCM 抓取 | 删除 |
| audio/framework/plugs/source/adc_file.c | PCM 抓取、测试音 | 删除 |
| audio/interface/recoder/ai_voice_recoder.[ch] | open_with_tx 和固定 Opus 合同 | 恢复原生接口 |
| rdx_record_spike.[ch] | 一次性音频 Spike | 删除 |

可能保留的原生接缝：

- multi_protocol_main.c 中 RDX 所需 ATT Payload 和 cbuf 产品配置；
- lib_btctrler_config.c 中 RDX 在线录音需要的 DLE 和 2M PHY；
- adc_file.c 中 STREAM_SCENE_AI_VOICE 使用 16-bit 的通用修复，但必须单独做 RDX OFF 和原 AI Voice 回归；若专用 Pipeline 不再需要则删除。

## 4. 核心领域模型与统一语言

### 4.1 录音基础设施

录音基础设施是 RDX 内部公共设施，不是在线录音的别名。它负责：

- 保证任一时刻只有一个逻辑录音会话；
- 仲裁会话控制者；
- 校验格式白名单；
- 打开、验证和关闭 BR56 音频 Pipeline；
- 从 AI_TX 接收编码帧；
- 通过固定队列把帧交给当前启用的输出目的地；
- 汇总统一状态、错误和统计；
- 在系统强制条件下可靠回收资源。

录音基础设施不负责：

- 解析 APP Wire 命令；
- 构造在线状态 ACK；
- 发送 BLE Notify；
- 创建或写入本地文件；
- 根据 Ability 决定自身是否编译。

### 4.2 录音会话、采集周期和输出目的地

**录音会话**是一次逻辑上的用户录音，从业务成功创建会话开始，到用户停止或系统强制终止为止。`session_id` 在整个会话内不变，Pause/Resume 不创建新会话。

**会话控制者**是创建并控制当前录音会话的业务 Service，不等同于输出渠道。首版由 Online Service 控制会话；未来设备按键、本地业务或其他入口可以成为控制者，但输出目的地不得冒充会话 owner。

创建者默认在 Session 全程保持控制权。其他已认证 Service 可以请求挂接或摘除自身 Destination，但不得隐式 STOP、Pause 或 Resume 当前 Session。控制权变更必须通过显式 `TRANSFER_CONTROL`，记录旧 controller、新 controller、request_id 和原因，并由当前控制者或授权策略批准。

**采集周期**是一次连续占有音频资源租约并运行 Pipeline 的区间。一个录音会话可以包含多个采集周期；Pause 结束当前采集周期并释放租约，Resume 在同一 `session_id` 下取得新租约并递增 `capture_generation`。Adapter 回调必须同时校验 `session_id` 和 `capture_generation`，防止暂停前或旧 Pipeline 的延迟帧污染新周期。

**用户暂停**与**资源挂起**必须区分：

- `PAUSED_BY_USER` 表示控制者明确暂停，只能由合法 Resume 请求恢复；
- `SUSPENDED_BY_RESOURCE` 表示 USB 抢占或共享资源丢失等系统条件结束了采集周期，记录具体 cause，由会话 Service 决定何时显式恢复；
- BLE 断连导致 Online Destination 摘除不等于暂停 Session；
- 两种状态都不推进 `active_pts`，但协议 ACK、超时、恢复权限和终止策略不同。

**输出目的地**消费当前会话的编码帧并完成一种交付目标：

- 在线目的地：把帧实时交给 RDX TX Scheduler；
- 本地目的地：未来把帧异步交给存储写入任务；
- 诊断目的地：开发阶段对帧进行受控验证。

一个会话可以挂接多个输出目的地。未来允许同一帧同时在线发送和本地保存；BLE 断开只移除或暂停在线目的地，本地目的地可以继续，重连后可按业务策略重新挂接在线目的地。当前阶段只实例化在线目的地，不提前实现本地空壳。

每个目的地在挂接时必须声明重要性：

- `REQUIRED`：目的地失败会使当前业务目标不成立，由会话 Service 决定终止、暂停或降级整个 Session；
- `OPTIONAL`：目的地失败时可以只摘除该目的地，其他目的地继续。

重要性由会话 Service 根据具体业务组合指定，Engine 不得硬编码“任一目的地失败就终止全部”。当前纯在线会话的 Online Destination 是 `REQUIRED`；未来“本地录音并在线镜像”可以把 Local 设为 `REQUIRED`、Online 设为 `OPTIONAL`。

_避免使用_：以“在线 owner”“本地 owner”表示输出渠道；把 Pause 叫作 STOP；把采集周期叫作新录音会话。

### 4.3 录音产物

**录音产物**是本地录音生成并需要持久化提交的文件及其索引、时间轴和标记元数据。采集停止后，产物可以独立经历 `COMMITTING -> COMMITTED/FAILED`；文件尾、索引和同步不得继续占用音频资源租约，也不得仅因提交未完成而阻塞新的在线录音。

未来是否允许在旧产物提交期间创建新的本地产物，由 Storage Service 的介质能力和操作租约决定，不由 Record Engine 的唯一 Session 隐式决定。

本地停止必须区分两个里程碑：

- `SESSION_STOPPED`：Pipeline 已关闭、音频资源租约已释放且不会再产生帧，由 Engine 报告；
- `ARTIFACT_COMMITTED`：正常 STOP 后文件尾、索引、marks 和持久化同步完成，产物可进入正常目录，由 Storage Service 报告；
- `COMMITTED_RECOVERED`：重启后通过完整性验证并成功重建索引的恢复产物，可以发布但必须保留 recovery 标志。

未来协议不得在 `ARTIFACT_COMMITTED` 或 `COMMITTED_RECOVERED` 前宣称文件保存成功。Storage Service 必须能在重启后识别并恢复或终结 `OPEN/COMMITTING` 产物；无法满足格式和完整性合同的产物进入 `FAILED/QUARANTINED`，不得进入正常文件列表。

### 4.4 RecordFrame 与有效时间轴

**RecordFrame** 是 Engine 交给各 Destination 的不可变内部帧合同，不改变 V23 在线 Wire。它至少包含：

    struct rdx_record_frame {
        u32 session_id;
        u32 capture_generation;
        u32 session_frame_seq;
        u32 capture_frame_seq;
        u64 active_pts;
        u32 duration;
        u32 flags;
        const u8 *payload;
        u16 payload_len;
    };

- `session_frame_seq` 在同一 Session 内跨 Pause 连续递增；
- `capture_frame_seq` 在每个采集周期从零开始；
- `active_pts` 使用单调时钟且排除 Pause 时间，是 Mark 和本地产物索引的统一时间轴；
- `duration` 来自已验证格式合同，不能仅用回调到达间隔猜测；
- `FIRST_AFTER_RESUME`、`DISCONTINUITY` 等 flags 显式描述边界和已知缺口；
- payload 仍是临时借用数据，Destination 异步消费必须复制。

AI_TX 回调写入帧池的是尚未取得有效时间轴身份的候选编码帧，不直接创建正式 RecordFrame。Engine worker 按当前格式 Profile 校验候选帧并执行采集资格过滤；只有通过过滤的帧才分配 `session_frame_seq/capture_frame_seq/active_pts` 并成为 RecordFrame。这样预热、无效格式或其他采集层丢弃不会在所有 Destination 共享的时间轴上制造假帧和缺口。

Online Destination 继续只把兼容头和原始 Opus payload 写入 V23 在线包，不把这些内部元数据加入线上合同。

**会话标记**是附着在当前 Session 有效时间轴上的业务元数据，不属于某一个 Destination。Session Metadata Service 管理 canonical mark journal；Online ACK、本地产物索引和未来其他消费者使用同一个确定结果，不能各自维护一套 mark。

Mark 请求携带 `request_id/session_id/source`，只在 `ACTIVE` 接受。Engine worker 在处理该控制请求的串行点读取当前 `active_pts` 并生成 Mark；`STARTING/PAUSING_BY_USER/PAUSED_BY_USER/SUSPENDING_BY_RESOURCE/SUSPENDED_BY_RESOURCE/STOPPING` 一律返回 `BAD_STATE`。Mark 上限、去重窗口和 Wire 结果码属于 Service 兼容策略，不是 Engine 基础设施常量；参考工程的 20 个上限和 6 秒去重只能作为首个待验证策略。

### 4.5 录音请求、标识和状态所有权

**录音请求**是业务 Service 提交的一次异步开始、停止或其他会话意图。每个请求具有 `request_id`；`request_id` 用于关联命令及完成结果，`session_id` 用于隔离不同逻辑录音，`capture_generation` 用于隔离同一会话内不同采集周期，三者不得混用。

状态所有权固定如下：

| 所有者 | 拥有的状态 | 不得拥有 |
| --- | --- | --- |
| 业务 Service | Wire 命令幂等、业务和协议状态、会话控制意图 | Pipeline 和 ATT 队列状态 |
| Record Engine | 录音会话、采集周期、音频资源和输出目的地状态 | Wire 字符串和 BLE 包状态 |
| Session Metadata Service | canonical mark journal、Mark 兼容策略和元数据结果 | Pipeline、文件写入和 BLE Transport |
| TX Scheduler | 包的排队、传输接纳、取消和 QoS 状态 | 录音业务状态 |

Engine 控制事件和音频帧必须使用物理分离的投递通道。普通 controller request 使用固定控制队列；当前 Session 的合法 STOP 使用独立 `stop_requested` latch；SHUTDOWN、USB 抢占和锁存故障使用 system-event latch。所有 latch 都携带完整 generation 并唤醒 worker，因此 STOP、EXIT 和故障处置不依赖普通控制队列空位，也不能在帧队列满时一同丢失。

普通 controller request 与可信 system event 也必须使用不同的提交入口和事件类型：

- controller request 必须携带 `request_id/controller_id` 并接受当前控制权校验；
- system event 必须携带固定 `system_event_source/cause`，只能由 USB、生命周期、安全管理等已注册平台入口产生；
- controller 不得通过伪造 controller_id 或特殊 request type 获得“系统强制”权限；
- 两类事件使用各自的固定容量入口，最终都只能由 Engine worker 串行改变 Session，并在日志和完成事件中保留来源；
- worker 每次结束当前有界临界步骤后，先检查已锁存的 system event，再检查 `stop_requested`，最后处理下一项普通请求；system event/STOP 不得中断到一半的 Pipeline close、租约释放或状态提交；
- 同 source、type 和目标 generation 的重复 system event 合并并锁存，不重复执行资源回收；安全条件收敛后，尚未执行的冲突普通请求以 `CANCELLED` 或 `BAD_STATE` 完成；
- system event 入口满不得静默丢弃：重复事件继续合并，新安全事件锁存故障并唤醒 worker；容量和最坏处理时间必须由事件序列测试证明。

合法 STOP 的首次请求原子设置 `stop_requested`，保存 `engine_generation/session_id/capture_generation/controller_id` 和首个 request_id，并立即关闭该 generation 的逻辑帧接纳闸门；此后到达的匹配回调计入 `stop_discarded`，不再产生新的数据面故障。重复 STOP 不重复触发关闭，也不保存无界 alias 列表，只更新 `last_request_id` 和饱和 `duplicate_count`。worker 在结束当前有界临界步骤后先处理 system event，再处理 `stop_requested`，然后才处理普通请求和音频帧。普通控制队列满时，START、查询和其他请求立即返回 `CONTROL_QUEUE_FULL`；不得挤占 STOP/system-event latch，也不得覆盖已经锁存的根因。

同一优先级入口内以 Engine worker 的实际出队顺序作为并发请求的唯一裁决，不用回调到达时间或 wall clock 猜测先后；system event 的优先规则只作用在有界临界步骤之间。Pause 与 Mark 并发时：Mark 先出队则按 Pause 切点前的 `active_pts` 成功；Pause 先出队则 Mark 返回 `BAD_STATE`。诊断日志必须记录两个 `request_id` 和最终处理顺序。

### 4.6 传输接纳

**传输接纳**表示数据包已被本地 ATT 发送队列接受。它不表示数据已经通过空口发送，也不表示 RDX APP 已收到。

在保持 V23、Notify 和现有 APP 不变的前提下，TX Scheduler 的 Notify completion 统一采用传输接纳语义。未来若业务要求 APP 级可靠确认，必须另行定义应用层 ACK 或可靠传输合同，不得把 Notify 的本地返回值包装成对端确认。

_避免使用_：实际发送成功、空口成功、APP 已收到。

### 4.7 音频资源租约与 RDX 操作租约

**音频资源租约**是 RDX 录音或 USB 音频使用共享采集资源前必须原子取得的独占资格。USB 具有更高优先级，可以请求 Engine 强制停止当前采集周期并释放租约。仅查询 busy 状态再打开 Pipeline 不构成安全仲裁。

**RDX 操作租约**由未来的 Operation Coordinator 管理，用于表达录音、存储写、文件提交、文件上传、扫描、格式化、删除和 OTA 等业务操作的兼容矩阵。音频资源租约解决平台 ADC/USB 冲突，RDX 操作租约解决业务级资源冲突，二者不得合并成一个万能锁。

默认优先级和冲突策略如下：

1. 关机、解绑、恢复出厂等安全操作可以强停录音并执行；
2. USB 音频可以抢占录音的采集周期；
3. 用户录音可以暂停或取消 Bulk 上传和后台扫描；
4. OTA 和格式化仅在无活动 Session、无未完成产物提交时启动；
5. 文件删除不得作用于活动、`OPEN` 或 `COMMITTING` 产物；
6. Bulk 上传优先级最低，必须支持暂停、恢复和取消。

各 Service 只能通过 Operation Coordinator 申请具名操作租约，不得重新引入跨模块读取 `busy` 标志的隐式仲裁。

### 4.8 Ability

RDX_COMPAT_DEVICE_ABILITY 是外部业务合同，不是录音基础设施的源码裁剪开关。

规则如下：

- RDX_ABILITY_CONFERENCE_RECORDING 表示 APP 可以使用在线会议录音；
- RDX_ABILITY_LOCAL_STORAGE 表示本地录音及相关存储业务已经完整实现；
- RDX_ABILITY_RECORD_PAUSE_RESUME 表示对应业务已经实现暂停/恢复；
- 未声明 Ability 的业务必须返回 unsupported，不得存在隐藏入口；
- Ability 清除不裁剪 Engine、Audio Adapter 或公共录音节点；
- TCFG_RDX_ENABLE 为 0 时，整个 RDX 及其录音基础设施退出。

当前真实 Ability 应收敛为：

    RDX_ABILITY_RTC |
    RDX_ABILITY_CONFERENCE_RECORDING

即 0x00000022。Local Storage、Pause/Resume、Record Mark 和 Flashnote 在实现和验收完成前不得广播。

Flashnote 当前只有协议和 Ability 占位，没有可作为 Golden Behavior 的参考业务实现。本架构不为它增加 Engine 特殊状态；其 Ability 保持关闭。待产品语义、目标 APP 行为和验收标准明确后，再作为独立 Service 复用既有 Session、Destination 和 Operation Coordinator 能力。

## 6. RDX 专用 Pipeline

### 6.1 Pipeline 合同

使用 JL 工具建立名为 rdx_record 的专用 Pipeline：

    PA3 ADC mono
        -> AGC
        -> Encoder
        -> AI_TX

冻结的 MEETING_V1 格式：

| 参数 | 值 |
| --- | ---: |
| 输入 | PA3 ADC，两脚驻极体，physical mono |
| PCM | 16000 Hz / 16 bit / mono |
| 编码 | Opus |
| 码率 | 32000 bit/s |
| 帧长 | 20 ms |
| 封装 | raw |
| 合法编码帧 | 固定 80 B，mono TOC |

禁止向首版 Pipeline 加入：

- Channel Expander；
- AI_RX、Decoder 或 DAC；
- USB CVP；
- Bluetooth Sync；
- DNS、AEC、EQ 等尚未重新验证的处理；
- RDX 私有 Sink 节点。

### 6.2 Adapter 行为

rdx_record_audio_br56 必须：

1. 检查 USB Mic/Speaker 和录音资源是否可用；
2. 按 rdx_record 名称或冻结 UUID 解析专用 Pipeline；
3. 设置 Encoder、AI_TX 和 stream 格式；
4. 在启动前安装 AI_TX 回调；
5. 查询或验证最终格式；
6. 启动 Pipeline；
7. 把帧交给 Engine，并携带 `session_id/capture_generation`；
8. 幂等停止和释放 Pipeline。

缺少 Pipeline、节点不存在、格式不一致或任一 ioctl 失败时必须 fail-closed。不得回退到 ai_voice，也不得使用工具默认参数继续录音。

### 6.3 格式白名单

公共请求使用格式 ID，而不是允许业务自由拼装参数：

    RDX_RECORD_FORMAT_MEETING_V1

Engine 内部可以把格式 ID 解析成完整格式 Profile，以支持 Adapter 校验、采集资格过滤和 Destination 初始化。`MEETING_V1` Profile 明确包含 `payload_len = 80`、mono Opus TOC、`frame_duration = 20 ms` 和 `warmup_frames = 10`；这些是当前已验证的严格合同，不是统计期望。未来本地录音需要新格式时新增独立 ID 和 Profile，不改变 MEETING_V1。

候选帧 slot 仍按大于 80 B 的编译期安全上限设计，用于先安全接收、计数并拒绝异常回调；安全上限不扩大合法格式。预热候选帧也必须先满足长度上限并接受 Profile 校验。第一个正式候选帧不符合 80 B/mono TOC/20 ms 合同时，START 以 `FORMAT_MISMATCH` 失败；ACTIVE 期间出现不合格帧时，不创建 RecordFrame、不发送，锁存格式错误并终止当前纯在线 Session。

## 7. Engine 概念合同

### 7.1 请求合同

以下是概念合同，不是本阶段冻结的 C ABI。实现接口可以随分阶段落地演进，但不得破坏 `request_id`、`session_id` 和 `capture_generation` 的语义边界。

    enum rdx_record_request_type {
        RDX_RECORD_REQUEST_START = 0,
        RDX_RECORD_REQUEST_STOP,
        RDX_RECORD_REQUEST_PAUSE,
        RDX_RECORD_REQUEST_RESUME,
        RDX_RECORD_REQUEST_MARK,
        RDX_RECORD_REQUEST_ATTACH_DESTINATION,
        RDX_RECORD_REQUEST_DETACH_DESTINATION,
        RDX_RECORD_REQUEST_TRANSFER_CONTROL,
    };

    struct rdx_record_request {
        u32 request_id;
        enum rdx_record_request_type type;
        enum rdx_record_controller_id controller_id;
        enum rdx_record_controller_id new_controller_id;
        enum rdx_record_format_id format_id;
        enum rdx_record_destination_id destination_id;
        enum rdx_record_destination_requirement requirement;
        const struct rdx_record_destination_ops *destination_ops;
        void *destination_priv;
        enum rdx_record_mark_source mark_source;
    };

    int rdx_record_submit_async(const struct rdx_record_request *request);

    enum rdx_record_system_event_type {
        RDX_RECORD_SYSTEM_USB_PREEMPT = 0,
        RDX_RECORD_SYSTEM_LINK_LOST,
        RDX_RECORD_SYSTEM_CCC_OFF,
        RDX_RECORD_SYSTEM_SHUTDOWN,
        RDX_RECORD_SYSTEM_FACTORY_RESET,
        RDX_RECORD_SYSTEM_ENGINE_FAULT,
    };

    int rdx_record_submit_system_event(
        enum rdx_record_system_event_source source,
        enum rdx_record_system_event_type type,
        enum rdx_record_cause cause);

`rdx_record_submit_async()` 对非 STOP 请求的返回值只表示请求是否成功复制到普通请求入口，不表示操作已经完成，也不表示当前资源一定可用；队列满明确返回 `CONTROL_QUEUE_FULL`。合法 STOP 由专用 latch 接受，其返回值只表示首次锁存或成功合并到有界幂等摘要。BUSY、格式不支持、租约失败、控制权转移被拒绝等真实结果通过携带同一 `request_id` 的 Engine 完成事件异步返回。`rdx_record_submit_system_event()` 使用独立可信入口，不伪造 request_id 或 controller；其完成结果按 source、type 和 cause 关联。这样可以避免同步检查与 worker 实际状态之间的竞态，并防止业务请求冒充系统强制事件。

### 7.2 数据生命周期

- submit_async 必须在返回前复制 request 内容，不保存调用者栈地址；
- Destination ops 具有静态生命周期；
- destination_priv 的生命周期必须覆盖其挂接区间；
- Engine 完成事件包含 request_id、session_id、capture_generation、controller_id、result 和终止信息；
- Engine 交给 Destination 的 RecordFrame 及 payload 只在当前调用期间有效；
- Destination 若要异步处理必须复制数据；
- TX Scheduler 入队时必须完成自己的包数据复制。

Destination 合同至少包含挂接、消费 RecordFrame、暂停、恢复、摘除和强制取消。挂接成功只表示该目的地已准备消费帧；Online Destination 在第一个正式 RecordFrame 到达时把该帧复制到专用启动保留槽并返回 DATA_READY。未来 Local Destination 可以在录音产物建立成功后采用不同的就绪条件。异步完成必须携带对应标识且只能完成一次；强制取消必须有界且幂等。

Destination 的同步 `consume()` 只能执行有界复制，不得等待其内部队列、文件系统或 Transport。每个异步 Destination 拥有自己的固定队列、峰值和 overflow 统计。Engine 不承诺多个 Destination 对同一帧原子全成或全败：已经被一个 Destination 接纳的数据不得因另一个 Destination 失败而回滚。

### 7.3 Session、控制者和目的地

Engine 任一时刻只允许一个 Session：

- IDLE 时第一个 START 请求创建 Session 并确定会话控制者；
- 非控制者不得直接 STOP、PAUSE 或 RESUME 当前 Session，也不得提交系统强制事件；
- 控制权只能通过显式 TRANSFER_CONTROL 改变，成功事件必须同时记录旧 controller、新 controller、request_id 和原因；
- 目的地可以按业务策略动态挂接和摘除，不取得会话控制权；
- 挂接请求必须声明 REQUIRED 或 OPTIONAL，Engine 报告单个目的地故障，Service 决定 Session 处置；
- 同一帧可以分发给多个目的地；目的地之间不得互相调用；
- 不自动缓存“等前一个 Session 停止后再启动”的新 START；
- USB 抢占、断连、关机等系统事件只能通过可信 system event 入口触发强制处置。

`engine_generation`、`request_id`、`session_id` 和 `capture_generation` 都使用非零 32 位计数器分配；零值固定表示“无标识”。`engine_generation` 在 Engine 每次成功初始化时更新，用于隔离 exit/re-init 前后的运行时事件。分配器允许回绕，不追求跨重启或设备全寿命永久唯一，但不得分配与当前活跃请求、Session 或采集周期冲突的值。

这些标识都是 opaque token，只允许做完整上下文等值匹配，禁止用 `<`、`>` 或差值判断事件新旧。Engine 内部事件至少匹配适用的 `engine_generation/session_id/capture_generation`；请求完成再匹配 `request_id`；BLE/TX 事件还必须匹配 `connection_generation`。任一字段不匹配的延迟事件只计数后丢弃，不改变当前对象。Adapter 必须在启动回调时捕获完整标识，并在停流时执行注销及有界排空，不能在回调到达时读取“当前 Session”再给旧帧贴上新 ID。

## 8. 状态和事件模型

### 8.1 Engine 技术状态

    IDLE
      -> STARTING
      -> ACTIVE
      -> PAUSING_BY_USER
      -> PAUSED_BY_USER
      -> RESUMING
      -> ACTIVE
      -> SUSPENDING_BY_RESOURCE
      -> SUSPENDED_BY_RESOURCE
      -> RESUMING
      -> ACTIVE
      -> STOPPING
      -> IDLE

当前在线 START/STOP 阶段只实现 `IDLE -> STARTING -> ACTIVE -> STOPPING -> IDLE` 子集，但状态和事件编号必须为 Pause/Resume 和资源挂起留出明确演进空间。`PAUSED_BY_USER` 只能响应合法 controller 的 Resume；`SUSPENDED_BY_RESOURCE` 记录系统 cause，不能在资源恢复时自动 Resume。两者都保留 Session 和 `session_id`、结束采集周期、释放音频资源租约且不推进 `active_pts`；显式 Resume 创建新的 `capture_generation`。

Engine worker 是 Session、采集周期、Pipeline、目的地和技术状态的唯一写入者。

### 8.2 Pause/Resume 切点

Pause 必须形成确定切点：

1. Engine worker 处理 PAUSE 控制请求时关闭当前 `capture_generation` 的新帧接纳闸门；
2. 停止或注销 AI_TX 回调来源，防止继续生产；
3. 已经进入 Engine 帧队列且标识匹配的帧全部按正常顺序 drain 给 Destination；
4. drain 完成后关闭 Pipeline、释放音频资源租约并进入 `PAUSED_BY_USER`；
5. drain 必须有界；超时则丢弃余帧、记录缺口，在后续首帧设置 `DISCONTINUITY`，并强制结束当前采集周期。

Resume 在同一 `session_id` 下创建新 `capture_generation` 并重新取得音频资源租约。Resume 后的预热帧：

- 属于新的 `capture_generation`，但不递增 `session_frame_seq`；
- 不推进 `active_pts`，不能计入有效录音时间；
- 第一个正式 RecordFrame 带 `FIRST_AFTER_RESUME`，若上一周期 drain 或停止不完整则同时带 `DISCONTINUITY`；
- 预热、租约或 Pipeline 启动失败时，Session 保持原来的 `PAUSED_BY_USER` 或 `SUSPENDED_BY_RESOURCE`，报告本次 Resume 请求失败，允许合法 controller 重试，不把失败伪装成新 Session。

### 8.3 在线协议状态

    IDLE
      -> START_PENDING
      -> STREAMING
      -> STOP_PENDING
      -> IDLE

Online Service 拥有协议状态，但不得直接操作 Pipeline。

### 8.4 回调规则

以下上下文只投递事件：

- ATT write；
- HCI disconnect；
- CCC change；
- AI_TX frame callback；
- USB 音频状态事件；
- timer；
- TX completion。

它们不得直接执行 Engine 状态迁移、open/close Pipeline 或修改会话控制者。

Engine worker 的事件选择规则固定为：完成当前有界临界步骤，优先处理已锁存 system event，其次处理当前 Session 的 `stop_requested`，再按普通请求入口的实际出队顺序处理 controller request，最后消费音频帧。普通请求或音频帧持续到达不得饿死 STOP 和安全事件；system event/STOP 也不能撕裂进行到一半的资源提交。事件日志至少记录 source、入队序号、处理序号、匹配上下文和最终结果。

### 8.5 重复和迁移态命令

| 当前状态 | 命令 | 处理 |
| --- | --- | --- |
| ACTIVE | START | 幂等返回当前 START 状态，不重开 |
| IDLE | STOP | 幂等返回 STOP 状态 |
| STARTING | START | 合并重复请求，最终只完成一次 |
| STARTING | STOP | 取消启动并安全关闭 |
| STOPPING | STOP | 合并重复请求 |
| STOPPING | START | 不缓存，APP 在 STOP 完成后重试 |

不得无限缓存相反命令，否则网络延迟或旧事件可能在用户意图结束后重新启动录音。

相反目标命令的完成与 ACK 规则固定如下：

- `STARTING + STOP`：STOP 取代当前启动意图；取消 START ACK、启动首包保留槽和 START 请求，Engine 安全关闭 Pipeline 并释放租约。原 START request 以 `CANCELLED` 完成，只在 `SESSION_STOPPED` 后排队一个 STOP ACK；
- `STOPPING + START`：不缓存、不重启、不创建新的 Engine START；当前 STOP 正常完成并只排队一个 STOP ACK，APP 必须在稳定 IDLE 后重新发送 START；
- 任一阶段收到断连、CCC off、USB 抢占、关机等 system event 时，由 system event 取代 Wire ACK 目标；若当前 connection 已不可发送，只收敛内部状态，不在新 connection generation 补发旧 ACK。

V23 Wire 不携带 request ID，因此幂等关联由 Online Service 在当前 `connection_generation` 内维护：

- 每次合法 Wire 命令仍分配新的内部 `request_id`，用于审计该次输入；
- `STARTING + START` 或 `STOPPING + STOP` 不再次向 Engine 提交请求；当前幂等操作只保存 `first_request_id`、`last_request_id` 和饱和 `duplicate_count`，Engine 只产生一次完成事件，协议层只排队一个目标状态 ACK；
- `ACTIVE + START` 或 `IDLE + STOP` 不改变 Engine，重新声明当前稳定状态；若同一 connection/session 下相同状态 ACK 尚在 Scheduler 等待，则与待发 ACK 去重；
- 相反目标命令按表中规则取消或拒绝，不排成未来自动动作；
- 连接断开或 `connection_generation` 改变时清空 Wire 幂等缓存和待发 ACK 去重键，旧连接的重复命令和完成事件不得命中新连接。

不得为每个重复 Wire 命令保存 alias 或完成对象。详细输入可使用限频日志记录，但日志限频不得改变幂等计数和最终状态。

## 9. START 时序

START 必须同时区分三个里程碑：

1. Engine 启动：音频资源租约已取得，Pipeline 已成功打开；
2. 数据面就绪：Engine worker 完成 MEETING_V1 预热和格式过滤并产生第一个正式 RecordFrame；Online Destination 把完整在线包复制到专用启动保留槽，由 Engine 转发对应标识的 DATA_READY；
3. 在线可流：START 状态 ACK 已获得 TX Scheduler 的传输接纳。

推荐时序：

    APP START
        -> Protocol 校验 Wire
        -> Online Service 校验 Ability 和安全条件
        -> Service 分配 request_id 并 submit_async
        -> Engine 创建 START 事务和 session_id
        -> 认领并清零固定候选帧池及 Online 队列
        -> TX Scheduler 预留关键 START ACK 槽
        -> Online Destination 预留启动首音频包槽
        -> Engine 原子取得音频资源租约
        -> Audio Adapter 以 capture_generation 打开 Pipeline
        -> AI_TX 回调把候选编码帧写入 Engine 固定帧池
        -> Engine worker 按 MEETING_V1 Profile 丢弃并统计前 10 个预热帧
        -> Engine 为第一个合格帧分配正式 RecordFrame 序号和 active_pts
        -> Online Destination 把该帧复制到启动保留槽并返回就绪
        -> Engine 转发带 request_id/session_id/generation 的 DATA_READY
        -> Online Service 排队 START ACK
        -> TX Scheduler 回报 START ACK 传输接纳
        -> Online Service 进入 STREAMING
        -> 把启动保留槽的首包转入 REALTIME_AUDIO 队列

START 采用事务式资源顺序：校验配置与安全条件，认领固定数据面资源，预留关键 START ACK/首音频包槽，取得音频租约，最后才打开 Pipeline。任一步失败都按相反顺序幂等回滚；输出容量必须先于音频资源和 Pipeline，禁止“采集已启动但无处交付”的半启动状态。

整个启动过程必须有统一超时。超时数值由目标硬件测量确定，不在架构阶段拍脑袋冻结。ACK 获得传输接纳前，除专用保留槽中的一个首包外，不得向 TX Scheduler 累积在线音频；其余新帧按明确的启动等待策略丢弃并统计。START 失败、超时、断连或 ACK 被取消时，必须按事务逆序关闭 Pipeline、释放音频租约、取消保留槽、逻辑释放固定数据面资源和 Session，并清除该 Session 的待发音频，然后上报停止状态或现有 V23 可表达的失败语义。

预热属于格式 Profile 的采集资格规则，不属于 Online Destination。Engine 的通用代码只执行当前 Profile，不硬编码“10 帧”；MEETING_V1 Profile 提供这一已验证数值。预热候选帧不创建 RecordFrame、不推进正式序号或 `active_pts`，所有 Destination 因而从同一个第一帧和同一有效时间轴开始。Destination 可以定义自身额外的业务就绪条件，但不得各自重定义公共采集预热。

MEETING_V1 的每个候选帧都执行长度和 mono TOC 校验。预热期异常只计数并继续等待满足合同的预热样本，但必须受统一 START timeout 限制；预热完成后的第一个不合格正式候选帧使 START 失败。ACTIVE 中的任一不合格候选帧视为数据合同破坏，不能作为普通可丢帧抖动处理。

## 10. 帧路径与背压

### 10.1 Engine 帧队列

本期 RDX 自有候选帧池、Online Destination 队列、TX Scheduler 的 CONTROL/REALTIME_AUDIO 队列、启动首包槽和两个控制入口全部使用编译期固定容量；不得在 START/STOP 路径为这些对象反复 `malloc/free`。容量按编译期 slot 上限、队列深度和目标硬件最低内存水位共同验收。START 只原子认领并清零当前 Session 所需 slot，STOP 做逻辑释放和敏感状态清零；未来 Local/BULK 队列在对应 Ability 实现时另行增加，本期不预占 RAM。

AI_TX 回调只允许：

1. 校验 session_id 和 capture_generation；
2. 校验基础帧长度上限；
3. 复制 payload 到预分配固定 slot，并填写候选帧的捕获上下文；不得在回调中分配正式序号或推进 active_pts；
4. 投递 FRAME_READY；
5. 立即返回。

禁止在 AI_TX 回调中：

- malloc/free；
- 等待 mutex、semaphore 或 BLE；
- 直接调用 Destination 的慢操作；
- 直接发送 Notify；
- 直接写文件；
- 直接停止 Pipeline。

Engine worker 从固定队列取候选帧，先按格式 Profile 完成预热和格式资格过滤，再为合格帧创建 RecordFrame，并按固定顺序同步调用当前启用的 Destination。Destination 获得的是临时借用数据；需要异步消费时必须自行复制。一个目的地失败后，Engine 锁存并上报该目的地错误；Service 根据 REQUIRED/OPTIONAL 和当前业务目标决定摘除、降级、暂停或终止，不能默认把所有目的地一起停止。

同一 RecordFrame 的稳定分发顺序为 REQUIRED 优先，再在同一重要性内按 REALTIME、LOCAL_STORAGE、DIAGNOSTIC 等静态优先级排序。这个顺序只保证行为可复现，不提供跨目的地事务：例如 Local REQUIRED 已接纳而 Online OPTIONAL 失败时，该帧仍然是有效的本地数据。

### 10.2 队列满

Engine 公共帧队列一次无法接纳合法 ACTIVE 候选帧，就已经形成 V23 无法表达的流中缺口：

1. 记录 overflow 和 queue peak；
2. 锁存 QUEUE_FULL；
3. 通过必达控制路径唤醒 Engine worker；
4. Engine worker 终止当前采集周期并报告受影响的 REQUIRED/OPTIONAL 目的地；
5. 当前纯在线 Service 终止 Session；未来多 Destination 由业务目标决定暂停、降级或终止；
6. 禁止静默丢帧后继续宣称当前纯在线采集周期正常。

队列深度必须通过最大帧、最低内存水位和实机调度确定。当前 16 帧只能作为测量基线，不能未经评估永久冻结。

Destination 私有队列满与 Engine 公共队列满必须区分：

- OPTIONAL Destination 满：锁存错误并通知 Service，按策略摘除或降级该目的地；
- 当前 REQUIRED Online Destination 一次无法接纳：立即终止纯在线 Session；未来其他 REQUIRED Destination 由 Service 暂停或终止；
- Engine 公共帧队列满：说明采集公共层已经失速，终止当前采集周期；
- 所有 `consume()` 都必须有 WCET/最大复制量约束，不允许慢 Local writer 阻塞 Online 实时流。

### 10.3 Online Destination

rdx_online_record_stream 负责：

- 确认 MEETING_V1；
- 维护 received、packaged 和 discarded 统计，并对账 Engine 的 warmup_dropped/produced；
- 生成兼容头；
- START 闸门期间只保留第一个合法完整在线包；
- START ACK 获得传输接纳后，将保留包和后续包复制进 TX Scheduler `REALTIME_AUDIO` 队列；
- 把 Scheduler 无法接纳、实时包过期或明确发送失败转成 Online Destination 错误。

它不得调用 rdx_ble_transport_send。

当前 V23 音频包没有帧序号和缺口表达。Online Service 进入 STREAMING 后，候选帧池/Engine 队列 overflow、Online 队列 overflow、格式错误、REALTIME_AUDIO 包过期或明确发送失败中的任一项，都会锁存首个根因并终止纯在线 Session；不允许继续发送一条 APP 无法解释为有缺口的流。预热丢弃和 START ACK 等待期按第 9 节策略丢弃的帧不属于流中缺口，但必须使用不同计数器，不得混入 ACTIVE overflow。

## 11. 统一 TX Scheduler

### 11.1 单一发送所有者

迁移完成后，所有 RDX Notify 必须经过 rdx_tx_scheduler：

    ACK、状态包、普通控制包
        -> CONTROL

    在线音频包
        -> REALTIME_AUDIO

    未来文件列表和录音文件上传
        -> BULK_FILE

    三类 QoS
        -> rdx_tx_scheduler
        -> rdx_ble_transport_send

协议、在线 Destination 和设备管理模块不得绕过 Scheduler。

### 11.2 调度规则

- `CONTROL` 具有固定容量和最高优先级，其中录音状态 ACK 使用普通控制包不可占用的关键保留槽；
- START 在打开 Pipeline 前必须同时预留关键 START ACK 槽和启动首音频包槽；STOP 使用独立关键槽，或在 START 槽生命周期结束后原子复用同一 Session 的状态 ACK 槽；
- 关键状态 ACK 槽按 `connection_generation/session_id/state` 绑定，旧连接或旧 Session 不得复用；
- `REALTIME_AUDIO` 具有时效性，过期包不得无限重试；
- `BULK_FILE` 当前仅保留调度合同，未来业务必须支持暂停、恢复和取消；
- 控制包优先于尚未获得传输接纳的音频和 Bulk 包；
- 每次可发送事件只发送有限批次；
- ATT cbuf 暂满时保留包并等待 CAN_SEND_NOW 或短时重试；
- 普通 CONTROL 队列满不得侵占关键录音状态 ACK 槽；REALTIME_AUDIO 一次无法接纳当前纯在线帧即回报明确错误；
- 每个包都产生传输接纳、明确失败或取消完成事件；
- 断连时按 generation 和 session_id 清除陈旧音频；
- 未完成控制包必须向原提交者回报取消；
- 解绑和恢复出厂的延迟断开从 ACK 获得传输接纳开始计时，不能从入队时计时。

START/STOP ACK 都有统一 deadline。连接仍有效但关键 ACK 在 deadline 内未获 ATT 传输接纳时，完成为 `ACK_TIMEOUT`：START 必须回滚并终止 Session；STOP 保持已经安全收敛的 IDLE 状态，不得为了补发 ACK 重新打开 Session。连接已经失效时按 connection generation 取消 ACK，只收敛内部状态。

BLE Transport 的发送尝试必须标准化为三态结果，Scheduler 不得直接依赖平台零/非零返回习惯：

- `ACCEPTED`：包已获得本地 ATT 传输接纳；
- `RETRYABLE`：ATT cbuf 暂满或暂不可发送，包仍由 Scheduler 持有，等待 CAN_SEND_NOW 或有界重试；
- `FATAL`：connection generation、CCC、Payload 长度或 Transport 状态已经无效，当前包不能继续。

单次 `RETRYABLE` 不终止 Session。REALTIME_AUDIO 包超过实时 deadline 或重试预算后转换为 `REALTIME_EXPIRED`，锁存故障并终止当前纯在线 Session；`FATAL` 立即锁存 `TRANSPORT_FATAL` 并终止。deadline 和重试预算通过目标硬件测量确定，不能无限重试，也不能把所有非零平台返回值混成同一种失败。

## 12. STOP 与异常时序

### 12.1 在线正常停止

    APP STOP
        -> Online Service stop_async
        -> Engine 关闭当前 generation 的新帧接纳闸门
        -> Audio Adapter 停止 Pipeline 并注销 AI_TX 回调
        -> Engine 释放音频资源租约
        -> 丢弃 Engine 中尚未成为 RecordFrame 的候选帧和未分发 RecordFrame
        -> Online Destination 取消尚未被 TX Scheduler 接纳的尾包
        -> TX Scheduler 取消该 Session 尚未获 ATT 传输接纳的 REALTIME_AUDIO 尾包
        -> Engine 报告 SESSION_STOPPED 并释放 Session
        -> Online Service 排队 STOP ACK
        -> TX Scheduler 回报传输接纳或明确失败
        -> Online Service 回到 IDLE

正常 STOP 是确定的快速切点，不有界 drain 音频尾帧：尚未获 ATT 传输接纳的数据全部取消并计数，已经获 ATT 传输接纳的包不可撤回。STOP ACK 只在 `SESSION_STOPPED` 和本地待发音频取消完成后排队；Scheduler 的单一发送所有权保证后续不会再接纳该 Session 的新音频。未来 Pause 使用第 8.2 节的有界 drain，不能复用 STOP 的快速丢弃语义。STOP 必须幂等。

### 12.2 强制停止

以下条件触发系统强制终止或相应目的地摘除：

- BLE 断连；
- TX CCC 关闭；
- 解绑或恢复出厂；
- USB 音频开始抢占资源；
- 关机或 RDX 退出；
- ACTIVE 候选帧池、Engine/Online 队列或 REALTIME_AUDIO 路径一次无法接纳；
- Destination 失败或超时；
- Pipeline 异常。

强制停止仍必须通过独立控制邮箱唤醒 Engine worker 回收资源。断连或 CCC off 时，若不存在本地目的地则终止 Session；未来若存在可继续的本地目的地，默认只摘除在线目的地，是否终止整个 Session 由会话控制策略决定。无需发送 STOP ACK 的路径仍必须使各自内部状态收敛。

system event 与 controller request 使用独立入口，不能由 Wire 命令直接构造。Engine 完成事件必须保留 system event source、cause 和最终处置（终止、目的地摘除或资源挂起），不能统一压成 STOP。

终止迁移只允许提交一次 `termination_mode/cause`。裁决规则如下：

1. STOP latch 成功时立即关闭逻辑帧接纳，随后匹配回调只计为 `stop_discarded`；
2. worker 开始终止迁移时，已经锁存的 system event 或故障优先于用户 STOP；同一优先级按实际锁存顺序取首项；
3. 一旦提交主 termination cause 就不可改写，之后到达的 STOP、故障或 system event 只作为有界 secondary cause 位图/计数记录；
4. 日志和完成事件必须同时保留主 cause 及 secondary 摘要，避免 USB_PREEMPT、FORMAT_MISMATCH 等被并发 STOP 掩盖。

格式错误、队列 overflow、REALTIME_EXPIRED、TRANSPORT_FATAL 等内部故障导致强停时，如果原 `connection_generation` 仍匹配、链路仍加密且 TX CCC 有效，则在 `SESSION_STOPPED` 和该 Session 音频取消完成后，通过关键状态槽发送一次 V23 STOP 状态。V23 不携带内部错误细节，真实 cause 只保留在事件、统计和日志中。断连、CCC off 或 connection generation 已改变时不发送，也不得向新连接补发旧 STOP。

### 12.3 BLE 断连与重连

BLE 连接变化只由会话 Service 解释为业务策略，Engine 只提供目的地挂接、摘除和会话控制机制：

- 当前纯在线会话断连后，Online Destination 失败且它是唯一 REQUIRED 目的地，Service 终止 Session；
- 未来带本地 REQUIRED 目的地的会话断连后，Service 摘除或暂停 Online Destination，本地继续；
- 重连不会自动创建新 Session，也不会改变本地产物身份；
- 只有重新满足 AppKey、绑定、加密、TX CCC、MTU/Payload 和其他安全门控后，Service 才能重新挂接 Online Destination；
- 是否自动重新挂接属于具体业务兼容策略，并使用新的 connection generation；
- Engine 不硬编码参考工程的“重连 3 秒后恢复在线流”。

### 12.4 未来本地录音停止

Engine 不假设 Destination 是 BLE。未来本地 Destination 和 Storage Service：

- START 成功前创建文件并写入必要头部；
- write 只做非阻塞入队；
- STOP 时摘除本地 Destination，结束帧写入并把录音产物交给 Storage Service；
- Engine 在采集和帧输入结束后报告 SESSION_STOPPED；
- 文件尾、索引和同步在独立的录音产物生命周期中异步提交，成功后报告 ARTIFACT_COMMITTED；
- 提交必须有最大完成超时和崩溃恢复合同；
- 提交失败只改变产物状态，不重新占用已释放的音频资源租约；
- 不允许文件系统无限阻塞 Engine。

关机、RDX 退出和恢复出厂不得无限等待 `ARTIFACT_COMMITTED`。生命周期编排者只等待配置的有界 deadline；到期后要求 Storage Service 持久化最小 recovery marker，随后继续退出。marker 至少能够定位未完成 Artifact 及其最后已确认提交阶段，不能把“已停止采集”误写成“已提交成功”。

在线 Destination 的“丢弃未接纳尾帧后快速停止”不得硬编码为所有 Destination 的统一策略。

### 12.5 录音产物提交与恢复原则

具体存储介质和文件系统确定前，先冻结以下最低持久性原则：

- 录制过程中使用不可见的 `OPEN` 临时产物；
- 音频主体只追加，不原地重写既有帧；
- 提交时依次持久化完整尾部、索引、有效时间轴和 canonical mark journal；
- 最后使用介质可支持的可恢复原子步骤发布目录项并进入 `COMMITTED`；
- 启动恢复可以识别最后一个完整帧边界，截断损坏尾部并重建索引，或明确标记 `FAILED`；
- 成功恢复并通过完整性验证的产物原子发布为 `COMMITTED_RECOVERED`，保留 recovery 标志供 Catalog、上传和诊断识别；
- 无法验证或无法安全重建的产物进入 `FAILED/QUARANTINED`，不得出现在正常 Catalog；
- recovery marker 只用于发现和定位未完成提交，不得绕过帧边界、索引、时间轴和 mark journal 的完整性校验；
- `COMMITTED` 产物不可再被恢复流程修改；
- 具体采用 rename、双目录项、generation、CRC 或日志，由选定介质的原子写能力决定，不能提前假设通用文件系统语义。

## 13. USB 音频资源策略

USB 是当前 Type-C 产品主业务，优先级高于 RDX 录音。必须建立不含 RDX 业务知识的通用音频资源租约：

- USB 和 RDX 在打开共享采集资源前都必须原子 acquire；
- USB 已持有租约时，录音 START 异步完成为 BUSY；
- RDX 持有租约时，USB 通过租约管理器发起高优先级 `REVOKE`，在收到明确 `GRANT` 前不得打开共享 ADC；
- 不允许第二条 ADC Pipeline 短暂启动后再判断冲突；
- 状态查询只用于诊断，不作为原子互斥正确性的依据；
- RDX 不得修改 UAC、CVP、PCMIC 或 USB 核心状态。

抢占采用两阶段 `REVOKE -> GRANT`：

    USB 请求 acquire/preempt
        -> 租约管理器锁存 preempt token，阻止新的 RDX acquire
        -> 向 Engine 投递 USB_PREEMPT system event
        -> Engine 关闭当前帧接纳闸门
        -> Adapter 停止 Pipeline 并注销 AI_TX 回调
        -> Engine 完成有界队列清理并 release 原租约
        -> 租约管理器校验 preempt token 和 lease generation
        -> 明确 GRANT USB
        -> USB 才允许打开共享 ADC

每次抢占使用 opaque preempt token 和 lease generation，陈旧 release/grant 不得命中新请求。抢占必须有 deadline；若 Engine、Adapter 或租约释放未在 deadline 内完成，租约管理器返回 `PREEMPT_TIMEOUT`，USB 本次启动失败且不得绕过租约强开 ADC。RDX 侧锁存资源回收故障并继续 fail-closed 处置，直到能够证明旧持有者已经释放。

阶段 B 前必须先验证 BR56/JL SDK 可实现的 acquire/release/两阶段抢占接缝及其回调上下文；若现有 API 不足，只能增加通用资源仲裁接缝。实现后必须在目标硬件验证“USB 先开”和“录音先开、USB 后抢占”两种时序，并证明不存在双 ADC 瞬时并发。

USB 抢占后的业务结果按 Session 目标区分：

- 当前纯在线 Session：Online 是唯一 REQUIRED Destination，Service 终止 Session，APP 必须重新 START；
- 未来含 Local REQUIRED Destination 的 Session：Service 可以保留 Session 和产物，进入 `SUSPENDED_BY_RESOURCE(USB_PREEMPT)`；
- USB 释放资源只改变可用条件，不自动恢复采集；原 controller 必须显式 Resume，成功取得新租约后才能创建新的 `capture_generation`；
- 用户已经暂停的 Session 不因 USB 来去而改写为资源挂起，`PAUSED_BY_USER` 保持用户意图优先。

## 14. 在线业务安全门控

在线录音申请 Engine 前必须同时满足：

- RDX_ABILITY_CONFERENCE_RECORDING 已声明；
- AppKey 校验通过；
- 设备已绑定；
- BLE 链路已加密；
- TX CCC 已开启；
- 有效 ATT Value Payload 能容纳 98 B；
- 当前没有 USB 音频和其他录音 Session；
- 没有解绑、恢复出厂或关机 pending；
- 没有 OTA、格式化或其他独占操作租约；
- TX Scheduler 已初始化且 CONTROL/REALTIME_AUDIO 资源合同成立。

任一条件不满足都不得打开 Pipeline。

“有效 Payload”必须同时考虑协商 ATT MTU 和本地发送上限，不能仅把 `app_ble_att_vaild_len_get()` 的 cbuf 可写长度当成 `MTU - 3`。安全门控及重连挂接必须使用当前 connection generation 的状态；旧连接事件不得满足新连接的门控。

未声明会议录音 Ability 时收到录音命令应记录 unsupported，不得存在“广播没有声明但命令仍可使用”的隐藏功能。

## 15. 错误模型

Engine 和业务层必须保留明确错误，不因 V23 Wire 表达能力有限而在内部压成布尔值：

| 错误 | 含义 |
| --- | --- |
| BUSY | 录音 Session 或 USB 资源已被占用 |
| NO_MEMORY | 创建任务、队列或 Pipeline 资源失败 |
| UNSUPPORTED_FORMAT | 格式 ID 不在白名单 |
| FORMAT_MISMATCH | Pipeline 实际格式不符合合同 |
| START_FAILED | Pipeline 或 Destination 启动失败 |
| START_TIMEOUT | 启动闸门未在限定时间内完成 |
| CONTROL_QUEUE_FULL | 普通 controller request 固定队列已满；STOP/system event latch 不受影响 |
| ACK_TIMEOUT | 关键 START/STOP ACK 未在 deadline 内获得 ATT 传输接纳 |
| BAD_STATE | 当前 Session 状态不接受该请求，例如 `PAUSED_BY_USER` 时 Mark |
| NOT_CONTROLLER | 请求者没有当前 Session 控制权 |
| CONTROL_TRANSFER_REJECTED | 显式控制权转移未获授权或目标 controller 不可用 |
| RESOURCE_PREEMPTED | USB 等高优先级资源事件结束了当前采集周期 |
| PREEMPT_TIMEOUT | 音频租约未在抢占 deadline 内安全撤销，USB 不得启动 |
| QUEUE_FULL | ACTIVE 候选帧或 RecordFrame 无法进入固定数据面队列，纯在线流出现不可表达缺口 |
| REALTIME_EXPIRED | REALTIME_AUDIO 包超过实时 deadline 或重试预算，当前 V23 流已形成不可表达缺口 |
| TRANSPORT_FATAL | BLE connection、CCC、Payload 或 Transport 状态已经无效，包不可重试 |
| DRAIN_TIMEOUT | Pause/Stop 切点的已入队帧未能在限定时间内排空 |
| DESTINATION_FAILED | 某输出目的地无法继续消费 |
| DESTINATION_OVERFLOW | 某输出目的地的私有队列已满 |
| DESTINATION_TIMEOUT | 输出目的地摘除或取消超时 |
| ARTIFACT_COMMIT_FAILED | 录音产物提交失败 |
| ARTIFACT_RECOVERY_REQUIRED | 重启后发现 OPEN 或 COMMITTING 产物需要恢复 |
| ARTIFACT_QUARANTINED | 恢复时无法满足格式或完整性合同，产物禁止发布 |
| SHUTDOWN_DEADLINE | 退出 deadline 内未完成产物提交，已转入 recovery marker 路径 |
| SHUTDOWN_TIMEOUT | 本期 RDX 退出屏障未在 deadline 内收敛，仍可被回调访问的对象不得释放 |
| LINK_LOST | BLE 链路或 CCC 丢失 |
| CANCELLED | 迁移态请求被显式取消 |

完成事件必须分别表达 `termination_mode` 与 `cause`，例如“系统强制终止 + USB_PREEMPT”或“正常停止 + USER_REQUEST”；不得把 `FORCED_STOP` 与 `LINK_LOST/QUEUE_FULL` 等根因压进同一枚举。当前 V23 若只能表达停止状态，Online Service 可以把多个内部错误映射为 STOP，但串口日志、统计和完成事件必须保留真实根因。

### 16.3 在线业务条件依赖

当 Ability 包含 RDX_ABILITY_CONFERENCE_RECORDING 时，额外检查或验证：

这些依赖不得提前进入 Engine。

### 16.5 RDX OFF 与 Ability OFF

两类关闭语义必须区分：

- Ability 不含 Conference Recording：Engine、Audio Adapter、专用 Pipeline 和 TX Scheduler 仍属于 RDX 基础设施；在线命令入口返回 unsupported；
- TCFG_RDX_ENABLE 为 0：整个 RDX、录音基础设施和专用 Pipeline 增量都应退出。

rdx_integration_config.h 只能裁剪 C 侧源码，不能修改 x6flow 或 stream.bin。若工程继续要求验证 RDX OFF 零残留，必须建立由 JL 工具生成的 RDX ON/OFF 产品 Profile 或等价生成联动；不得用晚期 undef/define 制造只有部分资源关闭的配置。

## 17. 生命周期

推荐初始化顺序：

    rdx_tx_scheduler
        -> rdx_operation_coordinator（本期最小操作集）
        -> rdx_record_engine
        -> rdx_online_record_service
        -> protocol/transport 接入

推荐退出顺序：

    停止接受新协议命令
        -> Online Service 取消新请求入口
        -> 向常驻 Engine worker 投递 SHUTDOWN system event
        -> 有界同步等待 Engine 到 IDLE、Pipeline 关闭和音频租约释放
        -> 有界同步等待 Engine/Online/TX 队列清理及 Scheduler 取消完成
        -> 注销 Transport/AI_TX/USB 回调
        -> 销毁 Online Service
        -> 销毁 Engine worker 和固定控制入口
        -> 销毁 Operation Coordinator
        -> 销毁 TX Scheduler

未来 Local Storage 启用后，在“强制停止当前 Session 和采集周期”与“销毁 Engine”之间增加独立分支：要求 Storage Service 提交未完成 Artifact，在退出 deadline 内等待；超时则持久化 recovery marker 并继续退出。该分支不是本期在线录音实现内容。

Engine 内部使用异步事件收敛，但 `rdx_protocol_stop()` 等生命周期编排者必须提供有界同步退出屏障。若 deadline 内未达到上述条件，记录 `SHUTDOWN_TIMEOUT` 并保持 fail-closed：不得释放 worker、回调上下文、固定队列或仍被租约引用的对象。最终平台掉电路径服从平台总 deadline，不无限等待；若硬件强制掉电，日志必须区分“平台终止等待”和“RDX 已安全退出”，不得虚报成功。

所有 init、stop 和 exit 必须幂等；未来即使 Artifact 提交超时，也不得无限阻塞关机或退出。除 session_id 外，Transport 连接还应维护 generation；旧连接的延迟完成事件不得作用于新连接。

## 18. 运行时资源策略

“基础设施始终编译”不等于“上电即占用完整运行时资源”。

推荐：

- RDX 启用期间保留一个小型常驻 Engine worker、固定控制入口和 system-event latch，初始化成功后才允许协议接入；
- 本期帧池、Online Destination 队列、CONTROL/REALTIME_AUDIO 队列和启动首包槽使用静态固定容量；START 只认领并清零，STOP 做逻辑释放，不反复 malloc/free；
- START 时打开 Pipeline/Encoder 并取得其 SDK 动态资源；STOP 后关闭并释放这些 SDK 动态资源，常驻 worker、固定 RDX 缓冲区、控制入口与 latch 保持可用；
- RDX exit 时先停止协议接入并通过常驻 worker 收敛 Session，再销毁 worker；
- 最终策略以 100 次启停和最低内存水位验证为依据。

常驻控制面和固定 RDX 缓冲区的 RAM、栈峰值及最低内存必须单独记录。禁止为了节省这部分内存在 STOP 后销毁 worker或反复申请队列，否则 EXIT、USB 抢占、内存碎片和延迟故障将变得不可控。未来业务缓冲区不得在 Ability 关闭时提前常驻。

- 重复 START/STOP 不重复操作 Engine、不堆积相同待发 ACK；
- 普通控制队列满时合法 STOP 仍通过独立 latch 收敛；START/其他请求明确返回 CONTROL_QUEUE_FULL；
- START/STOP 关键 ACK 槽不被普通控制包占用；ACK_TIMEOUT 不会留下活动 Pipeline 或重新打开已停止 Session；
- RETRYABLE 在 deadline/预算内不会误强停；REALTIME_EXPIRED 与 FATAL 分别留下准确 cause；
- 内部故障在原连接仍有效时只发送一次 V23 STOP，断连/CCC off 后不发送且新连接不收到旧通知；
- 重复 Wire 命令只增加饱和 duplicate_count，不导致控制 RAM 随请求数增长；
- START 任一步失败均按事务逆序回滚，无“Pipeline 已打开但输出容量未预留”的半启动状态；
- 常驻 Engine 控制 worker 在空闲、活动和退出路径均能接收 system event，STOP 后无大帧缓存残留；
- RDX 固定队列在 100 次 START/STOP 中不发生 malloc/free、碎片增长或越界，未来业务未启用时不占对应缓冲 RAM；
- RDX exit 在 deadline 内完成同步屏障；超时路径保持回调对象有效并记录 SHUTDOWN_TIMEOUT；
- 无未解释的静默丢帧；
- Engine 和 TX 队列不持续增长；
- USB 先开时录音拒绝正确；
- 录音先开、USB 后启动时无双 ADC 瞬时破坏；
- 当前纯在线被 USB 抢占后安全终止，APP 重新 START 后可以恢复在线录音；
- USB 只有在 `REVOKE -> release -> GRANT` 完成后才能启动；`PREEMPT_TIMEOUT` 时 USB 保持关闭；
- 普通业务请求不能伪造 system event，非 controller 不能停止当前 Session；
- system event 不被普通请求或音频帧饿死，重复事件只触发一次资源回收；
- 旧 engine/session/capture/connection generation 事件均不能改变当前状态；
- BLE 断连、CCC off、解绑和恢复出厂均安全回收；
- 1M 回退路径和目标手机兼容性通过；
- 目标硬件串口日志确认真实 termination_mode、cause 和资源恢复。

### 22.3 未来业务启用门槛

以下项目不是本期在线录音交付条件，而是未来声明相应 Ability 或移植对应业务时追加的门槛：

- Pause/Resume：切点前已入队帧完整 drain，或以 DRAIN_TIMEOUT/discontinuity 明确解释；资源恢复不自动 Resume；

## 25. 最终决策摘要

1. 首版在线录音功能成立，但当前结构仍是 Spike，不作为生产架构继续扩展；
2. 录音 Engine 是 RDX 内部公共基础设施，业务 Service 控制唯一逻辑 Session，在线、本地和诊断是可组合的输出目的地；
3. Ability 只描述真实外部业务能力，不裁剪公共录音基础设施；
4. RDX ON 时始终编译录音基础设施，但空闲时不应占用大运行时资源；
5. 使用 RDX 专用 Pipeline，恢复 ai_voice 公共接口；
6. Engine 使用唯一 worker；request_id、session_id 和 capture_generation 分别隔离请求、会话和采集周期；
7. 控制邮箱与帧队列物理分离，STOP、EXIT 和锁存故障必须必达；
8. AI_TX 回调只写固定队列，不直接 BLE 或文件操作；
9. 所有 RDX Notify 统一由 TX Scheduler 发送，采用 CONTROL、REALTIME_AUDIO、BULK_FILE 三类 QoS；
10. Notify completion 表示本地 ATT 传输接纳，不表示空口成功或 APP 已收到；
11. USB 和 RDX 使用原子音频资源租约；USB 优先并可请求强制停止；
12. Pause 保持同一 Session，结束采集周期并释放音频租约；
13. 本地录音产物的异步提交与采集 Session 分离；
14. RDX Operation Coordinator 负责录音、存储、上传、扫描、格式化、删除和 OTA 的业务操作兼容矩阵；
15. rdx_integration_config.h 只验证最终 JL 配置，不反向开启生成宏；
16. JL 原生代码只保留无 RDX 知识的必要通用接缝；
17. 当前 Ability 收敛为 RTC 与 Conference Recording；
18. 本次只迁移在线 START/STOP，不提前实现本地录音空壳，但公共合同纳入已知后期业务约束；
19. 公共 C ABI 不在设计阶段提前冻结，按阶段实现并通过事件序列和故障注入验证；
20. 构建与静态检查是合入门槛，目标硬件耐久和串口证据是生产就绪门槛。
21. Engine 内部以 RecordFrame 统一序号、有效时间轴、Pause/Resume 和 discontinuity 语义，V23 Wire 保持不变；
22. Destination 由 Service 声明 REQUIRED/OPTIONAL，单个目的地失败不由 Engine 自动扩大为全局失败；
23. 断连与重连策略属于会话 Service；Engine 不硬编码三秒恢复或其他 APP 策略；
24. SESSION_STOPPED 与 ARTIFACT_COMMITTED 是两个独立里程碑，未提交产物不得对外宣称保存成功；
25. Flashnote 不是当前参考 Golden Behavior，不增加 Engine 特殊状态且 Ability 保持关闭。
26. Pause 先关闭当前采集周期的接纳闸门，再有界 drain 已入队帧；超时必须留下 discontinuity；
27. Resume 预热帧不推进 session_frame_seq 和 active_pts，失败时 Session 保持原来的 `PAUSED_BY_USER` 或 `SUSPENDED_BY_RESOURCE`；
28. Session Metadata Service 在 Engine 串行点生成 canonical Mark，Pause/Mark 并发以控制邮箱出队顺序裁决；
29. 每个异步 Destination 使用独立固定队列，Engine consume 不得等待；REQUIRED/OPTIONAL 决定故障处置；
30. 多目的地分发顺序稳定但不提供跨目的地原子事务，已接纳的数据不回滚；
31. 本地产物遵循 append-only 主体和原子发布目录项原则，恢复只能处理未提交产物。
32. 用户暂停与资源挂起分别使用 `PAUSED_BY_USER` 和 `SUSPENDED_BY_RESOURCE`；资源恢复不自动 Resume；
33. 当前纯在线 Session 被 USB 抢占时终止；未来 Local REQUIRED Session 可以保留并进入资源挂起；
34. 会话控制权不能隐式接管，只能通过可审计的 TRANSFER_CONTROL 改变；
35. 普通 controller request 与可信 system event 使用不同入口和事件类型，业务请求不能冒充系统强制事件；
36. 退出等待 Artifact 提交必须有界，超时进入 recovery marker 路径而不是无限阻塞；
37. 恢复成功的产物发布为 `COMMITTED_RECOVERED` 并保留 recovery 标志，失败产物进入 `FAILED/QUARANTINED`；
38. request_id、session_id 和 capture_generation 使用非零 32 位计数器，只要求不与当前活跃对象冲突，不承诺永久全局唯一。
39. 本期只实现公共框架和在线 START/STOP；后期业务当前只冻结边界，不创建运行时空壳、不开放命令和 Ability，并在各自移植阶段单独验收。
40. system event 与 controller request 使用固定独立入口；worker 在有界临界步骤之间优先处理锁存的 system event，重复事件合并，冲突普通请求明确取消；
41. USB 抢占采用两阶段 `REVOKE -> GRANT`；只有旧租约安全释放后才允许 USB 打开 ADC，超时返回 PREEMPT_TIMEOUT 并保持 fail-closed；
42. 所有 generation 和 ID 都是 opaque token，只允许完整上下文等值匹配，禁止用数值大小判断新旧；
43. 本期 Operation Coordinator 只实现在线录音与真实安全操作的最小集合；USB 使用独立音频租约，未来存储/传输操作不注册空壳；
44. 文档共同确认后架构冻结；合入需要确定性事件序列和开发门控 fake 测试，生产就绪仍必须以目标硬件证据确认。
45. MEETING_V1 预热属于格式 Profile 的采集资格过滤；候选帧通过过滤后才创建正式 RecordFrame，所有 Destination 共享同一首帧、序号和 active_pts；
46. RDX 启用期间保留小型常驻 Engine 控制 worker以及本期编译期固定帧池和在线队列；Session 期间只认领固定 slot，Pipeline/Encoder 的 SDK 动态资源只在活动采集周期持有；
47. 正常 STOP 使用快速切点并取消所有未获 ATT 传输接纳的音频，完成 SESSION_STOPPED 和取消后才排队 STOP ACK；Pause 未来使用有界 drain；
48. V23 重复命令由 Online Service 使用有界 first/last/count 摘要和 connection/session ACK 去重实现幂等，不重复提交 Engine 操作，也不缓存未来自动动作。
49. 本期 RDX 自有帧池和在线队列全部使用编译期固定容量，START/STOP 只认领和逻辑释放，不反复 malloc/free；未来业务缓冲区不提前占 RAM；
50. MEETING_V1 的 80 B、mono TOC 和 20 ms 是严格帧合同；异常正式帧不创建 RecordFrame、不发送，并以 FORMAT_MISMATCH 终止当前纯在线 Session；
51. RDX exit 使用异步 SHUTDOWN 加有界同步屏障；超时不得释放仍可能被回调访问的对象，最终掉电受平台总 deadline 约束；
52. `STARTING + STOP` 取消启动并只产生 STOP ACK；`STOPPING + START` 不缓存、不重启，APP 必须在 IDLE 后重新 START。
53. 合法 STOP 使用独立 `stop_requested` latch，不依赖普通控制队列空位；普通队列满时其他请求返回 CONTROL_QUEUE_FULL；
54. 当前 V23 STREAMING 后对不可恢复缺口零容忍：任一数据面 overflow、格式错误、实时包过期或明确发送失败都锁存首因并终止纯在线 Session；
55. TX Scheduler 为 START/STOP 状态 ACK 保留关键槽；ACK_TIMEOUT 只按当前状态安全收敛，不得重开 Session 补发；
56. START 按固定数据面资源、关键 ACK/首包槽、音频租约、Pipeline 的顺序事务式获取，任一步失败都逆序幂等回滚。
57. 终止迁移只提交一次主 termination cause；已锁存 system event/故障优先于 STOP，后续事件仅记录 secondary 摘要；
58. Transport 发送结果标准化为 ACCEPTED/RETRYABLE/FATAL；RETRYABLE 受实时 deadline 和重试预算约束，过期转换为 REALTIME_EXPIRED；
59. 内部故障强停后，仅在原 connection generation、加密和 CCC 仍有效时发送一次 V23 STOP 状态，不携带内部 cause，也不向新连接补发；
60. V23 重复命令幂等状态只保存 first_request_id、last_request_id 和饱和 duplicate_count，不保存无界 alias 列表。

本文仍在分阶段实施和逐轮架构复核。已确认的目标边界与当前里程碑事实直接维护在本文；尚未完成的目标不得写成已落地能力，也不得仅凭构建通过宣称硬件行为已经验证。后续实现若需要改变已经确认的边界，应先更新本文，再修改代码。
