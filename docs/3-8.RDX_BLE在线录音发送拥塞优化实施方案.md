> 文档状态：v0.3，阶段 0 诊断代码、clean/all 与 60 s A 组实机基线已完成；低日志 B 组受预编译库限制待补
> 编写日期：2026-08-24
> 目标工程：AC710N / BR56 Type-C 有线耳机
> 前置文档：`docs/3-7.RDX_USB通话在线录音评估与实施方案.md`
> 基线日志：`会丢失一部分录音，录音不完整。上下行播放正常.log`
> 阶段 0 A 组日志：`COM3_2026-08-24_10-40-50.log`（仅作硬件证据，不纳入代码提交）
> 本文范围：仅解决 RDX Engine / Destination / BLE ATT 在线发送侧的反压、排队和丢帧问题
> 变更约束：不修改 Near/Far Tap、PCM Bridge、音频图和当前 `80 B raw Opus` APP 合同；分阶段实施，每阶段可独立回退

## 1. 结论

**[已确认事实]** 3-7 已经完成 USB 通话 Near/Far 取流、有界 PCM Bridge、mono 混音、标准 Opus 编码、Call Backend、scene `1` START/STOP 以及 APP 基本解码闭环。当前问题不是“上下行不能同时合并”，而是混合 Opus 帧进入 Engine 之后，Destination 和 BLE/ATT 出口长期低于每秒 50 帧的产生速率。

**[已确认事实]** 基线会话产生 `2061` 个 20 ms Opus 帧，对应约 41.22 s 有效编码时间；Call Audio 侧 `pcm=2061/2061/2061`、`overflow=0`、`generation_drop=0`、`opus=2061/164880`，说明 PCM Bridge 和编码连续、每帧稳定为 80 B。同一会话中 Engine 丢弃 `91` 帧；Destination 处理到 `1750` 帧时已有 `338` 帧因 TX 队列满而丢弃，因此全会话已确认的丢帧下限为 `429` 帧，即 8.58 s，实际可能更多。

**[推荐设计]** 第一优先级不是增大队列、降低码率或反复请求 7.5 ms 连接间隔，而是把当前“每产生一帧就立即试发，失败后等下一帧再重试”改为“有界入队 + `ATT_EVENT_CAN_SEND_NOW` 事件驱动排空”。BLE 协议栈上下文只发送可发通知，不直接排空业务队列；所有 TX 队列变更和 `app_ble_att_send_data()` 仍在单一任务上下文完成。

**[推荐设计]** 优化必须保持当前“USB 主链优先、录音队列有界”的安全边界。即使 BLE 永久不可发，也不得阻塞 Near/Far Tap、PCM Bridge、PCMIC 或 PCSPK；队列达到上限时仍允许丢弃最旧录音帧作为最后保护，但“长期无丢帧”必须成为本文的验收目标，不能把安全丢帧等同于问题已解决。

## 2. 与 3-7 的边界

### 2.1 3-7 已经交付的能力

- Near/Far 两路 USB PCM Tap 与格式代次管理；
- 两路异构采样率/位宽归一和有界 PCM Bridge；
- Near 样本主时钟的 20 ms mono 混音；
- `16 kHz / mono / 32 kbps / 20 ms / 80 B raw Opus` 编码；
- Meeting/Call 双 Backend 与单 Engine 互斥；
- APP scene `1` START/STOP、真实 scene ACK 和录音状态闭环；
- USB 通话主链不被录音反压拖死的安全回退。

### 2.2 3-8 仅处理的链路

```text
AI_TX / Opus candidate
        -> RDX Record Engine candidate queue
        -> Online Destination TX queue
        -> RDX BLE transport
        -> ATT notification
        -> APP
```

### 2.3 本阶段非目标

- 不调整 Near/Far Tap 位置；
- 不修改 PCM Bridge、SRC、混音系数或时钟基准；
- 不修改 `.x6flow`、`stream.bin` 或 JL 可视化音频图；

## 3. 当前发送合同与理论需求

### 3.1 单帧封包

**[已确认事实]** 当前每个 Opus 帧的业务包为：

```text
"*DEV#stream#80#80#" + 80 B raw Opus
```

Wire 头长度为 18 B，因此每帧应用层载荷为 98 B。编码周期为 20 ms，即每秒 50 帧：

```text
50 frames/s * 98 B = 4900 B/s
4900 B/s * 8 = 39.2 kbit/s
```

上述只是应用层有效载荷，尚未计入 ATT、L2CAP、Link Layer 和空中重传开销；但在 2M PHY、DLE 251 和足够连接事件下，39.2 kbit/s 并不应天然超过 BLE 能力。因此当前日志证明的是“ATT 发送路径存在持续反压”，还不能等同为“2M PHY 物理带宽不足”。

### 3.2 当前 BLE 参数

| 项目 | 设备请求/配置 | 基线日志实际结果 | 结论 |
| --- | ---: | ---: | --- |
| ATT MTU | 交换大 MTU | `514` | 98 B 应用包可容纳 |
| DLE TX octets | `251` | `251` | 已生效 |
| DLE TX time | `2120` | `2120` | 已生效 |
| PHY | 2M | TX/RX 均为 `2` | 已生效 |
| Connection interval | `6-6` = 7.5 ms | 录音时被更新为 `10`、后为 `9` | 手机最终保持 12.5/11.25 ms |
| Slave latency | `0` | `0` | 符合预期 |

**[已确认事实]** `ble_op_conn_param_request()` 返回成功只代表请求已提交，不代表手机必须长期保持 7.5 ms。当前代码已在连接、录音开始和 slow update 时请求高吞吐参数；因此只继续调小 interval 不是第一优化项。

## 4. 基线证据与丢帧定位

### 4.1 会话时间与输入状态

**[已确认事实]** 长会话 session `3` 从设备运行时间 `00:01:22.048` 开始，到 `00:02:03.545` 停止，约 41.5 s；`2061 * 20 ms = 41.22 s` 与会话持续时间相符。Far Tap 以 96 kHz / 2 ch 启动，Near Tap 以 44.1 kHz / 1 ch 启动，录音期间没有出现任一 Tap stop。

### 4.2 分层证据

| 链路层 | 基线日志 | 判断 |
| --- | --- | --- |
| Call PCM / Encoder | `pcm=2061/2061/2061 overflow=0 generation_drop=0 resets=1 opus=2061/164880` | PCM 入队、出队和 80 B Opus 完整对账；`resets=1` 是本次初始时间线建立，不是运行期反复复位 |
| Record Engine | `produced=2061 enqueued=2061 overflow=91 mismatch=0 stale=0 stop_discarded=0` | Destination 处理不及时已反压到 16 帧 candidate queue，丢弃 91 帧 |
| Online Destination @250 | `sent=193 pending=15 peak=16 drop=42` | 约 5 s 已达队列上限并丢帧，不是只在 STOP 尾部丢帧 |
| Online Destination @1750 | `sent=1397 send_fail=1704 pending=15 peak=16 drop=338` | 长期发送速率低于 50 fps，队列几乎一直满载 |
| ATT 发送资源 | `remain size` 多次从 3916 B 降到 162 B | 发送缓冲持续被耗尽 |
| 协议栈反压 | 会话区间约 1777 次 `stack_resume_fail!!!:21` | 与 ATT 低剩余空间和 TX 丢帧同时出现 |

### 4.3 对账

在 `frames=1750` 时：

```text
sent + pending + drop
= 1397 + 15 + 338
= 1750
```

`send_fail=1704` 是重复尝试失败次数，不是 1704 个不同录音包。`drop=338` 才是该时刻已被 Destination 明确丢弃的唯一录音包数。Engine 的 `overflow=91` 发生在 Destination 之前，与 TX 队列的 338 帧不重复。

### 4.4 为什么不是上下行合并失败

Near/Far 在 PCM Bridge 中先归一、对齐并混为一路 16 kHz mono，APP 并不同时接收两路异构 PCM。本次只产生 `2061` 个混合 Opus 帧，而不是 Near/Far 各 `2061` 帧后再向 APP 发送 `4122` 帧。Call Audio 侧编码对账完整，明确丢帧计数均出现在 Engine 候选队列和 Destination TX 队列，所以当前的主要质量问题应在发送出口解决。

## 5. 当前发送实现的局限

### 5.1 当前行为

1. Destination 每收到一个新 Opus 帧，先调用 `rdx_mvp0_record_drain_queue()`；
2. `drain_queue()` 在同一次调用中循环调用 `rdx_mvp0_send()`；
3. `rdx_ble_transport_send()` 先读取 `app_ble_att_vaild_len_get()`，空间不足返回 `-2`；
4. 发送失败后保留队头，函数返回；
5. 当前没有处理 `ATT_EVENT_CAN_SEND_NOW`，也没有因 ATT 恢复可发而主动唤醒 Destination；
6. 下一次排空主要依赖下一个 20 ms 录音帧到来。

### 5.2 问题

- “新音频帧到来”同时承担产生数据和恢复旧积压的职责；
- ATT 何时可发与 20 ms 音频节拍无关，轮询式重试可能错过最佳发送窗口；
- 队列长期满载时，每个新帧都会先引起一次重试失败，然后再丢最旧包；
- 高频失败、队列搬运和每包十六进制串口日志会进一步占用 CPU/串口时间；
- 当前 `send_fail_count` 没有按 `-1`、`-2` 和 `app_ble_att_send_data()` 的真实返回码分类，无法区分无连接、ATT 空间不足和其他协议栈失败。

## 7. 目标设计

### 7.1 事件驱动数据流

```text
AI_TX callback / encoded candidate
              |
              v
       RDX Record Engine task
              |
              v
   Destination bounded TX queue ---- queue full ---> drop oldest + counter
              |
              | poll/drain with bounded budget
              v
      rdx_ble_transport_send()
          | success          | ATT busy/no space
          v                  v
       sent++       arm CAN_SEND_NOW once, return
                                 |
                                 v
BLE packet handler: ATT_EVENT_CAN_SEND_NOW
          |
          | set tx-ready latch only
          v
   wake existing RDX Record Engine task
          |
          v
 Destination poll/drain in task context
```

### 7.2 线程与所有权边界

**[推荐设计]** BLE packet handler 中不得直接调用 `rdx_mvp0_record_drain_queue()`，也不得在回调中修改 TX 队列头尾。回调只完成以下操作：

1. 校验当前 `con_handle` 和连接代次；
2. 清除 `can_send_request_pending`；
3. 置位 `tx_ready_latch`；
4. 唤醒已有 `rdx_record` 任务。

**[推荐设计]** Record Engine 增加轻量 Destination-ready 通知，不新建常驻 TX 任务。可以给 `rdx_record_destination_ops` 增加可选 `poll` 操作，由 Engine 任务消费 ready latch 后调用；也可以使用等价的内部通知机制。具体符号名称可在实施时按现有 C 风格收敛，但不得把 Destination 队列所有权分散到 BLE 回调与 Engine 两个上下文。

### 7.3 排队和排空规则

1. 首轮保持 TX 队列深度 16，不用增大队列掩盖平均吞吐不足；
2. 新录音包先按 FIFO 入队，再由同一任务的 poll/drain 发送，避免“有时直发、有时入队”形成双路序列；
3. 一次唤醒最多发送有界数量的包，建议 Spike 起始值为 4；避免一次清空占满 Engine 任务时间；
4. 发送成功后再移动队头；失败时保留队头，记录分类返回码；
5. 遇到 ATT busy/空间不足时只 arm 一次 can-send-now；未收到事件前不重复请求；
6. can-send 事件后如队列仍非空且再次 busy，重新 arm 一次；
7. 断连、CCC off、STOP、Pause 和 capture generation 切换时必须清理 ready/request latch，旧连接事件不得排空新会话队列；
8. 队列真满时继续丢最旧包以保护实时性和 USB 主链，但只有 `queue_drop_count` 计入真实丢帧；busy 重试不计入丢帧。

### 7.4 参考工程与目标工程的区别

**[已确认事实]** BR28 参考工程的 RDX BLE server 已处理 `ATT_EVENT_CAN_SEND_NOW`，其回调主要清发送状态并 `os_sem_post()` 唤醒私有发送任务。这证明“BLE 可发事件只用来唤醒业务发送上下文”是参考工程也采用的模式。

**[推荐设计]** 目标 BR56 工程不复制参考工程的 `BleBulkSendData`、`BLE_SendData`、全局发送标志或私有任务。目标工程已有独立 `app_ble` handle、RDX Record Engine 任务和有界 Destination 队列，应仅复用事件驱动原则，并在本工程现有所有权边界内实现。

## 8. 分阶段实施计划

### 阶段 0：冻结基线、补齐可观测性和低日志 A/B

**目标：** 不改变发送策略，先将每一类失败和队列对账收敛为可比较数据，同时确认高频串口日志的影响。

**实施项：**

1. 区分并统计：未连接/CCC off、`valid_len` 不足、`app_ble_att_send_data()` 各返回码；
2. 增加 `can_send_request_count`、`can_send_event_count`、`spurious_event_count`、`valid_len_min/max`、TX 队列峰值和真实 drop 计数；
3. 在会话 STOP/强制终止时打印一行最终对账，不依赖每 250 帧的中间快照；
4. 定位 `[APP-BLE] app_ble_att_send_data` 每包十六进制打印的 SDK 日志开关或 no-log 库配置；不手改生成二进制或猜测不存在的宏；
5. 使用相同手机、相同通话时长、相同音频内容对比“完整包 hex log”和“低日志”两组结果。

**[已实现并完成 A 组实机验证，2026-08-24]** 当前代码没有改变发送调度：没有调用 `att_server_request_can_send_now_event()`，没有由 `ATT_EVENT_CAN_SEND_NOW` 排空队列，也没有修改 16 包队列、BLE 参数或 80 B APP 合同。已完成以下可观测性闭环：

- BLE transport 在录音窗口内分别统计链路/CCC不可用、`valid_len` 不足和 `app_ble_att_send_data()` 非零返回码，并保存最多 4 种真实返回码及次数；
- 记录 `valid_len` 样本最小/最大值、MTU、最终连接间隔/latency、PHY和DLE；
- `ATT_EVENT_CAN_SEND_NOW` 当前只计数，不唤醒任务；阶段 0 没有发出 RDX 请求，因此 `can_req=0`。实机表明共享 `app_ble`/ATT 层仍会产生事件，这些非 RDX 自有事件计入 `spurious_evt`，所以 `can_evt` 不要求为 0；阶段 1 仍必须在 busy 后显式挂起一次 RDX 请求并用 pending latch 区分所有权；
- Destination 新增 `destination_in`、`cancel_discard` 和最终STOP/强制终止对账；STOP采用“不等待BLE尾包”的现有策略，清队列前先把未发包计入 `cancel_discard`，STOP_PENDING期间Engine已交付但不再发送的尾帧也计入该项；Pause丢弃是 `cancel_discard` 的子集，并单独输出 `pause_discard`；
- Engine新增累计 `warmup_discard`、STOP时尚未消费的candidate计数以及 `destination_out`，可与Destination按 `session/capture` 对账；
- `RDX_CFG_BLE_TX_DIAG_ENABLE` 默认开启，关闭后停止阶段0详细统计更新和输出，不改变录音业务行为。

**[已确认限制]** `[APP-BLE] app_ble_att_send_data---` 和随后的完整payload十六进制打印不在本仓库可编辑源码中。仓库只有 `SDK/interface/btstack/third_party/common/app_ble_spp_api.h` 接口，实际 `app_ble` 实现来自预编译SDK对象，未检索到可用的单模块日志宏或no-log替代库。因此本阶段不手改库文件，也不通过关闭全局UART日志冒充低日志对照；低日志B组需要杰理提供关闭该打印的库/开关后再执行。现有固件可先完成A组与失败分类验证。

**[构建证据，2026-08-24]** 已从 `SDK/` 执行 `.vscode\winmk.bat clean` 和 `.vscode\winmk.bat all`，编译、链接与固件打包通过；`output/update.ufw` SHA-256 为 `90D4628ACFE0C431D8E5C6C7B0EC1460822EAF77057DBDA914B3F10945FD06E0`。构建末尾为 `Device Offline`，说明本轮没有下载到目标板，不能据此声明硬件行为通过。

**[A 组实机证据，2026-08-24]** `COM3_2026-08-24_10-40-50.log` 覆盖 Near-only、Far-only、双讲和静音/恢复等场景，产生 `3041` 个 20 ms 帧，对应约 60.82 s。Call Audio 为 `pcm=3041/3041/3041`、`overflow=0`、`generation_drop=0`、`opus=3041/243280`，证明 PCM Bridge 和 80 B Opus 编码连续；Engine 对账为 `3041 = warmup_discard 10 + overflow 221 + stop_discarded 6 + destination_out 2804`，Destination 对账为 `2804 = sent 2153 + tx_drop 639 + cancel_discard 12`，STOP 后 `pending=0`。拥塞窗口内 `valid_samples=4910 = app_ok 2154 + busy_valid_len 2756`，`unavailable=0`、`app_error=0`，说明失败全部发生在 ATT 可用空间预检查，不是连接/CCC不可用或底层发送返回错误。最终链路为 MTU 517、interval 9、latency 0、2M PHY、DLE 251/2120；`can_req=0` 时仍收到 `can_evt=886`，均按非 RDX 自有事件计入 `spurious_evt`。录音期间多次 CPU 采样达到 99%～100%，预编译 `app_ble` 每包 payload 日志是尚未排除的重要干扰变量；日志文件不纳入提交。

**阶段验收：**

- 构建通过，但只记录为构建证据；

### 阶段 1：`ATT_EVENT_CAN_SEND_NOW` 事件驱动 Spike

**目标：** 在不修改队列深度、连接参数和 APP 合同的情况下，让 ATT 恢复可发事件主动驱动积压队列排空。

**实施项：**

1. BLE transport 处理 `ATT_EVENT_CAN_SEND_NOW`并增加可发请求/ready 通知接口；
2. Destination 增加事件驱动 poll/drain，队列由 `rdx_record` 任务单上下文消费；
3. busy 时只 arm 一次 request，事件到来后用有界 burst 排空；
4. 保留 16 包 TX 队列和丢最旧安全策略；
5. 引入连接代次/session/capture 校验，防止旧 can-send 事件污染新会话；
6. 使用独立编译开关保留当前轮询式路径，便于在同一代码基线上快速构建回退版本。

**首轮验证场景：**

1. 60 s Near-only；
2. 60 s Far-only；
3. 60 s 双讲；
4. 60 s 双方分别静音后恢复；
5. 上述场景各执行 3 次；
6. 额外执行 scene `0` 会议录音 60 s 回归。

**阶段验收：**

- Call Audio `overflow=0`、`generation_drop=0`；
- Engine `overflow=0`、`mismatch=0`、`stale=0`；
- Destination `drop=0`；
- STOP 时 TX 队列可对账，不留旧 session 包；
- busy 可以出现，但必须由 can-send 事件恢复，不能转化为队列 drop；
- APP 播放无可感知中断，Near/Far 都可听；
- USB 通话上下行、放歌、提示音、HID 和枚举无回归问题。

**回退条件：** 出现卡死、复位、旧会话串包、STOP 无法收敛、USB 主链受损，或 event request 长期不回调且无超时保护时，立即回退到阶段 0。

### 阶段 2：调度、控制包优先级与连接参数收敛

**前置：** 只有阶段 1 事件驱动路径稳定，但仍有可重现丢帧、状态 ACK 失败或起始瞬时拥塞时，才进入本阶段。

**实施项：**

1. 根据阶段 1 统计对比 burst budget `1/2/4/8`，以 `drop=0` 和不饿饿 Engine 为准；
2. 评估为 START/STOP/PAUSE/RESUME/record state ACK 增加有界控制包重试或优先级，避免状态包被长录音流挤压；
3. 保持 latency `0`、2M PHY 和 DLE 251，对比手机实际 interval `6/9/10`（7.5/11.25/12.5 ms）下的持续发送结果；
4. 限制 slow-update 参数重请求频率，避免与手机反复交替参数形成无效振荡；
5. 评估是否要求 CCC、MTU 与高吞吐参数进入可接受状态后再放行音频帧；等待必须有有界超时，不得让 APP START 无限挂起；
6. 如 APP 可控，由 APP 侧记录 Android/iOS 连接优先级申请和最终参数，设备日志与 APP 日志按时间对齐。

**阶段验收：**

- 在手机最终保持 interval `9` 或 `10` 时仍可 10 min `drop=0`；
- 录音起始 5 s 内不出现队列打满；
- START/STOP/PAUSE/RESUME 状态不丢失；
- 无连接参数无限重请求或任务抖动。

### 阶段 3：平均载荷降级或 Wire 合同演进

**前置：** 仅当事件驱动、低日志、burst 调度和连接参数矩阵都完成，且特定目标手机仍无法维持 98 B / 20 ms 时，才允许进入。

| 选项 | 预期效果 | 代价/约束 | 决策 |
| --- | --- | --- | --- |
| Opus 32 -> 24 kbit/s | 理论 payload 降至约 60 B/20 ms | 当前 APP 固定 80 B 合同可能不接受 | 需 APP 明确验证新 Profile |
| Opus 32 -> 16 kbit/s | 理论 payload 降至约 40 B/20 ms | 语音质量进一步下降 | 只作最低带宽候选 |
| 40 ms Opus 帧 | 包头频率减半 | 延时增加，一次丢包影响更长，APP 合同变化 | 需独立 Profile |
| 一个 notification 聚合多个 Opus 帧 | 减少 ATT/应用头开销 | APP 必须知道帧边界，不能盲目拼接 raw Opus | 必须版本化 Wire 并联合修改 APP |
| 增大 TX 队列 | 吸收短时毛刺 | 不解决长期吞吐不足，只会增加延时和 RAM | 只在已证明为短时毛刺时小幅调整 |

**[推荐设计]** 本阶段不修改现有 `MEETING_V1` 冒充兼容，应创建明确版本化的新数据合同，并保留旧 APP/旧固件的拒绝和回退路径。

### 阶段 4：长稳、回归和量产收敛

1. Call 通话录音连续 2 h；
2. Meeting 在线录音连续 2 h；
3. Call START/STOP 100 次；
4. Call PAUSE/RESUME 50 次；
5. BLE 断连/重连 30 次；
6. CCC off/on 30 次；
7. USB Speaker/MIC 分别 close/open 和格式切换；
8. 至少一台 Android 和一台 iOS 目标手机覆盖；
9. 记录 CPU 峰值、最低空闲 RAM、TX 队列峰值和所有对账计数；
10. USB 通话、放歌、提示音、HID 和枚举完整回归。

**量产退出门槛：**

- 正常连接条件下 Engine `overflow=0`、Destination `drop=0`；
- 每次会话的设备发送帧数与 APP 接收通知数可对账；
- APP 播放 Near/Far 完整，无周期空洞、卡顿和无法解析；
- 断连、CCC off、source lost 等强制终止允许有受控的尾部丢弃，但必须单独记录 `cancel_discard`，不与拥塞 drop 混淆；
- 不因 BLE 发送恢复事件出现死循环、任务饥饿、旧会话串包、ASSERT 或复位；
- 不破坏 scene `0` 会议录音和非录音 RDX 命令。

## 9. 统计与对账合同

### 9.1 阶段0实际输出

```text
[RDX][ENGINE] stopped ... produced=<n> overflow=<n> mismatch=<n>
 stale=<n> stop_discarded=<n> warmup_discard=<n> destination_out=<n>
[RDX][TXQ] final reason=<cancel|detach> session=<id> capture=<generation>
 destination_in=<n> sent=<n> pending=<n> tx_drop=<n>
 cancel_discard=<n> pause_discard=<n> accounted=<n>
 queued=<n> q_peak=<n> send_fail=<n>
[RDX][TXQ] ble unavailable=<n> busy_valid_len=<n>
 app_ok=<n> app_error=<n> valid_samples=<n> valid_min=<n> valid_max=<n>
[RDX][TXQ] can_req=<n> can_evt=<n> spurious_evt=<n>
 mtu=<n> interval=<n> latency=<n> phy=<tx>/<rx> dle=<octets>/<time>
[RDX][TXQ] app_ret code=<code> count=<n>
```

Engine与TXQ必须以 `session/capture` 关联。`send_fail`是重复尝试数，`tx_drop`才是队列满造成的唯一包丢失数；`app_ok/app_error`覆盖录音窗口内所有RDX ATT调用，包含START状态包，不能代替纯音频的 `sent`。阶段0新增代码不打印每个音频payload，但SDK预编译 `app_ble` 仍会打印，按第8节限制处理。

### 9.2 正常 STOP 的对账公式

当 Engine 和 Destination 都已排空：

```text
produced = warmup_discard + overflow + mismatch + stale
           + stop_discarded + destination_out
destination_out = destination_in
destination_in = sent + tx_drop + cancel_discard
pending = 0
```

若 STOP 采用“不等待 BLE 尾包、直接取消”策略，未发队列必须转入 `cancel_discard`，然后再清队列。不允许在 detach 时直接将 `pending` 清零而不留统计。

### 9.3 APP 对账

当前 Wire 包不含 frame sequence，APP 只能计数 notification 并通过音频听感发现缺口。阶段 0～2 不增加序号，避免破坏已验证合同；验收时至少对比“设备 sent”和“APP notification 数”。若仍无法定位空中或 APP 侧丢包，再在阶段 3 评估版本化序号字段，不得直接改现有头。

## 10. 验证方法

### 10.1 每轮必查

| 层级 | 必查项 | 通过标准 |
| --- | --- | --- |
| PCM Bridge | PCM in/queued/dequeued、overflow、generation_drop | 三个帧数对账，两类 drop 为 0 |
| Encoder | Opus frames/bytes/invalid length | `bytes = frames * 80`，invalid 为 0 |
| Engine | produced/warmup/overflow/mismatch/stale/stop discard/destination out | 满足第9.2节对账；正常连接下除warm-up外的异常为0 |
| Destination | in/sent/pending/drop/cancel | 满足对账，正常会话 drop 为 0 |
| BLE | valid_len、return code、can request/event、queue peak | busy 可恢复，无永久 pending |
| APP | notification 数、解码、Near/Far 内容 | 与设备 sent 对账，可连续播放 |
| USB 主链 | 上行、下行、放歌、提示音、HID | 全部正常，无录音反压影响 |

### 10.2 推荐的可重复测试内容

1. Near-only：远端静音，本地连续读固定文本；
2. Far-only：本地静音，远端播放固定语音；
3. 双讲：两端同时说话；
4. 本地静音 10 s，恢复 10 s；
5. 远端静音 10 s，恢复 10 s；
6. 双方同时静音 10 s，再同时恢复；

## 14. 最终决策摘要

| 决策 | 冻结结果 |
| --- | --- |
| 问题定位 | 主要丢帧在 Engine/Destination/BLE ATT 发送出口，不是 Near/Far 不能合并 |
| 首要修复 | 有界 TX 队列 + `ATT_EVENT_CAN_SEND_NOW` 事件驱动排空 |
| 任务边界 | BLE 回调只置位/唤醒，TX 队列和发送仍由现有 RDX 任务单上下文拥有 |
| 队列深度 | 首轮保持 16，不先靠增大队列掩盖长期吞吐不足 |
| BLE 参数 | 保持 2M、DLE 251、latency 0；interval 优化在事件驱动之后实测决定 |
| 日志 | 取消每包 payload hex dump，改为低频统计和会话终止对账 |
| APP 合同 | 阶段 0～2 保持 80 B raw Opus；只有证明平均吞吐仍不足后才评估新 Profile |
| 安全原则 | USB 通话主链永远优先；BLE 不可发时录音可有界丢帧/终止，不得反压 USB |

**[推荐设计]** 下一个代码行动为阶段 1：保持队列深度、连接参数和 80 B APP 合同不变，实施 can-send-now 事件驱动 Spike。BLE 回调只校验代次、置位和唤醒现有 RDX 任务，由任务上下文执行有界 burst 排空；低日志 B 组在取得杰理 no-log 库或明确开关后补做，并继续作为最终性能验收的前置证据。
