## 1. 结论

**[已确认事实]** 3-7 已经完成 USB 通话 Near/Far 取流、有界 PCM Bridge、mono 混音、标准 Opus 编码、Call Backend、scene `1` START/STOP 以及 APP 基本解码闭环。本文启动时的问题不是“上下行不能同时合并”，而是混合 Opus 帧进入 Engine 之后，Destination 和 BLE/ATT 出口曾长期低于每秒50帧的产生速率；该问题在最新安全wrapper短时复验中已不再出现。

**[已确认事实]** 基线会话产生 `2061` 个 20 ms Opus 帧，对应约 41.22 s 有效编码时间；Call Audio 侧 `pcm=2061/2061/2061`、`overflow=0`、`generation_drop=0`、`opus=2061/164880`，说明 PCM Bridge 和编码连续、每帧稳定为 80 B。同一会话中 Engine 丢弃 `91` 帧；Destination 处理到 `1750` 帧时已有 `338` 帧因 TX 队列满而丢弃，因此全会话已确认的丢帧下限为 `429` 帧，即 8.58 s，实际可能更多。

**[已确认事实]** 阶段 1 首轮长会话产生 `3386` 帧，Call Audio 为 `pcm=3386/3386/3386`、`overflow=0`、`generation_drop=0`，但最终只有 `2588` 帧发送成功，Destination 丢弃 `765` 帧。事件驱动将 Engine overflow 从阶段 0 正式基线的 `221` 降至 `7`，但 Destination 丢包率从约 `22.8%` 变为约 `22.7%`，BLE 平均出口吞吐没有得到根治。

**[已确认事实]** 同一日志的第一段会话发送 `61` 帧后停止恢复，最终 `can_req=4`、`can_ready=3`；代码复核确认 `rdx_mvp0_record_drain_queue()` 在发送 busy 时提前返回，绕过函数尾部的 can-send arm。这说明首轮实现没有完整满足“busy 必须挂起恢复事件”的设计，同时缺少 pending 请求丢事件后的超时自恢复。

**[已确认事实]** `COM3_2026-08-24_11-55-03.log` 的第一次会话在 `frames=500 sent=500 pending=0 drop=0` 后触发SDK硬断言：`user_att_send_streamer(): send_list_len(0) >= packet_size(114)`，断言位置为预编译BLE协议栈 `att_send.c:602`，随后发生异常复位。114 B正好对应当前98 B Wire包加SDK内部16 B发送管理开销，因此可以确认故障发生在录音notification进入ATT发送列表时。断言前RAM仍有约39 KB、CPU约85%，且RDX TX队列没有积压，排除64包业务FIFO耗尽、内存不足和平均吞吐不足作为本次断言的直接原因。

**[已确认事实]** 同一固件复位后的第二次会话连续产生 `4115` 帧，`warmup_discard=10`、`destination_out=4105`、`sent=4105`、`tx_drop=0`、Engine `overflow=0`、`q_peak=6/64`。期间出现的71次ATT busy全部恢复，最低空闲RAM约42 KB，没有再次断言。这证明64包有界队列、busy统一arm、CAN_SEND唤醒和超时重挂可以消化短时出口毛刺；但一次成功不能否定第一次已经暴露的偶发安全边界问题。

**[安全决策]** 直连 `ble_op_multi_att_send_data()` 虽是SDK公开接口，但在本工程中绕过了持有连接/Profile/CCC生命周期的 `app_ble` handle封装。`app_ble_att_vaild_len_get()`与直连发送是两个独立调用；仅凭串口日志不能继续细分为SDK内部调度竞态还是发送列表生命周期竞态，但硬断言已经足以否决该旁路作为量产路径。正式实现必须统一回到 `app_ble_att_send_data()`，并从日志标签层关闭wrapper的INFO级逐包打印；不得用一次无断言长会话继续为直连路径背书。

**[已确认事实，安全wrapper短时复验通过，2026-08-24]** `COM3_2026-08-24_13-38-46.log` 在同一次连续上电周期内完成两次独立录音。第一次约79 s，`produced=3939`、`warmup_discard=10`、`destination_in=3929`、`sent=3929`；第二次约86 s，`produced=4306`、`warmup_discard=10`、`destination_in=4296`、`sent=4296`。两次均为 Engine `overflow=0/mismatch=0/stale=0`、Call Audio `overflow=0/generation_drop=0`、TXQ `tx_drop=0/pending=0/app_error=0/q_peak=1/64/direct_att=0`，合计8225个录音包全部交付安全wrapper。日志中没有 `att_send.c:602`、`send_list_len`、ASSERT、异常栈或重新启动痕迹，设备运行时间从 `00:00:01` 连续增长到 `00:03:26`；用户也确认两次测试均未出现复位。第二次由 `PCSPK LOST CONNECT` 触发 `cause=7` 源失效收口，不是设备复位；`CALL_AUDIO resets=1` 是单次录音时间线建立计数，也不是系统复位计数。

**[已确认事实]** 两次安全wrapper会话最终均为 MTU `517`、interval `9`、latency `0`、2M PHY、DLE `251/2120`；最低空闲RAM约45 KB，录音稳定期总CPU约76%～82%。逐包 `[APP-BLE]app_ble_att_send_data---` INFO日志已经消失。两次会话没有出现ATT busy，因此 `can_req=0`、`q_peak=1`，本轮直接证明的是wrapper调用边界安全和正常链路吞吐；严重拥塞下的71次busy恢复能力仍由前一版会话提供证据，不能把本轮解释为已经重新覆盖全部拥塞故障注入。

**[阶段结论]** 结合3-7已经完成的Near/Far混录、APP scene `1`控制和mono raw Opus解析闭环，当前可以确认USB通话在线录音功能已经初步实现。该结论表示短时功能与设备侧发送完整性通过，不等同于2小时长稳、Android/iOS矩阵、100/50次控制循环和空中链路/APP逐包对账已经达到量产门槛。

**[推荐设计]** 第一优先级仍是把发送调度收敛为“有界入队 + `ATT_EVENT_CAN_SEND_NOW` 事件驱动排空”。BLE 协议栈上下文只发送可发通知，不直接排空业务队列；所有 TX 队列变更和底层 ATT 发送仍在单一任务上下文完成。队列扩容只能吸收短时毛刺，必须与 busy 正确 arm、丢事件恢复和低日志发送路径同时实施，不能单独用 RAM 掩盖长期平均吞吐不足。

**[推荐设计]** 优化必须保持当前“USB 主链优先、录音队列有界”的安全边界。即使 BLE 永久不可发，也不得阻塞 Near/Far Tap、PCM Bridge、PCMIC 或 PCSPK；队列达到上限时仍允许丢弃最旧录音帧作为最后保护，但“长期无丢帧”必须成为本文的验收目标，不能把安全丢帧等同于问题已解决。

## 3. 当前发送合同与理论需求

### 3.1 单帧封包

**[已确认事实]** 当前每个 Opus 帧的业务包为：

```text
"*DEV#stream#80#80#" + 80 B raw Opus
```

Wire 头长度为 18 B，因此每帧应用层载荷为 98 B。编码周期为 20 ms，即每秒 50 帧：

```text
50 frames/s * 98 B = 4900 B/s
4900 B/s * 8 = 39.2 kbit/s
```

上述只是应用层有效载荷，尚未计入 ATT、L2CAP、Link Layer 和空中重传开销；但在 2M PHY、DLE 251 和足够连接事件下，39.2 kbit/s 并不应天然超过 BLE 能力。因此当前日志证明的是“ATT 发送路径存在持续反压”，还不能等同为“2M PHY 物理带宽不足”。

**[实现经验]** SDK内部发送列表还会为当前98 B应用包增加16 B管理开销，断言日志中的 `packet_size=114` 即来自 `98 + 16`。业务层仍只向APP发送98 B，APP合同没有变化；这16 B只能用于解释SDK发送池容量和断言，不能加入Wire长度或让APP按114 B解析。

### 3.2 当前 BLE 参数

| 项目 | 设备请求/配置 | 基线日志实际结果 | 结论 |
| --- | ---: | ---: | --- |
| ATT MTU | 交换大 MTU | `514` | 98 B 应用包可容纳 |
| DLE TX octets | `251` | `251` | 已生效 |
| DLE TX time | `2120` | `2120` | 已生效 |
| PHY | 2M | TX/RX 均为 `2` | 已生效 |
| Connection interval | `6-6` = 7.5 ms | 录音时被更新为 `10`、后为 `9` | 手机最终保持 12.5/11.25 ms |
| Slave latency | `0` | `0` | 符合预期 |

**[已确认事实]** `ble_op_conn_param_request()` 返回成功只代表请求已提交，不代表手机必须长期保持 7.5 ms。当前代码已在连接、录音开始和 slow update 时请求高吞吐参数；因此只继续调小 interval 不是第一优化项。

## 4. 基线证据与丢帧定位

### 4.1 会话时间与输入状态

**[已确认事实]** 长会话 session `3` 从设备运行时间 `00:01:22.048` 开始，到 `00:02:03.545` 停止，约 41.5 s；`2061 * 20 ms = 41.22 s` 与会话持续时间相符。Far Tap 以 96 kHz / 2 ch 启动，Near Tap 以 44.1 kHz / 1 ch 启动，录音期间没有出现任一 Tap stop。

### 4.2 分层证据

| 链路层 | 基线日志 | 判断 |
| --- | --- | --- |
| Call PCM / Encoder | `pcm=2061/2061/2061 overflow=0 generation_drop=0 resets=1 opus=2061/164880` | PCM 入队、出队和 80 B Opus 完整对账；`resets=1` 是本次初始时间线建立，不是运行期反复复位 |
| Record Engine | `produced=2061 enqueued=2061 overflow=91 mismatch=0 stale=0 stop_discarded=0` | Destination 处理不及时已反压到 16 帧 candidate queue，丢弃 91 帧 |
| Online Destination @250 | `sent=193 pending=15 peak=16 drop=42` | 约 5 s 已达队列上限并丢帧，不是只在 STOP 尾部丢帧 |
| Online Destination @1750 | `sent=1397 send_fail=1704 pending=15 peak=16 drop=338` | 长期发送速率低于 50 fps，队列几乎一直满载 |
| ATT 发送资源 | `remain size` 多次从 3916 B 降到 162 B | 发送缓冲持续被耗尽 |
| 协议栈反压 | 会话区间约 1777 次 `stack_resume_fail!!!:21` | 与 ATT 低剩余空间和 TX 丢帧同时出现 |

### 4.3 对账

在 `frames=1750` 时：

```text
sent + pending + drop
= 1397 + 15 + 338
= 1750
```

`send_fail=1704` 是重复尝试失败次数，不是 1704 个不同录音包。`drop=338` 才是该时刻已被 Destination 明确丢弃的唯一录音包数。Engine 的 `overflow=91` 发生在 Destination 之前，与 TX 队列的 338 帧不重复。

### 4.4 为什么不是上下行合并失败

Near/Far 在 PCM Bridge 中先归一、对齐并混为一路 16 kHz mono，APP 并不同时接收两路异构 PCM。本次只产生 `2061` 个混合 Opus 帧，而不是 Near/Far 各 `2061` 帧后再向 APP 发送 `4122` 帧。Call Audio 侧编码对账完整，明确丢帧计数均出现在 Engine 候选队列和 Destination TX 队列，所以当前的主要质量问题应在发送出口解决。

## 5. 阶段0发送实现的局限

### 5.1 阶段0行为

1. Destination 每收到一个新 Opus 帧，先调用 `rdx_mvp0_record_drain_queue()`；
2. `drain_queue()` 在同一次调用中循环调用 `rdx_mvp0_send()`；
3. `rdx_ble_transport_send()` 先读取 `app_ble_att_vaild_len_get()`，空间不足返回 `-2`；
4. 发送失败后保留队头，函数返回；
5. 当前没有处理 `ATT_EVENT_CAN_SEND_NOW`，也没有因 ATT 恢复可发而主动唤醒 Destination；
6. 下一次排空主要依赖下一个 20 ms 录音帧到来。

### 5.2 问题

- “新音频帧到来”同时承担产生数据和恢复旧积压的职责；
- ATT 何时可发与 20 ms 音频节拍无关，轮询式重试可能错过最佳发送窗口；
- 队列长期满载时，每个新帧都会先引起一次重试失败，然后再丢最旧包；
- 高频失败、队列搬运和每包十六进制串口日志会进一步占用 CPU/串口时间；
- 当前 `send_fail_count` 没有按 `-1`、`-2` 和 `app_ble_att_send_data()` 的真实返回码分类，无法区分无连接、ATT 空间不足和其他协议栈失败。

## 7. 目标设计

### 7.1 事件驱动数据流

```text
AI_TX callback / encoded candidate
              |
              v
       RDX Record Engine task
              |
              v
   Destination bounded TX queue ---- queue full ---> drop oldest + counter
              |
              | poll/drain with bounded budget
              v
      rdx_ble_transport_send()
          | success          | ATT busy/no space
          v                  v
       sent++       arm CAN_SEND_NOW once, return
                                 |
                                 v
BLE packet handler: ATT_EVENT_CAN_SEND_NOW
          |
          | set tx-ready latch only
          v
   wake existing RDX Record Engine task
          |
          v
 Destination poll/drain in task context
```

### 7.2 线程与所有权边界

**[推荐设计]** BLE packet handler 中不得直接调用 `rdx_mvp0_record_drain_queue()`，也不得在回调中修改 TX 队列头尾。回调只完成以下操作：

1. 校验当前 `con_handle` 和连接代次；
2. 清除 `can_send_request_pending`；
3. 置位 `tx_ready_latch`；
4. 唤醒已有 `rdx_record` 任务。

**[推荐设计]** Record Engine 增加轻量 Destination-ready 通知，不新建常驻 TX 任务。可以给 `rdx_record_destination_ops` 增加可选 `poll` 操作，由 Engine 任务消费 ready latch 后调用；也可以使用等价的内部通知机制。具体符号名称可在实施时按现有 C 风格收敛，但不得把 Destination 队列所有权分散到 BLE 回调与 Engine 两个上下文。

### 7.3 排队和排空规则

1. 首轮保持 TX 队列深度 16，不用增大队列掩盖平均吞吐不足；
2. 新录音包先按 FIFO 入队，再由同一任务的 poll/drain 发送，避免“有时直发、有时入队”形成双路序列；
3. 一次唤醒最多发送有界数量的包，建议 Spike 起始值为 4；避免一次清空占满 Engine 任务时间；
4. 发送成功后再移动队头；失败时保留队头，记录分类返回码；
5. 遇到 ATT busy/空间不足时只 arm 一次 can-send-now；未收到事件前不重复请求；
6. can-send 事件后如队列仍非空且再次 busy，重新 arm 一次；
7. 断连、CCC off、STOP、Pause 和 capture generation 切换时必须清理 ready/request latch，旧连接事件不得排空新会话队列；
8. 队列真满时继续丢最旧包以保护实时性和 USB 主链，但只有 `queue_drop_count` 计入真实丢帧；busy 重试不计入丢帧。

### 7.4 参考工程与目标工程的区别

**[已确认事实]** BR28 参考工程的 RDX BLE server 已处理 `ATT_EVENT_CAN_SEND_NOW`，其回调主要清发送状态并 `os_sem_post()` 唤醒私有发送任务。这证明“BLE 可发事件只用来唤醒业务发送上下文”是参考工程也采用的模式。

**[推荐设计]** 目标 BR56 工程不复制参考工程的 `BleBulkSendData`、`BLE_SendData`、全局发送标志或私有任务。目标工程已有独立 `app_ble` handle、RDX Record Engine 任务和有界 Destination 队列，应仅复用事件驱动原则，并在本工程现有所有权边界内实现。

### 7.5 本次BLE拥塞治理的可复用工程经验

**[经验结论]** 本次问题不能概括为“BLE带宽不足”，最终有效方案也不是单纯增加RAM或调整连接参数，而是同时修正发送调度、队列边界、事件恢复、SDK所有权和日志开销。后续项目遇到实时音频BLE拥塞时，应按以下顺序处理，不能跳过分层诊断直接改码率或绕过平台封装。

1. **先分层对账，再判断丢包位置。** Call Audio/Encoder连续而Engine或Destination丢帧，说明问题在编码后出口，不是Near/Far无法混音；`send_fail`表示重试次数，不等于真实丢包，只有`tx_drop`、`overflow`和明确的`cancel_discard`才进入丢帧对账。设备`sent`只证明安全wrapper接受了通知，空中链路和APP是否完整仍须用APP notification计数验证。
2. **有界FIFO只吸收毛刺，不创造平均吞吐。** 64包队列约占6.2 KB，可缓存约1.28 s的20 ms音频，适合吸收连接参数切换和短时ATT busy；如果长期平均出口低于50帧/s，队列最终仍会打满。队列满时丢最旧录音包是保护USB主链的最后边界，不能把“有界丢包”写成质量问题已经解决。
3. **所有busy出口必须汇合到同一个arm路径。** 首轮代码在busy后提前`return`，绕过函数尾部的can-send请求，曾造成队列永久停止恢复。正确做法是只要FIFO非空，无论因为`valid_len`不足、底层busy还是burst预算耗尽退出，都统一进入一次`ATT_EVENT_CAN_SEND_NOW` arm；成功发送后才能移动队头。
4. **CAN_SEND事件只能唤醒拥有队列的任务。** BLE回调不得直接排空Destination，也不得修改队列头尾；它只校验连接代次，清除本次pending，置ready latch并唤醒RDX任务。pending必须绑定connection/session/capture，STOP、断连、CCC off和generation切换时清理，避免旧事件排空新会话。共享ATT层会产生大量非RDX自有事件，因此必须区分`can_evt`、`can_ready`和`spurious_evt`，不能把每个CAN_SEND事件都当成本业务授权。
5. **事件请求必须有合并和丢事件自恢复。** 同一connection/session/capture只保留一个pending请求，避免重复arm；pending超过100 ms仍未收到所属事件时，清理旧请求并重新arm。最终日志必须检查`timeout_rearm`、`arm_fail`和`pending`，正常STOP时`pending`必须回到0。
6. **公开底层API不等于可以绕过本工程所有权边界。** `ble_op_multi_att_send_data()`虽为SDK公开接口，但本工程的连接、Profile、CCC和发送生命周期由`app_ble` handle持有。直连版在RDX队列无积压、RAM仍充足时触发`send_list_len(0) >= packet_size(114)`硬断言；同一固件复位后另一次会话成功，也不能否定这个偶发安全缺口。正式路径必须统一使用`app_ble_att_send_data(rdx_ble.hdl, ...)`，并删除直连产品开关，防止后续为追求性能重新打开旁路。
7. **日志性能问题应在日志级别解决，不能用旁路API解决。** 预编译wrapper每秒约50次的完整payload dump确实会放大CPU和串口抖动，但正确修复是在仓库`btstack_log_config.c`关闭`APP_BLE` INFO，保留warning/error与RDX低频对账；不能为了少打印日志而绕开安全wrapper。
8. **先修调度和安全，再考虑改变APP合同。** 当前98 B Wire包只需要约39.2 kbit/s，2M PHY、DLE 251、interval 9下已完成两轮零丢包；没有证据要求立即降码率、改40 ms帧或聚合多帧。只有安全调度、低日志、连接参数矩阵和长稳仍失败，才允许建立版本化新Profile，不能直接破坏现有80 B raw Opus合同。
9. **实时主业务必须拥有不可反压的优先级。** BLE永久不可发、APP断连或录音队列打满时，只能有界丢弃或终止录音，不得阻塞Near/Far Tap、PCM Bridge、PCMIC或PCSPK。录音完整性是质量目标，USB通话不中断是更高等级的安全边界。
10. **偶发断言必须用独立会话重复验证。** 构建通过、单次零丢包或复位后一次成功都不能证明发送层安全；一次硬断言足以否决路径。安全wrapper需要多次独立START/STOP/source-lost会话和后续长稳共同验证。日志中的`CALL_AUDIO resets=1`是录音时间线建立计数，不是系统复位，判断设备复位必须结合运行时间是否回零、启动日志、异常栈和业务状态重新初始化。

**[证据边界]** 前一版约82 s会话验证了71次busy均可通过“统一arm + CAN_SEND唤醒 + 超时重挂”恢复，但该版本同时暴露了直连ATT断言；最新安全wrapper两次会话验证了调用边界安全和正常链路零丢包，但当时没有产生busy。两组证据必须组合解读：可以保留事件恢复机制并确认wrapper短时安全，不能声称某一份日志已经同时覆盖严重拥塞、调用安全和全部异常路径。

**冻结的最佳实践组合：**

| 维度 | 冻结做法 | 禁止回退 |
| --- | --- | --- |
| 队列 | 64包有界Destination FIFO，满队列丢最旧并计`tx_drop` | 无界缓存、反压USB主链 |
| 调度 | RDX单任务有界burst排空，busy统一arm | 音频节拍盲目轮询、busy提前返回 |
| 事件 | CAN_SEND回调只置位/唤醒，pending绑定连接与会话 | 在BLE回调直接排空或修改队列 |
| 恢复 | pending合并，100 ms超时重挂 | 永久pending、无限重复arm |
| ATT边界 | `app_ble_att_send_data(rdx_ble.hdl, ...)` | 直连multi-ATT旁路 |
| 日志 | 关闭`APP_BLE` INFO，保留错误和低频对账 | 每包payload dump、为关日志绕过wrapper |
| APP合同 | 维持80 B raw Opus，先完成调度与长稳 | 未经APP版本化直接降码率/聚合 |
| 验证 | Engine/TXQ/APP分层对账，多次独立会话与长稳 | 用编译成功或单次成功替代硬件验收 |

### 阶段 1：`ATT_EVENT_CAN_SEND_NOW` 事件驱动 Spike

**目标：** 在不修改队列深度、连接参数和 APP 合同的情况下，让 ATT 恢复可发事件主动驱动积压队列排空。

**实施项：**

1. BLE transport 处理 `ATT_EVENT_CAN_SEND_NOW`并增加可发请求/ready 通知接口；
2. Destination 增加事件驱动 poll/drain，队列由 `rdx_record` 任务单上下文消费；
3. busy 时只 arm 一次 request，事件到来后用有界 burst 排空；
4. 保留 16 包 TX 队列和丢最旧安全策略；
5. 引入连接代次/session/capture 校验，防止旧 can-send 事件污染新会话；
6. 使用独立编译开关保留当前轮询式路径，便于在同一代码基线上快速构建回退版本。

**[首轮实现，已完成实机验证但未通过退出门槛，2026-08-24]** 本轮保持 16 包 TX 队列、BLE 参数和 80 B APP 合同不变，完成以下 Spike：

- `RDX_CFG_BLE_TX_CAN_SEND_ENABLE` 默认开启；设为 `0` 可恢复阶段0的直发/轮询路径；`RDX_CFG_BLE_TX_BURST_BUDGET` 首轮为 `4`，并限制在 `1～16`；
- 每个音频包统一先进入 Destination FIFO，候选帧消费路径每次最多直发 `1` 包，避免一批候选帧形成无界发送循环；
- 队列非空或发送 busy 时只保留一个 RDX can-send pending，请求重复调用只计入 `can_coalesced`，不重复向 ATT arm；
- `ATT_EVENT_CAN_SEND_NOW` 回调只校验连接代次、取出 session/capture、清 pending，并调用 Engine ready 通知；回调不读取或修改 Destination 队列；
- Engine 使用带 session/capture 的 destination-ready latch 唤醒现有 `rdx_record` 任务，任务上下文每次事件最多排空 `4` 包；若仍有积压则重新 arm；
- STOP、Pause、断连、CCC off、统计重置及新连接都会清理 pending；旧事件即使迟到，也只能触发带当前请求代次的空检查，不能发送旧队列；
- 新增 `can_ready`、`can_coalesced`、`drain`、`event_poll`、`budget_hit`、`burst_peak` 和 `arm_fail` 终止统计，用于判断事件是否真正恢复发送。

### 阶段 2：调度、控制包优先级与连接参数收敛

**前置：** 只有阶段 1 事件驱动路径稳定，但仍有可重现丢帧、状态 ACK 失败或起始瞬时拥塞时，才进入本阶段。

**实施项：**

1. 根据阶段 1 统计对比 burst budget `1/2/4/8`，以 `drop=0` 和不饿死 Engine 为准；
2. 评估为 START/STOP/PAUSE/RESUME/record state ACK 增加有界控制包重试或优先级，避免状态包被长录音流挤压；
3. 保持 latency `0`、2M PHY 和 DLE 251，对比手机实际 interval `6/9/10`（7.5/11.25/12.5 ms）下的持续发送结果；
4. 限制 slow-update 参数重请求频率，避免与手机反复交替参数形成无效振荡；
5. 评估是否要求 CCC、MTU 与高吞吐参数进入可接受状态后再放行音频帧；等待必须有有界超时，不得让 APP START 无限挂起；
6. 如 APP 可控，由 APP 侧记录 Android/iOS 连接优先级申请和最终参数，设备日志与 APP 日志按时间对齐。

## 9. 统计与对账合同

### 9.1 阶段0/1实际输出

```text
[RDX][ENGINE] stopped ... produced=<n> overflow=<n> mismatch=<n>
 stale=<n> stop_discarded=<n> warmup_discard=<n> destination_out=<n>
[RDX][TXQ] final reason=<cancel|detach> session=<id> capture=<generation>
 destination_in=<n> sent=<n> pending=<n> tx_drop=<n>
 cancel_discard=<n> pause_discard=<n> accounted=<n>
 queued=<n> q_peak=<n> send_fail=<n>
[RDX][TXQ] ble unavailable=<n> busy_valid_len=<n>
 app_ok=<n> app_error=<n> valid_samples=<n> valid_min=<n> valid_max=<n>
[RDX][TXQ] can_req=<n> can_evt=<n> spurious_evt=<n>
 can_ready=<n> can_coalesced=<n> timeout_rearm=<n> pending=<0|1>
[RDX][TXQ] mtu=<n> interval=<n> latency=<n>
 phy=<tx>/<rx> dle=<octets>/<time>
[RDX][TXQ] drain=<n> event_poll=<n> budget_hit=<n>
 burst_peak=<n> arm_fail=<n> budget=<n> depth=<n> direct_att=0
[RDX][TXQ] app_ret code=<code> count=<n>
```

Engine与TXQ必须以 `session/capture` 关联。`send_fail`是重复尝试数，`tx_drop`才是队列满造成的唯一包丢失数；`app_ok/app_error`覆盖录音窗口内所有RDX ATT调用，包含START状态包，不能代替纯音频的 `sent`。安全收口版通过关闭 `APP_BLE` INFO抑制预编译wrapper逐包payload打印，并固定输出 `direct_att=0` 作为路径证据。

### 9.2 正常 STOP 的对账公式

当 Engine 和 Destination 都已排空：

```text
produced = warmup_discard + overflow + mismatch + stale
           + stop_discarded + destination_out
destination_out = destination_in
destination_in = sent + tx_drop + cancel_discard
pending = 0
```

若 STOP 采用“不等待 BLE 尾包、直接取消”策略，未发队列必须转入 `cancel_discard`，然后再清队列。不允许在 detach 时直接将 `pending` 清零而不留统计。

### 9.3 APP 对账

当前 Wire 包不含 frame sequence，APP 只能计数 notification 并通过音频听感发现缺口。阶段 0～2 不增加序号，避免破坏已验证合同；验收时至少对比“设备 sent”和“APP notification 数”。若仍无法定位空中或 APP 侧丢包，再在阶段 3 评估版本化序号字段，不得直接改现有头。

## 14. 最终决策摘要

| 决策 | 冻结结果 |
| --- | --- |
| 问题定位 | 主要丢帧在 Engine/Destination/BLE ATT 发送出口，不是 Near/Far 不能合并 |
| 首要修复 | 有界 TX 队列 + `ATT_EVENT_CAN_SEND_NOW` 事件驱动排空 |
| 任务边界 | BLE 回调只置位/唤醒，TX 队列和发送仍由现有 RDX 任务单上下文拥有 |
| 队列深度 | 首轮16包不足以吸收出口毛刺；修正版使用64包（约1.28 s/增加约6.2 KB），仍要求长期平均吞吐达标和`drop=0` |
| BLE 参数 | 保持 2M、DLE 251、latency 0；interval 优化在事件驱动之后实测决定 |
| ATT调用边界 | 统一使用持有RDX app_ble handle的`app_ble_att_send_data()`；删除直连multi-ATT分支和产品开关 |
| 日志 | 关闭仓库`APP_BLE` INFO标签抑制wrapper逐包payload dump；保留warning/error、RDX低频统计和终止对账 |
| APP 合同 | 阶段 0～2 保持 80 B raw Opus；只有证明平均吞吐仍不足后才评估新 Profile |
| 安全原则 | USB 通话主链永远优先；BLE 不可发时录音可有界丢帧/终止，不得反压 USB |
| 当前里程碑 | 安全wrapper两次短时会话合计8225包零丢包、无断言/复位；USB通话在线录音功能初步实现 |

**[推荐设计]** 当前两次安全wrapper短时会话已经通过，下一步不再修改ATT调用边界，也不恢复直连ATT。补做第3次重复会话后进入10 min稳定性验证；随后按阶段4执行2小时、控制循环、断连/CCC/source-lost、Android/iOS和Meeting回归。每轮继续确认逐包 `[APP-BLE]app_ble_att_send_data---` 日志不出现、最终固定为`direct_att=0`，并检查 `pending=0`、`q_peak<64`、Engine/TX `drop=0`、USB主链正常以及APP通知数和解析连续性。
