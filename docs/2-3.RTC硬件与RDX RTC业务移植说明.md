# 2-3 RTC 硬件与 RDX RTC 业务移植说明

## 1. 文档目的与提交拆分

RTC 移植分为两个独立部分，必须分开提交和验收：

1. **第一部分：补齐 JL 原生 RTC 基础设施缺陷**。包括硬件 RTC 驱动、接口 ABI、`CLK_SEL_LRC`、闹钟中断、softoff 备用电源域保持、关机闹钟唤醒及板端测试。
2. **第二部分：移植 RDX RTC 业务**。包括 RDX Unix 时间戳解析、硬件 RTC 写入与回读、VM 备份恢复以及真实业务 ACK。

截至 2026-08-10，第一部分已经完成编译以及 `RTC_TEST_ITEM_ALL`、`RTC_TEST_ITEM_SOFTOFF` 两轮实机验证，可以独立提交；第二部分随后已完成代码移植和干净编译，等待 RDX 上位端与重启恢复实机验收后单独提交。

本次明确使用硬件 RTC，不移植通过系统节拍累加秒数的软件模拟 RTC。

## 2. 第一部分范围

### 2.1 本次保留

- 启用 BR56 片上硬件 RTC；
- RTC 时钟源固定为 `CLK_SEL_LRC`；
- 补齐当前 SDK 缺失的 BR56 RTC/LPTMR 驱动对象；
- 对齐新版 RTC 驱动的头文件和板级平台数据 ABI；
- 支持时间读写、日历换算和连续走时；
- 支持运行态一次性闹钟及中断回调；
- ISR 只投递消息，RTC 读取、关闭闹钟和业务通知在 `app_core` 任务态执行；
- softoff 时保持 LRC/RTC 备用电源域；
- 支持 RTC 闹钟从 softoff 自动唤醒；
- 保留默认关闭的 RTC 板端测试模块。

### 2.2 本次不包含

- `rdx_rtc.c/.h`；
- RDX 启动时的 RTC/VM 恢复；
- RDX 停止或关机时的 RTC 时间备份；
- RDX RTC 命令对硬件 RTC 的真实写入；
- RDX RTC 命令基于业务结果返回成功或失败；
- `CFG_RDX_RTC_BACKUP` VM ID；
- RDX 与 `TCFG_APP_RTC_EN` 的编译期依赖检查；
- 软件模拟 RTC 和周期保存定时器。

撤回后，现有 RDX RTC 命令恢复为工程原有的数字格式校验和回显行为，不会设置硬件 RTC。该行为只用于保持第一部分提交前的 RDX 基线，不代表 RDX RTC 业务已经完成。

RTC 时钟源明确配置为：

```c

```

```c
const bool control_rtc_enable = 1;
const u32 control_rtc_clk_sel = RTC_CLK_RES_SEL;
```

```c
power_control(PCONTROL_SF_KEEP_LRC, 1);
```

目标工程的旧 PMU 库不支持 `PCONTROL_RTC_CLK`，实机曾打印：

```text

```

因此本次不调用该命令，时钟选择由 `control_rtc_clk_sel` 提供，softoff 保持由 `PCONTROL_SF_KEEP_LRC` 完成。

## 4. 闹钟与中断处理

新增独立桥接层：

```text
RTC/LPTMR IRQ
    → rtc_alarm_isr_callback()
    → 向 app_core 投递 Q_CALLBACK
    → rtc_alarm_handle_in_task()
    → 关闭一次性闹钟并读取触发时间
    → rtc_alarm_event_notify()
```

`rtc_alarm_event_notify()` 是弱函数，后续产品业务可覆盖。基础层不增加铃声、UI、重复闹钟或 RDX 闹钟协议。

`rtc_wakup_source()` 是以中断返回指令结束的底层 IRQ 入口，不能在任务态直接调用。早期中断通过桥接层的 pending 状态在 `app_core` 就绪后重投递；若 softoff 冷启动清空 BSS，桥接层会从 `PWR_RTC_WK_REASON_ALM` 恢复并合成一次 `RTC_WKUP_EVENT`。一次性 replay 标记可避免后续模式切换重复通知。

新版 RTC 驱动写闹钟时要求闹钟已经使能，正确顺序为：

```c
rtc_alarm_en(0);
rtc_alarm_en(1);
write_ret = rtc_write_alarm(&alarm);
```

其中 `RTC_SUCC` 的值为 `3`，不能按传统的返回 `0` 判断成功。测试还必须检查闹钟回读值和使能状态。

## 5. RTC 测试模块

测试入口位于：

```text
SDK/apps/earphone/rtc_test.c
SDK/apps/earphone/include/rtc_test.h
```

支持以下独立测试项：

| 测试项 | 验证内容 |
| --- | --- |
| `RTC_TEST_ITEM_REG_DUMP` | RTC 初始时间和寄存器状态 |
| `RTC_TEST_ITEM_BASIC_RW` | 时间写入、读回及偏差 |
| `RTC_TEST_ITEM_TIMING` | RTC 与系统定时器的连续走时偏差 |
| `RTC_TEST_ITEM_ALARM` | 运行态闹钟编程、回读和中断 |
| `RTC_TEST_ITEM_UTILS` | 日期加秒、时间戳和星期换算 |
| `RTC_TEST_ITEM_SOFTOFF_WAKE` | softoff、备用域保持和闹钟唤醒 |

测试模块会改写时间、设置闹钟或主动进入 softoff，因此正式提交默认配置为：

```c
#define RTC_TEST_ENABLE 0
```

默认 `RTC_TEST_ITEM_SAFE` 只包含寄存器快照、日期工具和走时，不改写硬件时间、不设置闹钟，也不进入 softoff。`RTC_TEST_ITEM_ALL` 包含全部运行态项目；`RTC_TEST_ITEM_SOFTOFF` 是独立的 softoff 场景，内部组合寄存器快照和关机唤醒测试，无需在配置处手写按位或。运行态闹钟和 softoff 测试共享同一个硬件闹钟，测试模块会在编译期禁止二者同时运行。测试闹钟延迟 3 秒启动，使应用任务和 RTC 初始化稳定后再编程。softoff 测试设置未来 60 秒闹钟，再延迟 2 秒进入软关机，并在唤醒后检查 `PWR_RTC_WK_REASON_ALM`。

走时测试默认允许 RTC 与系统时间相差不超过 `RTC_TEST_TIMING_TOLERANCE_SEC=2` 秒，并同时检查采样周期期望值和两者之间的差值。

完整回归固定分为两轮：先运行 `RTC_TEST_ITEM_ALL`，覆盖寄存器快照、基础读写、日期工具、连续走时和运行态闹钟；再运行 `RTC_TEST_ITEM_SOFTOFF`，覆盖备用电源域保持和关机闹钟唤醒。两轮全部通过即可覆盖当前 RTC 基础设施的功能测试。`RTC_TEST_ITEM_SAFE` 仅用于不方便改写时间或设置闹钟时的非破坏性检查，不能替代完整回归。

## 8. 第二部分实现：RDX RTC 业务

第二部分在第一部分完成后单独实施，以下 1 至 9 项代码已完成，第 10 项实机回归待执行：

1. 新增硬件专用 `rdx_rtc.c/.h`，不保留软件 RTC 分支；
2. 严格解析 `*APP#rtc#<timestamp>#` 的 Unix UTC 秒；
3. 做数字长度、`u32` 溢出和有效年份范围检查；
4. 将时间戳转换为 `struct sys_time` 并写入硬件 RTC；
5. 写后读取硬件 RTC，只有回读一致才允许返回成功；
6. 分配不冲突的 VM ID，保存最后可信时间并做写后回读；
7. 启动时按硬件时间有效性决定是否从 VM 恢复；
8. RDX 停止或平台关机时只保存业务备份，不关闭 RTC 或清除硬件闹钟；
9. ACK 必须反映解析、硬件写入和 VM 写入的真实结果；
10. 单独完成 RDX 上位端设置时间、读取验证、异常 ACK 和重启恢复回归。

第二部分不得改变第一部分已经验证的 LRC、平台数据 ABI、中断桥接、一次性闹钟和 softoff 唤醒行为。

### 8.1 代码接入

新增硬件专用模块：

```text
SDK/apps/common/third_party_profile/rdx_protocol/rdx_rtc.c
SDK/apps/common/third_party_profile/rdx_protocol/rdx_rtc.h
```

业务生命周期接入 `rdx_protocol_start()`、`rdx_protocol_stop()` 和 `platform_uninitcall`。启动时读取硬件 RTC；若硬件时间无效或仍是板级 `def_sys_time` 初始占位日期，则尝试从 VM 恢复。停止协议时先备份并清除 started 状态；平台进入 softoff 时只有协议仍在运行才执行兜底备份，避免同一次退出重复写 VM。两种路径都不关闭 RTC、不关闭闹钟，也不改写第一部分的唤醒配置。

VM 使用独立 ID：

```c
#define CFG_RDX_RTC_BACKUP 16
```

该 ID 与现有 `CFG_RDX_DEVICE_STATE=15` 及其他产品 VM ID 不冲突。RDX RTC 不设置独立业务开关：`TCFG_APP_RTC_EN` 是 JL 原生 RTC 能力的唯一开关，启用 RDX 时由 `rdx_integration_config.h` 在编译期强制检查该能力。`rdx_mvp0_compat_config.h` 仅声明协议兼容数据及 `RDX_ABILITY_RTC` 能力位，不负责控制 RTC 基础模块或 RDX RTC 生命周期。

### 8.2 命令与 ACK

`*APP#rtc#<timestamp>#` 只接受 1 至 10 位十进制数字，并检查逐位累加是否溢出 `u32`。解析后通过 RTC 日期工具转换为 UTC 日历时间。默认年份范围为 2000 至 2099，可通过 `RDX_RTC_VALID_YEAR_MIN/MAX` 在产品集成配置中覆盖，并带编译期范围检查。

成功路径依次验证：

1. `rtc_write_time()` 返回成功；
2. 立即读取硬件 RTC，Unix 时间戳与请求值一致；
3. VM 已是相同值时跳过擦写，否则写入 `CFG_RDX_RTC_BACKUP`；
4. 立即读取 VM，值与请求值一致。

四项全部通过时返回：

```text
*DEV#rtc#0#<timestamp>#
```

解析、范围、硬件或 VM 任一环节失败时返回 `result=1`。无法形成有效数字值的畸形请求返回：

```text
*DEV#rtc#1#0#
```
