# AC710N RDX 在线录音暂停恢复与录音标记移植说明

> 文档状态：代码移植和固件构建已完成，目标 APP/硬件功能回归待执行
> 日期：2026-08-13
> 适用工程：AC710N/BR56 Type-C 专用 PC 模式
> 继承文档：`3-2.RDX在线录音业务移植评估与实施路线.md`、`3-3.RDX录音基础设施架构优化方案.md`

## 1. 本次结论

本次在既有在线会议录音 START/STOP 基础上完成两项移植：

1. `*APP#record#2#...` 暂停和 `*APP#record#3#...` 恢复；
2. `*APP#recmark#` 在线录音标记及 `*DEV#recmark#...` 结果上报。

实现遵守 `3-3` 已冻结的领域模型：Pause 结束当前采集周期但不结束逻辑 Session；Resume 在同一 `session_id` 下创建新的 `capture_generation`；Mark 由 Engine worker 在控制请求串行点读取排除暂停和预热帧的 `active_pts`，再交给 Session Metadata Service 形成 canonical mark journal。

目标产品当前只有在线 Destination，没有本地录音文件和 Artifact。因此：

- Pause/Resume 保持同一个内部 `session_id`，但 V23 状态包没有可上报的文件 SN/文件名；
- Mark 成功应答固定使用 `sn=0`、空 `filename`，`index/offset_ms/source` 有效；
- 本次不移植参考工程的 RAW 文件续写、`UXFILE.DAT` 保存和 marks 持久化；
- BLE 断连或 CCC 关闭仍按现有在线业务策略强制结束 Session，不复制参考工程的离线存储续录行为。

完整固件构建只能证明代码完成编译、链接和打包，不能替代目标 APP、串口和音频听测。

## 3. 冻结的 Wire 合同

### 3.1 暂停和恢复

目标接受长、短两种会议录音命令：

```text
APP -> Device
*APP#record#2#
*APP#record#2#0#1#
*APP#record#3#
*APP#record#3#0#1#

Device -> APP
*DEV#record#2#0#1#0#1#0#
*DEV#record#3#0#1#0#1#0#
```

目标工程没有 Local Storage，状态包沿用既有 24 B 无文件字段版本。不得为了匹配参考日志中的 36 B 本地存储报文而伪造 SN 和 filename。

### 3.2 录音标记

```text
APP -> Device
*APP#recmark#

Device -> APP
*DEV#recmark#result#sn#filename#index#offset_ms#source#
```

结果码和目标行为如下：

| result | 语义 | 目标处理 |
| ---: | --- | --- |
| 0 | OK | 追加 canonical mark，返回新 index 和有效时间偏移 |
| 1 | BAD_STATE | 非 ACTIVE、Session 不匹配或请求被取消 |
| 2 | BUSY | 命中 6 秒去重窗口或控制队列满 |
| 3 | FULL | 当前 Session 已有 20 个标记 |

当前只有 APP 入口，`source=1`。公共枚举保留 `source=0` 给未来设备按键入口，但本次没有修改按键业务。

## 4. 状态机和时序

### 4.1 Pause

```text
ONLINE STREAMING
    -> PAUSE_PENDING
    -> Engine PAUSING_BY_USER
    -> 关闭新帧接纳闸门
    -> 停止并注销当前 BR56 Pipeline 回调来源
    -> drain 固定候选帧队列并丢弃未接纳的在线发送尾帧
    -> 释放 audio_capture_lease
    -> Engine PAUSED_BY_USER
    -> ONLINE PAUSED
    -> 上报 Wire state=2
```

候选队列深度固定为 16，因此 Pause drain 有明确上界。进入稳定 PAUSED 前清空在线层尚未接纳的发送尾帧并累计 `pause_discard_count`，防止旧采集周期的数据在 Resume 后补发。Pause 不执行 Destination detach，不清除 `session_frame_seq`、Metadata journal 或 Session 控制权。

### 4.2 Resume

```text
ONLINE PAUSED
    -> RESUME_PENDING
    -> Engine RESUMING
    -> capture_generation + 1
    -> 重新取得 audio_capture_lease
    -> 以原 MEETING_V1 格式重开 Pipeline
    -> Engine ACTIVE
    -> ONLINE STREAMING
    -> 上报 Wire state=3
```

Resume 保持 `session_id` 和 `session_frame_seq`。新采集周期的 `capture_frame_seq` 和预热计数从零开始；前 10 个预热 Opus 帧不推进 `session_frame_seq/active_pts`。恢复后的第一个正式 RecordFrame 带 `FIRST_AFTER_RESUME`。

租约或 Pipeline 重开失败时 Session 保持 `PAUSED_BY_USER`，上报当前暂停状态，允许 APP 重试；不得把失败转换为新 Session。

### 4.3 Mark 与 Pause 的串行切点

Mark、Pause 和 Resume 使用 Engine 的普通控制队列。Engine worker 是唯一处理者：

- Mark 先出队：按当时 `active_pts` 生成标记，然后 Pause；
- Pause 先出队：Engine 先进入 `PAUSED_BY_USER`，后续 Mark 返回 BAD_STATE；
- Resume 先出队：恢复 ACTIVE 后，后续 Mark 可成功。

`active_pts = session_frame_seq * 20 ms`。它只统计已通过格式检查、预热过滤并成为正式 RecordFrame 的帧，因此自然排除 Pause、每次 Resume 的预热和被拒绝候选帧。

## 5. 模块边界

### 5.1 Record Engine

`rdx_record_engine` 新增 PAUSE、RESUME 和 MARK 请求及完成事件，负责：

- 校验 controller、Session 和技术状态；
- 形成 Pause/Resume 的采集周期切点；
- 在 worker 串行点为 Mark 生成确定 `active_pts`；
- 保持跨 Pause 连续的 `session_frame_seq`；
- 递增并校验 `capture_generation`。

Engine 不包含 Wire 字符串、标记上限、去重窗口或 BLE 发送逻辑。

### 5.2 Session Metadata Service

新增 `rdx_session_metadata_service.[ch]`，负责：

- 每次 START 成功时创建当前 Session 的 canonical mark journal；
- 应用 20 个上限和 6000 ms 去重策略；
- 分配从 1 开始的 index；
- STOP/强制结束时统一清理；
- 向 Online ACK 返回同一个确定结果。

该模块不操作 Pipeline、文件系统或 BLE Transport。未来移植本地录音时，Artifact 索引必须读取这里的 journal，不能再维护第二套 marks。

### 5.3 MVP0 Protocol / Online Service

`rdx_mvp0_protocol.c` 负责：

- 严格匹配 Pause/Resume/Recmark Wire 命令；
- 维护在线协议态和当前 Wire state；
- 把控制意图提交给 Engine；
- 把 Engine/Metadata 结果编码为兼容状态包和 Recmark 包。

它不直接 open/close BR56 Pipeline。

## 6. 配置和 Ability

### 6.1 产品层唯一配置入口

产品只在 `rdx_mvp0_compat_config.h` 配置 `RDX_COMPAT_DEVICE_ABILITY`。Ability 既是广播给 APP 的能力声明，也是实现模块的唯一编译配置源：

```c
#define RDX_COMPAT_DEVICE_ABILITY              \
    (RDX_ABILITY_RTC                          | \
     RDX_ABILITY_CONFERENCE_RECORDING         | \
     RDX_ABILITY_RECORD_PAUSE_RESUME           | \
     RDX_ABILITY_RECORD_MARK)
```

当前值为 `0x00000622`。Local Storage 和 Flashnote 仍未开放。产品层不再配置 `TCFG_RDX_RECORD_PAUSE_RESUME_ENABLE`、`TCFG_RDX_RECORD_MARK_ENABLE` 等平行开关，避免出现“APP 看见能力但固件没有实现”或“固件包含实现但未广播能力”的双向失配。

### 6.2 集成层自动派生

`rdx_integration_config.h` 只读 Ability 并自动派生内部 `RDX_CFG_*` 门控：

```text
RDX_COMPAT_DEVICE_ABILITY
    -> RDX_CFG_RTC_ENABLE
    -> RDX_CFG_CONFERENCE_RECORDING_ENABLE
    -> RDX_CFG_RECORD_PAUSE_RESUME_ENABLE
    -> RDX_CFG_RECORD_MARK_ENABLE
```

派生门控统一控制：

- MVP0 Wire 命令解析和响应实现；
- Record Engine 的可选 Pause/Resume/Mark 分支；
- RTC、Record Engine 和 Session Metadata 源文件选择；
- RTC、录音音频图等平台依赖检查。

依赖关系在编译期强制校验：`RECORD_PAUSE_RESUME` 和 `RECORD_MARK` 必须同时具备 `CONFERENCE_RECORDING`；当前目标未实现的 Ability 位也会直接触发编译错误，不能只广播而没有实现。产品只声明能力，集成层负责验证当前硬件配置能否承载该能力，不在集成头文件中偷偷打开 RTC 或音频节点。

Mark 上限 20 和 6000 ms 去重窗口属于本次冻结的 V24 兼容策略，已下沉到 `rdx_session_metadata_service.c` 内部，不作为普通产品配置暴露。

## 9. 目标硬件验收清单

以下项目不能由编译替代：

1. APP 显示 Pause/Resume 和 Record Mark 控件，广播 Ability 为 `0x00000622`；
2. START 后 Pause，串口依次出现 `PAUSE_PENDING -> PAUSED_BY_USER`，APP 收到 state=2；
3. Pause 期间不再出现 `*DEV#stream#`，USB MIC 可以在租约释放后正常启动；
4. Resume 后 `session_id` 不变、`capture_generation` 增加，APP 收到 state=3；
5. Resume 的前 10 个预热帧不发送，第一个正式帧后声音无异常爆音；
6. Pause 前后音频拼接可解码，播放时长不包含暂停区间；
7. ACTIVE 标记成功，返回 `sn=0/filename=""/index=1/source=1`；
8. 6 秒内重复标记返回 result=2，窗口外 index 增加；
9. Pause、IDLE、STARTING 和 STOPPING 标记返回 result=1；
10. 第 21 个标记返回 result=3；
11. 验证 Mark/Pause 和 Mark/Resume 紧邻命令的串行结果；
12. Pause 状态下 STOP、断连、CCC off、USB 抢占、解绑和恢复出厂均能收敛到 IDLE；
13. Resume 租约失败保持 PAUSED，可再次 Resume；
14. 连续 100 次 START/PAUSE/RESUME/STOP 无任务、租约、Pipeline 或内存泄漏；
15. USB Speaker、USB MIC、BLE/RDX、RTC 和原 START/STOP 行为无回归。

建议串口 Golden Trace 至少记录：Wire RX、内部 request_id、session_id、capture_generation、Engine 状态、active_pts、Mark result/index、租约 acquire/release 和最终 Wire TX。

## 10. 已知边界和后续项

- 当前 Recmark journal 只驻留 RAM，Session 结束即清理；这是在线无 Artifact 产品的明确行为，不是持久化完成；
- 当前在线状态和音频包仍直接使用既有 MVP0 发送入口，统一 TX Scheduler 的完整 QoS 收敛仍按 `3-3` 后续阶段执行；
- Resume 成功 ACK 当前以 Pipeline 成功重开为切点；若 APP/硬件回归要求“首个正式帧已接纳”语义，应把 ACK 延后到 Resume 后第一个有效 RecordFrame，不得增加重复 ACK；
- 暂停队列固定且 drain 有界，但当前没有单独的 drain 超时/`DISCONTINUITY` 故障注入计数；生产就绪前需补异常注入；
- 设备按键打标、本地文件续写、marks 持久化、Artifact 恢复和文件列表同步均不在本次范围；
- 本文把参考行为冻结为兼容基线，最终仍以目标 APP 对目标固件的串口、音频和交互结果为准。
