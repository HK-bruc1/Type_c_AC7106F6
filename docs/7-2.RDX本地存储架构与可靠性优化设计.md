## 3. O3-B：Storage Executor 与线程所有权收敛

### 3.1 目标与当前差距

把“RDX Storage Service”与“新建一个 OS 任务”解耦，同时闭合 FAT 单一所有权和 Destination 非阻塞合同。

O3-B1 实施前差距：

- 录音 append 由 `rdx_storage` 执行，但 START 的 open/marker、正常 SEAL 的 close/publish/index 等部分 FAT 操作仍可能由 `rdx_record` 执行；
- Storage worker 在持有 Service mutex 时调用 append 和 marker FAT I/O，Record worker 的 `consume()` 可能等待该 mutex；
- 当前实现既付出了独立任务成本，又没有完全取得“所有 FAT 只在一个执行上下文”的收益；
- O3-A 已解决 APP STOP deadline，但没有完成上述线程所有权重构。

### 3.2 目标模型

~~~text
Audio callback / btstack
        |
        | bounded copy / command snapshot
        v
Record Engine + Coordinator
        |
        | StorageCommand / FrameBatch
        v
Storage Service state machine
        |
        | selected executor
        v
JL sd0/FAT Native Backend
~~~

Storage Service 维护业务状态机；Storage Executor 只决定在哪个可阻塞上下文执行 Backend。Executor 可以是专用任务、经审计的 JL 现有文件任务，或满足严格时延条件的协作式 pump，但三者在同一构建中只能选择一个。

### 3.3 实施顺序

1. 先把锁缩短：锁只保护队列指针、状态快照和 completion token，不包围 `fopen/fwrite/fclose/f_format`。
2. 增加单个 worker-owned in-flight 批次：在锁内取得队列所有权，解锁后执行 FAT，完成后重新加锁提交计数或错误。
3. 将 START、WRITING checkpoint、SEAL、publish、index commit、recover、容量、列表、上传、删除和格式化全部转成 Storage Command，由同一 Executor 执行。
4. 为 Command 定义优先级、屏障和公平性：
   - START open 必须先于该 Artifact 的任何 FrameBatch；
   - STOP/SEAL 是 STOP cut 之前全部 FrameBatch 的提交屏障，不能越过已接纳帧，也不能被后续低优先级请求饿死；
   - ABORT、介质撤销和关机属于紧急控制命令，可取消尚未执行的普通批次并锁存稳定失败原因；
   - 周期 checkpoint、枚举和上传属于可延后命令，不能持续阻塞 STOP/ABORT；
   - FORMAT、删除、恢复和录音按 Operation Lease 互斥，不能仅依赖队列顺序碰巧串行；
   - 连续 FrameBatch 必须设置受控 budget，给控制命令提供有界运行机会。
5. START/STOP/ABORT 和文件操作使用完整 token：至少包含 operation token、connection generation、Session/capture generation 或 Artifact generation。Executor completion 必须在提交状态前重新验证 token，禁止旧 completion 作用到新连接、新 Session 或已取消操作。
6. 定义 Command 队列满和取消语义：返回稳定 `BUSY/QUEUE_FULL/TIMEOUT`，不得覆盖旧命令；取消后关闭 worker-owned 句柄并只发送一次最终 completion。
7. 从公共 `rdx_local_storage_service.h` 移除 `system/includes.h`、`OS_MUTEX` 等 JL SDK 类型。平台同步对象放入 BR56 私有实现或不透明 executor context，在 O3-B 闭合线程所有权时同步关闭公共边界污染，不延后到 O5。
8. 完成上述所有权闭合后，再比较三种执行策略：

| 策略 | 优点 | 风险 | 采用条件 |
| --- | --- | --- | --- |
| 保留并缩小 `rdx_storage` | 隔离 FAT 阻塞，所有权最清楚 | 独立栈、队列和调度成本 | O1 后 RAM 达标，栈可降且 CPU 可接受 |
| 复用 JL 现有文件 Executor | 不新增任务，保持阻塞隔离 | 公开 API、生命周期和任务所有权可能不稳定 | 只能使用 JL 已提供且当前产品可审计的正式接口 |
| 合并到 `rdx_record` 协作 pump | 少一个任务和上下文切换 | FAT 抖动会阻塞 Engine、在线镜像和控制命令 | O2 后所有 FAT 调用最坏时延均小于 Engine 缓冲预算，且压测零溢出 |

默认不选择在 `btstack`、`app_core` 或音频回调直接写 FAT。若现有 JL 文件任务没有可用公共接口，应保留一个缩小后的 Storage Executor，而不是修改 JL FAT 内部实现。

### 3.4 O3-B1：锁尾 append 与公共边界去平台化（2026-09-04）

本切片只完成实施顺序第 1、2、7 项以及 SEAL 的必要汇合保护，不把 O3-B 整体标记为完成：

- BR56 私有实现新增“后端执行锁”和“短状态锁”。执行锁串行化 Backend 事务；状态锁只保护队列指针、录音接纳状态、worker 唤醒边沿和 operation 快照；
- Storage worker 在状态锁内把队首最多 6 帧/480 B 复制到 worker-owned `scratch.write_batch`，同时推进 `queue_head`、减少 `queue_count`，随后释放状态锁执行 Native `append` 或 Legacy `raw_write`；Legacy 单帧也必须先复制到 scratch，不能出队后继续引用可被生产者覆盖的原槽位；
- 成功写入后重新加状态锁校验 Artifact generation，并只使用 in-flight scratch 中的稳定副本提交逐帧 CRC 与 persisted 计数；FAT 写期间原批次已经真正脱离队列，生产者可使用完整 16 槽接纳容量，不再把 6 个 in-flight 槽位错误地计入排队占用；
- append 失败路径先在短状态锁内关闭帧接纳、清空队列并快照句柄/FAILED marker，再在锁外执行 close、marker、index 清理与 quarantine；
- SEAL 在观察到队列清空后必须再取得执行锁，等待可能仍在进行的 append/checkpoint 完成，才允许 close/publish/index，避免 queue count 已提交但 checkpoint 尚未返回时发生并行 FAT 操作；
- `rdx_local_storage_service.h` 不再包含 `system/includes.h`，也不再暴露 `OS_MUTEX`；BR56 同步对象收进 `rdx_local_storage_service.c` 的私有 platform context；
- 本切片没有新增或删除任务，`rdx_storage` 仍使用原任务表项和 1024 words 栈。是否移除该任务必须等单 FAT owner 与目标板时延证据闭合后再裁决。

首版验证与目标板反证：

- 首版 RDX Host Golden Trace 为 17/17，但专项只在 append 内重入 1 帧，没有覆盖“队列已满、首批 in-flight、同时再到达 6 帧”的容量边界；这是测试遗漏，Host 通过不能作为首版设计正确的证据；
- 首版正式 BR56 配置完成增量编译和链接，使用 `RUN_POST_SCRIPT=echo`，未执行下载后处理；当时 `.bss = 0xABF4 = 44,020 B`，比 7-1 提交配置净增 32 B。该 map 只属于首版构建记录，不能替代修正版重新构建；
- `COM3_2026-09-04_14-14-00.log` 与首版打包镜像时间线一致。长通话录音终止前计数为 `produced=6593 / accepted=6592 / persisted=6576 / rejected=1 / dropped=1`，其中 `accepted - persisted = 16` 正好等于 Local 队列深度；Engine 随后以 `cause=5 / result=10`（`QUEUE_FULL`）强制结束；
- 首版把 append 中的 6 帧保留在原队首槽位，状态锁释放后生产者实际只剩 `16 - 6 = 10` 个可用槽。FAT/调度毛刺期间队列达到 16 即触发上述失败。由此可以确认 Local 强停是 O3-B1 首版 in-flight 所有权设计造成或显著放大的回归，不应归因于 APP STOP，也不能靠提高队列深度掩盖；

### 3.5 O3-B2：同步命令槽与单 FAT owner（2026-09-04）

本切片先闭合实施顺序第 3 项的目标端线程所有权，并完成第 4、5、6 项中能够在单槽合同内稳定定义的部分；它不等同于 O3-B 整体完成：

- BR56 私有 platform context 新增一个同步命令槽、完成信号量和非零单调 token，状态明确区分 `pending / running / completion_ready`。前一调用者按 token 领取结果前，后一命令只能得到稳定 `BUSY`，不能覆盖尚未领取的 completion；
- `recover`、序号预留与 Index 高水位提交、START/open、attach marker、cancel START、SEAL/publish/index、ABORT、同步容量/列表/删除/格式化、quiesce 和 shutdown 均保留原同步 API，但目标端内部改为投递到 `rdx_storage` 并等待对应 token；Host 继续同步执行同一 command dispatcher，保持可重复 Golden Trace；
- 同步命令只借用调用者输入/输出缓冲到 API 返回。当前等待不设置超时，因此 worker 不会在调用者返回后继续访问失效栈对象，也不会产生“超时返回后旧 completion 写入新操作”的悬空边界；代价是 worker 失活时可能无界等待，deadline 与可取消异步 completion 仍是后续必补项，不能把当前 token 写成完整取消合同；
- worker 每轮固定按“同步生命周期命令、APP 文件 operation、最多 6 帧 FrameBatch”取活，同步命令只在 APP operation idle 时允许入槽，因此当前保证的是命令对 FrameBatch 的优先级，不把它误写成支持跨 operation 抢占的完整调度器。正常录音期间 APP operation 已由 active gate 禁止；SEAL 在命令入槽的同一状态锁区先锁存 STOP cut，worker 接管后排空全部已接纳帧，再执行 close、全文校验、marker、publish 和 Index commit，取消了调用线程每 tick 轮询队列的旧实现；
- `rdx_local_storage_service_pump()` 在 BR56 上拒绝非 `rdx_storage` 调用，避免公共测试入口重新形成第二条目标端 FAT 执行路径；Host pump 保留用于批量、短写、队列满和 CRC 的确定性测试；
- shutdown 先由 storage owner 执行 active Artifact 失败清理和 media quiesce，命令 completion 被调用者领取后才终止 worker，避免旧实现先杀任务、再由调用线程直接关闭文件；
- Native Adapter init 原先在 Service/worker 创建前调用 `sd0_ready()`，会间接检查或创建 `RDXTMP/RDXBAD` 目录。现拆为无 FAT 的介质/根路径 probe，目录布局只允许由 worker 上的 `ensure_ready()` 建立；这是闭合启动阶段单 owner 时发现并修正的遗漏边界。

### 3.6 O3-B3：命令 deadline、取消与迟到 completion（2026-09-04）

本切片闭合 O3-B2 的同步无限等待边界，但不把单槽扩张成通用多命令队列，也不提前实现 O5 的跨业务 Operation Lease：

- Service 在入槽时把命令参数复制到 worker-owned `service_command`，输出先写入同一所有权对象；只有调用者以匹配 token 领取 completion 后，才复制到调用者输出缓冲。普通同步命令 deadline 为 5 秒，可能执行全文 CRC 或格式化的 SEAL/FORMAT 为 120 秒；调用者超时返回后，worker 不再访问其栈对象；
- 尚未被 worker 领取的普通命令允许在 deadline 处取消；`CANCEL_START / SEAL / ABORT / SHUTDOWN` 属于 must-run，deadline 只能使调用者放弃等待，不能撤销已经承诺的清理、提交或关机屏障；
- 已运行命令超时后进入 abandoned。worker 的匹配迟到 completion 不得提交到后来操作：迟到 START 自动执行 cancel，迟到 ATTACH 自动 ABORT，其余迟到结果按命令合同丢弃或完成必要收敛；slot 在迟到 completion 被核对、收敛和释放前不能复用；
- shutdown deadline 不再删除仍执行 FAT 的 worker，避免任务被杀死后遗留句柄、半写事务或第二 owner。连续 FrameBatch 仍以 6 帧 budget 给同步命令提供调度机会；
- `rdx_storage_command_slot` 提供独立纯状态机，并覆盖非零 token 回绕、陈旧 token、pending 取消、must-run pending、running abandoned、匹配与非匹配迟到 completion。RDX Host Golden Trace 由 17 组增加为 18 组，当前 18/18 通过；
- 诊断构建按每个 Artifact 输出 Executor wake post/合并/失败、最大唤醒时延、FrameBatch 数、Local 队列峰值、命令等待/执行最大值、timeout、pending cancel、must-run pending 和 late completion。Backend 同时保留各类 FAT 最大值及分位桶，终态能够关联调度与介质时延。

### 3.7 复发 ATT P0：发送 credit 与公开 Adapter 所有权收口

参考工程的公开边界显示，原生 RDX 通过 `rdx_protocol_task_create()` 建立协议发送 worker，`BLE_SendData` 使用 `send_sem / send_pending / bulk_sending`，BLE Server 另有 `ble_send_queue_mutex`。预编译 `librdxApp.a` 使内部算法不能完整静态审计，但可以确认其设计方向是单发送 worker、信号量/credit 驱动，而不是由每个 20 ms 音频帧无条件继续填充 ATT 私有列表。

当前工程在 O2 背压门闩后只会在发送失败时进入 `tx_waiting`；正常 `ACCEPTED` 后，下一帧仍会在 20 ms 后再次检查 `valid_len` 并直接提交。`COM3_2026-09-04_14-14-00.log` 的断言发生在第二次 START ACK 后约 2 秒，期间没有新的管理/文件控制 TX 日志，因此“两个 RDX 调用者恰好同时进入 wrapper”不是已证实根因；能够确认的是正常成功路径仍没有把 ATT ready 当成逐包 credit，私有发送列表仍可能存在多个 RDX 包生命周期重叠。

本轮在 RDX/JL 公开集成边界实施以下止血，不增加任务、不扩大 TX 队列，也不修改 `att_send.c`：

1. Online Destination 在调用 `app_ble` 前先登记当前 Session/capture 的 can-send 所有权，防止极快的共享 ready 事件先于 waiter 建立而丢失；
2. 每个 owned `ATT_EVENT_CAN_SEND_NOW` 最多提交一个 Online 包；正常 `ACCEPTED` 后也保持 `tx_waiting`，下一帧只入有界队列，必须等待下一 credit；
3. START 状态 ACK 与首个 Opus 包使用同一 credit 边界：START ACK 发送前先登记 waiter，首帧不能紧随 ACK 进入私有 ATT 列表；
4. Streaming 期间仍不为每包主动调用 JL 全局 can-send 请求；Transport 只登记 RDX token，依赖 wrapper 已产生的共享 ready 事件，100 ms 无事件时沿用既有一次有界 native fallback；
5. Transport Adapter 复用已有 `tx_lock` 增加非阻塞 `app_send_active` 入口所有权。Record、btstack 和 Storage completion 若同时进入 `rdx_transport_send()`，只有一个调用者执行 `valid_len + app_ble_att_send_data()`，其他调用者返回 `RETRYABLE`；自旋锁不跨 SDK 调用持有，不新增 mutex 或任务。

Host 的 Online 背压用例现覆盖 START ACK credit、首次 `RETRYABLE` 后等待，以及普通 `ACCEPTED` 后下一帧也必须等待新 credit；17/17 组通过。由于 Host fake 无法执行 JL 私有 ATT 列表，Host 结果只能证明 RDX 状态机与重试合同，不能单独证明 `att_send.c:602` 已关闭。

`COM3_2026-09-04_14-51-13.log` 随后完成两轮连续长录音与正常 START/STOP，START 状态回执、STOP 快速回执均 `ret=0`，第二轮在第一轮 Commit 后重新分配 Session、Capture、SN 和文件名并成功运行约 181 秒，未出现 `att_send.c:602`、`send_list_len`、APP STOP 超时或运行期异常复位。这是 credit/gate 修正后的首份目标板正向证据，足以把 ATT P0 从当前提交阻塞项降为后续观察项。

证据边界必须保留：两轮终态都是 `mode=1 / cause=1`，即 APP 正常 STOP，不是 link lost、CCC off、USB preempt 或其他强制终止；正式配置关闭了 BLE TX 详细诊断，因此日志没有 `pending`、`send_overlap` 等 TXQ 终态字段，不能把“未打印”解释为统计值为 0。异常终止后立即重连/START、主动制造 ATT 拥塞及诊断镜像下的 `pending=0 / send_overlap=0` 仍留在后续压力矩阵，不再阻塞当前阶段提交。

### 3.8 故障归属与验证经验

1. 同一份日志连续出现两个故障，不代表二者存在同一根因。`accepted - persisted = 16` 与 Local 队列深度精确相等，且 Engine 以 `cause=5` 结束，足以把第一项定位到 O3-B1 首版 in-flight 槽位所有权；新 Session 成功建立后才出现与旧 P0 相同行号和包长的 ATT 断言，应作为独立发送生命周期问题处理。
2. 回归归属应同时看“变更边界”和“日志不变量”。O3-B1 首版当时没有修改 BLE Transport 或 Online Destination，所以 `att_send.c:602` 属于 7-1 背压方案没有彻底建立逐包 credit 的遗留边界，而不是 O3-B1 新造的断言类型；反过来，Local 队列容量下降则由 O3-B1 首版直接造成，不能归给 APP STOP 或 BLE。
3. Host fake 能验证队列、generation、credit gate 和重试合同，但不能执行 JL 私有 ATT 列表；Host 全绿不能替代目标板断言回归。测试必须补齐真实容量边界，例如“16 槽已满、6 帧成为 in-flight、append 期间再到达 6 帧”，不能只测空队列内重入一帧。
4. 阶段性关闭必须写清样本。两轮约三分钟正常录音可以证明正常路径不再高频复现，但不能证明异常终止、极端拥塞和量产长稳；诊断关闭时也不能把缺失的统计字段写成零。后续复发时应按新日志重新打开问题，而不是维护永久正确的结论。
5. 修复应停留在 RDX/JL 公开集成边界：释放真实队列容量、建立逐包 credit、串行化公开发送入口并保留 JL 私有断言。不得靠扩大队列、猜测 `valid_len` 安全余量、降低断言等级或修改 `att_send.c` 掩盖所有权错误。
6. 执行所有权迁移会同时迁移调用链的栈压力，不能因为新旧任务名义栈大小相同就假定峰值不变。`COM3_2026-09-04_16-10-06.log` 证明正常 SEAL 通过并不能覆盖 ABORT：后者多经过 `service_fail`、失败 Marker 写入与回读验证，实际把 4 KiB storage 栈下界越过约 40 B。
7. 单 owner 不只是并发约束，也提供了安全的 scratch 复用条件。对 index、全文 CRC、Marker 写入和 Marker 回读这些互斥步骤，应优先复用既有 Backend scratch 降低任务栈峰值；不得仅为通过一次异常路径继续扩大常驻任务栈，也不得取消 Marker 回读验证掩盖问题。
8. 失败终态日志必须结合调用语义解释。LINK_LOST 的 ABORT 主动以 `RDX_STORAGE_RESULT_IO_ERROR` 结束并清理未发布 Artifact，因此 `failed result=7 cause=3` 本身不是“quarantine 失败”的证据；应继续核对是否出现栈溢出/复位、下一次 START 是否成功、失败 SN 是否误入 Index，以及后续正常 Artifact 能否完整提交。
9. 单 operation gate 能防止 APP 重试覆盖在途容量或列表缓冲，但仅打印并吞掉重复命令不等于正式 Wire 错误合同。本阶段可把“原请求成功、重复请求 BUSY、后续请求恢复”作为串行化正向证据；O4 仍应为 APP 提供稳定的 BUSY/重试响应，避免依赖客户端定时重发碰巧恢复。
10. 诊断总开关为 1 不代表每个翻译单元都实际编入诊断。可移植源码若依赖产品配置，必须在目标端条件分支显式取得配置，并以依赖文件、ELF 格式串和实机终态日志三层核对；没有打印只能记为“无证据”，不能填写零值。

### 3.9 O3-B 验收

- 任意 Backend FAT API 都能静态追踪到唯一 Executor；
- `consume()` 只做有界检查、复制、入队和唤醒，不等待 FAT；
- Service mutex 持锁区内不存在 FAT/VFS 调用；
- START/STOP/ABORT/FORMAT completion 均有 token、deadline、取消规则和明确失败结果，陈旧 completion 注入测试不能改变当前状态；
- STOP/SEAL 屏障不会越过 STOP cut 前帧，ABORT 和介质撤销不会被连续 FrameBatch 饿死，普通请求也有明确公平性预算；
- 公共 RDX 头文件不暴露 JL OS/FAT 类型；
- 以真实最大 FAT 时延、任务栈水位、任务 CPU、wake 次数和 runnable latency 记录最终任务策略；若删除 `rdx_storage`，必须证明 Engine 候选队列和在线镜像不受阻塞影响。

上述静态边界、Host 18/18、正式/诊断构建和 `COM3_2026-09-04_17-54-37.log`、`COM3_2026-09-04_18-23-25.log` 两轮目标板证据已经闭合 O3-B 当前验收范围。最终策略为保留专用 `rdx_storage`：实测全文 close/CRC 可达 5.89 秒，当前又没有可审计的 JL 公共文件 Executor，删除任务会把不可接受的 FAT 阻塞重新引入 Engine/Online。诊断镜像 76.9% 栈 HWM、故障注入和长稳矩阵按上文边界继续进入 O5，不回退本阶段的单 owner 与 completion 合同。

## 4. O4：文件列表、上传与正式 Wire 优化

### 4.1 目标

消除长文件上传的 O(包数 × 索引/开关文件) 放大，并补齐正式广播后的稳定错误合同。

### 4.2 实施项

1. 上传请求首次按 SN 查找并验证文件身份，建立带 connection generation 和 operation token 的只读上传会话。
2. 同一上传会话保持一个只读句柄或 Backend cursor，后续 80 B 包只做有界 seek/read；顺序请求不得重复枚举和加载 A/B index。
3. 上传结束、自动删除、BLE 断连、超时、格式化和新会话替换时必须关闭句柄并使 token 失效。
4. 若 APP 重传旧包，允许在同一已验证文件内 seek，但不得重新走全量身份发现。
5. 文件列表采用 O1 的随机访问流式 encoder；每个 `requested_pack` 必须能按同一 generation 确定性重建。发送期间索引变化应返回稳定失效结果并要求重新开始，不拼接两个 generation，也不继续引用已被上传、容量或删除操作复用的 scratch。
6. Local Wire 忙时返回明确 BUSY/失败结果，不允许静默 `[DROP]`。Transport busy 与 Storage operation busy 使用不同内部原因，Wire 再按既有合同映射。

### 4.3 O4 验收

- 一次完整上传只做一次身份解析和一次文件打开，断连后零句柄残留；
- 1 小时录音文件上传不随包数重复读取索引；
- 首包、顺序包、重复包、短尾包、非法偏移、断连续传和自动删除均有 Host 与目标板证据；
- 列表首包、尾包、重复包、乱序包、非法包、generation 变化和 32 项最坏 JSON 均有 Golden Trace；
- 上传期间的 CPU、文件打开次数和平均包时延形成统计；
- busy、not found、identity mismatch、I/O error 和 disconnect 均返回稳定语义。

## 5. O5：架构边界与量产长稳

### 5.1 目标

在性能路径和 O3-B 公共边界稳定后，补齐跨功能租约、异常恢复和长期可靠性。

### 5.2 实施项

1. 引入统一 Operation Lease，覆盖录音、恢复、枚举、上传、删除、格式化、USB Host Ownership、OTA 和关机；替换分散 busy 标志。
2. 完成 metadata/marks 到 Artifact 的提交合同，不再只提交裸 Opus 帧和占位字段。
3. 实现未入索引 marker 的有界发现与恢复裁决：
   - 只扫描受控的内部事务目录并设置条目上限和时间预算，不退化为启动时全 FAT 无界扫描；
   - 校验 artifact_id、marker CRC、状态、临时文件身份、实际长度和 durable 长度；
   - 明确 WRITING Artifact 是截断到最近 durable checkpoint 后恢复、冻结为部分文件，还是隔离删除；不能凭文件存在猜测完成；
   - 恢复 completion、隔离原因和重复启动结果必须幂等。
4. 补齐断电切点：open 后、append 中、flush 前后、checkpoint 前后、publish 前后、index A/B commit 前后和终态 marker 前后。
5. 单独审计格式化的全局 WDT 边界：当前实现以 `wdt_disable()` 包围 `f_format()`，虽然与 JL 示例一致，但若格式化不返回会失去看门狗恢复能力。必须确认是否存在 JL 正式长操作接口、所有返回路径恢复 WDT，并与关机、OTA、USB Host Ownership 和介质撤销协调。
6. 建立低空间提交保留量：为最后一批音频、音频 flush、终态 marker、根目录 publish、A/B Index 和失败隔离预留紧急空间，不允许写满介质后才发现无法提交。当前索引达到 32 项时 START 已返回 `NO_SPACE`，继续保持“START 前拒绝”作为首版策略；若未来增加淘汰，必须另行定义原子删除合同。
7. 建立介质寿命策略：统计每天 marker、Index、目录项和 FAT 热点事务，冻结耐久性门槛；可评估有界预分配或簇分配优化，但只能使用 JL 公开接口，不修改 FAT 核心。
8. 补齐格式化后重启/再录音、容量耗尽、坏块/I/O 错误、SN 高水位和旧 marker 迁移。
9. 执行 Local + Online + USB Audio + BLE 控制的跨功能长稳，并记录 CPU、分池 heap、栈、队列、调度、时延和文件一致性趋势。

### 5.3 O5 验收

- 公共 RDX 头文件可在不包含 JL SDK 的 Host 构建中使用；
- 互斥操作均由租约矩阵裁决，无隐式并发 FAT 访问；
- 未入索引 WRITING marker 能按明确决策恢复或隔离，重复启动结果幂等，且恢复时间受内部目录上限约束；
- 格式化所有完成/失败路径恢复 WDT，低空间场景仍有资源完成终态提交或明确隔离；
- 24 小时长稳零断言、零复位、零栈溢出、零未解释丢帧和零句柄泄漏；
- 断电恢复结果与文档决策表一致；
- 量产报告明确列出仍接受的产品风险，不用“功能可用”替代可靠性结论。

## 6. 性能与可靠性指标

以下指标承接 7-1 已完成基线，并定义后续阶段必须继续采集的证据和门槛。尚未取得目标板数据的项目不得填写推测值。

| 类别 | 必须采集 | 后续门槛或承接基线 |
| --- | --- | --- |
| Heap | RAM0/RAM1 各自 total/used/free、事件低水位、最大连续块、未释放块 | 零分配器断言；各池门槛由 O0 失败申请和安全系数冻结，不使用合计 20 KiB 经验值 |
| 动态申请 | 失败申请大小、调用点、目标池、FAT 每次申请大小与次数 | 保持 O2 批量写效果；Executor 重构后申请频率和峰值不得回归 |
| 静态 RAM | BSS/DATA、RDX 大对象逐项大小 | 7-1 提交配置最终 `.bss=43,988 B`；后续增量必须逐项解释并验证 |
| 栈 | `rdx_record`、Storage Executor、`btstack`、`jlstream_*` HWM | 峰值不超过配置 75% |
| CPU | Idle、Online-only、Local-only、Local + Online | 不出现持续满载；最终阈值由同配置 A/B 压测冻结 |
| 调度 | Storage Executor CPU、wake、上下文切换、runnable latency、连续运行时间 | 不饿死控制命令，不对同优先级 `jlstream_*` 形成可复现回归 |
| 队列 | Engine candidate、Online TX、Local frame 的峰值和溢出 | 正常场景零溢出、零未解释 drop |
| FAT 时延 | append、flush、checkpoint、close、publish、index、read、format | 记录最大值和分位值；不得超过相应队列/deadline 预算 |
| STOP | 1 分钟、30 分钟、2 小时文件 | `SESSION_STOPPED` 保持早于 APP 首次重试窗口且不随文件长度线性增长；强 Commit 时延单独统计 |
| 上传 | 打开次数、索引读取次数、包时延、断连清理 | 每会话一次身份解析和一次打开 |
| 一致性 | produced、accepted、VFS accepted、durable、verified、size、CRC、index | 正常 STOP 按选定 Commit 等级闭合，不混用 expected 与 on-media CRC |
| 介质寿命 | 音频、marker、Index、目录/FAT 事务及每天热点重写估算 | checkpoint 周期满足冻结后的耐久性预算 |

后续阶段不设置合计空闲 RAM 的固定经验门槛。最终门槛必须同时包含 RAM0/RAM1 各自低水位、最大失败申请、连续块或页池证据、介质事务峰值及安全系数；任何单一合计 free 数值都不能替代分配器证据。

### 7.1 构建矩阵

| 镜像 | Local Ability | Native Backend | Online | 用途 |

| Online 基线 | 0 | 0 | 1 | 固定音频与 BLE 资源基线 |
| Local-only | 1 | 1 | 0 | 隔离 FAT、任务和 Artifact 成本 |

### 7.2 场景矩阵

1. 同一次上电连续执行 20 次 5 分钟正常 START/STOP，逐轮检查 RAM0/RAM1、句柄、任务和基线回落；
2. 30 分钟与 2 小时 Local + Online 长录音；
3. Pause/Resume 反复 100 次后 STOP；
4. Online 拥塞、BLE 断连和重连期间继续 Local；
5. 先执行至少 1 分钟通话录音并强制断开，随后立即再次 START；检查 START ACK 与首包 credit、Local `accepted == persisted`、Online `pending=0`，不得出现 `QUEUE_FULL`、`att_send.c:602` 或异常复位；
6. 音频 flush 前后、checkpoint 前后和 marker 关闭后的断电恢复；未实现 WRITING marker 发现时必须明确记为“不支持”，不能用已索引恢复替代；
7. 文件列表 0、1、31、32 项与索引满，并覆盖最大 JSON、随机包、重复包、乱序包及 generation 变化；
8. 大文件顺序上传、重复包、非法偏移和中途断连；
9. 录音与列表、上传、删除、格式化的互斥组合；
10. 格式化后立即重启并重新录音；
11. 剩余空间不足但仍需完成终态 marker/publish/Index 的保留量边界，以及 Backend I/O error 和 marker/index 校验失败；
12. FORMAT 超时、失败、关机/OTA/USB 接管相邻发生时的 WDT 恢复和句柄清理；
13. 连续 FrameBatch 下 STOP/ABORT/介质撤销不饥饿，队列满、取消和陈旧 completion 注入不改变新 Session；
14. 24 小时介质写放大与热点事务统计，结合目标介质规格验证 checkpoint 耐久性预算。

- Host Golden Trace 全量通过；
- Windows 从 `SDK/` 执行 `.vscode\winmk.bat all`，涉及源码选择或链接布局时先执行 `.vscode\winmk.bat clean`；

## 8. RDX 与 JL 原生边界

### 8.1 必须保持的 RDX 约束

- Protocol 只负责 Wire 解析、鉴权、幂等键和结果映射；
- Record Engine 拥有 Session、Capture Generation、STOP cut 和音频资源；
- Coordinator 编排录音与 Artifact 生命周期，不直接成为 FAT Backend；
- Storage Service 拥有 Artifact、索引和文件操作状态机；
- Storage Executor 拥有全部 Backend 调用的执行顺序，但不是领域对象；
- Native Backend 只适配已挂载的 JL sd0/FAT，不建立第二套设备管理和挂载；
- REQUIRED Local 与 OPTIONAL Online 的失败语义保持隔离；
- `persisted`、`durable`、`verified` 必须由明确事件推进，不能把 `fwrite()` 返回、rolling CRC 或 marker 自身关闭直接等同于 Artifact 已提交。

### 8.2 允许的 JL 集成修改

- `SDK/apps/earphone/app_main.c` 中必要的任务表或最终删除的任务表项；
- `SDK/apps/earphone/include/rdx_integration_config.h` 中产品门控和运行策略参数；
- `SDK/apps/earphone/include/rdx_diagnostic_config.h` 中 RDX 可裁剪监测与诊断门控；
- `SDK/apps/earphone/log_config/lib_system_config.c` 中 FAT write 与临时诊断配置；
- `SDK/build/genFileList.c` 中受同一门控约束的源文件选择；
- RDX 的 BR56 Adapter 与 Product Integration；
- 在 RDX Transport Adapter 内使用已有自旋锁建立非阻塞发送入口所有权，并在 Online Destination 使用 Session/capture token 管理 ATT ready credit；
- 经目标板验证后，通过公开 `f_flush_wbuf()` 建立必要的 sd0/FAT 刷新边界；
- 对 JL 既有格式化接口增加 RDX 上层租约、deadline、completion 和 WDT 恢复审计，不改变 `f_format()` 内部实现。

### 8.3 禁止扩张的边界

- 不修改 JL SD/MMC 驱动和 FAT 核心来规避上层内存问题；
- 不修改 JL allocator 或关闭 `vmalloc_` 断言来掩盖失败；
- 不复制或接管 dev_manager 初始化、add、mount 和卸载生命周期；
- 不依赖未公开的 JL 内部任务数据结构；
- 不为删除 `rdx_storage` 而调用没有公开稳定合同的 JL 私有文件任务入口；
- 不同时启用 Native index 与 Legacy UXFILE/DAT 两套文件事实源；
- 不在公共 RDX 头文件暴露 `FILE *`、`OS_MUTEX`、设备节点或 mount handle。
- 不通过猜测 `valid_len` 安全余量、扩大 ATT/RDX 队列、降低断言等级或恢复 direct multi-ATT 旁路来掩盖 `att_send.c:602`。

## 9. 提交与回退策略

后续每个阶段独立提交，禁止把 Executor 重构、上传优化、恢复策略和量产压测混成一个无法定位回归的大提交。

建议顺序：

1. `refactor(rdx): 收敛存储执行器与 FAT 线程所有权`
2. `perf(rdx): 优化长文件上传会话与句柄复用`
3. `fix(rdx): 完善本地存储操作租约与异常恢复`
4. `test(rdx): 补齐本地存储长稳与断电恢复矩阵`

每个实现提交必须包含：

- 修改前后 map 差异；
- 对应阶段 Host 测试结果；
- 目标板日志摘要与未验证项；
- Artifact Commit、durability 和 recovery 证据；
- 明确回退开关或能够单独 revert 的范围；
- 不提交串口原始日志、生成的 `fileList.mk`、对象、固件输出、缓存或 `tide-bridge/`。

O3-B 不以“删除 `rdx_storage` 任务”为预设结果。若公开 JL 文件执行接口不可用，或协作式 pump 的 FAT 最坏时延会破坏 Engine/Online deadline，应保留一个缩小后的专用 Executor。

## 10. 推进原则

1. 先完成 O3-B 的单 FAT owner、锁外 I/O 和 completion token，再决定任务载体；
2. 再完成 O4 的上传会话、流式列表 generation 和正式错误合同；
3. 最后完成 O5 的恢复、租约、WDT、低空间、介质寿命和量产长稳；
4. 每一阶段都必须同时通过 Host、正式构建和对应目标板矩阵；
5. 只完成编译不得声称硬件行为通过，只完成短测不得声称量产长稳通过；
6. 优化不得破坏 Local REQUIRED、强 Artifact Commit、Protocol 不访问 FAT 和 JL 私有实现不修改的边界。
