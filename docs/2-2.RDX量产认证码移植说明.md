# AC710N RDX 量产认证码移植说明

> 文档状态：v1.1（Provider 重构和干净构建已完成，量产烧录及目标 APP 实机验证待完成）
> 编写日期：2026-08-08
> 目标工程：AC710N / BR56 Type-C 有线耳机
> 参考工程：`t2616cc-firmware/`（JL701N / BR28，仅用于确认认证码布局、字段和读取行为）
> 关联文档：`docs/2-1.RDX_APP业务移植实施方案.md`
> 领域词汇：`CONTEXT.md`
> 架构决策：`docs/adr/0001-rdx量产身份边界.md`
> 官方说明：<https://doc.zh-jieli.com/Tools/zh-cn/firmware_tools/mac_update/authcode.html>

## 1. 文档目的与实施结论

本文记录 RDX 量产身份从开发期硬编码迁移到杰理认证码区的实施方法，覆盖认证码数据合同、固件配置、Flash 布局、运行时读取、CRC 校验、字段解析、失败处理和量产验证。

本次移植完成后：

- AuthKey 不再使用 `RDX_COMPAT_AUTH_KEY` 硬编码；
- Label SN 不再使用 `RDX_COMPAT_LABEL_SN` 硬编码；
- BLE MAC 从量产认证码的第二字段取得，并设置为 RDX BLE 地址；
- Wi-Fi MAC 因后续需要由外部设备传递，暂时保留 `RDX_COMPAT_WIFI_MAC = "000000000000"`；
- 认证码块缺失、CRC 错误或字段格式错误时，RDX 拒绝启动，不使用全零身份继续上线；
- 调试固件在启动时分别打印 AuthKey、BLE MAC 和 Label SN，便于逐字段核对；
- 量产关闭 `TCFG_DEBUG_UART_ENABLE` 后，上述三条明文日志不参与编译；
- 所有构建均不再打印包含真实 AuthKey 的完整 `authsn` 上行报文。

USB Audio、USB MIC、HID、音频流程和 RDX 绑定状态不属于本次改动范围。

## 2. 量产数据合同

### 2.1 数据格式

本文使用以下术语：烧录工具写入的 `crc + len + payload` 称为“认证码块”，其中的 54 B 文本称为“量产身份记录”，AuthKey 只指第一个 24 B 字段。完整定义见 `CONTEXT.md`。

当前 RDX 量产身份记录包含三个以英文逗号分隔的 ASCII 字段：

```text
<AuthKey>,<BLE_MAC>,<Label_SN>
```

字段长度是固定合同：

| 字段 | 长度 | 格式 | 用途 |
| --- | ---: | --- | --- |
| AuthKey | 24 B | `[A-Za-z0-9]{24}` | RDX 设备认证字段 |
| 分隔符 | 1 B | `,` | 字段分隔 |
| BLE MAC | 12 B | 大小写均可的十六进制字符串，不带冒号 | RDX BLE 公共单播地址 |
| 分隔符 | 1 B | `,` | 字段分隔 |
| Label SN | 16 B | `[A-Za-z0-9]{16}` | 标签序列号 |
| 合计 | 54 B | 文本 | 小于默认认证码上限 128 B |

量产示例：

```text
T2620NV20260624XHM000001,E8392C53D3C3,T2620NVXHM000001
```

解析结果：

```text
AuthKey  = T2620NV20260624XHM000001
BLE MAC  = E8392C53D3C3
Label SN = T2620NVXHM000001
```

BLE MAC 还必须满足以下最低有效性要求：

- 不能为 `000000000000`；
- 不能为 `FFFFFFFFFFFF`；
- 最高显示字节的 I/G 位不能为 1，即不能使用组播地址。

输入允许小写十六进制 MAC，固件对外上报时统一格式化为大写。单台固件无法判断不同设备之间是否重复，跨设备和跨批次唯一性由认证码签发及量产文件归档流程保证。

### 2.2 文件类型

本项目的量产数据是文本，应使用 `.csv` 方式转换和烧录，不应改成 `.hex`：

- `.csv`：字符串 `E8392C53D3C3` 按 12 个 ASCII 字节写入；
- `.hex`：工具会把整行当成二进制 hex；本项目记录包含字母 `T`、`N`、`V` 和逗号，本身也不是合法的整行 hex 数据。

每一行代表一颗芯片的唯一身份。确认原始文件无表头、空行和多余空白，字段长度及计划数量正确后，使用杰理 `license_to_auth_csv.exe` 转换：

```powershell
license_to_auth_csv.exe your_product_key.csv
```

转换后生成烧录工具可识别的：

```text
JL_your_product_key.csv
```

官方转换工具入口：<https://pkgman.jieliapp.com/s/authcsv>。仓库不保存或封装该外部可执行文件。

## 3. 固件认证码开关

### 3.1 不能直接修改生成文件

`SDK/cpu/br56/tools/isd_config.ini` 是编译生成文件。`SDK/build/Makefile.mk` 会预处理：

```makefile
-E -P cpu/br56/tools/isd_config_rule.c -o cpu/br56/tools/isd_config.ini
```

因此直接修改 `isd_config.ini` 会在下次编译时被覆盖。

### 3.2 永久配置位置

在 `SDK/cpu/br56/tools/isd_config_rule.c` 的 `[SYS_CFG_PARAM]` 段加入：

```c
[SYS_CFG_PARAM]
SPI = CAT4(CONFIG_SPI_DATA_WIDTH, CONFIG_SPI_CLK_DIV, CONFIG_SPI_MODE, CONFIG_SPI_PORT);
AUTH_CODE = 1;
```

重新编译后，生成的 `isd_config.ini` 应包含：

```ini
[SYS_CFG_PARAM]
SPI = 4_3_0_0;
AUTH_CODE = 1;
```

该开关有意保持无条件开启，不跟随 `TCFG_RDX_ENABLE`。量产身份是产品级不可变资产；诊断版或过渡固件即使临时关闭 RDX，也应继续携带认证码烧录支持，降低重新部署时破坏已有身份的风险。决策背景见 `docs/adr/0001-rdx量产身份边界.md`。

### 3.3 不需要配置独立认证码地址

当前记录只有 54 B，小于杰理默认 128 B 上限，因此不需要增加：

```ini
[BURNER_PASSTHROUGH_CFG]
AUTH_CODE_ADDR = ...;
```

参考工程中的以下配置也不是认证码地址：

| 配置 | 职责 |
| --- | --- |
| `BTIF_ADR` | JL 蓝牙或系统配置保留区 |
| `PRCT_ADR` | 代码保护区域 |
| `VM_ADR` | VM 参数存储区域 |

不要为了认证码移植照搬参考工程的 SPI、串口、BTIF、PRCT 或 VM 地址。BR28 与 BR56 的板级和 Flash 规划不同。

## 4. 默认认证码 Flash 布局

### 4.1 地址计算

BR56 SDK 与参考 BR28 工程使用相同的默认尾部布局：

```c
flash_capacity = sdfile_get_disk_capacity();
flash_addr = flash_capacity - 256 + 80;
```

其中：

```text
80 = 64 + 16
```

必须通过运行时 Flash 容量计算，不要把地址硬编码为固定绝对值。当前构建后处理检测到的物理 Flash 为 2 MB，而工程配置和不同批次硬件可能发生变化，动态计算可以保持兼容。

常见容量对应地址如下：

| Flash 容量 | 认证码头部地址 | 文本起始地址 |
| ---: | ---: | ---: |
| 1 MB `0x100000` | `0x0FFF50` | `0x0FFF54` |
| 2 MB `0x200000` | `0x1FFF50` | `0x1FFF54` |

`rdx_platform_br56.c` 使用 `sdfile_flash_addr2cpu_addr()` 将 Flash 偏移转换为 CPU 可访问地址。`rdx_identity.c` 不直接依赖该杰理平台接口。

### 4.2 数据头格式

认证码区不是从地址开始直接存放纯文本，前面包含 4 B 头部：

```c
typedef struct {
    u16 crc;
    u16 len;
    u8 data[0];
} __attribute__((packed)) rdx_auth_code_block_t;
```

布局如下：

```text
flash_capacity - 256 + 80
        |
        +-- crc       2 B
        +-- len       2 B
        +-- data      len B
```

CRC 计算范围包含 `len` 字段和完整数据：

```c
CRC16(&auth_code->len, auth_code->len + sizeof(auth_code->len))
```

烧录工具写入的 `len` 可能包含末尾 `\0`。运行时代码同时兼容 54 B 纯文本和 55 B 含结束符的形式，但去掉可选结束符后必须严格等于 54 B。

## 5. RDX 运行时移植实现

### 5.1 修改文件

```text
修改  SDK/apps/common/third_party_profile/rdx_protocol/rdx_identity.c
修改  SDK/apps/common/third_party_profile/rdx_protocol/rdx_identity.h
修改  SDK/apps/common/third_party_profile/rdx_protocol/rdx_mvp0_protocol.c
修改  SDK/apps/common/third_party_profile/rdx_protocol/rdx_platform_br56.c
修改  SDK/apps/common/third_party_profile/rdx_protocol/rdx_platform_br56.h
修改  SDK/apps/common/third_party_profile/rdx_protocol/rdx_ble_transport_br56.c
修改  SDK/apps/earphone/include/rdx_mvp0_compat_config.h
修改  SDK/cpu/br56/tools/isd_config_rule.c
```

### 5.2 模块边界

认证码块的存储格式与 RDX 量产身份记录的字段合同分属不同层次：

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| `rdx_platform_br56` | Flash 容量、尾部地址、CPU 地址映射、头部、长度和 CRC | AuthKey、MAC、Label SN 的业务格式 |
| `rdx_identity` | `24,12,16` 字段解析、字符集、MAC 有效性、运行时身份缓存和 GATT/广播字段 | 杰理 Flash 地址和 BLE 控制器操作 |
| `rdx_ble_transport_br56` | Controller MAC、BLE Handle MAC、GATT Handle 和广播 | 认证码块解析 |
| `rdx_mvp0_protocol` | 通过 Identity Getter 组织线上应答 | Flash、CRC 和身份来源 |

平台 Provider 接口为：

```c
int rdx_platform_read_auth_code(u8 *buffer, u16 buffer_size, u16 *data_len);
```

它只返回通过头部、长度和 CRC 校验的原始 payload，不返回已经解析的 RDX 字段。这样更换认证码存储布局不会修改协议层，更换 RDX 字段合同时也不会修改 Flash 驱动。

### 5.3 初始化流程

RDX 启动时按以下顺序加载量产身份：

```text
rdx_protocol_start()
        |
        +-- rdx_device_state_init()
        |
        +-- rdx_identity_init()
                |
                +-- rdx_platform_read_auth_code()
                |       +-- 获取 Flash 容量和认证码头部
                |       +-- 检查 len 范围
                |       +-- 校验 CRC16
                |
                +-- 检查文本总长度为 54 B
                +-- 检查两个逗号的固定位置
                +-- 检查 AuthKey 和 Label SN 字符集
                +-- 检查 BLE MAC 格式和最低有效性
                +-- 复制 AuthKey、BLE MAC、Label SN
                +-- 构造 GATT Identity
        |
        +-- rdx_mvp0_protocol_init()
        |
        +-- rdx_ble_transport_init()
                +-- le_controller_set_mac()
                +-- app_ble_set_mac_addr()
                +-- 开始广播
```

只有所有认证码检查都通过，RDX 才继续启动并开始广播。

### 5.4 字段映射

| 量产字段 | 运行时目标 | 使用位置 |
| --- | --- | --- |
| AuthKey | `rdx_factory_identity.auth_key[25]` | GATT Identity、`*DEV#authsn#` |
| BLE MAC | `rdx_factory_identity.ble_mac[6]` / `ble_mac_string[13]` | Controller、RDX BLE Handle、广播 Manufacturer Data、`authsn` |
| Label SN | `rdx_factory_identity.label_sn[17]` | GATT Identity、`authsn` |
| Wi-Fi MAC | `RDX_COMPAT_WIFI_MAC` | `authsn`，当前固定为 12 个 `0` |

BLE 控制器内部地址按低字节在前保存。文本 `E8392C53D3C3` 转换后的内部 6 B 顺序是：

```text
C3 D3 53 2C 39 E8
```

对外显示和协议上报时再按高字节到低字节格式化，因此仍为：

```text
E8392C53D3C3
```

### 5.5 失败策略

量产身份是 RDX 上线的必要条件。读取失败时不使用开发期占位数据，`rdx_identity_init()` 返回错误，`rdx_protocol_start()` 停止后续协议和广播初始化。

错误码使用命名常量和不重叠的区间。认证码块 Provider 错误如下：

| 错误码 | 含义 |
| ---: | --- |
| `-101` | Provider 参数无效 |
| `-102` | Flash 容量无效 |
| `-103` | Flash 地址转换失败 |
| `-104` | 认证码块长度为 0 或超过 128 B |
| `-105` | 调用方缓冲区不足 |
| `-106` | CRC16 校验失败 |

量产身份记录解析错误如下：

| 错误码 | 含义 |
| ---: | --- |
| `-201` | 去除可选 `\0` 后不是 54 B |
| `-202` | 两个逗号不在固定位置 |
| `-203` | AuthKey 包含非字母数字字符 |
| `-204` | BLE MAC 包含非十六进制字符 |
| `-205` | BLE MAC 为全零、全 `FF` 或组播地址 |
| `-206` | Label SN 包含非字母数字字符 |

BLE Transport 初始化使用 `-301` 至 `-304` 区分 Controller MAC、Handle 分配、Handle MAC 和广播启动失败；底层原始返回值只出现在对应诊断日志中，不与身份解析错误混用。`rdx_device_state_init()` 的错误发生在身份加载之前，由其自身日志识别。

失败日志示例：

```text
[RDX] factory identity invalid stage=block code=-106
[RDX] start failed=-106
```

### 5.6 调试与量产日志

开发阶段允许像参考工程一样逐字段核对量产身份，但不打印拼接后的完整 `authsn` Wire。`rdx_mvp0_send_auth_sn()` 只记录：

```text
[RDX][TX] cmd=authsn len=<长度> ret=<结果>
```

不再记录：

```text
[RDX][TX] cmd=authsn wire=<包含AuthKey的完整报文>
```

当 `CONFIG_DEBUG_ENABLE=1` 时，初始化成功后分别打印三个字段：

```text
[RDX] factory identity loaded
[RDX] factory AuthKey=T2620NV20260624XHM000001
[RDX] factory BLE_MAC=E8392C53D3C3
[RDX] factory Label_SN=T2620NVXHM000001
```

`CONFIG_DEBUG_ENABLE` 由 `TCFG_DEBUG_UART_ENABLE` 决定。量产配置关闭调试串口后，三条字段明文日志不参与编译；普通成功日志仍不包含身份字段。

## 6. 量产烧录流程

### 6.1 生成支持认证码的固件

1. 确认 `isd_config_rule.c` 已配置 `AUTH_CODE = 1;`；
2. 执行干净构建；
3. 检查生成的 `isd_config.ini` 仍包含认证码开关；
4. 使用仓库根目录 `output/jl_isd.fw` 部署烧录程序。

Windows 构建命令：

```powershell
Set-Location SDK
$env:Path = "$PWD\tools\utils;$env:Path"
make clean
make
```

### 6.2 准备认证码文件

1. 每行写入一条 54 B 量产身份记录，不添加表头；
2. 保存为原始 `.csv`；
3. 确认文件无表头、空行、多余空白和明显重复项，字段长度及计划数量正确；
4. 使用官方 `license_to_auth_csv.exe` 转换为 `JL_*.csv`；
5. 保存原始文件、转换文件和使用记录，依靠认证码签发与归档防止跨批次重复使用。

### 6.3 部署和更新注意事项

- 初次量产时选择支持认证码的固件和转换后的认证码文件；
- 烧录器按文件中的可用顺序为每颗芯片分配一行；
- 正常情况下不要勾选“强制更新认证码”，避免覆盖芯片已有身份和浪费新码；
- 勾选“强制更新认证码”会覆盖已有身份；
- **根据杰理工具文档，重新部署时未选择认证码文件且未勾选强制更新，会擦除芯片已有认证码；**
- 认证码未使用完时更换烧录文件，应先导出并妥善保存剩余认证码，防止重复或丢失；
- 使用配置信息更新工具读取或更新认证码前，芯片中必须已经烧有支持认证码的固件。

## 7. 验证方法

### 7.1 编译验证

必须确认：

- `make clean && make` 成功；
- `rdx_platform_br56.c`、`rdx_identity.c`、`rdx_ble_transport_br56.c` 和 `rdx_mvp0_protocol.c` 完成编译并成功链接；
- `SDK/cpu/br56/tools/isd_config.ini` 中存在 `AUTH_CODE = 1;`；
- `git diff --check` 和 `git diff --cached --check` 均无空白错误；
- `SDK/cpu/br56/tools/init.bin` 等构建生成物不混入认证码源码提交。

本次实施已完成上述检查，BR56 干净构建通过并生成 `output/jl_isd.fw`。后处理时目标设备离线，并出现既有的 `ALIGN_DIR/anc_ext.bin` 缺失提示，但构建退出码为 0；这两项不等同于实机下载或认证码烧录验证。

### 7.2 烧录后串口验证

烧入示例认证码后，启动阶段应出现：

```text
[RDX] factory identity loaded
[RDX] factory AuthKey=T2620NV20260624XHM000001
[RDX] factory BLE_MAC=E8392C53D3C3
[RDX] factory Label_SN=T2620NVXHM000001
[RDX] MVP0 started
```

不应出现：

```text
[RDX] factory identity invalid stage=<block|record> code=<错误码>
```

开发日志中允许出现上述三个独立字段，但不应出现拼接后的完整 Wire：

```text
[RDX][TX] cmd=authsn wire=
```

量产关闭 `TCFG_DEBUG_UART_ENABLE` 后，再检查固件和 UART 输出均不包含示例 AuthKey 明文。

实机验证时至少使用以下负例确认 RDX fail-closed：AuthKey 或 Label SN 含 `#`、逗号、空白或控制字符；BLE MAC 为全零、全 `FF`、组播地址或非十六进制；记录长度和 CRC 错误。本次不引入外部依赖或新的测试框架。

### 7.3 BLE 与 APP 验证

| 验证项 | 预期结果 |
| --- | --- |
| BLE 广播地址 | 显示为量产字段 `E8392C53D3C3` |
| Manufacturer Data | MAC 字段与量产 BLE MAC 一致 |
| GATT Identity | 包含量产 AuthKey、BLE MAC 和 Label SN |
| `authsn` 应答 | AuthKey、BLE MAC、Label SN 为量产值；Wi-Fi MAC 暂时为 `000000000000` |
| AppKey 认证 | 使用量产身份后仍可完成 MVP0 握手 |
| 绑定/解绑 | 不清除或改变 AuthKey、BLE MAC、Label SN |
| 恢复出厂 | 只恢复 RDX 可变状态，不擦除量产身份 |
| 冷启动 | 多次断电重启后身份保持一致 |

`authsn` 线上格式保持：

```text
*DEV#authsn#<AuthKey>#<BLE_MAC>#<WiFi_MAC>#<Label_SN>#
```

开发阶段可通过三条独立启动日志辅助核对；量产阶段关闭调试串口，并由 APP 或抓包工具核对线上字段。

### 7.4 USB 共存回归

认证码读取只发生在 RDX 初始化阶段，但仍应在实机确认：

- Type-C 插拔和 USB 枚举正常；
- USB Speaker 播放正常；
- USB MIC 上行正常；
- HID 线控正常；
- RDX BLE 广播、连接和 `authsn` 查询不会触发 USB reset；
- 绑定、解绑和恢复出厂后量产身份不变。

## 8. 当前边界和后续事项

当前仍有以下边界：

1. Wi-Fi MAC 暂时固定为 `000000000000`，外部设备传递接口确定后应改为运行时 Provider；
