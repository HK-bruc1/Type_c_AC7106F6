## 1. 当前结论

RDX BLE MVP0 已按“模块化、最小侵入 JL 原生平台”的目标完成实现和架构整改。当前代码只移植 APP 发现设备、建立 BLE/GATT 连接、读取身份、订阅通知、AppKey 认证和进入 `APP-ready` 所需的最小闭环，不移植 701 的录音、文件、Wi-Fi、SPI、RTC 设置、充电仓控制、LED、马达和实际 OTA 业务。

当前状态如下：

| 项目 | 状态 | 结论 |
| --- | --- | --- |
| MVP0-A：广播、GATT、读写、Notify | 已完成 | nRF Connect 和目标 APP 已验证 |
| MVP0-B：最小握手与 `APP-ready` | 已完成 | Battery、Version、AppKey、RTC、OS Type 已验证 |
| RDX 架构整改 | 已完成 | 命名、职责、产品配置和最终门控已收敛 |
| RDX ON 构建与静态合同 | 已完成 | 构建、Map、GATT、官方库哈希和门控预处理通过 |
| USB Speaker 与 BLE 短时共存 | 阶段通过 | 最新日志中播放期间完成两轮 BLE 连接和协议交互 |
| 完整实机稳定性 | 未完成 | Mic 实录、HID 操作、长时压力、反复插拔和多机型仍待补齐 |
| JLStudio 隔离构建矩阵 | 未完成 | 当前完成真实头文件预处理矩阵，尚未完成全部组合的独立工程构建 |

这意味着当前代码可以作为 MVP0 开发和后续产品化的基线，但不能把短时日志表述为量产稳定性验收完成。

## 2. 架构硬约束

### 2.1 单一用户配置入口

用户只通过 JL 产品配置表达：

1. 是否启用第三方协议；
2. 是否选择 `RDX_EN`；
3. 是否启用最终 BLE；
4. 是否使用当前 Type-C 专用 PC 应用模式。

工程不再提供 `RDX_BLE_MVP0_ENABLE`、`RDX_APP_ENABLE` 等平行开关。代码统一使用最终派生的 `TCFG_RDX_ENABLE`。

### 2.2 RDX OFF 零残留

`TCFG_RDX_ENABLE=0` 时必须满足：

- 不编译 5 个 RDX 源文件；
- 不向链接器注入 `librdxApp.a`；
- 不注册 RDX 生命周期、GATT、回调或消息处理；
- 不产生 RDX 广播、日志、任务、定时器或 VM 行为；
- 不因 RDX 启动 BLE 栈；
- 不继续套用 RDX 的单连接和窄 ATT RAM 合同。

若未来其他模块合法使用 BLE，RDX OFF 只撤销 RDX 对 BLE 的使用权，不负责关闭其他模块拥有的 BLE 功能。

### 2.3 最小侵入 JL 原生平台

依赖方向保持单向：

```text
PC / USB / UAC / Audio
        │
        │ 只调用通用第三方协议生命周期
        ▼
multi_protocol_main
        │
        │ TCFG_RDX_ENABLE 门控
        ▼
rdx_protocol_entry
        ├── rdx_ble_transport_br56
        ├── rdx_identity
        └── rdx_mvp0_protocol
                └── rdx_appkey_verifier
```

USB、UAC、Mic、HID、音频、板级和电源模块不得包含 `rdx_*` 头文件或业务判断。RDX 可以调用 JL 公共 BLE API，但 JL 核心业务模块不得反向依赖 RDX。

## 3. 配置分层和最终门控

### 3.1 四层职责

| 层级 | 文件 | 职责 |
| --- | --- | --- |
| JL 工具源 | `src/*.json`、`project.jlproj` | 产品模式、BLE、USB、音频和第三方协议选择 |
| JL 生成配置 | `SDK/apps/earphone/board/br56/sdk_config.h` | JL 可视化工具生成结果，直接修改或重新生成，不做 RDX 二次宏覆盖 |
| 产品集成策略 | `SDK/apps/earphone/include/rdx_integration_config.h` | 在最终产品配置稳定后派生 `TCFG_RDX_ENABLE`，拒绝非法组合 |
| MVP0 开发兼容数据 | `SDK/apps/earphone/include/rdx_mvp0_compat_config.h` | 当前 701 兼容身份、版本、AppKey 列表、广播间隔和固定测试电量 |

当前没有必要增加 `rdx_app_config.h` 或公共 `rdx_protocol_config.h`。只有未来出现真正跨产品、由公共协议实现消费的配置时，才评估新增公共协议配置头。

### 3.2 当前产品配置

| 配置项 | 当前值 | 说明 |
| --- | ---: | --- |
| `TCFG_APP_PC_EN` | 1 | Type-C USB Device/UAC 应用模式 |
| `TCFG_APP_BT_EN` | 0 | 不启用完整蓝牙应用和经典蓝牙模式 |
| `TCFG_USER_BLE_ENABLE` | 1 | 为 RDX 提供 BLE 栈 |
| `TCFG_THIRD_PARTY_PROTOCOLS_ENABLE` | 1 | 启用第三方协议框架 |
| `TCFG_THIRD_PARTY_PROTOCOLS_SEL` | `RDX_EN` | 只选择 RDX |
| `TCFG_BT_BLE_ADV_ENABLE` | 0 | 默认广播关闭，由 RDX Handle 生成广播 |
| `TCFG_USB_SLAVE_AUDIO_SPK_ENABLE` | 1 | UAC 下行播放 |
| `TCFG_USB_SLAVE_AUDIO_MIC_ENABLE` | 1 | UAC 麦克风上行 |
| `TCFG_USB_SLAVE_HID_ENABLE` | 1 | USB HID 线控 |

`RDX_EN` 在 BR56 工程中使用未占用的 bit 17。701 的 bit 18 已被本工程 `MULTI_CLIENT_EN` 使用，不能照抄。

### 3.3 最终派生

`app_config.h` 先处理 JL 配置、在线调试派生和 `TCFG_TYPEC_EARPHONE_CASE`，然后只包含一次 `rdx_integration_config.h`。最终逻辑为：

```c
#if TCFG_THIRD_PARTY_PROTOCOLS_ENABLE && \
    (TCFG_THIRD_PARTY_PROTOCOLS_SEL & RDX_EN)

#if TCFG_THIRD_PARTY_PROTOCOLS_SEL != RDX_EN
#error "RDX BLE MVP0 cannot coexist with other third-party protocols"
#endif

#if !TCFG_USER_BLE_ENABLE
#error "RDX requires final TCFG_USER_BLE_ENABLE"
#endif

#if !TCFG_TYPEC_EARPHONE_CASE
#error "RDX BLE MVP0 requires the Type-C dedicated PC application mode"
#endif

#define TCFG_RDX_ENABLE 1
#else
#define TCFG_RDX_ENABLE 0
#endif
```

第三方协议总开关 OFF 时，即使选择值仍残留 `RDX_EN`，最终门控也必须为 0。MVP0 阶段禁止 RDX 与其他配置源协议共存。

### 3.4 RDX RAM 资源合同

Controller、Host/GATT 和 ATT 三类资源都使用最终 `TCFG_RDX_ENABLE` 门控：

| 资源 | RDX ON | 非 RDX 常规分支 |
| --- | ---: | ---: |
| Controller 模块 | 纯 LE | 由 SDK 原配置决定 |
| LE Role | Slave + Advertising | 由其他协议决定 |
| HCI 连接数 | 1 | 2 |
| GATT Server / Client | 1 / 0 | 2 / 1 |
| Slave 多链路 | 0 | 1 |
| ATT Local Payload | 64 B | 517 B |
| ATT Send cbuf | 512 B | 1024 B |

`TCFG_AUDIO_DAC_BUFFER_TIME_MS=20 ms` 是当前 JL 产品音频配置，不属于 RDX 模块门控。它应在 `src/音频配置.json` 与生成的 `sdk_config.h` 中直接保持一致，RDX ON/OFF 都使用相同值。

运行日志中的完整 ATT MTU 517 与本地 64 B 发送 Payload 不冲突。`ble_op_multi_att_send_init()` 的第三个参数是本地最大 ATT 发送负载，只要求不大于协商 MTU 的有效负载；MVP0 最大报文小于 64 B。

## 4. 当前模块结构和职责

```text
SDK/apps/common/third_party_profile/rdx_protocol/
├── rdx_protocol_entry.c/.h          # 模块生命周期入口
├── rdx_ble_transport_br56.c/.h      # BR56 BLE/GATT 适配
├── rdx_identity.c/.h                # 身份和广播制造商数据
├── rdx_mvp0_protocol.c/.h           # MVP0 最小协议状态机
├── rdx_appkey_verifier.c/.h         # AppKey 解密结果校验适配
└── librdxApp.a                      # 701 官方库，只按需抽取加密对象

SDK/apps/earphone/include/
├── rdx_integration_config.h         # 当前产品最终门控和非法组合检查
└── rdx_mvp0_compat_config.h         # 当前产品的 MVP0 开发兼容数据
```

### 4.1 生命周期入口

`rdx_protocol_entry` 只负责幂等启动和停止：

- 启动时先初始化 MVP0 Protocol 回调，再初始化 BLE Transport；
- BLE Transport 失败时回滚 Protocol；
- 停止时先退出 BLE Transport，再清理 Protocol 状态；
- 不承担广播字段、GATT 读写或具体协议命令处理。

### 4.2 BR56 BLE Transport

`rdx_ble_transport_br56` 负责：

- 387 B GATT Profile；
- GAP Name、Identity、Battery 和 CCC Read；
- RX Write、TX Notify 和 OTA Write 忽略；
- 广播、扫描响应、连接、MTU、断开和恢复广播；
- 调用 `rdx_identity` 获取身份数据；
- 把协议数据交给 `rdx_mvp0_protocol`。

### 4.3 Identity

`rdx_identity` 只负责：

- 从 Controller 读取 BLE MAC；
- 构造 Case 形态 Identity Read；
- 返回 Local Name；
- 构造 Manufacturer Specific Data。

Battery 已从 Identity 职责移除。GATT Battery 和 MVP0 Battery 都直接消费 `RDX_MVP0_FIXED_BATTERY_LEVEL`。

### 4.4 MVP0 Protocol

`rdx_mvp0_protocol` 保存每条连接的四个状态：

```text
connected
identity_read
ccc_ready
app_ready
```

Identity Read 可能被手机 GATT 缓存跳过，因此只用于返回数据和诊断，不是进入 `APP-ready` 的硬门槛。断开连接会清空全部状态。

### 4.5 AppKey Verifier

`rdx_appkey_verifier` 只适配官方 `rdx_appkey_decryption_handle()`：

1. 检查 32 B AppKey Payload；
2. 前 16 B 作为 key，后 16 B 作为 ciphertext；
3. 调用官方解密函数一次；
4. 与兼容配置中的合法 16 B AppKey 列表比较；
5. 返回前清零临时 key 和 plaintext。

它不包含 BLE、产品身份或协议状态机逻辑。

## 5. 构建注入和官方库边界

`SDK/build/genFileList.c` 是 RDX 源码和静态库的唯一构建注入点：

```text
#if TCFG_RDX_ENABLE
    rdx_protocol_entry.c
    rdx_ble_transport_br56.c
    rdx_identity.c
    rdx_mvp0_protocol.c
    rdx_appkey_verifier.c
    librdxApp.a
#endif
```

`SDK/build/Makefile.mk` 只提供通用 `THIRD_PARTY_LIBS` 链接扩展点，不出现 RDX 专用判断。生成的 `fileList.mk` 不作为配置源手工维护。

官方 `librdxApp.a` 当前包含多个 701 对象，但 Map 只允许抽取：

```text
rdx_encryption.c.o
```

以下对象不得进入 MVP0：

```text
rdx_protocol.c.o
rdx_queue.c.o
rdx_uxfile.c.o
xxpUart.c.o
```

不得调用 701 的 `rdx_app_all_init()` 或 `rdx_protocol_task_create()`，否则会引入录音、文件、Wi-Fi、SPI、VM、电源和外设依赖。

## 6. 初始化和退出时序

### 6.1 启动

```text
pc_task_start
    ├── USBSTACK_START
    └── multi_protocol_pc_start
            └── btstack_init
                    └── BT_STATUS_INIT_OK
                            └── multi_protocol_bt_init
                                    ├── le_device_db_init
                                    ├── app_ble_sm_init
                                    ├── app_ble_init
                                    ├── ble_op_multi_att_send_init
                                    └── rdx_protocol_start
                                            ├── rdx_mvp0_protocol_init
                                            └── rdx_ble_transport_init
                                                    └── 开始广播
```

`pc.c` 只调用通用 `multi_protocol_pc_start()`，不等待 BLE 初始化完成，因此不改变 USB 枚举主时序。

### 6.2 连接与断开

连接成功后 Transport 保存 Handle，清空 CCC，主动发起 MTU 交换并通知 Protocol。断开后清空 Handle、MTU、CCC 和 Protocol 状态；若模块仍处于初始化状态，则重新设置广播参数和数据并开启广播。

### 6.3 退出

```text
pc_task_stop
    └── multi_protocol_pc_stop
            ├── multi_protocol_bt_exit
            │       ├── rdx_protocol_stop
            │       └── app_ble_exit
            └── btstack_exit
```

RDX Transport 退出时停止广播、断开现有连接、释放 BLE Handle 并清零状态。所有入口和出口保持幂等。

## 7. BLE 外部兼容合同

### 7.1 广播和扫描响应

Advertising Data：

```text
Flags 0x0A
+ Complete Local Name
```

Scan Response：

```text
Manufacturer Specific Data
    = PRODUCT_CODE
    + reversed BLE MAC
    + FACTORY_CODE
    + mode/bound byte
    + ability（4 B，小端）
    + optional protocol version
    + PRODUCT_TYPE
    + SELF_MARK
```

当前广播间隔为 160 个 0.625 ms 单位，即 100 ms。

### 7.2 GATT Profile

| 服务/特征 | UUID 或 Handle | MVP0 行为 |
| --- | --- | --- |
| GAP Device Name | `0x2A00`, value `0x0003` | 返回兼容 Local Name |
| RDX Primary Service | `06068D0C-6B97-11EF-B864-0240AC120002` | 保留 |
| RDX RX | value `0x0006` | Write Without Response，送入 MVP0 Protocol |
| RDX TX | value `0x0008` | Notify，CCC `0x0009` |
| RDX Identity | value `0x000B` | 返回 Case 形态身份字符串 |
| Battery Service | `0x180F` | 保留 |
| Battery Level | `0x2A19`, value `0x000E` | 固定返回 100，CCC `0x000F` |
| OTA Service | 701 兼容 UUID | 只保留服务指纹 |
| OTA RX/TX | value `0x0012` / `0x0014` | OTA 写入忽略，CCC `0x0015` |

当前 Profile 为 387 B，Handle、UUID 和属性排列与 701 参考工程逐字节一致。

### 7.3 MVP0 最小命令

| APP 请求 | 设备响应 | 说明 |
| --- | --- | --- |
| `RDX_MVP0_PING` | `RDX_MVP0_PONG` | 通路诊断 |
| `*APP#battery#` | `*DEV#battery#0#0#100#` | 使用兼容固定电量 |
| `*APP#version#` | `*DEV#version#<HW>#<FW>#` | 使用兼容版本 |
| `*APP#appkey#<32B>#` | `*DEV#appkey#0#` 或 `#1#` | 成功后进入 `APP-ready`，失败后断开 |
| `*APP#rtc#<timestamp>#` | `*DEV#rtc#<result>#<timestamp>#` | 严格解析 Unix UTC 秒，写入并回读硬件 RTC，同时写入并回读 VM；两路均成功时 `result=0`，否则为 `1` |
| `*APP#ostype#...` | `*DEV#ostype#` | 兼容回执 |

所有发送都要求连接有效且 TX CCC 已开启。AppKey 请求必须严格为前缀、32 B Payload 和尾 `#` 组成的 45 B 报文；只有校验成功且成功发出响应后才设置 `app_ready=1`。

录音、文件、Wi-Fi 和其他未知命令不在 MVP0 范围内，当前保持不响应。

## 8. 开发兼容配置

`rdx_mvp0_compat_config.h` 当前镜像 701 Zenchord Case 测试身份，内容包括：

- Local Name、Product Code、Factory Code、Product Type 和 Self Mark；
- Charge Case 形态、Bound State、Ability 和 Protocol Version；
- Hardware/Firmware Version；
- 三组兼容 AppKey；
- 广播间隔和固定测试电量；
- 全零 AuthKey 与 Label SN 开发占位值。

RDX RTC 不设置独立业务开关。`TCFG_APP_RTC_EN` 是 JL 原生 RTC 能力的唯一开关；启用 RDX 时，`rdx_integration_config.h` 在编译期要求该能力已经开启。`rdx_mvp0_compat_config.h` 只声明协议兼容数据，Manufacturer Data 中的 `RDX_ABILITY_RTC` 表示已满足的集成能力，不承担基础模块开关职责。

该文件属于当前 Type-C 产品的 MVP0 开发兼容数据，不是公共协议配置，也不是正式量产身份。它不得：

- 覆盖 BLE、PC、BT、UAC、HID 或音频基础宏；
- 保存未经授权的客户量产秘密；
- 被其他产品当成默认身份直接复用；
- 增加录音、文件、Wi-Fi 或 OTA 等业务开关。

量产前必须确定目标产品形态、唯一身份、MAC、AuthKey、Label SN、AppKey 管理和烧录方案。


与移植前日志相同阶段相比，普通 free heap 增加约 16.2 KiB；RDX 额外占用一部分 physical memory，但当前剩余 64 KiB，未触发原有 `vmalloc_ 147` 问题。

当前开发配置启用 RDX 资源监控：RDX 启动时打印一次 Flash 代码区容量、已用量和代码余量，随后每 10 秒打印合并 SRAM 的 `total/used/free/min_free`，日志统一使用 KB。内部统计兼容 SDK 的 RAM0 和可选 RAM1 内存池，对外只呈现芯片运行时可分配 SRAM 汇总。Flash 数据来自 SDK 运行时 `boot_info.vm`，代码余量按 `VM 实际大小 - TCFG_VM_SIZE` 计算，与 post-build `FLASH INFO` 中的 `LAVE_SIZE` 一致，表示保留产品最小 VM 后固件代码及资源还能增长的空间。监控由 `TCFG_RDX_RESOURCE_MONITOR_ENABLE` 控制，量产配置应关闭该诊断模块。

### 11.2 已定性的日志消息

- 两次 `<error> [USB]usb reset`、20 次 `setup_interface()` 失败、CVP 配置文件和 EQ 系数告警在移植前日志中同样存在，不是本次 RDX 整改引入；
- `ATT MTU = 514` 是扣除 3 B ATT 头后的有效负载，`[RDX] mtu=517` 是完整 MTU；
- `LL Adv already destroy` 每次连接出现一次，但断开后广播都成功恢复，当前属于 SDK 重复停止广播的低风险日志噪声；
- `PCSPK LOST CONNECT` 出现在第一次 BLE 连接之前，随后 Speaker 自动重新打开，时间顺序不支持“BLE 建链导致中断”的判断；若当时没有人为暂停或切换播放，后续压力测试仍需关注。

### 11.3 当前发现的配置告警

日志出现：

```text
fail select SC!!!,need config_le_sm_sub_sc_enable = 1
```

当前 RDX 分支为 `config_le_sm_support_enable=1`，而 SC 子功能关闭；公共 `multi_protocol_profile_init()` 仍按通用协议调用带 MITM/Bonding 参数的 `app_ble_sm_init()`。本次 MVP0 使用应用层 AppKey，未依赖 BLE Bonding，因此该告警没有阻断连接和认证，但属于待收敛的安全配置半状态。

后续首选方案是：在 `TCFG_RDX_ENABLE` 下关闭未使用的 SM 支持并跳过通用 `app_ble_sm_init()`，以消除告警并进一步释放 RAM。实施前需确认目标 APP 不要求 BLE 层配对；修改后至少回归 AppKey、重连和手机缓存行为。该项尚未写入当前代码。

## 15. 回退方式

功能回退只通过产品配置关闭第三方协议或取消选择 `RDX_EN`，然后从配置源重新生成并干净构建。不得通过删除单个 RDX 源文件、注释生命周期调用或手写覆盖 JL 生成宏形成半关闭状态。

如果后续修改导致以下任一情况，应回到当前 MVP0 基线单独诊断：

- APP 无法进入 `APP-ready`；
- GATT、广播、Identity 或握手报文变化；
- Map 抽取全量 RDX 业务对象；
- RDX OFF 仍有源码、库、符号或运行行为；
- 再次出现 `vmalloc_ 147`、异常复位或 USB 重枚举；
- USB Speaker、Mic 或 HID 出现可复现回归。
